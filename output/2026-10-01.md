## 🧪 重要知识点 & 动手实验

- **知识点 1：Int4 权重量化与打包（W4A8）**
  - **是什么**：把 float16 的权重压成 4 位整数，8 个权重塞进一个 int32，激活值保持 int8 做矩阵乘。
  - **为什么重要**：显存直接省 4 倍，CPU/GPU 都能跑更大模型。不懂打包布局（比如 8 个 nibble 怎么排）就会读错权重、算错结果。
  - **动手试试**：
    ```python
    import torch

    # 模拟 8 个 int4 权重打包进一个 int32
    values = torch.tensor([1, -2, 3, -4, 5, -6, 7, -8], dtype=torch.int32)
    packed = torch.zeros(1, dtype=torch.int32)
    for i, v in enumerate(values):
        packed |= (v & 0xF) << (4 * i)
    print("packed:", hex(packed.item()))

    # 解包
    unpacked = []
    for i in range(8):
        nibble = (packed >> (4 * i)) & 0xF
        unpacked.append(int(nibble) - 16 if nibble > 7 else int(nibble))
    print("unpacked:", unpacked)
    ```
  - **预期结果**：看到 `packed` 是一个十六进制数，`unpacked` 和原始 `values` 完全一致。你就掌握了 int4 打包的核心逻辑。

- **知识点 2：CUDA Graph 下的双缓冲避免竞态**
  - **是什么**：用两块缓冲区轮流使用，让第 N 步的 kernel 读 A 块时，第 N+1 步往 B 块写数据，互不干扰。
  - **为什么重要**：异步调度 + CUDA Graph 场景下，如果 host 端用阻塞拷贝写 device buffer，会覆盖上一步还在读的数据，导致结果随机出错。
  - **动手试试**：
    ```python
    import torch

    # 模拟双缓冲：两块 pinned host staging + 两个 event
    device_buf = torch.zeros(4, device="cuda")
    staging = [torch.empty(4, pin_memory=True) for _ in range(2)]
    events = [torch.cuda.Event(), torch.cuda.Event()]
    slot = 0

    for step in range(4):
        events[slot].synchronize()  # 等上一轮该 slot 的拷贝完成
        staging[slot].copy_(torch.full((4,), float(step)))  # host 写
        device_buf.copy_(staging[slot], non_blocking=True)  # H2D
        events[slot].record()
        slot ^= 1  # 切换 slot
        print(f"step {step}, device_buf = {device_buf.tolist()}")
    ```
  - **预期结果**：每一步 `device_buf` 都能正确显示当前 step 的值，不会出现"上一步的值被下一步覆盖"的现象。

- **知识点 3：投机解码的采样掩码回放**
  - **是什么**：投机解码时 draft 模型猜了 K 个 token，target 模型验证后可能接受一部分。采样掩码记录每一步"允许哪些 token"，回放时按位置对齐。
  - **为什么重要**：训练侧需要知道"模型当时在什么分布下采样的"，否则蒸馏/RL 数据就错了。投机解码让位置对齐变复杂。
  - **动手试试**：
    ```python
    # 模拟投机解码的掩码回放
    draft_tokens = [10, 20, 30]        # draft 猜的 3 个 token
    accepted = [True, True, False]     # target 只接受了前 2 个
    masks = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]  # 每一步的掩码

    replayed = [m for m, ok in zip(masks, accepted) if ok]
    print("回放的掩码:", replayed)  # 只保留被接受位置
    ```
  - **预期结果**：输出 `[[1,2,3],[4,5,6]]`，即只回放被接受 token 对应的掩码，与 Commit 8 的思路一致。

- **知识点 4：增量 detokenizer 的 UTF-8 边界处理**
  - **是什么**：一个中文字符占 3 个字节，可能被拆到两个 token 里。增量解码器必须等字节凑齐才能输出字符。
  - **为什么重要**：如果不等齐就输出，会得到乱码；如果无脑等，又会把不该合并的 token 粘在一起。Commit 13 就是在解决"什么时候可以独立锚定新 token"。
  - **动手试试**：
    ```python
    # 模拟 UTF-8 字节流被 token 切分
    text = "你好"
    raw = text.encode("utf-8")
    print("完整字节:", raw)

    # 假设 tokenizer 把它切成 [raw[:2], raw[2:]]
    chunk1, chunk2 = raw[:2], raw[2:]
    # 错误做法：各自 decode
    print("错误:", chunk1.decode("utf-8", errors="replace"), chunk2.decode("utf-8", errors="replace"))
    # 正确做法：拼起来再 decode
    print("正确:", (chunk1 + chunk2).decode("utf-8"))
    ```
  - **预期结果**：错误做法输出乱码，正确做法输出"你好"。你就理解了为什么增量解码需要 pending buffer。

- **知识点 5：权重加载时的 dtype 校验**
  - **是什么**：加载 checkpoint 时检查权重文件的 dtype 和模型参数的 dtype 是否一致，不一致就警告。
  - **为什么重要**：bf16 checkpoint 加载到 fp16 参数里，数值会静默变化，训练/推理结果可能悄悄变差。Commit 17 加了 warning 让问题可见。
  - **动手试试**：
    ```python

    import logging
    logging.basicConfig(level=logging.WARNING)

    param = torch.nn.Parameter(torch.zeros(4, dtype=torch.float16))
    weight_data = torch.randn(4, dtype=torch.bfloat16)

    if param.dtype != weight_data.dtype:
        logging.warning(
            "dtype mismatch: weight=%s param=%s", weight_data.dtype, param.dtype
        )
    ```
  - **预期结果**：看到一条 WARNING 日志，提示 dtype 不一致。这就是 Commit 17 在真实代码里做的事。

  - **对新手意味着什么**：分布式推理不再是论文概念，而是线上部署的默认选项。学会理解 KV 缓存的物理布局（哪个 pool、多少字节、怎么切页），是进入大模型推理工程的敲门砖。

- **关键词：KV 缓存量化（FP8 / FP4 / NVFP4）**
  - **一句话解释**：把 KV 缓存从 16 位浮点压到 8 位甚至 4 位，显存占用减半甚至更多，代价是精度略降。
  - **为什么社区在关注**：今天的 commit 涉及 fp8 unified_kv、NVFP4 checkpoint、block scale 注册——量化已经细到"同一模型里不同层用不同精度"。
  - **对新手意味着什么**：只会调 `--dtype fp8` 已经不够了，要理解"哪些层能压、压完怎么传、怎么和 PD 对齐"。

- **关键词：DSV4 / DSA 稀疏注意力**
  - **一句话解释**：DeepSeek-V4 系列模型用的稀疏注意力机制，只算一部分 token 的注意力，省算力。
  - **为什么社区在关注**：今天有 5 个 commit 涉及 DSA/DSV4（#41987、#41337、#41163、#40471、#40913），包括去掉 CPU 同步、命名 FlashMLA KV 格式、HiCache host pool 声明。这说明 DSV4 是当前最活跃的模型适配方向。
  - **对新手意味着什么**：稀疏注意力是下一代长上下文模型的核心技术，现在参与进去正好赶上窗口期。

- **关键词：Router 可观测性 & 就绪门控**
  - **一句话解释**：路由器在启动时先"确认邻居状态"再对外服务，并把内部状态暴露成 Prometheus 指标。
  - **为什么社区在关注**：今天有 4 个 router 相关 commit（#41610、#42010、#41999、#40699），全部围绕"bootstrap 失败时怎么办、怎么让人看见"。
  - **对新手意味着什么**：分布式系统的难点不在正常路径，而在故障路径。学会设计就绪探针和指标，是从"能跑"到"能运维"的关键。

- **关键词：异构硬件适配（AMD / PPU / XPU）**
  - **一句话解释**：同一套代码要跑在 NVIDIA、AMD、国产加速卡上，需要分别适配 kernel 和通信路径。
  - **为什么社区在关注**：今天有 AMD gfx950 PD 分离（#39166）、PPU CI 注册（#39788）、XPU 测试修复（#41915）、AITER MLA ASM 路径（#40750）。
  - **对新手意味着什么**：CUDA 不是唯一选择，会写跨平台 kernel 的人非常稀缺。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV 缓存的"分页"与"注册"（PD 分离基础）

- **是什么**：KV 缓存不是一整块内存，而是切成固定大小的"页"（page），每页存若干 token 的 KV。PD 分离时，prefill 机器要把这些页的地址（指针）告诉 decode 机器，decode 机器按页号去取。
- **为什么重要**：如果两边对"一页有多大、一共有几页"理解不一致，就会读到越界内存或者读到脏数据。今天的 commit #41924 就是在修"full KV 和 SWA KV 用了不同 dtype 时，block scale 注册漏了一个"的问题。
- **动手试试**：
  ```python
  # 模拟一个简化的分页 KV 缓存
  import torch

  page_size = 4          # 每页 4 个 token
  num_pages = 8          # 共 8 页
  head_dim = 16

  # 分配一个 [num_pages, page_size, head_dim] 的池子
  kv_pool = torch.zeros(num_pages, page_size, head_dim, dtype=torch.float16)

  # 写入第 2 页第 1 个 slot
  kv_pool[2, 1] = torch.arange(head_dim, dtype=torch.float16)

  # 模拟"注册"：告诉远端每页的起始指针和每页字节数
  data_ptrs = [kv_pool.data_ptr() + i * kv_pool[0].nbytes for i in range(num_pages)]
  item_lens = [kv_pool[0].nbytes] * num_pages
  print("页数:", len(data_ptrs), "每页字节:", item_lens[0])

  # 模拟远端按页号取数据
  remote_page = 2
  offset = remote_page * kv_pool[0].nbytes
  recovered = torch.frombuffer(
      (torch.uint8 * kv_pool[0].nbytes).from_buffer(
          (torch.uint8 * (kv_pool.data_ptr() + 0)).from_buffer(bytearray(1))
      ), dtype=torch.uint8
  ) if False else None
  # 简化：直接验证页内数据
  print("第2页第1个slot:", kv_pool[2, 1][:4])
  ```
- **预期结果**：你会看到页数、每页字节数，以及第 2 页第 1 个 slot 的前 4 个值。理解"页号 × 每页字节 = 偏移量"这个核心公式，就理解了 PD 传输的地址计算基础。

### 知识点 2：CPU 同步为什么是性能杀手（DSA k-pool indexer）

- **是什么**：GPU 是异步执行的，CPU 要读 GPU 上的数据（比如 seq_lens）必须等 GPU 算完并拷贝回 CPU，这叫 D2H 同步。这个等待会让 GPU 空转。
- **为什么重要**：commit #41987 去掉了每步都做的 CPU seq_lens 同步，因为解码阶段根本不需要——它只需要知道"batch 是不是空的"，这个信息在 GPU 上就能判断。
- **动手试试**：
  ```python
  import torch, time

  device = "cuda" if torch.cuda.is_available() else "cpu"
  x = torch.randn(1024, 1024, device=device)

  # 慢：每次都同步
  t0 = time.time()
  for _ in range(100):
      _ = x.sum().item()   # .item() 强制 D2H 同步
  t1 = time.time()

  # 快：保持异步
  t2 = time.time()
  for _ in range(100):
      _ = x.sum()          # 返回 GPU tensor，不同步
  t3 = time.time()

  print(f"同步耗时: {t1-t0:.4f}s")
  print(f"异步耗时: {t3-t2:.4f}s")
  print(f"加速比: {(t1-t0)/(t3-t2):.1f}x")
  ```
- **预期结果**：在有 GPU 的机器上，异步版本会快几十倍。这就是为什么"去掉一次不必要的同步"能显著提升吞吐。

### 知识点 3：量化中的 block scale（混合精度 KV）

- **是什么**：量化时，不是整个张量共用一个缩放因子，而是每 32 或 128 个元素一组，每组一个 scale。这样精度损失更小。
- **为什么重要**：commit #41924 修的是"full KV 用 MXFP8、SWA KV 用普通 FP16 时，只注册了 full 的 scale，漏了 SWA 的"。如果漏了，decode 端解量化时就会用错 scale，输出全是噪声。
- **动手试试**：
  ```python
  import torch

  def quantize_mxfp8(x, block=32):
      """简化的 MXFP8 风格分块量化"""
      orig_shape = x.shape
      x = x.flatten()
      pad = (-len(x)) % block
      x = torch.cat([x, torch.zeros(pad)])
      x = x.view(-1, block)
      # 每块取绝对值最大作为 scale
      scale = x.abs().max(dim=1, keepdim=True).values / 127.0
      scale = scale.clamp(min=1e-8)
      q = (x / scale).round().clamp(-128, 127).to(torch.int8)
      return q, scale, orig_shape

  def dequantize(q, scale, orig_shape, block=32):
      x = q.float() * scale
      return x.flatten()[:orig_shape.numel()].view(orig_shape)

  x = torch.randn(256)
  q, s, shape = quantize_mxfp8(x)
  x_hat = dequantize(q, s, shape)
  print("原始:", x[:4])
  print("还原:", x_hat[:4])
  print("最大误差:", (x - x_hat).abs().max().item())
  ```
- **预期结果**：误差应该在 0.01 量级。如果你故意把 scale 改成 0 或者用错块的 scale，误差会爆炸——这就是漏注册 scale 的后果。

### 知识点 4：FlashMLA 的 KV 格式命名（为什么"猜格式"会出错）

- **是什么**：FlashMLA 是 DeepSeek 系列用的注意力 kernel。它支持多种 KV 缓存布局，有些布局的字节数完全一样（比如 528 B/token），只能靠"有没有 RoPE"来区分。
- **为什么重要**：commit #41337 给 FlashMLA 调用加了显式的 `kv_format` 参数，因为"528 B/token 的 zero-RoPE cache"和"V4.1 的格式"shape 完全一样，kernel 无法自己判断。
- **动手试试**：
  ```python
  # 模拟：两个不同格式但字节数相同的 KV 缓存
  B, S, H, D = 1, 128, 8, 66   # 66 * 2 bytes = 132 B per head
  kv_a = torch.zeros(B, S, H, D, dtype=torch.float16)  # 格式 A
  kv_b = torch.zeros(B, S, H, D, dtype=torch.float16)  # 格式 B

  print("格式A shape:", kv_a.shape, "字节:", kv_a.nbytes)
  print("格式B shape:", kv_b.shape, "字节:", kv_b.nbytes)
  print("shape相同?", kv_a.shape == kv_b.shape)
  print("字节相同?", kv_a.nbytes == kv_b.nbytes)

  # 如果 kernel 只看 shape，就会把 A 当成 B 处理
  # 显式传 format 才能避免
  def flashmla_forward(kv, kv_format):
      if kv_format == "V32_NO_ROPE":
          return "按无RoPE布局解析"
      elif kv_format == "V32":
          return "按有RoPE布局解析"
      else:
          raise ValueError(f"未知格式: {kv_format}")

  print(flashmla_forward(kv_a, "V32_NO_ROPE"))
  print(flashmla_forward(kv_b, "V32"))
  ```
- **预期结果**：你会看到两个张量 shape 和字节数完全相同，但语义不同。这解释了为什么"显式传格式"比"让 kernel 猜"更安全。

### 知识点 5：Router 的 bootstrap 与就绪门控

- **是什么**：多个 router 副本组成集群时，新启动的副本会从兄弟副本"拉取"KV 树快照（bootstrap）。如果拉取失败，它就不应该对外说自己"就绪"。
- **为什么重要**：commit #40699 加了 `--kv-bootstrap-seed-required`：如果兄弟节点存在但树拉不下来，`/readyz` 返回 503。commit #42010 去掉了"快照客户端构建失败时回退到 introspection 客户端"的逻辑，因为那个客户端会跟随重定向，可能把几 GB 的快照发到恶意 URL。
- **动手试试**：
  ```bash
  # 启动一个简单的 HTTP 服务模拟 router
  python3 -c "
  from http.server import HTTPServer, BaseHTTPRequestHandler
  import json

  class H(BaseHTTPRequestHandler):
      def do_GET(self):
          if self.path == '/readyz':
              # 模拟：bootstrap 未完成
              self.send_response(503)
              self.end_headers()
              self.wfile.write(b'not ready')
          else:
              self.send_response(200)
              self.end_headers()
              self.wfile.write(json.dumps({'status':'ok'}).encode())

  HTTPServer(('localhost', 18080), H).serve_forever()
  " &
  sleep 1

  # 测试就绪探针
  curl -s -o /dev/null -w "readyz HTTP状态: %{http_code}\n" http://localhost:18080/readyz
  curl -s -o /dev/null -w "其他路径 HTTP状态: %{http_code}\n" http://localhost:18080/health

  kill %1
  ```
- **预期结果**：`/readyz` 返回 503，其他路径返回 200。在 Kubernetes 里，503 会让 Pod 不被加入 Service 端点，避免把流量打到还没准备好的副本上。

## 📋 逐条解读

### 1. [DFlash] Keep grouped-conv taps inside each request's block so NaN/Inf cannot leak across requests

- **代码层面**：改的是 `python/sglang/srt/models/dflash.py` 里的 `_grouped_conv` 函数。原来用 `out = out + coefficients[:, tap] * shifted * (position >= tap).view(-1, 1, 1)`，现在改成先用 `torch.where` 把越界位置的 shifted 置零，再乘系数。效果一样，但避免了 `0 * NaN = NaN` 的问题。
- **新手概念课堂**：想象你在做"滑动窗口平均"，窗口不能跨过每个请求的边界。原来的写法是"先乘再屏蔽"，如果越界位置恰好是 NaN（比如前一个请求的 padding），`0 * NaN` 还是 NaN，会污染当前请求。新写法是"先屏蔽再乘"，NaN 被 `torch.where` 替换成 0，就不会传播了。
- **对你有什么影响**：如果你用 DFlash 模型做批量推理，之前可能偶尔遇到某些请求输出 NaN，现在这个 bug 被修了。

### 2. [DSA] Stop forcing the per-step CPU seq_lens sync for the k-pool indexer

- **代码层面**：改了两个文件。`dsa_indexer_kpool.py` 里把 `len(forward_batch.seq_lens_cpu) == 0` 改成 `forward_batch.seq_lens.shape[0] == 0`，用 GPU 上的 shape 判断空 batch，不再读 CPU 镜像。`dsa_backend.py` 里删掉了 `self.needs_cpu_seq_lens = self.dsa_index_kpool > 1` 这行，因为现在不需要了。
- **新手概念课堂**：CPU 和 GPU 之间有一条"窄桥"（PCIe），每次过桥都要等。判断"batch 是不是空的"只需要知道数组长度，这个信息在 GPU 上就有，没必要把整个数组搬回 CPU 再数一遍。
- **对你有什么影响**：用 DeepSeek 稀疏注意力 + k-pool indexer 时，解码速度会略有提升，尤其是在高并发场景下。

### 3. [DSV4/DSA] Name the FlashMLA KV format and drop the V4.1 support probe

- **代码层面**：`dsa_backend.py` 里新增 `self.flashmla_kv_format = "V32_NO_ROPE" if self.qk_rope_head_dim == 0 else "V32"`，并在调用 FlashMLA 时传入 `kv_format=self.flashmla_kv_format`。`deepseek_v4_memory_pool.py` 里删掉了 V4.1 支持探测逻辑。`pyproject.toml` 和 Dockerfile 里把 `sglang-kernel` 从 0.4.7 升到 0.4.8。
- **新手概念课堂**：就像寄快递时，两个包裹重量一样但一个写着"易碎"一个没写。如果快递员只看重量，就会把易碎品当普通包裹扔。FlashMLA 的两种 KV 格式字节数相同，必须显式告诉它"这是哪种"。
- **对你有什么影响**：用 DeepSeek-V4 系列模型时，不会再出现"格式猜错导致输出乱码"的问题。同时需要升级 `sglang-kernel` 到 0.4.8。

- **对你有什么影响**：在 AMD gfx950 上用 DeepSeek-V4 做 PD 分离时，如果两端配置不一致，会得到清晰的错误信息，而不是默默输出错误结果。

### 6. [sgl-router] Exclude portless prefills and retry bootstrap discovery

- **代码层面**：`health.rs` 里新增测试 `readiness_rejects_portless_prefill`，如果 prefill worker 没有 `bootstrap_port`，`/readyz` 返回 503。`manager.rs` 里给 bootstrap 发现加了重试逻辑。`circuit_breaker.rs` 里给 `CircuitBreakerConfig` 加了 `PartialEq` 和 `config()` 方法。
- **新手概念课堂**：prefill worker 需要告诉 decode worker "我的 bootstrap 端口是多少"，否则 decode 找不到它。就像你打电话给朋友，但没告诉他你的分机号，他转接不过去。
- **对你有什么影响**：router 启动时，如果 prefill worker 没配 bootstrap 端口，会明确报"未就绪"，而不是等到请求来了才失败。

### 7. [Router] Drop the snapshot client's redirect-following fallback

- **代码层面**：`index.rs` 里把 `match reqwest::Client::builder()...build() { Ok(c) => c, Err(e) => { warn!(...); http.clone() } }` 改成直接 `.build().expect(...)`。去掉了"构建失败时回退到 introspection 客户端"的逻辑。
- **新手概念课堂**：快照客户端配置了"不跟随重定向"，这是安全措施。如果构建失败就回退到"跟随重定向"的客户端，等于把安全措施绕过了。而且那个客户端的超时是给 `/server_info` 设计的，拉几 GB 的快照必然超时。
- **对你有什么影响**：router 的 KV bootstrap 更安全，不会被恶意重定向引导到内网其他服务。

### 8. [PD] Fix block scale registration for mixed full/SWA KV dtypes

- **代码层面**：`utils.py` 里 `append_dsa_tail` 函数原来只检查 `full_kv_pool` 是不是 MXFP8，现在改成分别检查 `full_kv_pool` 和 `swa_kv_pool`，各自决定是否注册 `BLOCK_SCALE` 和 `BLOCK_SCALE_SWA`。测试文件里新增了 4 种组合的测试。
- **新手概念课堂**：full KV 和 SWA（滑动窗口注意力）KV 可能用不同精度。如果 full 用 MXFP8 但 SWA 用 FP16，原来只注册 full 的 scale，decode 端拿到 SWA 数据后不知道用什么 scale 解量化，就会出错。
- **对你有什么影响**：混合精度 KV 配置下，PD 传输不再丢失 SWA 的 scale，输出正确。

### 9. [KDA+Kimi K3] Speed up LTX-2.3 QK norm and split RoPE on H200
