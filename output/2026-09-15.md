## 🧪 重要知识点 & 动手实验

### 知识点 1：前缀缓存（Prefix Cache）如何工作
- **是什么**：把 prompt 中已经算过的 KV 块按哈希存起来，下一个请求如果前缀相同就直接命中，跳过 prefill。
- **为什么重要**：在多轮对话、RAG、few-shot 场景里，前缀复用能省掉 50%+ 的算力。不懂的话，你可能写出"每次都重算"的推理服务。
- **动手试试**：
  ```bash
  pip install vllm
  # 启动一个服务
  python -m vllm.entrypoints.openai.api_server --model Qwen/Qwen2.5-0.5B-Instruct &
  # 发两次相同前缀的请求，观察 metrics
  curl http://localhost:8000/metrics | grep -E "prefix_cache|num_requests"
  ```
  然后看 `vllm:gpu_prefix_cache_hit_rate` 是不是第一次 0、第二次接近 1。
- **预期结果**：第二次请求的 TTFT（首 token 时间）明显比第一次短，命中率上升。

### 知识点 2：Prometheus 指标里 ITL 和 TPOT 的区别
- **是什么**：ITL（Inter-Token Latency）是"相邻两次流式输出之间的时间"；TPOT（Time Per Output Token）是"每请求平均每 token 时间"。
- **为什么重要**：推测解码（speculative decoding）一次吐多个 token，两者会明显不同。选错指标会误判服务性能。
- **动手试试**：
  ```bash
  # 打开 vLLM 的 /metrics 端点，抓这两个指标
  curl -s http://localhost:8000/metrics | grep -E "inter_token_latency|request_time_per_output_token"
  ```
  再跑一次 `vllm bench serve --model Qwen/Qwen2.5-0.5B-Instruct --num-prompts 20`，对比 benchmark 输出的 TPOT 和 metrics 里的直方图。
- **预期结果**：当输出包含多 token 时（比如开启 spec decode），两个指标会分叉，你就理解文档为什么强调它们不能混用了。

### 知识点 3：CUDA IPC 张量与共享内存引用计数
- **是什么**：CUDA IPC 允许进程间共享 GPU 显存，但每个消费者进程必须独立"注册"一次映射，否则引用计数错乱。
- **为什么重要**：commit #56472 修的就是权重缓存守护进程"只导出一次 IPC 张量给多个客户端"导致的崩溃。多进程部署（比如 daemon + engine）时极易踩坑。
- **动手试试**：
  ```python
  import torch, torch.multiprocessing as mp
  def worker(t):
      # 每个子进程独立消费 IPC 张量
      print("worker sees:", t.sum().item())
  if __name__ == "__main__":
      t = torch.ones(4, device="cuda")
      t.share_memory_()
      ps = [mp.Process(target=worker, args=(t,)) for _ in range(2)]
      [p.start() for p in ps]; [p.join() for p in ps]
  ```
- **预期结果**：两个子进程都能正常读到张量；如果只导出一次给多个客户端，第二个会报 `CUDA error: invalid resource handle`。这就是 commit 要修的场景。

### 知识点 4：MoE 通信与计算重叠（DeepEP）
- **是什么**：MoE 层里 token 要先 all-to-all 分发到专家所在 GPU，算完再 all-to-all 收回来。异步化就是让"算共享专家"和"收 combine 结果"并行。
- **为什么重要**：在 8 卡、16 卡 MoE 推理里，通信可能占 30%+ 的时间。重叠做得好，吞吐直接翻倍。
- **动手试试**：
  ```python
  # 阅读测试文件即可理解契约
  # tests/kernels/moe/test_deepep_v2_async_finalize.py
  # 关注 finalize_async 返回的 event，以及 receiver 如何 wait
  ```
  然后自己写一个假的 buffer，验证 `async_with_compute_stream=True` 时 event 会被 wait，`False` 时不会。
- **预期结果**：你能画出"dispatch → 专家计算 → combine(event) → 共享专家计算 → event.wait → 拷贝结果"的时序图。

### 知识点 5：JSON Schema → 文法编译（xgrammar）
- **是什么**：把 JSON Schema 编译成一个上下文无关文法，模型每生成一个 token 就用这个文法约束词表。
- **为什么重要**：Agent 场景下，模型必须输出合法 JSON，否则下游解析器就崩。但 JSON Schema 特性极多，很多边角 case 会被静默忽略（如 `propertyNames` + `patternProperties` 组合）。
- **动手试试**：
  ```python
  from xgrammar import Grammar
  from xgrammar.testing import _is_grammar_accept_string
  schema = {"type": "object", "properties": {"age": {"type": "integer"}}, "required": ["age"]}
  g = Grammar.from_json_schema(schema)
  print(_is_grammar_accept_string(g, '{"age": 18}'))   # True
  print(_is_grammar_accept_string(g, '{"age": "x"}'))  # False
  ```
- **预期结果**：你能亲眼看到文法如何拒绝非法输出，理解为什么 vLLM 要维护一个"不支持特性列表"。

## 🧪 重要知识点 & 动手实验

- **知识点 1：DCP 逻辑槽位与物理行的映射**
  - **是什么**：DCP（Distributed Context Parallel）把 KV Cache 按 `slot % dcp_size == dcp_rank` 的规则切分，每张卡只保存自己那一份，行号是 `slot // dcp_size`。
  - **为什么重要**：如果你直接拿"逻辑 ID"去索引本地 KV Cache，会读到别的 rank 的数据，表现为"输出乱码"或"结果不稳定"，而且只在特定 dcp_size 下复现，非常难查。
  - **动手试试**：
    ```python
    import torch

    def maybe_dcp_kernel_indices(indices, dcp_size, dcp_rank):
        if dcp_size == 1:
            return indices
        return indices[dcp_rank::dcp_size] // dcp_size

    # 模拟 dcp_size=4, 当前 rank=1，逻辑槽位 0..15
    indices = torch.arange(16)
    print(maybe_dcp_kernel_indices(indices, 4, 1))
    # 输出: tensor([0, 1, 2, 3])  —— 因为 rank1 拥有 slot 1,5,9,13，映射到行 0,1,2,3
    ```
  - **预期结果**：你会看到 rank 1 只拿到 4 个物理行，且是 `slot // 4` 的结果。如果这里写错，KV Cache 恢复时就会"串门"。

- **知识点 2：KV Cache 的"分层"命中判定**
  - **是什么**：一块 KV 可能同时在 GPU 和 CPU 上有一份副本。Router 需要知道"哪张卡在哪个 tier 上还有这块 KV"，才能把请求路由过去。
  - **为什么重要**：如果 Router 只看"有没有"而不看"在哪一层"，就会出现"以为命中 GPU，结果要跨 PCIe 拉数据"的假命中，延迟反而更高。
  - **动手试试**：
    ```python
    # 伪代码：模拟 tiered tree 的插入与删除
    class TieredTree:
        def __init__(self):
            self.owners = {}  # hash -> set of (worker, tier)

        def insert_tiered(self, worker, hashes, tier):
            for h in hashes:
                self.owners.setdefault(h, set()).add((worker, tier))

        def remove_tiered(self, worker, hashes, tier):
            for h in hashes:
                self.owners.get(h, set()).discard((worker, tier))

    tree = TieredTree()
    tree.insert_tiered("w1", [10, 20], tier="host")
    tree.insert_tiered("w1", [10, 20], tier="device")
    tree.remove_tiered("w1", [20], tier="device")  # 只删 device 层
    print(tree.owners[20])  # 仍然是 {('w1', 'host')}，host 层还在
    ```
  - **预期结果**：device 层被清掉，但 host 层保留。这就是 Commit 11 的核心修复：**删一层不能把整块都删了**。

- **知识点 3：融合算子 QK Norm + RoPE**
  - **是什么**：把 RMSNorm（对 Q/K 做归一化）和 RoPE（旋转位置编码）合并成一个 kernel，避免中间结果写回显存。
  - **为什么重要**：这两个算子在每个 attention 层都要跑，融合后能省一次读写显存，长序列下收益明显；不融合的话，显存带宽就是瓶颈。
  - **动手试试**：
    ```python
    import torch

    def fused_qk_norm_rope(q, k, q_weight, k_weight, eps=1e-6):
        # 简化版：只做 RMSNorm，RoPE 略
        def rms_norm(x, w):
            var = x.pow(2).mean(dim=-1, keepdim=True)
            return x * torch.rsqrt(var + eps) * w
        return rms_norm(q, q_weight), rms_norm(k, k_weight)

    q = torch.randn(2, 4, 64)
    k = torch.randn(2, 4, 64)
    qw = torch.ones(64)
    kw = torch.ones(64)
    qn, kn = fused_qk_norm_rope(q, k, qw, kw)
    print(qn.shape, kn.shape)
    ```
  - **预期结果**：输出形状不变，但你应该理解：真实 kernel 里这两步是在同一个 `parallel_for` 里完成的，省了一次显存往返。

- **知识点 4：LoRA adapter 槽位准入控制**
  - **是什么**：每张卡能同时加载的 LoRA adapter 数量有限（比如 8 个）。新请求进来前，必须先检查"这张卡上现在有没有空槽"。
  - **为什么重要**：PD 分离场景下，Decode 节点如果盲目接收请求，会出现"adapter 槽位不够 → 请求排队 → 超时"的雪崩。
  - **动手试试**：
    ```python
    class LoraAdmission:
        def __init__(self, max_slots=2):
            self.max_slots = max_slots
            self.running = set()

        def can_schedule(self, req_lora_id, running_loras):
            if req_lora_id in running_loras:
                return True  # 已在跑，直接复用
            return len(running_loras) < self.max_slots

    adm = LoraAdmission(max_slots=2)
    running = {"lora_a", "lora_b"}
    print(adm.can_schedule("lora_a", running))  # True，复用
    print(adm.can_schedule("lora_c", running))  # False，槽位满
    ```
  - **预期结果**：你会看到"复用已加载的 adapter"永远允许，但"加载新 adapter"要受槽位限制。Commit 8 就是把这个判断搬到了 Decode 准入路径上。

- **知识点 5：可插拔内核分发（OOT Dispatch）**
  - **是什么**：一个算子可以同时注册多个后端（JIT/Torch/厂商），运行时按硬件能力自动选一个。
  - **为什么重要**：在 AMD/NPU 上，某些 JIT kernel 不可用，需要自动 fallback 到 Torch 实现，否则整个模型跑不起来。
  - **动手试试**：
    ```python
    class ClampPositionOp:
        priority = ("JIT", "TORCH")
        capabilities = {"JIT": {"CUDA", "HIP"}}

        def forward_native(self, seq_lens):
            return torch.clamp(seq_lens - 1, min=0).to(torch.int64)

        def forward_jit(self, seq_lens):
            # 假装调了 CUDA kernel
            return self.forward_native(seq_lens)

        def __call__(self, seq_lens, backend="JIT"):
            if backend == "JIT" and "CUDA" in self.capabilities["JIT"]:
                return self.forward_jit(seq_lens)
            return self.forward_native(seq_lens)

    op = ClampPositionOp()
    print(op(torch.tensor([0, 5, 10])))
    # 输出: tensor([0, 4, 9])
    ```
  - **预期结果**：你会看到同一个调用入口，可以根据硬件能力走不同实现。这就是 Commit 15 引入的 `BaseFusedOp` 模式。
