## 🧪 重要知识点 & 动手实验

### 知识点 1：CUDA Graph 捕获与 `intermediate_tensors`

- **是什么**：CUDA Graph 把一串 GPU 算子"录下来"变成一张图，之后每次执行只需重放，省掉 Python/调度开销。`intermediate_tensors` 是流水线并行中上一层传给下一层的中间结果。
- **为什么重要**：捕获时如果不传 `intermediate_tensors=None`，模型会误以为有真实数据，导致捕获失败或结果错误。这是流水线并行 + 图捕获的经典坑。
- **动手试试**：
  ```bash
  # 安装 vLLM 后，用一个小模型开 CUDA Graph
  python -m vllm.entrypoints.openai.api_server \
      --model Qwen/Qwen2.5-0.5B-Instruct \
      --enforce-eager False
  ```
  然后发一个请求：
  ```bash
  curl http://localhost:8000/v1/completions -H "Content-Type: application/json" -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "prompt": "Hello",
    "max_tokens": 16
  }'
  ```
- **预期结果**：服务正常返回。如果捕获时报错 `intermediate_tensors` 相关，就是今天 Commit 1 修的问题。

### 知识点 2：FP8 缓存的"2 的幂"缩放（power-of-two scale）

- **是什么**：把 FP8 的缩放因子强制取成 2 的幂（如 2^-3、2^4），这样在硬件里做乘除就是移位，既快又精确。
- **为什么重要**：Commit 12 发现 SM100 上非 2 的幂的缩放会精度丢失，改成 `exp2f(ceilf(log2f(x)))` 后 SM90/SM100 都能无损读取。
- **动手试试**：
  ```python
  import torch, math
  x = torch.tensor([0.037, 0.512, 3.14159])
  # 非 2 的幂缩放
  s1 = x.abs().max() / 448.0
  # 2 的幂缩放
  s2 = 2 ** math.ceil(math.log2(max(s1, 1e-4)))
  print("原始:", x)
  print("scale1:", s1, "还原:", (x / s1).to(torch.float8_e4m3fn).to(torch.float32) * s1)
  print("scale2:", s2, "还原:", (x / s2).to(torch.float8_e4m3fn).to(torch.float32) * s2)
  ```
- **预期结果**：你会发现用 2 的幂缩放时，反量化后的值更"干净"，误差更可控。

### 知识点 3：稀疏注意力的 top-k 索引与"ragged"批次

- **是什么**：稀疏注意力只让每个 query 关注最相关的 top-k 个 key。当一批请求长度不一时，索引就是"ragged"（参差不齐）的。
- **为什么重要**：Commit 14 发现"看似均匀"的批次（比如 8 个 token 分给 6 个请求）会被误判为可均匀 reshape，导致崩溃。修复方法是用 `num_decode_tokens % decode_lens.shape[0] != 0` 判断。
- **动手试试**：
  ```python
  # 模拟 ragged 判断
  num_decode_tokens = 8
  decode_lens = [1, 2, 3, 2]  # 4 个请求，总长 8
  print("整除吗?", num_decode_tokens % len(decode_lens) == 0)  # True，但实际不均匀！
  decode_lens2 = [1, 1, 1, 1, 1, 1, 1, 1]
  print("整除吗?", num_decode_tokens % len(decode_lens2) == 0)  # True，且均匀
  ```
- **预期结果**：第一个例子整除但实际不均匀，说明"整除"只是必要条件，不是充分条件——这正是 Commit 14 的坑点。

### 知识点 4：自定义 Logits Processor（MRV2 接口）

- **是什么**：Logits Processor 在模型输出概率分布后、采样前，对 logits 做修改（比如禁止某些 token、加偏置）。
- **为什么重要**：Commit 15 把接口从 V1 迁移到 MRV2，并强调"一行 logits ≠ 一个请求"——投机解码时一个请求可能对应多行。
- **动手试试**：
  ```python
  from vllm.v1.worker.gpu.sample.logits_processor import LogitsProcessor

  class BanTokenProcessor(LogitsProcessor):
      def __init__(self, vllm_config, req_states):
          self.banned = -1

      def add_request(self, req_idx, sampling_params):
          # 从自定义参数里读要禁止的 token
          self.banned = getattr(sampling_params, "banned_token", -1)
          return self.banned >= 0

      def apply(self, logits):
          if self.banned >= 0:
              logits[:, self.banned] = float("-inf")
          return logits

      def is_argmax_invariant(self):
          return False
  ```
- **预期结果**：注册后，被禁止的 token 永远不会被采样出来。注意 MRV2 的 `add_request` 返回 bool 表示"这个请求是否需要处理"。

## 🧪 重要知识点 & 动手实验

- **知识点 1：Triton 算子融合（Kernel Fusion）**
  - **是什么**：用 Triton 写一个 kernel 同时完成多步计算，避免中间结果反复读写显存。
  - **为什么重要**：LLM 推理中大量时间花在 memory-bound 的小算子上（激活、归一化、缩放）。融合能带来 1.5-3x 加速。不懂这个，你写的推理代码会慢得离谱。
  - **动手试试**：
    ```python
    import torch, triton, triton.language as tl

    @triton.jit
    def fused_silu_mul(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
        # 融合 SiLU(x) * y 两个算子
        offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
        mask = offs < n
        x = tl.load(x_ptr + offs, mask=mask)
        y = tl.load(y_ptr + offs, mask=mask)
        silu = x * tl.sigmoid(x)
        tl.store(out_ptr + offs, silu * y, mask=mask)

    n = 1024 * 1024
    x = torch.randn(n, device="cuda")
    y = torch.randn(n, device="cuda")
    out = torch.empty_like(x)
    fused_silu_mul[(triton.cdiv(n, 1024),)](x, y, out, n, BLOCK=1024)

    # 对比 PyTorch 原生两步
    ref = torch.nn.functional.silu(x) * y
    print("max diff:", (out - ref).abs().max().item())
    ```
  - **预期结果**：`max diff` 接近 0（浮点误差内）。用 `torch.cuda.Event` 计时，融合版通常比两步 PyTorch 快 1.3-2x。

- **知识点 2：投机解码的 Draft-Verify 流程**
  - **是什么**：小模型（draft）一次生成 K 个候选 token，大模型（target）一次 forward 并行验证，接受匹配的前缀。
  - **为什么重要**：这是目前最主流的无损加速方案。理解它才能看懂 SGLang 里 EAGLE、MTP、DFlash 这些名词。
  - **动手试试**：
    ```python
    # 用伪代码模拟投机解码的核心逻辑
    def speculative_decode(draft_model, target_model, prompt, K=4):
        tokens = prompt.copy()
        while True:
            # 1. Draft: 小模型自回归生成 K 个 token
            draft_tokens = []
            draft_logits = []
            cur = tokens
            for _ in range(K):
                logits = draft_model(cur)
                t = logits.argmax(-1)
                draft_tokens.append(t)
                draft_logits.append(logits)
                cur = cur + [t]

            # 2. Verify: 大模型一次 forward 验证 K+1 个位置
            target_logits = target_model(tokens + draft_tokens)

            # 3. 从左到右逐个比对，接受匹配的
            accepted = 0
            for i, t in enumerate(draft_tokens):
                if target_logits[i].argmax(-1) == t:
                    accepted += 1
                else:
                    # 拒绝后从 target 分布采样一个修正 token
                    tokens.append(target_logits[i].argmax(-1))
                    break
            else:
                # 全部接受，额外采样一个
                tokens.append(target_logits[-1].argmax(-1))

            tokens = tokens + draft_tokens[:accepted]
            if len(tokens) > 100: break
        return tokens
    ```
  - **预期结果**：理解"一次 target forward 换来多个 token"的加速原理。真实场景中接受率约 60-80%，端到端加速 1.5-2.5x。

- **知识点 3：KV Cache 的 Slot 映射（逻辑地址 → 物理地址）**
  - **是什么**：把"第 N 个 token"这种逻辑位置，翻译成显存里实际的 KV cache 行号。
  - **为什么重要**：PD 分离、HiSparse、RadixCache 都依赖这个映射。搞错了就是数据错乱、结果乱码。Commit 9 专门写了个 Triton kernel 做这件事。
  - **动手试试**：
    ```python
    import torch

    # 模拟：逻辑 slot -> 物理 row 的映射
    num_mapping = 100
    mapping = torch.arange(num_mapping, device="cuda", dtype=torch.int32) * 2  # 逻辑 i -> 物理 2i

    # 请求的 token 逻辑位置，-1 表示 padding
    locations = torch.tensor([17, 18, -1, 5, 0, -1], device="cuda", dtype=torch.int32)

    # 手写翻译（Commit 9 用 Triton 做了同样的逻辑）
    physical = torch.where(
        locations >= 0,
        mapping[locations.clamp(min=0)],
        locations,  # 保留 -1
    )
    print("logical: ", locations.tolist())
    print("physical:", physical.tolist())
    # 期望: [34, 36, -1, 10, 0, -1]
    ```
  - **预期结果**：看到逻辑位置被正确翻译成物理行号，padding 的 `-1` 原样保留。这就是 Commit 9 那个 Triton kernel 做的事。

- **知识点 4：量化格式 MXFP4 / NVFP4 的 Block Scaling**
  - **是什么**：每 32 个元素共享一个缩放因子（scale），用 4-bit 存数据 + 8-bit 存 scale。
  - **为什么重要**：MoE 模型专家参数巨大，4-bit 量化能省 75% 显存。但 block scale 的粒度和格式（E4M3 vs E8M0）决定了精度和硬件兼容性。
  - **动手试试**：
    ```python
    import torch

    def mxfp4_quantize(x, block_size=32):
        """简化的 MXFP4 量化：每 32 元素一个 scale"""
        orig_shape = x.shape
        x = x.reshape(-1, block_size)
        # 每个 block 的最大绝对值作为 scale
        scale = x.abs().amax(dim=-1, keepdim=True) / 7.0  # FP4 E2M1 最大 6/7
        scale = scale.clamp(min=1e-8)
        # 量化到 [-7, 7] 的整数（真实 MXFP4 用 E2M1 浮点）
        q = (x / scale).round().clamp(-7, 7).to(torch.int8)
        # 反量化
        deq = (q.float() * scale).reshape(orig_shape)
        return deq, q, scale

    x = torch.randn(4, 128) * 3
    deq, q, scale = mxfp4_quantize(x)
    print(f"原始 std: {x.std():.4f}, 反量化 std: {deq.std():.4f}")
    print(f"相对误差: {((x - deq).norm() / x.norm()).item():.4f}")
    print(f"压缩比: {x.numel() * 32 / (q.numel() * 4 + scale.numel() * 8):.1f}x")
    ```
  - **预期结果**：相对误差约 5-15%，压缩比约 6-7x。这就是为什么 MXFP4 在 MoE 上这么香——精度可接受，显存省一大截。

- **知识点 5：Pipeline Parallel 的 Prefetch 与跨阶段流水**
  - **是什么**：把模型切成多段放在不同 GPU 上，每段处理完传给下一段；prefetch 是提前把下一批数据/权重准备好。
  - **为什么重要**：PP 是超大模型（70B+）部署的必备技能。Commit 11 加了"Prefetch Ticket"机制，让 PP0 提前通知后续 stage 去存储层预取 KV。
  - **动手试试**：
    ```python
    import asyncio

    async def pp_stage(stage_id, input_queue, output_queue, prefetch_queue):
        """模拟一个 PP stage：处理输入 + 预取下一批"""
        while True:
            data = await input_queue.get()
            if data is None: break

            # 模拟计算
            await asyncio.sleep(0.1)
            result = f"stage{stage_id}({data})"

            # 提前通知下一 stage 预取（类似 Commit 11 的 prefetch ticket）
            await prefetch_queue.put(f"prefetch_for_{result}")
            await output_queue.put(result)

    async def main():
        q1, q2, q3 = asyncio.Queue(), asyncio.Queue(), asyncio.Queue()
        pf = asyncio.Queue()

        stages = [
            asyncio.create_task(pp_stage(0, q1, q2, pf)),
            asyncio.create_task(pp_stage(1, q2, q3, pf)),
            asyncio.create_task(pp_stage(2, q3, asyncio.Queue(), pf)),
        ]

        for i in range(3):
            await q1.put(f"batch{i}")
        await asyncio.sleep(1.0)

        # 打印预取队列
        while not pf.empty():
            print("prefetch event:", await pf.get())

        for t in stages: t.cancel()

    asyncio.run(main())
    ```
  - **预期结果**：看到每个 stage 处理完后都发出了 prefetch 事件。真实场景中，这个 prefetch 会触发从 SSD/远端存储拉取 KV cache，隐藏 I/O 延迟。
