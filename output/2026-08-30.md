### 知识点 2：缓存的生命周期管理 (Commit 4)
- **是什么**：将模型的缓存（如 Qwen2.5-VL 的 RoPE 缓存）从"全局静态缓存"改为"实例级缓存"，随模型销毁而释放。
- **为什么重要**：使用 `@lru_cache` 的缓存是全局的，模型被删除后缓存仍占用显存，导致内存泄漏。在频繁加载/卸载模型的多租户场景下，这是致命的。
- **动手试试**：
```python
from functools import lru_cache

# 错误示范：全局缓存，模型销毁后缓存仍在
@lru_cache(maxsize=1024)
def get_rope(t, h, w):
    return f"rope_{t}_{h}_{w}"

# 正确示范：实例级缓存，随对象销毁
class QwenVL:
    def __init__(self):
        self._cache = {}
    def get_rope(self, t, h, w):
        key = (t, h, w)
        if key not in self._cache:
            self._cache[key] = f"rope_{t}_{h}_{w}"
        return self._cache[key]

model = QwenVL()
print(model.get_rope(1, 2, 3))
del model  # 缓存随对象一起被回收
```
- **预期结果**：理解实例级缓存与全局缓存的区别，以及为什么前者更安全。

### 知识点 1：PyTorch张量散射操作（Scatter）的内存优化
- **是什么**：将稀疏的嵌入向量按掩码位置填入目标张量的操作，`masked_scatter_`和`index_copy_`是两种实现方式。
- **为什么重要**：`masked_scatter_`会物化巨大的bool掩码和前缀和数组，导致大量瞬时显存占用。在长序列、大batch场景下可能直接OOM。`index_copy_`通过计算行索引，将瞬时内存从O(num_tokens × hidden)降到O(num_tokens)。
- **动手试试**：
```python
import torch

# 模拟：num_tokens=10000, hidden=4096
num_tokens, hidden = 10000, 4096
dest = torch.randn(num_tokens, hidden, device='cuda')
mask = torch.zeros(num_tokens, 1, dtype=torch.bool, device='cuda')
mask[::3] = True  # 约1/3位置需要填充
src = torch.randn(mask.sum().item(), hidden, device='cuda')

# 方法1：masked_scatter_（高内存）
torch.cuda.reset_peak_memory_stats()
dest.masked_scatter_(mask.expand_as(dest), src)
peak1 = torch.cuda.max_memory_allocated()

# 方法2：index_copy_（低内存）
torch.cuda.reset_peak_memory_stats()
flat_mask = mask.view(-1)
ranks = torch.cumsum(flat_mask, dim=0) - 1
ranks = ranks.masked_fill(~flat_mask, src.size(0))
rows = torch.full((src.size(0)+1,), dest.size(0), dtype=torch.long, device='cuda')
rows.scatter_(0, ranks, torch.arange(flat_mask.numel(), device='cuda'))
dest.index_copy_(0, rows[:src.size(0)], src)
peak2 = torch.cuda.max_memory_allocated()

print(f"masked_scatter_ 峰值显存: {peak1/1024**2:.2f} MB")
print(f"index_copy_ 峰值显存: {peak2/1024**2:.2f} MB")
```
- **预期结果**：`index_copy_`的峰值显存显著低于`masked_scatter_`，且两者计算结果一致。掌握后你就能理解为什么生产代码要避免使用`masked_scatter_`。

### 知识点 2：asyncio任务的生命周期管理
- **是什么**：Python asyncio事件循环只持有任务的弱引用，如果外部没有强引用，任务可能被垃圾回收器回收而停止执行。
- **为什么重要**：在分布式推理中，后台任务（如结果监听、健康检查、过期清理）一旦被GC回收，会导致请求卡死、资源泄漏等难以排查的问题。
- **动手试试**：
```python
import asyncio

async def background_task():
    count = 0
    while True:
        count += 1
        print(f"后台任务运行中... {count}")
        await asyncio.sleep(1)

async def buggy_demo():
    # 错误写法：没有持有强引用
    asyncio.create_task(background_task())
    await asyncio.sleep(3)
    print("3秒后，任务可能已被GC回收")

async def fixed_demo():
    # 正确写法：持有强引用
    tasks = set()
    task = asyncio.create_task(background_task())
    tasks.add(task)
    task.add_done_callback(tasks.discard)
    await asyncio.sleep(3)
    print("3秒后，任务仍在运行")

# 运行buggy版本，观察任务是否在第3秒前停止
# asyncio.run(buggy_demo())
# 运行fixed版本，观察任务持续运行
# asyncio.run(fixed_demo())
```
- **预期结果**：`buggy_demo`中后台任务可能在3秒内被GC回收而停止打印；`fixed_demo`中任务持续运行。掌握后你就能理解为什么sglang要维护`_background_tasks`集合。

### 知识点 3：KV缓存的生命周期管理
- **是什么**：KV缓存是推理引擎为每个请求维护的键值缓存，其生命周期（分配、提交、释放）需要精确管理。`kv_allocated_len`表示已分配的长度，`kv_committed_len`表示已提交（可被安全使用）的长度。
- **为什么重要**：在prefill和decode阶段，KV缓存的分配和提交时机不同步。如果不正确管理，可能导致内存泄漏、数据竞争或错误的结果。将这两个字段统一到`ReqKvInfo`类中，是为了让内存管理的职责更清晰。
- **动手试试**：
```python
# 概念演示：理解allocated vs committed的区别
class ReqKvInfo:
    def __init__(self):
        self.kv_allocated_len = 0  # 已分配
        self.kv_committed_len = 0  # 已提交

req = ReqKvInfo()

# prefill阶段：分配了100个token的KV空间，但只有80个token被真正计算并提交
req.kv_allocated_len = 100
req.kv_committed_len = 80

# 此时，KV缓存中[0, 80)是有效的，[80, 100)是未初始化的
print(f"有效KV范围: [0, {req.kv_committed_len})")
print(f"分配但未提交: [{req.kv_committed_len}, {req.kv_allocated_len})")

# decode阶段：每步分配1个token并立即提交
req.kv_allocated_len += 1
req.kv_committed_len += 1
print(f"decode后有效KV范围: [0, {req.kv_committed_len})")
```
- **预期结果**：理解`allocated`和`committed`的区别，以及为什么需要这两个字段。掌握后你就能理解sglang中`alloc_for_extend`和`alloc_for_decode`的作用。

### 知识点 4：FP16精度饱和导致的数据损坏
- **是什么**：在ROCm平台上，将bf16数据转换为fp16时，如果数值超过fp16的最大值（65504），会发生饱和（变成inf或NaN），从而破坏all-reduce的结果。
- **为什么重要**：在分布式训练/推理中，all-reduce是高频操作。如果数据在转换过程中被破坏，会导致模型输出错误。这个问题在AMD GPU上尤为突出，因为其指令集允许编译器进行激进的优化。
- **动手试试**：
```python
import torch

# 模拟bf16到fp16的转换精度问题
bf16_tensor = torch.tensor([70000.0, -70000.0, 1000.0], dtype=torch.bfloat16, device='cuda')
print(f"bf16原始值: {bf16_tensor}")

# 直接转换（可能饱和）
fp16_direct = bf16_tensor.to(torch.float16)
print(f"fp16直接转换: {fp16_direct}")

# 带缩放转换（保持精度）
scale = 0.5
fp16_scaled = (bf16_tensor.float() * scale).to(torch.float16)
print(f"fp16带缩放: {fp16_scaled}")

# 反向缩放
restored = fp16_scaled.float() / scale
print(f"恢复后的值: {restored}")
```
- **预期结果**：`fp16_direct`中超过65504的值会变成inf，而`fp16_scaled`能正确表示。掌握后你就能理解为什么sglang要在QuickReduce中引入缩放机制。

### 知识点 5：MoE门控中的共享专家处理
- **是什么**：在MoE（混合专家）模型中，门控网络负责选择top-k个专家。当存在共享专家时，门控需要正确处理，避免重复标记或越界。
- **为什么重要**：在DeepSeek V3/R1等模型中，共享专家是性能关键。如果门控错误地将共享专家标记为路由专家，会浪费一个路由槽位，甚至导致内存越界。
- **动手试试**：
```python
# 概念演示：理解共享专家与路由专家的区别
num_routed_experts = 384  # 路由专家数

# 错误方式：门控输出8个专家，其中1个是共享专家标记

# 但门控不再输出共享专家标记，而是由专门的remap逻辑处理

print(f"每个token需要选择 {top_k} 个专家")
print(f"其中路由专家 {num_routed_topk_correct} 个，共享专家 {num_fused_shared_experts} 个")

```
- **预期结果**：理解共享专家与路由专家的区别，以及为什么门控不能重复标记共享专家。掌握后你就能理解sglang中`num_fused_shared_experts_for_gate`的作用。
