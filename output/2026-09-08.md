## 🧪 重要知识点 & 动手实验

- **知识点 1：MoE 内核配置调优**
  - **是什么**：MoE 层包含多个专家网络，其计算可视为多个小矩阵乘法 (GEMM)。内核配置 (如 `BLOCK_SIZE_N`, `num_stages`) 决定了这些 GEMM 在 GPU 上如何被切分和调度。
  - **为什么重要**：同样的模型和硬件，不同的配置可能带来 21% 的性能差异 (如 Commit 9)。手动调优不现实，vLLM 通过预生成的配置文件 (JSON) 自动为不同硬件和模型形状选择最优配置。
  - **动手试试**：
    ```bash

    # 2. 尝试修改其中一个配置 (例如将 "1" 的 BLOCK_SIZE_N 改回 128) 并运行一个 MoE 模型的 benchmark，对比性能差异。
    # 3. (可选) 阅读 vllm/model_executor/layers/fused_moe/__init__.py 了解配置是如何被加载和选择的。
    ```
  - **预期结果**：你会看到 JSON 文件里针对不同 batch size (key: "1", "2", "4"...) 有不同的 `BLOCK_SIZE_*` 和 `num_stages`。修改配置后，模型的吞吐量 (throughput) 或延迟 (latency) 会发生变化，直观感受到调优的作用。

- **知识点 2：CUDA 程序化依赖启动 (PDL)**
  - **是什么**：一种 CUDA 特性 (SM90+)，允许一个 Kernel 在依赖的前一个 Kernel 未完全结束时就开始执行，通过硬件指令 (`cudaGridDependencySynchronize`) 来确保数据就绪，实现 Kernel 间流水线重叠。
  - **为什么重要**：在 LLM 推理中，如 `QKV投影` -> `fusedQKNormRope` 这样的小 Kernel 链很常见。传统方式下，Kernel 启动和执行的间隙 (tail effect) 会造成 GPU 空闲。PDL 能有效消除这个间隙，提升小 batch 场景的延迟表现。
  - **动手试试**：
    ```bash
    # 1. 查看 Commit 6 中修改的 kernel 文件
    # vllm/csrc/libtorch_stable/fused_qknorm_rope_kernel.cu
    # 2. 定位 cudaGridDependencySynchronize() 和 cudaTriggerProgrammaticLaunchCompletion() 的调用位置。
    # 3. (高级) 使用 Nsight Systems 或 Nsight Compute 分析一个使用了该 Kernel 的模型的 GPU Kernel 时间线，观察有无重叠。
    ```
  - **预期结果**：你会看到代码中在读取输入前和写完输出后分别添加了"等待"和"触发"指令。通过性能分析工具，可以观察到这两个 Kernel 的执行时间有重叠，从而理解 PDL 的工作原理。

- **知识点 4：KV Cache 状态管理**
  - **是什么**：KV Cache 用于存储历史 token 的 Key 和 Value，避免重复计算。在 Prefix Caching 和 Mamba 等混合架构中，需要精确管理每个请求的 KV 块位置和 checkpoint 索引。
  - **为什么重要**：如果状态管理出错，会导致模型生成错误结果或直接崩溃 (如 Commit 10 的 AssertionError)。这是推理引擎中最复杂、最易出错的部分之一。

- **知识点 5：数据并行 (DP) 下的服务配置语义**
  - **是什么**：当使用 `--data-parallel-size` 时，`--max-num-seqs` 是**每个 DP rank** 的限制，而 `--max-num-queued-reqs` 是**整个服务器**的限制。
  - **为什么重要**：如果混淆这两个概念，会导致服务配置不当。例如，你设置了 `DP=4, max-num-seqs=256`，但 `max-num-queued-reqs` 仍为 `256`，那么服务器实际能处理的并发请求数远低于预期 (4*256=1024)，因为排队限制会提前触发。
  - **动手试试**：

  - **预期结果**：你会看到当 `--max-num-queued-reqs` 小于 `data-parallel-size * max-num-seqs` 时，即使 GPU 利用率不高，服务器也会开始拒绝新的请求，从而理解这两个参数的区别。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Triton 内核特化（Kernel Specialization）与编译膨胀
- **是什么**：Triton 编译器会为每个不同的参数值（如张量步长）生成一份独立的机器码，称为"特化"。参数被标记为 `constexpr` 就会触发特化。
- **为什么重要**：如果某个参数取值非常多（如 EAGLE 页表的行步长随上下文长度变化），特化会导致编译出成千上万份内核，内存暴涨。commit 13 正是修复了这个问题。
- **动手试试**：
  ```python
  import torch
  import triton
  import triton.language as tl

  @triton.jit
  def kernel_specialized(x_ptr, stride: tl.constexpr):  # 会特化
      pass

  @triton.jit(do_not_specialize=["stride"])  # 不会特化
  def kernel_not_specialized(x_ptr, stride):
      pass

  # 观察缓存大小
  for i in range(100):
      x = torch.randn(1024, device='cuda')
      kernel_specialized[(1,)](x, i)  # 每次不同 stride，产生 100 份内核
      kernel_not_specialized[(1,)](x, i)  # 只有 1 份内核

  print(f"特化内核缓存数: {len(kernel_specialized.device_caches[0][0])}")
  print(f"非特化内核缓存数: {len(kernel_not_specialized.device_caches[0][0])}")
  ```
- **预期结果**：特化版本缓存数接近 100，非特化版本只有 1。你会直观理解为什么 `do_not_specialize` 能防止编译爆炸。

### 知识点 2：投机解码（Speculative Decoding）的非贪心采样
- **是什么**：投机解码中，草稿模型生成候选 token，目标模型验证。传统实现只支持"贪心"（每次选概率最高的 token），不支持带随机性的采样（temperature/top-k/top-p）。
- **为什么重要**：贪心解码会导致生成结果单一重复，不支持多样化的应用场景。commit 6 让 NPU 支持了非贪心采样，扩展了投机解码的适用范围。
- **动手试试**（用 SGLang 跑一个对比实验）：
  ```bash
  # 安装 sglang 后，启动带投机解码的 server
  python -m sglang.launch_server \
    --model-path Qwen/Qwen2.5-1.5B-Instruct \
    --speculative-algorithm EAGLE \
    --speculative-num-steps 3 \
    --speculative-eagle-topk 4 \
    --speculative-use-rejection-sampling \
    --port 30000

  # 用不同 temperature 请求，观察输出多样性
  curl http://localhost:30000/generate \
    -H "Content-Type: application/json" \
    -d '{"text": "写一首关于春天的诗", "sampling_params": {"temperature": 0.1}}'
  curl http://localhost:30000/generate \
    -H "Content-Type: application/json" \
    -d '{"text": "写一首关于春天的诗", "sampling_params": {"temperature": 1.5}}'
  ```
- **预期结果**：temperature=0.1 时输出基本确定，temperature=1.5 时每次输出不同。同时观察吞吐量，投机解码在长输出时能提升 2-3 倍。

### 知识点 3：Radix Cache（前缀缓存）与递归算法转迭代
- **是什么**：Radix Cache 缓存 LLM 计算过的 KV 状态，当新请求与旧请求共享前缀时直接复用。commit 2 将其中的 DFS 排序从递归改为迭代实现。
- **为什么重要**：递归在树深度大时会爆栈（Python 默认递归限制 ~1000 层），而 LLM 的 prompt 前缀树可能非常深。改成迭代后更健壮，也更容易理解和调试。
- **动手试试**（体验递归转迭代）：
  ```python
  # 模拟一个很深的树（如 2000 层）
  class Node:
      def __init__(self):
          self.children = {}
          self.weight = 1

  # 构建深度 2000 的链
  root = Node()
  cur = root
  for i in range(2000):
      cur.children[i] = Node()
      cur = cur.children[i]

  # 递归版本（会爆栈）
  def calc_weight_recursive(node):
      for child in node.children.values():
          calc_weight_recursive(child)
          node.weight += child.weight

  # 迭代版本（安全）
  def calc_weight_iterative(root):
      stack = [(root, False)]
      while stack:
          node, visited = stack.pop()
          if visited:
              for child in node.children.values():
                  node.weight += child.weight
          else:
              stack.append((node, True))
              for child in reversed(list(node.children.values())):
                  stack.append((child, False))

  try:
      calc_weight_recursive(root)
      print("递归成功")
  except RecursionError:
      print("递归爆栈了！")

  calc_weight_iterative(root)
  print("迭代成功，weight =", root.weight)
  ```
- **预期结果**：递归版本抛出 `RecursionError`，迭代版本正常执行。你会理解为什么 commit 2 要做这个转换。

### 知识点 4：分布式一致性（Rank Consistency）
- **是什么**：在多卡/多机分布式系统中，所有进程（rank）必须在同一迭代中做相同的决策（如中止哪些请求），否则会导致集合通信（collective）挂起。
- **为什么重要**：commit 20 修复了请求超时中止时各 rank 决策不一致导致 TP（Tensor Parallel）死锁的问题。这是分布式系统中最隐蔽、最难排查的 bug 类型。
- **动手试试**（模拟不一致导致的死锁）：
  ```python
  import torch
  import torch.distributed as dist
  import os

  # 启动两个进程模拟分布式
  # 终端1: python test_dist.py 0
  # 终端2: python test_dist.py 1

  def main(rank):
      dist.init_process_group('nccl', rank=rank, world_size=2)
      tensor = torch.tensor([rank]).cuda()

      # 模拟不一致决策：rank 0 不参与集合通信
      if rank == 0:
          print("Rank 0 决定跳过 all_reduce")
          # 什么都不做
      else:
          print("Rank 1 等待 all_reduce...")
          dist.all_reduce(tensor)  # 永远等不到 rank 0！

      print(f"Rank {rank} 完成")

  if __name__ == "__main__":
      main(int(os.environ['RANK']))
  ```
- **预期结果**：rank 1 会永远卡在 `all_reduce` 上（需要 Ctrl+C 终止）。这就是 commit 20 要解决的问题——所有 rank 必须同步做中止决策。

### 知识点 5：FP32 精度保护（数值稳定性）
- **是什么**：在混合精度训练/推理中，某些关键参数（如 MoE 的 bias）必须保持 FP32 精度，否则精度损失会导致结果错误。
- **为什么重要**：commit 18 修复了 GLM-5.2 的 MoE bias 被降为 BF16 后导致 top-k 选择错误的问题。在 AI 系统中，"差不多"的精度往往会导致"差很多"的结果。
- **动手试试**：
  ```python
  import torch

  # 模拟 BF16 精度损失如何改变 top-k 结果
  torch.manual_seed(42)
  gating_scores = torch.randn(1000, dtype=torch.float32)

  # 加一个很小的 bias（模拟 correction bias）
  bias = torch.tensor(0.001, dtype=torch.float32)
  scores_fp32 = gating_scores + bias

  # BF16 下 bias 可能被舍入掉
  scores_bf16 = (gating_scores + bias).to(torch.bfloat16).to(torch.float32)

  # 比较 top-8 结果
  topk_fp32 = torch.topk(scores_fp32, 8).indices
  topk_bf16 = torch.topk(scores_bf16, 8).indices

  diff = set(topk_fp32.tolist()) ^ set(topk_bf16.tolist())
  print(f"FP32 top-8: {topk_fp32.tolist()}")
  print(f"BF16 top-8: {topk_bf16.tolist()}")
  print(f"不一致的元素: {len(diff)} 个")

  # 再看 bias 大一点的情况
  bias = torch.tensor(0.5, dtype=torch.float32)
  scores_fp32 = gating_scores + bias
  scores_bf16 = (gating_scores + bias).to(torch.bfloat16).to(torch.float32)
  topk_fp32 = torch.topk(scores_fp32, 8).indices
  topk_bf16 = torch.topk(scores_bf16, 8).indices
  diff = set(topk_fp32.tolist()) ^ set(topk_bf16.tolist())
  print(f"\nBias=0.5 时不一致元素: {len(diff)} 个")
  ```
- **预期结果**：bias 很小时（0.001），BF16 下 top-k 结果与 FP32 不同（bias 被舍入掉）；bias 较大时（0.5），两者一致。这解释了 commit 18 为什么要"gated on the bias dtype"。

- **对你有什么影响**：Radix Cache 的 eviction 排序在极深前缀树场景下不再会崩溃，长上下文/长 prompt 场景更稳定。
