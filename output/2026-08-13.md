### 知识点 2：KV Cache 的释放策略（LIFO vs FIFO）
- **是什么**：当 KV 块不再被引用时，需要将其放回空闲队列以便复用。Commit 3 明确了两种策略：无哈希的块（未启用缓存）采用 LIFO（后进先出）以提升 GPU 缓存局部性；有哈希的块（启用前缀缓存）采用 FIFO（先进先出）以实现 LRU（最近最少使用）淘汰。
- **为什么重要**：这是核心调度逻辑的一部分，直接影响缓存命中率和 GPU 内存利用率。理解它有助于你配置 `--enable-prefix-caching` 参数。
- **动手试试**：
  ```python
  # 模拟一个简单的 LIFO/FIFO 队列，观察行为差异
  from collections import deque

  # LIFO: 后进的先出
  lifo_stack = []
  lifo_stack.append('block_A')
  lifo_stack.append('block_B')
  print(f"LIFO 弹出: {lifo_stack.pop()}")  # 输出 block_B

  # FIFO: 先进的先出
  fifo_queue = deque()
  fifo_queue.append('block_A')
  fifo_queue.append('block_B')
  print(f"FIFO 弹出: {fifo_queue.popleft()}")  # 输出 block_A
  ```
- **预期结果**：你会看到 LIFO 弹出最后加入的 `block_B`，而 FIFO 弹出最先加入的 `block_A`。这直观地展示了两种策略的区别。

### 知识点 5：Triton 内核的性能优化（掩码分支）
- **是什么**：在 GPU 内核中，条件分支（如 `if j == num_blocks - 1`）会影响性能。Commit 11 优化了 Triton 内核，只在最后一个块上应用昂贵的逐 token 掩码，而之前的块使用更快的统一掩码。
- **为什么重要**：这是 GPU 编程中常见的优化技巧——将昂贵操作限制在必要的范围内，可以显著提升性能。
- **动手试试**：
  ```python
  # 用 Python 模拟这种"分支优化"思想
  import time

  def slow_method(n):
      result = 0
      for i in range(n):
          # 每次都进行昂贵的检查
          if i == n - 1:
              result += 1
          result += 1
      return result

  def fast_method(n):
      result = 0
      for i in range(n - 1):
          # 快速路径，无检查
          result += 1
      # 只对最后一项进行特殊处理
      result += 2
      return result

  n = 10000000
  start = time.time()
  slow_method(n)
  print(f"慢方法耗时: {time.time() - start:.4f}秒")

  start = time.time()
  fast_method(n)
  print(f"快方法耗时: {time.time() - start:.4f}秒")
  ```
- **预期结果**：你会看到 `fast_method` 明显快于 `slow_method`，因为减少了循环内的分支判断。这模拟了 commit 中的优化思想。

## 🧪 重要知识点 & 动手实验

### 知识点 1：张量拷贝的"快照"陷阱（Commit 1）
- **是什么**：在 Python 中，`a = b` 只是让 `a` 指向 `b` 的同一个对象，修改 `a` 会影响 `b`。对 PyTorch 张量来说，`kv_indices` 是 `req_to_token` 的一个"视图"（view），它和原始数据共享内存。
- **为什么重要**：在异步或分阶段执行的推理引擎中，如果后续代码修改了 `req_to_token` 的内容，之前保存的 `req.prefix_indices` 也会跟着变，导致使用了错误的索引。这就是一个典型的"浅拷贝"导致的 bug。
- **动手试试**：
```python
import torch

# 模拟 req_to_token 池
req_to_token = torch.arange(20).reshape(4, 5)
kv_indices = req_to_token[1, :3]  # 这是一个视图 (view)

print("原始 kv_indices:", kv_indices)

# 模拟后续对池子的修改
req_to_token[1, 0] = 999

# 关键观察：kv_indices 也被修改了！
print("修改后的 kv_indices:", kv_indices)

# 解决方法：使用 .copy() 创建独立副本
kv_indices_snapshot = req_to_token[1, :3].to(dtype=torch.int64, copy=True)
req_to_token[1, 1] = 888
print("快照 kv_indices_snapshot:", kv_indices_snapshot)
```
- **预期结果**：你会看到 `kv_indices` 的值随原始数据变化，而 `kv_indices_snapshot` 保持不变。理解了这个区别，你就明白了 commit 1 为什么要加 `.to(dtype=torch.int64, copy=True)`。

### 知识点 2：FP8 量化与 GEMM 后端选择（Commit 8）
- **是什么**：FP8 是一种用 8 位浮点数（相比 BF16 的 16 位）来存储模型权重和激活值的技术，能大幅减少显存占用和计算量。GEMM（通用矩阵乘法）是神经网络中最核心的运算，针对不同硬件选择不同的 GEMM 实现（后端）能获得最佳性能。
- **为什么重要**：不同的后端（如 `flashinfer_cutedsl`、`flashinfer_cutlass`）有不同的硬件要求（SM100/SM103 vs SM120）和性能特性。选错了后端，轻则性能下降，重则直接报错无法运行。
- **动手试试**：
```bash
# 在 sglang 启动命令中指定 FP8 GEMM 后端
python -m sglang.launch_server \
  --model-path your-fp8-model \
  --fp8-gemm-backend flashinfer_cutedsl  # 尝试不同的后端

# 查看当前 GPU 算力（SM 版本）
nvidia-smi --query-gpu=name,compute_cap --format=csv
```
- **预期结果**：你会看到不同后端在启动时可能有不同的日志输出，或者在某些 GPU 上直接报"不支持"的错误。了解自己 GPU 的算力版本（如 9.0 对应 SM90）是选择正确后端的第一步。

### 知识点 3：NUMA 感知的进程绑定（Commit 9）
- **是什么**：在多路 CPU 服务器上，内存访问距离不同 CPU 核心的延迟不同（NUMA 架构）。把 GPU 的 worker 进程绑定到 GPU 所在的 NUMA 节点，可以减少跨节点内存访问，提升性能。
- **为什么重要**：默认开启自动 NUMA 绑定（`SGLANG_AUTO_NUMA_BIND=true`），但如果你的系统不支持或配置有问题，可能会导致启动失败。了解如何关闭它（`SGLANG_AUTO_NUMA_BIND=false`）是排查问题的关键。
- **动手试试**：
```bash
# 查看你的系统 NUMA 拓扑
lscpu | grep -i numa

# 查看 GPU 所在的 NUMA 节点（Linux）
nvidia-smi topo -m

# 运行 sglang 时禁用自动 NUMA 绑定
SGLANG_AUTO_NUMA_BIND=false python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct
```
- **预期结果**：你会在 `lscpu` 输出中看到 NUMA 节点信息。如果系统有多个 NUMA 节点，启用绑定后性能可能略有提升；如果遇到启动问题，禁用绑定可能解决。

### 知识点 4：CUDA Graph 与 CPU-GPU 同步（Commit 16）
- **是什么**：CUDA Graph 是一种将一系列 GPU 内核启动捕获并重放的机制，能显著降低启动开销。但某些操作（如把数据从 GPU 拷贝到 CPU）是阻塞式的，会打断 Graph 的执行流程，影响性能。
- **为什么重要**：这个 commit 通过使用"固定内存"（pinned memory）和预分配缓冲区，避免了在关键路径上做阻塞式 D2H（设备到主机）拷贝，从而让 CUDA Graph 重放更流畅。
- **动手试试**：
```python
import torch
import torch.cuda as cuda

# 创建普通 CPU 张量
cpu_tensor = torch.zeros(10)
# 创建固定内存（pinned memory）张量
pinned_tensor = torch.zeros(10, pin_memory=True)

# 比较两者在 D2H 拷贝时的行为
gpu_tensor = torch.randn(10, device='cuda')

# 普通拷贝（可能阻塞）
cpu_tensor.copy_(gpu_tensor, non_blocking=False)

# 固定内存 + 非阻塞拷贝（不阻塞 CPU）
pinned_tensor.copy_(gpu_tensor, non_blocking=True)
cuda.synchronize()  # 需要手动同步
```
- **预期结果**：使用固定内存和非阻塞拷贝，CPU 不会被 GPU 操作阻塞，可以继续执行其他任务。在 CUDA Graph 中，这是避免同步等待的关键技巧。

### 知识点 5：多模态模型的显存预算（Commit 18）
- **是什么**：多模态模型（如能处理图片+文本的模型）除了 KV Cache 外，还需要额外的显存来缓存图片特征（embedding）。这个 commit 在计算 KV Cache 大小时，预先"预留"了这部分显存，防止后续分配时内存不足。
- **为什么重要**：如果你不预留，KV Cache 可能会占用过多显存，导致后续多模态特征缓存分配失败，程序崩溃。这解释了为什么同样显存下，多模态模型能服务的并发请求数更少。
- **动手试试**：
```bash
# 设置多模态缓存大小（单位 MB）
SGLANG_VLM_CACHE_SIZE_MB=1024 python -m sglang.launch_server \
  --model-path Qwen/Qwen2-VL-7B-Instruct

# 查看环境变量默认值
python -c "from sglang.srt.environ import envs; print(envs.SGLANG_VLM_CACHE_SIZE_MB.get())"
```
- **预期结果**：你会看到日志中打印了为多模态预留的显存量。调整这个值可以影响 KV Cache 的大小，进而影响最大并发数。
