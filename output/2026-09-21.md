## 🧪 重要知识点 & 动手实验

### 知识点 1：JSON Schema 的 `type` 可以是数组（结构化输出边界）

- **是什么**：JSON Schema 里 `"type": ["string", "null"]` 表示"字符串或 null"，这叫 union type。vLLM 的 xgrammar 后端要判断这种 schema 是否包含不支持的特性。
- **为什么重要**：如果不支持的特性（如 `multipleOf`、`uniqueItems`）被漏检，grammar 编译会静默失败或产出错误约束，模型输出就会不合规。真实场景里 Agent 拿到的 JSON 解析失败，整个 pipeline 就崩了。
- **动手试试**：
```python
from vllm.v1.structured_output.backend_xgrammar import (
    has_xgrammar_unsupported_json_features,
)

# 应该返回 True（含不支持的 multipleOf）
schema1 = {"type": ["number"], "multipleOf": 3}
print(has_xgrammar_unsupported_json_features(schema1))

# 应该返回 False（纯 union type，无特殊关键字）
schema2 = {"type": ["string", "null"]}
print(has_xgrammar_unsupported_json_features(schema2))
```
- **预期结果**：第一个输出 `True`，第二个输出 `False`。如果你看到第一个是 `False`，说明你用的是修复前的版本——这正是 #48416 修的 bug。

### 知识点 2：Whisper 的 30 秒窗口与 `truncation=True`

- **是什么**：Whisper 编码器只有固定 3000 帧（约 30 秒）的位置编码。超过 30 秒的音频必须被截断或切窗，否则张量形状对不上直接崩溃。
- **为什么重要**：语音转写场景里，用户上传的音频经常超过 30 秒。不处理就会 engine crash，用户看到的是 500 错误。
- **动手试试**：
```python
import numpy as np
from transformers import WhisperFeatureExtractor

fe = WhisperFeatureExtractor.from_pretrained("openai/whisper-large-v3-turbo")
audio = np.random.randn(fe.sampling_rate * 35).astype(np.float32)  # 35 秒

# 不加 truncation：形状会超过 3000 帧
out1 = fe(audio, sampling_rate=fe.sampling_rate, return_tensors="pt")
print("不截断:", out1["input_features"].shape)

# 加 truncation：被裁到 3000 帧
out2 = fe(audio, sampling_rate=fe.sampling_rate, return_tensors="pt", truncation=True)
print("截断后:", out2["input_features"].shape)
```
- **预期结果**：不截断时最后一维 > 3000，截断后正好等于 `fe.nb_max_frames`（3000）。这就是 #57769 加 `truncation=True` 的原因。

### 知识点 3：PAD_SLOT_ID——dummy 请求不能污染 KV Cache

- **是什么**：在 vLLM 的 block table 里，每个请求有一个 slot mapping，把 token 位置映射到 KV 缓存的具体槽位。dummy 请求（用于 CUDA graph padding）的 `idx_mapping = -1`，它的 slot 必须全部是 `PAD_SLOT_ID`（一个哨兵值，表示"不写"）。
- **为什么重要**：如果 dummy 请求复用了真实请求的 block-table 行，就会把垃圾数据写进别人的 KV 缓存，导致后续推理结果错乱——而且这种 bug 只在特定并发下出现，极难复现。
- **动手试试**：
```python
import torch
from vllm.v1.worker.gpu.block_table import BlockTables
from vllm.v1.attention.backends.utils import PAD_SLOT_ID

bt = BlockTables(
    block_sizes=[4], max_num_reqs=2, max_num_batched_tokens=16,
    max_num_blocks_per_group=[4], device=torch.device("cuda"),
    kernel_block_sizes=[4],
)
bt.append_block_ids(req_index=0, new_block_ids=([7, 8],), overwrite=True)
bt.apply_staged_writes()

qsl = torch.tensor([0, 3], dtype=torch.int32, device="cuda")
pos = torch.tensor([1, 2, 3], dtype=torch.int64, device="cuda")

real = bt.compute_slot_mappings(torch.tensor([0], device="cuda"), qsl, pos, 3)
dummy = bt.compute_slot_mappings(torch.tensor([-1], device="cuda"), qsl, pos, 3)
print("真实请求 slot:", real[0].tolist())
print("dummy 请求 slot:", dummy[0].tolist())
```
- **预期结果**：真实请求是 `[29, 30, 31]`（7*4+1 起），dummy 全是 `PAD_SLOT_ID`。如果 dummy 也返回了 29/30/31，说明你踩到了 #56734 修的 bug。

### 知识点 4：`torch.no_grad()` 与显存泄漏

- **是什么**：`torch.no_grad()` 告诉 PyTorch"这段计算不需要梯度"，从而不保存中间激活值。测试代码里如果忘了加，embedding 权重会被 autograd 图引用而无法释放。
- **为什么重要**：在 GPU 测试里，一个忘了 `no_grad` 的 embedding lookup 可能让几 GB 的权重常驻显存，导致后续测试 OOM。这是新手最容易犯的显存错误之一。
- **动手试试**：
```python
import torch

emb = torch.nn.Embedding(1000, 512).cuda()
ids = torch.randint(0, 1000, (8, 128)).cuda()

# 错误：会保留计算图
out1 = emb(ids)
print("有梯度时 out.requires_grad:", out1.requires_grad)

# 正确：不保留计算图
with torch.no_grad():
    out2 = emb(ids)
print("no_grad 时 out.requires_grad:", out2.requires_grad)
```
- **预期结果**：第一个 `True`，第二个 `False`。`False` 意味着中间张量可以被立即回收，这正是 #57868 想达到的效果。

### 知识点 5：XPU 上的 reduce_scatter 不均匀分片问题

- **是什么**：`reduce_scatter` 是分布式训练/推理里"归约后散播"的集合通信。当各 rank 数据量不同（不均匀）时，需要特殊处理。但如果进程看不到所有设备（如 external-LBDP 场景），标准的不均匀路径会失败。
- **为什么重要**：多卡推理时，如果每个 rank 处理的 token 数不一样（比如最后一个 batch 不满），就需要不均匀 reduce_scatter。XPU 上这个路径有 bug，会导致精度错误。
- **动手试试**（概念演示，无需多卡）：
```python
sizes = [3, 5, 2]  # 各 rank 数据量不同
if sizes.count(sizes[0]) == len(sizes):
    print("均匀，用 reduce_scatter_tensor")
else:
    print("不均匀，需要特殊处理")
    max_size = max(sizes)
    print(f"padding 后每个 rank 都是 {max_size}，最后再裁剪")
```
- **预期结果**：输出"不均匀，需要特殊处理"，并展示 padding 到 max_size 再裁剪的策略。这正是 #57779 在 XPU 上实现的 fallback。

## 🧪 重要知识点 & 动手实验

- **知识点 1：模型适配的"配置覆盖"机制（Model Overrides）**
  - **是什么**：当某个模型有特殊行为（比如要禁用某个优化、要开启多层级投机解码），不需要改核心代码，只需在 `arg_groups/model_overrides/` 下注册一个函数。
  - **为什么重要**：这是 SGLang 保持"核心代码干净 + 模型特异逻辑隔离"的关键设计。不懂这个，你可能把模型特判写进通用代码里，被 reviewer 打回。
  - **动手试试**：
    ```bash
    # 看看现有 overrides 长什么样
    ls python/sglang/srt/arg_groups/model_overrides/
    # 读一个最简单的例子
    cat python/sglang/srt/arg_groups/model_overrides/gigachat35.py
    ```
    输出应类似：
    ```python
    @_register_for("GigaChat35ForCausalLM", "GigaChat35ForCausalLMNextN")
    def _gigachat35_overrides(server_args, hf_config) -> dict:
        cfg = resolving_view(server_args)
        overrides = {"disable_shared_experts_fusion": True}
        if cfg.speculative_algorithm == "EAGLE":
            overrides["enable_multi_layer_eagle"] = True
        return overrides
    ```
  - **预期结果**：你会看到装饰器 `@_register_for` 把架构名映射到一个返回 dict 的函数，dict 里的 key 就是会被覆盖的 `ServerArgs` 字段。这就是"声明式覆盖"。

- **知识点 2：YaRN 长上下文扩展与 cos/sin cache**
  - **是什么**：YaRN 是一种让模型支持超长上下文的位置编码外推技术；`cos_sin_cache` 是预计算好的旋转位置编码表，长度不够时要"扩展"。
  - **为什么重要**：扩展 cache 时如果丢了 YaRN 的 scaling 参数，长文本推理结果会悄悄错乱（不报错，但输出质量崩坏）。这是典型的"静默 bug"。
  - **动手试试**：
    ```bash
    # 看修复的核心函数
    grep -n "_extend_yarn_cache" python/sglang/srt/layers/rotary_embedding/yarn.py
    # 看它如何被调用
    grep -rn "_ensure_cos_sin_cache_length" python/sglang/srt/layers/rotary_embedding/
    ```
    你会看到 `_extend_yarn_cache` 接收 `compute_inv_freq`（一个 lambda）和 `mscale`，确保新扩展的部分用的是同样的 YaRN 参数。
  - **预期结果**：理解"扩展 cache 必须重放原始 scaling 逻辑"这一原则。可以自己写个小脚本对比扩展前后的 `inv_freq` 是否一致。

- **知识点 3：Meta 设备与 offload 的"暂存"语义**
  - **是什么**：`meta` device 是 PyTorch 里"只有形状没有数据"的占位张量；offload 场景下参数先放 meta，等真正加载时才填数据。
  - **为什么重要**：Commit 8 修了一个回归——post-load 阶段遇到 meta 张量直接抛错，导致 offload meta/sharded_gpu 模式全挂。理解"什么时候 meta 是合法的"很关键。
  - **动手试试**：
    ```python
    import torch
    from torch import nn
    from sglang.srt.model_loader.post_load import stage_module_for_post_load

    m = nn.Module()
    m.meta_weight = nn.Parameter(torch.empty(1, device="meta"))
    m.register_buffer("scale", torch.ones(1))

    with stage_module_for_post_load(m, torch.device("cpu")):
        print("meta still meta:", m.meta_weight.is_meta)
        m.scale.add_(1)
    print("scale:", m.scale)
    ```
  - **预期结果**：输出 `meta still meta: True` 和 `scale: tensor([2.])`。说明 meta 张量被"放行"了，其他张量正常搬运。如果换成旧代码，这里会直接 RuntimeError。

- **知识点 4：投机解码下的 MoE 后端调度陷阱**
  - **是什么**：MoE（混合专家）层的量化 kernel 有多个后端；投机解码（speculative decoding）会在权重加载后切换全局后端，导致 `apply()` 里读到的后端和权重准备时的后端不一致。
  - **为什么重要**：Commit 19 就是修这个——必须用 `self._moe_runner_backend`（缓存的）而不是 `get_moe_runner_backend()`（全局的）。用错会走错 kernel，结果错误或崩溃。
  - **动手试试**：
    ```bash
    # 看修复前后的对比
    grep -n "moe_runner_backend" python/sglang/srt/layers/quantization/modelopt_quant.py | head -20
    # 跑新增的单元测试
    python -m pytest test/registered/unit/layers/quantization/test_modelopt_nvfp4_moe_dispatch.py -v
    ```
  - **预期结果**：测试全绿，你会看到测试用 `mock` 模拟了"缓存的 backend 是 TRTLLM，全局 backend 是别的"这种场景，验证 `apply()` 走的是 TRTLLM 路径。

- **知识点 5：启动日志的"进程重复"问题**
  - **是什么**：SGLang 启动时 `ModelConfig` 会被构造 3-4 次（主进程、scheduler 子进程、tokenizer 子进程等），如果每次都打 INFO 日志，用户会看到 4 遍同样的信息。
  - **为什么重要**：这是分布式系统日志设计的通用问题——"哪些日志该在哪个进程打"。Commit 6 系统性地清理了这类噪音。
  - **动手试试**：

  - **预期结果**：你会看到哪些行出现了多次。对照 `.claude/skills/clean-startup-log/SKILL.md` 里的分类表（SGLang 代码 API 用错 / log level 用错 / 跨进程重复 / 第三方库噪音），就能定位问题。

### 2. disaggregation: Fix FakeKVSender queue accumulation (#28652)

- **代码层面**：修改 `python/sglang/srt/disaggregation/fake/conn.py` 里的 `FakeKVSender`。原来 `has_sent` 永远为 False 时，`poll()` 会一直返回 `WaitingForInput`，导致 prefill 的 inflight 队列被永久占住。新增 `_check_waiting_timeout()`：从第一次 poll 开始计时（monotonic 时钟），超过 `SGLANG_DISAGGREGATION_WAITING_TIMEOUT` 就标记 `KVPoll.Failed`，让请求正常释放。
- **新手概念课堂**：disaggregation（分离式推理）把 prefill 和 decode 拆到不同机器。FakeKVSender 是测试用的假发送器（不真传数据，只模拟握手）。如果假发送器永远不"完成"，就像餐厅里一个客人永远占着桌子不点菜，后面的客人进不来。
- **对你有什么影响**：如果你在做 disaggregation 的单元测试或压力测试，不会再因为 FakeKVSender 卡死而 OOM；可以通过 `SGLANG_DISAGGREGATION_WAITING_TIMEOUT=600` 调整超时。

### 3. [Fix] Preserve YaRN scaling when extending rotary caches (#38786)

- **代码层面**：在 `mrope.py` 和 `rope_variant.py` 里新增 `_ensure_cos_sin_cache_length()`，调用 `yarn.py` 里新抽出的 `_extend_yarn_cache()`。这个函数接收 `compute_inv_freq` lambda 和 `mscale`，保证扩展 cos/sin cache 时用的是和原始计算相同的 YaRN 参数。NPU 路径还额外同步了 `cos_cached_total`/`sin_cached_total`。
- **新手概念课堂**：位置编码就像给每个 token 发一个"座位号"。YaRN 是一种"超长剧场"的座位编号方案——座位号超过原设计时要按同样规则继续编号。如果不小心用了普通编号规则，演员（模型）就会坐错位置，台词全乱。
- **对你有什么影响**：使用 YaRN 长上下文模型（如 Qwen 长文本版、DeepSeek 长文本版）时，动态扩展 cache 后输出质量不再悄悄下降。

### 4. [XPU] Enable HiSparse hierarchical sparse KV cache on Intel XPU (#32792)

- **代码层面**：`hisparse_coordinator.py` 里根据 `is_xpu()` 分支导入 kernel：XPU 走 `sgl_kernel` 的 AOT 实现，其他平台走 `sglang.kernels.ops.kvcache.hisparse`。XPU 上 `copy_cache_planned_mla` 直接抛错（无 AOT 实现），并禁用 shared-index prefetch，降级为同步 swap-in。同时禁止在 XPU 上用 `SGLANG_DEBUG_HISPARSE_SKIP_IO`（因为 AOT 算子不支持 skip_io）。
- **新手概念课堂**：HiSparse 是一种"只把常用的 KV cache 放在显存里，其余放主机内存"的分层策略。shared-index prefetch 是"提前把可能要用的数据搬上来"的优化。Intel XPU 上没有这个优化算子，所以只能老老实实同步搬运——慢一点但能用。
- **对你有什么影响**：在 Intel GPU 上跑 DeepSeek 系列（用了 MLA + HiSparse）现在能跑起来了，但会有 warning 提示 prefetch 被禁用。如果追求性能，还是建议 NVIDIA。
