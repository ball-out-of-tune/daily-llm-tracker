### 知识点 1：NCCL 通信器挂起/恢复（Commit 1）
- **是什么**：让 GPU 之间的通信器在空闲时“挂起”释放显存，需要时“恢复”重新初始化，且操作要幂等（重复调用不出错）。
- **为什么重要**：在多租户或动态调度场景，GPU 显存是稀缺资源。如果通信器一直占着显存，其他任务可能无法启动。

### 知识点 2：4-bit 量化（W4A16）与不同后端（Commit 6, 8, 13）
- **是什么**：把模型权重用 4-bit 存储，计算时用 16-bit 激活值。不同后端（NVIDIA 的 DSA、AMD 的 AITER、FlashInfer）用不同方式实现这个目标。
- **为什么重要**：4-bit 量化能把模型显存占用减少约 4 倍，是部署大模型的“杀手锏”。不同后端意味着不同硬件上的最佳选择不同。
- **动手试试**：
  ```python

  from vllm import LLM

  llm_fp16 = LLM(model="meta-llama/Llama-3.2-1B", dtype="float16")
  print(f"FP16 显存占用: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
  del llm_fp16
  
  # 4-bit 量化模型
  llm_4bit = LLM(model="meta-llama/Llama-3.2-1B", quantization="modelopt_fp4")
  print(f"4-bit 显存占用: {torch.cuda.memory_allocated() / 1e9:.2f} GB")
  ```
- **预期结果**：4-bit 模型的显存占用约为 FP16 的 1/4。你直观感受到了量化的威力。

### 知识点 3：CUDA Graph 捕获时的 GC 冻结（Commit 14）
- **是什么**：在录制 CUDA Graph 期间禁用 Python 垃圾回收，防止对象被意外销毁导致 Graph 失效。
- **为什么重要**：GC 可能在捕获过程中释放 Triton kernel 模块，导致录制好的 Graph 崩溃。这是生产环境中的隐蔽 bug。
- **动手试试**：
  ```python
  # 演示 GC 对 CUDA Graph 的影响（概念验证）
  import gc
  import torch
  
  # 模拟：捕获前冻结 GC
  gc.freeze()
  gc.disable()
  
  # 进行 CUDA Graph 捕获（简化版）
  g = torch.cuda.CUDAGraph()
  x = torch.randn(1000, 1000, device="cuda")
  with torch.cuda.graph(g):
      y = x * 2
  
  # 恢复 GC
  gc.unfreeze()
  gc.enable()
  
  # 回放 Graph
  g.replay()
  print(f"Graph 回放结果: {y.sum().item()}")  # 应该正常输出
  ```
- **预期结果**：Graph 能正常回放。如果去掉 `gc.freeze()`，在某些极端情况下可能崩溃。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 生命周期与弱引用（Weak Reference）
- **是什么**：`Commit 3` 中，`offloaded_state` 和 `offload_inflight` 字典从普通 `dict` 改为 `WeakKeyDictionary`。这意味着当请求（`Req`）对象被销毁时，字典中的对应条目会被自动清除，防止内存泄漏。
- **为什么重要**：在高并发服务器中，请求 ID 可能被复用（前一个请求刚结束，新请求就用了同一个 ID）。如果用一个普通字典以请求 ID 为 key，那么一个迟到的异步回调可能会错误地修改新请求的状态。使用 `Req` 对象本身作为 key（并配合弱引用）可以避免这个问题，因为旧请求对象被回收后，其状态条目也会消失。
- **动手试试**：
```python
import weakref

class Req:
    pass

# 普通字典
normal_dict = {}
# 弱引用字典
weak_dict = weakref.WeakKeyDictionary()

req = Req()
normal_dict[req] = "state"
weak_dict[req] = "state"

del req  # 删除唯一强引用

import gc
gc.collect()

print(f"普通字典大小: {len(normal_dict)}")  # 输出: 1 (键仍然存在，但对象已死)
print(f"弱引用字典大小: {len(weak_dict)}")  # 输出: 0 (条目被自动清除)
```
- **预期结果**：你会看到普通字典仍然保留着已删除对象的键（内存泄漏），而弱引用字典会自动清理。这说明 `WeakKeyDictionary` 是管理"对象生命周期绑定状态"的正确工具。

### 知识点 2：MoE 量化路径选择（W4A16 vs W4A8）
- **是什么**：`Commit 10` 和 `Commit 19` 为 MoE 层引入了多种量化路径：W4A16（4-bit 权重，16-bit 激活）和 W4A8（4-bit 权重，8-bit 激活）。通过 `--flashinfer-mxfp4-moe-precision fp8` 或环境变量 `SGLANG_FLASHINFER_CUTEDSL_NVFP4_W4A16` 来选择。
- **为什么重要**：不同的硬件（如 Hopper vs Blackwell）和不同的算子库（如 FlashInfer vs Marlin）对量化格式的支持不同。选错路径可能导致性能下降甚至无法运行。例如，`Commit 10` 提到 W4A8 路径需要 FlashInfer >= 0.6.18，且仅在 SM90 上可用。
- **动手试试**：
```bash
# 查看当前 FlashInfer 版本
python -c "import flashinfer; print(flashinfer.__version__)"

# 尝试启动一个 DeepSeek-V4 模型，使用 W4A16 路径
python -m sglang.launch_server \
  --model-path deepseek-ai/DeepSeek-V4-Flash-FP4 \
  --moe-runner-backend flashinfer_mxfp4 \
  --flashinfer-mxfp4-moe-precision default

# 如果 FlashInfer >= 0.6.18，尝试 W4A8 路径
python -m sglang.launch_server \
  --model-path deepseek-ai/DeepSeek-V4-Flash-FP4 \
  --moe-runner-backend flashinfer_mxfp4 \
  --flashinfer-mxfp4-moe-precision fp8
```
- **预期结果**：你会看到服务器成功启动并输出不同的 MoE runner 配置信息。如果 FlashInfer 版本过低，第二个命令会报错提示需要升级。这让你理解"量化路径"是硬件、库和模型三者的交集。

### 知识点 3：序列并行（Sequence Parallelism）
- **是什么**：`Commit 15` 引入了 `--enable-layernorm-sp`，它实现了 Megatron 风格的 LayerNorm 序列并行。核心思想是：当一个序列太长时，把它切分到多个 GPU 上，每个 GPU 只处理序列的一部分。
- **为什么重要**：序列并行是处理超长上下文（如 100K+ tokens）的关键技术。它允许你使用多个 GPU 来"分担"一个序列的计算，而不是简单地把不同序列放到不同 GPU 上。该 commit 还展示了严格的参数校验：`tp_size > 1`、不支持 DP attention、不支持投机解码。
- **动手试试**：
```bash
# 尝试在单 GPU 上启用（应该报错）
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --tp-size 1 \
  --enable-layernorm-sp

# 尝试在 2 个 GPU 上启用
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --tp-size 2 \
  --enable-layernorm-sp
```
- **预期结果**：第一个命令会失败并报错 `--enable-layernorm-sp requires tp_size > 1`。第二个命令应该成功启动。这让你理解：并非所有优化都适用于所有配置，框架会主动校验并给出清晰错误。

### 知识点 4：CUDA Graph 与可中断图（Breakable CUDA Graph）
- **是什么**：`Commit 14` 为 Qwen-Image 扩散模型引入了"可中断 CUDA 图"（BCG）。CUDA Graph 将一系列 GPU 内核预捕获并重放，以减少启动开销。但扩散模型包含动态操作（如条件分支），所以 BCG 允许在特定点中断图，执行非图操作后再继续。
- **为什么重要**：对于固定分辨率（如 1024x1024）的扩散模型推理，BCG 可以显著降低延迟。但代价是：需要为每个分辨率单独捕获图，且图捕获会额外占用约 5GB 显存。未捕获的分辨率会回退到即时执行（eager），性能会下降。
- **动手试试**：
```bash
# 启动 Qwen-Image，启用 BCG 并预热 1024x1024 分辨率
python -m sglang.launch_server \
  --model-path Qwen/Qwen-Image-2512 \
  --model-type diffusion \
  --tp-size 2 \
  --enable-breakable-cuda-graph \
  --warmup-resolutions 1024x1024

# 用 1024x1024 分辨率请求
# 观察日志中是否显示 "captured" 或 "eager"
```
- **预期结果**：你会看到服务器启动时进行图捕获，并输出相关日志。请求 1024x1024 图像时，延迟会明显低于未启用 BCG 的情况。如果请求其他分辨率（如 512x512），日志会显示该分辨率未捕获，回退到 eager 模式。

### 知识点 5：MoE 权重加载与排列（Weight Permutation）
- **是什么**：`Commit 13` 修复了 MiniMax-H3 DiT 模型中 QKV 投影权重在块级 FP8 量化下的加载问题。核心是：当权重被量化为块时（如 `weight_block_size=[128, 128]`），权重的排列（permutation）也需要按块进行，而不是按行。
- **为什么重要**：量化不仅改变了权重的数值表示，还可能改变权重的布局。在加载权重时，如果排列逻辑没有考虑量化块的大小，会导致权重和缩放因子错位，产生错误的推理结果。
- **动手试试**：
```python
# 模拟一个量化块的场景
import torch

# 假设 head_dim=128, 块大小为 [128, 128]
# 这意味着一个块覆盖 128 行权重
head_dim = 128
block_rows = 128

# 检查 head_dim 是否能被 block_rows 整除
if head_dim % block_rows:
    raise ValueError("block-quantized qkv needs a block size that divides the head dim")

# 如果整除，排列时需要按块移动
# 例如，将 3 个 head 的 qkv 权重从 [q1, k1, v1, q2, k2, v2] 重排为 [q1, q2, k1, k2, v1, v2]
# 但每个块（128行）必须作为一个整体移动
print(f"Block size {block_rows} divides head_dim {head_dim}: OK")
```
- **预期结果**：你会看到代码成功执行。如果你把 `head_dim` 改为 100（不能被 128 整除），代码会抛出 `ValueError`。这让你理解：量化格式会限制权重重排的灵活性。
