## 🧪 重要知识点 & 动手实验

### 知识点 1：量化格式转换（MXFP4 → int4）
- **是什么**：MXFP4 是 4 位浮点，int4 是 4 位整数，两者数值表示不同，需要重新计算缩放因子。
- **为什么重要**：不同 GPU 支持的量化格式不同。不懂转换，模型在 AMD 上直接跑不起来。
- **动手试试**：
```python
import torch
# 模拟 MXFP4 的 scale 和 int4 的 scale
mxfp4_scale = 0.5
int4_scale = mxfp4_scale * 2  # 简化示例
weights = torch.tensor([1.0, 2.0, 3.0])
quantized = (weights / int4_scale).round().clamp(-8, 7).to(torch.int8)
print("int4 weights:", quantized)
dequantized = quantized.float() * int4_scale
print("dequantized:", dequantized)
```
- **预期结果**：你会看到权重被量化到 -8~7 的整数范围，再反量化回来。理解 scale 的作用。

### 知识点 2：KV 缓存块与零初始化
- **是什么**：KV 缓存被分成固定大小的块（block），新分配的块需要清零，但异步加载的块不能清零。
- **为什么重要**：清零错误的块会导致注意力计算出错，输出乱码。
- **动手试试**：
```python
# 模拟块分配
blocks = [None] * 4
hit_blocks = {0, 1}  # 已命中的块
new_blocks = {2, 3}  # 新分配的块
need_zero = new_blocks - hit_blocks
print("需要清零的块:", need_zero)
# 异步加载的块不应清零
async_loaded = {2}
need_zero = need_zero - async_loaded
print("实际需要清零的块:", need_zero)
```
- **预期结果**：你会看到只有块 3 需要清零，块 2 因为异步加载被豁免。

### 知识点 3：CUDA Graph 与静态地址
- **是什么**：CUDA Graph 把一系列 kernel 调用录制成图，重放时要求所有张量地址不变。
- **为什么重要**：如果张量地址变了，图重放会读到旧数据，导致结果错误。
- **动手试试**：
```python
import torch
# 模拟 CUDA Graph 捕获
x = torch.zeros(4, device='cuda')
graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(graph):
    y = x + 1
# 修改 x 的值，地址不变
x.copy_(torch.tensor([1., 2., 3., 4.], device='cuda'))
graph.replay()
print(y)  # 应该是 [2, 3, 4, 5]
```
- **预期结果**：你会看到图重放后 y 正确更新。如果 x 被重新赋值（地址变了），结果就会错。

### 知识点 4：MoE 专家并行与 All2All
- **是什么**：MoE 中不同专家分布在不同 GPU 上，token 需要发送到对应专家，再收集回来。
- **为什么重要**：通信是 MoE 推理的瓶颈，All2All 优化直接决定吞吐。
- **动手试试**：
```python
# 模拟 All2All 分发
tokens = ["t1", "t2", "t3", "t4"]
experts = [0, 1, 0, 1]  # 每个 token 去哪个专家
gpu0 = [t for t, e in zip(tokens, experts) if e == 0]
gpu1 = [t for t, e in zip(tokens, experts) if e == 1]
print("GPU0 收到:", gpu0)
print("GPU1 收到:", gpu1)
```
- **预期结果**：你会看到 token 被分发到不同 GPU。理解 All2All 的基本逻辑。

### 知识点 5：结构化标签约束工具调用
- **是什么**：用语法规则约束模型输出，确保工具调用格式正确。
- **为什么重要**：模型经常输出非法 JSON，结构化约束可以强制格式正确。
- **动手试试**：
```python

output = '<tool_call>get_weather<arg_key>city</arg_key><arg_value>Beijing</arg_value></tool_call>'
```

### 知识点 1：KV 缓存的分层存储（HiCache）

- **是什么**：把 KV 缓存从 GPU 显存（L1）扩展到主机内存（L2）甚至磁盘（L3），像 CPU 的 L1/L2/L3 缓存一样分层。
- **为什么重要**：长上下文场景下，KV 缓存大小随序列长度线性增长，显存很快就不够。不懂分层缓存，你就无法部署 128K 甚至 1M 上下文的模型。
- **动手试试**：
  ```bash
  # 启动一个带 HiCache 的服务
  python -m sglang.launch_server \
    --model-path Qwen/Qwen2.5-7B-Instruct \
    --enable-hierarchical-cache \
    --hicache-ratio 2.0 \
    --hicache-write-policy write_through
  ```
  然后发一个长请求，观察日志中 `HiCache` 的命中率和显存占用。
- **预期结果**：你会看到日志里出现 `HiCache hit rate` 之类的指标，且显存占用明显低于不开 HiCache 时。

### 知识点 2：CUDA Graph 的"捕获安全"约束

- **是什么**：CUDA Graph 录制时，所有输入必须是固定的张量地址，不能有动态的 `.tolist()`、`.item()` 等 CPU-GPU 同步操作。
- **为什么重要**：不懂这个约束，你会在开启 CUDA Graph 后遇到莫名其妙的崩溃或结果错误。#41729 就是通过预计算 metadata 来避免在 graph 里做 D2H 同步。
- **动手试试**：
  ```python
  import torch
  
  # 反例：在 graph 里做 D2H 同步
  @torch.compile
  def bad_fn(x):
      indices = x.tolist()  # 这会触发同步，graph 捕获会失败
      return x[indices]
  
  # 正例：预计算好索引
  def good_fn(x, indices):
      return x[indices]
  ```
  试着用 `torch.cuda.graphs.make_graphed_callables` 包装这两个函数，观察哪个会报错。
- **预期结果**：`bad_fn` 会报 `RuntimeError: CUDA error: operation not permitted when stream is capturing`，`good_fn` 正常。

### 知识点 3：量化中的"层排除"机制

- **是什么**：量化配置里可以指定某些层不量化（比如 embedding、lm_head、某些 attention 投影），保持原始精度。
- **为什么重要**：#41870 的核心就是判断"哪些层该量化、哪些不该"。如果判断错了，要么精度崩，要么性能没提升。Quark 的 `is_linear_unquantized` 就是干这个的。
- **动手试试**：
  ```python
  # 查看一个量化配置的排除列表
  from transformers import AutoConfig
  config = AutoConfig.from_pretrained("amd/GLM-5.2-MXFP4")
  print(config.quantization_config.get("exclude_layers", []))
  ```
  然后对比不同量化模型（FP8、MXFP4、AWQ）的排除列表差异。
- **预期结果**：你会看到不同量化方案排除的层不一样，比如 FP8 可能排除 `lm_head`，而 MXFP4 可能只排除 `embed_tokens`。

### 知识点 4：分布式通信的"预热"

- **是什么**：在正式通信前，先做一次小规模的数据传输，让 NCCL 建立好通信通道、分配好缓冲区。
- **为什么重要**：#42026 在 KV 缓存大小计算前预热 EPLB 的 P2P 通信，避免第一次真正通信时因为 NCCL 初始化而 OOM。不懂这个，你可能会遇到"第一次请求特别慢"或"启动时 OOM"。
- **动手试试**：
  ```python
  import torch.distributed as dist
  import torch
  
  dist.init_process_group("nccl")
  rank = dist.get_rank()
  
  # 预热：先做一次小传输
  warmup = torch.zeros(1024, device="cuda")
  dist.all_reduce(warmup)
  torch.cuda.synchronize()
  
  # 再分配大 buffer
  big = torch.zeros(1 << 30, device="cuda")  # 1GB
  print(f"Rank {rank}: allocated 1GB after warmup")
  ```
- **预期结果**：先预热再分配大 buffer 不会 OOM，反之可能会。

### 知识点 5：前缀缓存的"检查点"抽象

- **是什么**：把请求的 KV 缓存"提交"到前缀树里，让后续请求可以复用这段前缀。
- **为什么重要**：#42202 把 `insert_req` 重命名为 `checkpoint`，语义更清晰：不是"插入请求"，而是"给当前 KV 状态打个检查点"。这个抽象是流式会话、投机解码、chunked prefill 的共同基础。
- **动手试试**：
  ```python
  # 模拟前缀缓存复用
  from sglang.srt.mem_cache.radix_cache import RadixCache
  
  cache = RadixCache(...)
  # 第一个请求：写入前缀
  cache.checkpoint(req1, up_to=100)
  # 第二个请求：复用前缀
  prefix_indices = cache.match_prefix(req2.input_ids)
  print(f"Reused {len(prefix_indices)} tokens")
  ```
- **预期结果**：第二个请求能匹配到第一个请求写入的前缀，日志显示复用 token 数。
