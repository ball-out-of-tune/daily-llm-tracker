### 知识点 1：MoE 专家并行负载均衡 (EPLB)

- **是什么**：MoE 模型中，不同"专家"网络被请求的频率差异很大。EPLB 会将热门专家复制多份（副本）分布到不同 GPU 上，并动态调整路由，使各 GPU 负载均衡。
- **为什么重要**：不理解 EPLB，你可能会困惑为什么模型权重里有"冗余"的专家副本。当新增模型架构（如 GLM-5.3-Flash）时，若未适配 EPLB，这些副本的权重永远不会被加载，模型会以错误的随机权重运行，导致输出完全错误。

### 知识点 2：CUDA Graph 捕获中的设备同步问题

- **是什么**：CUDA Graph 捕获是将 GPU 操作录制为一张图以便重放。在捕获过程中，如果代码里有 GPU 到 CPU 的数据拷贝（如 `.cpu()`、`.item()`），会强制设备同步（Device Sync），导致严重的性能下降。
- **为什么重要**：在 `build_for_cudagraph_capture` 这类每次"虚拟步骤"都会调用的函数中，一次意外的设备同步可能让 CUDA Graph 捕获时间增加数倍，甚至导致捕获失败。
- **动手试试**：
  1. 在 Python 中运行以下代码观察同步行为：

  ```python
  x = torch.randn(1000, 1000, device='cuda')
  torch.cuda.synchronize()
  start = time.time()
  y = x * 2  # GPU 上的异步操作
  # z = x.cpu()  # 取消注释此行，观察时间差异
  torch.cuda.synchronize()
  print(f"Time: {time.time() - start:.6f}s")
  ```
  2. 对比有无 `.cpu()` 调用的耗时差异。
  3. 阅读 `vllm/v1/attention/backends/gdn_attn.py` 中 `build_for_cudagraph_capture` 的修改，注意如何用 `query_start_loc_cpu` 替代设备端数据来避免同步。
- **预期结果**：你会看到 `.cpu()` 调用会导致显著的耗时增加（因为需要等待 GPU 完成所有前置操作才能拷贝数据），理解了为什么在 CUDA Graph 捕获路径中要严格避免这类操作。

### 知识点 3：投机解码 (Speculative Decoding)

- **是什么**：投机解码让一个小模型（草稿模型）先快速生成一串候选 token，然后由大模型（目标模型）并行验证这些 token 的正确性。如果验证通过，就能一次接受多个 token，显著加速。
- **为什么重要**：投机解码的加速效果取决于草稿模型与目标模型的配合。当草稿模型有特殊配置（如滑动窗口注意力）或运行在流水线并行下时，很多边界情况会导致崩溃或性能回退。理解投机解码的验证机制，有助于诊断这类问题。

### 知识点 4：模型权重加载与流水线并行 (Pipeline Parallel)

- **是什么**：流水线并行将模型按层切分到多个 GPU 上，每个 GPU 只负责一部分层。权重加载时需要判断哪些层属于当前 rank，跳过不属于自己的层。
- **为什么重要**：在 PP 下，如果权重加载逻辑没有正确处理"层归属"，模型会加载错误的权重或直接崩溃。今日多个 commit（如 Commit 1 和 Commit 4）都在修复 PP 场景下的权重加载和状态传播问题。

### 知识点 5：在线量化与部分预量化 Checkpoint

- **是什么**：在线量化指在模型加载时动态将权重从高精度（如 BF16）转换为低精度（如 FP8、MXFP8）。部分预量化 checkpoint 指原始模型只有部分层（如 MoE 专家层）已经量化，而其他层（如注意力层）仍是原始精度。
- **为什么重要**：以前如果要使用量化模型，必须找到完全预量化好的 checkpoint。现在 vLLM 支持对"未量化"的层单独应用在线量化方案，大大增加了灵活性——你可以在加载一个已有部分量化模型时，为剩余层指定新的量化方法。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Radix Cache 的 LRU/LFU 等缓存淘汰策略
- **是什么**：当 KV 缓存满了，需要删除一些旧的缓存前缀来腾出空间。不同的淘汰策略（如 LRU 淘汰最久未用的，LFU 淘汰使用次数最少的）决定了删除哪个前缀。
- **为什么重要**：缓存命中率直接影响推理速度。选错策略可能导致频繁的缓存未命中，拖慢响应。SGLang 允许你通过 `--radix-eviction-policy` 和 `--radix-eviction-policy-config` 来调整。
- **动手试试**：
  ```bash
  # 启动一个服务器，使用 SLRU 策略，并设置保护段大小为 4
  python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --radix-eviction-policy slru \
    --radix-eviction-policy-config '{"protected_threshold": 4}'
  ```
- **预期结果**：服务器能正常启动。之后你可以用不同前缀的请求压测，观察缓存命中率的变化，并与默认的 `lru` 策略对比。

### 知识点 2：KV Cache 的量化（FP8）
- **是什么**：把 KV 缓存（存的是 Key 和 Value 向量）从 FP16 降到 FP8 来节省显存，但会损失一些精度。
- **为什么重要**：长上下文场景下 KV 缓存是显存大头。量化它可以让你用更小的显存跑更长的上下文，但可能影响模型质量，尤其是在推理密集型任务上。
- **动手试试**：
  ```bash
  # 启动一个服务器，启用 FP8 KV Cache（注意：这可能降低精度）
  python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --kv-cache-dtype fp8_e4m3
  ```
- **预期结果**：服务器启动时打印的 KV 缓存显存占用会变小。你可以对比开启和关闭该选项时，同一问题的回答质量是否有差异。

### 知识点 3：注意力机制的优化（Skip-Softmax / BLASST）
- **是什么**：一种"有损"的注意力加速方法。它不再对所有的注意力分数都做 softmax 计算，而是跳过那些分数很低（贡献很小）的 token 块，从而节省计算。
- **为什么重要**：这是视频生成等长序列任务中提升性能的关键手段之一，能显著降低延迟。但它是有损的，需要权衡质量与速度。
- **动手试试**：
  ```python
  # 在 SGLang Diffusion 的请求中，通过 extra_body 开启该功能
  client.videos.create(
      model="<MODEL_PATH_OR_ID>",
      prompt="A cat walking on the moon",
      extra_body={
          "skip_softmax_params": {
              "threshold_scale_factor": 500.0,
              "start_step": 14,
          }
      },
  )
  ```
- **预期结果**：视频生成速度变快，但生成质量可能略有下降。你可以调整 `threshold_scale_factor` 来观察速度和质量的变化。

### 知识点 4：量化感知的模型加载（ModelOpt/FP8）
- **是什么**：一些模型（如 DeepSeek、xLLM）的权重本身就是量化的（如 NVFP4、FP8）。框架需要能正确识别并加载这些特殊格式，才能发挥其性能优势。
- **为什么重要**：如果加载逻辑有 bug，轻则性能不达标，重则直接加载失败或产生错误结果。今天的 commit 中有不少是修复这类问题的。
- **动手试试**：
  ```python

  ```
- **预期结果**：如果模型是量化格式，SGLang 的日志中会显示检测到量化，并选择相应的 kernel。如果格式不支持，会报错并提示你。

### 知识点 5：统一内存分配器（Unified Memory Allocator）
- **是什么**：一种新的内存管理方式，把不同类型的 KV 缓存（如 Mamba 的、SWA 的、普通注意力的）整合到一个统一的池子中，按需分配和回收。
- **为什么重要**：这种架构能更高效地利用显存，并为未来的新模型（如混合架构模型）提供更好的支持。它也是实现更复杂缓存策略（如分支点缓存）的基础。
- **动手试试**：
