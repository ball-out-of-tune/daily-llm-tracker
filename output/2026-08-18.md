## 🧪 重要知识点 & 动手实验

### 知识点 1：GPU 内存的"延迟释放"问题
- **是什么**：GPU（尤其是 ROCm/XPU）在进程退出后不会立即释放显存，而是"懒释放"，导致下一个进程启动时可能因显存不足而 OOM。
- **为什么重要**：在跑测试、多进程推理、服务重启时，如果不处理这个问题，你会看到莫名其妙的"CUDA out of memory"错误，但实际显存并没有被占用。
- **动手试试**：
  ```bash
  # 1. 启动一个占用显存的 Python 进程
  python -c "import torch; x = torch.ones(1000, 1000, device='cuda'); import time; time.sleep(5)"
  
  # 2. 进程结束后立即检查显存
  nvidia-smi  # 观察显存是否立即释放
  
  # 3. 等待几秒后再检查
  sleep 5 && nvidia-smi  # 观察显存是否延迟释放
  ```
- **预期结果**：如果你用的是 ROCm/XPU，会看到显存不会立即归零，而是过几秒才释放。这解释了为什么 vLLM 引入了 `wait_for_memory_to_settle()` 函数。

### 知识点 2：MXFP8 量化与 FlashInfer 的依赖关系
- **是什么**：MXFP8 是一种 8 位浮点量化格式，FlashInfer 是一个高性能注意力/量化内核库。vLLM 的 MXFP8 路径依赖 FlashInfer 提供的高效量化内核。
- **为什么重要**：如果 FlashInfer 未安装，直接走 MXFP8 路径会导致导入错误或运行崩溃。这次提交就是加了"守卫"，让代码在 FlashInfer 不可用时优雅降级。

### 知识点 4：DP 并行中"本地进程数"的计算
- **是什么**：在分布式推理中，`local_world_size` 是当前节点上的进程数，`data_parallel_size_local` 是当前节点上的数据并行度。启动线程数 = 两者乘积。
- **为什么重要**：如果只算 `local_world_size` 而忽略 `data_parallel_size_local`，会导致线程池过小，影响性能或触发死锁。
- **动手试试**：
  ```python
  # 模拟这个 bug 和修复
  local_world_size = 2
  data_parallel_size_local = 4
  
  # 修复前（错误）
  num_procs_before = local_world_size
  print(f"修复前: {num_procs_before} 个进程")  # 输出 2
  
  # 修复后（正确）
  num_procs_after = local_world_size * max(1, data_parallel_size_local)
  print(f"修复后: {num_procs_after} 个进程")  # 输出 8
  ```
- **预期结果**：你会看到修复前后进程数的差异，理解为什么 `max(1, ...)` 是必要的（当 DP 未启用时取 1）。

### 知识点 5：测试 fixture 的作用域（Scope）管理
- **是什么**：pytest 的 fixture 可以有不同的作用域（function、class、module、session），决定 fixture 的创建和销毁时机。
- **为什么重要**：如果 fixture 作用域过大（如 module），会导致测试之间互相影响（如显存不释放）；过小则性能差。
- **动手试试**：
  ```python

      print("\n[module] 创建重型资源")
      yield [1, 2, 3]
      print("[module] 销毁重型资源")
  
  def test_one(heavy_resource):
      print(f"test_one 使用 {heavy_resource}")
  
  def test_two(heavy_resource):
      print(f"test_two 使用 {heavy_resource}")
  
  # 运行: pytest test_scope.py -s
  # 观察资源只创建/销毁一次
  ```

### 知识点 1：配置袋（Config Bags）与发布-订阅模式

- **是什么**：SGLang 将进程级配置从直接读 `server_args` 字段改为通过 `publish()` 发布到命名空间袋（如 `get_exec()`、`get_memory()`、`get_parallel()`），业务代码从袋中读取解析后的配置值。
- **为什么重要**：直接读 `server_args` 的问题在于：启动参数在运行时可能被修改（如 DP 拓扑、量化配置），且不同进程（scheduler、tokenizer、encoder）需要不同的配置视图。配置袋提供了统一的、进程级的、可动态更新的配置访问方式。
- **动手试试**：
  ```python
  # 模拟 SGLang 的配置袋模式
  class ConfigBags:
      def __init__(self):
          self._bags = {}
          
      def publish(self, config: dict, role: str):
          """发布配置，投影到各命名空间袋"""
          self._bags['parallel'] = {
              'dp_size': config.get('dp_size', 1),
              'tp_size': config.get('tp_size', 1),
              'ep_size': config.get('ep_size', 1),
          }
          self._bags['memory'] = {
              'mem_fraction_static': config.get('mem_fraction_static', 0.9),
          }
          print(f"[{role}] 配置已发布")
          
      def get(self, namespace: str):
          if namespace not in self._bags:
              raise RuntimeError(f"配置袋 '{namespace}' 未发布")
          return self._bags[namespace]

  # 模拟进程入口
  ctx = ConfigBags()
  ctx.publish({'dp_size': 2, 'tp_size': 4}, role='scheduler')
  
  # 业务代码读取
  parallel = ctx.get('parallel')
  print(f"dp_size={parallel['dp_size']}, tp_size={parallel['tp_size']}")
  ```
- **预期结果**：你会看到配置通过 `publish` 统一发布，业务代码不再直接接触原始配置，而是通过命名空间袋读取。如果你尝试读取未发布的袋，会得到明确的错误提示——这就是"fail closed"行为。

### 知识点 2：推测解码中的 ngram 草稿与 FutureMap 异步中继

- **是什么**：ngram 推测解码用历史 token 序列生成草稿 token（无需额外的草稿模型），而 FutureMap 是用于在异步流水线（overlap 模式）中传递张量的机制。今天的 commit 优化了 ngram 草稿准备的 host 端开销（避免不必要的 `.cpu()` 调用），并让 accept tokens 通过 FutureMap 中继。
- **为什么重要**：推测解码的性能取决于草稿生成的速度和 accept tokens 传递的准确性。在 overlap 模式下，一个迭代的结果要延迟一个迭代才被消费，所以需要仔细管理状态同步。
- **动手试试**：
  ```python
  # 模拟 ngram 草稿生成的核心逻辑
  def generate_ngram_drafts(corpus, current_tokens, ngram_size=3, num_drafts=4):
      """从语料库中查找与当前 token 序列匹配的 ngram，生成草稿"""
      drafts = []
      # 取最后 ngram_size 个 token 作为查询
      query = tuple(current_tokens[-ngram_size:])
      
      for i in range(len(corpus) - ngram_size):
          if tuple(corpus[i:i+ngram_size]) == query:
              # 找到匹配，取后面的 token 作为草稿
              draft = corpus[i+ngram_size:i+ngram_size+num_drafts]
              drafts.append(draft)
              if len(drafts) >= 3:  # 最多找 3 个候选
                  break
      return drafts

  # 示例
  corpus = [1, 2, 3, 4, 5, 1, 2, 3, 6, 7, 8, 1, 2, 3, 9, 10]
  current = [1, 2, 3]  # 当前最后 3 个 token
  drafts = generate_ngram_drafts(corpus, current)
  print(f"找到 {len(drafts)} 个草稿候选:")
  for d in drafts:
      print(f"  {d}")
  ```
- **预期结果**：你会看到 ngram 算法如何从历史语料中找出与当前上下文匹配的续写候选。这比基于模型的草稿生成快得多（无额外前向传播），但质量取决于语料库的覆盖度。

### 知识点 3：FLOPs 精确估算——为什么 `tokens×(tokens+1)/2` 是错的

- **是什么**：prefill 阶段的注意力 FLOPs 应该等于"每个 chunk 与 cached prefix 的 query-key 对"加上"chunk 内部的因果对"，而不是简单的总 token 数公式。
- **为什么重要**：如果你用错误的 FLOPs 估算，speed-of-light 分析就会失真——你可能在优化一个并不存在的瓶颈，或者低估了真实的计算量。
- **动手试试**：
  ```python
  def prefill_attention_pairs(extend_lens, prefix_lens):
      """精确计算 prefill 的因果 query-key 对数量"""
      # prefix_pairs: 每个 chunk 的 query 与 cached prefix 的 key 形成的对
      prefix_pairs = sum(c * p for c, p in zip(extend_lens, prefix_lens))
      # within_chunk_pairs: chunk 内部的因果对（上三角）
      within_chunk_pairs = sum(c * (c + 1) / 2.0 for c in extend_lens)
      return prefix_pairs + within_chunk_pairs

  # 对比新旧公式
  extend_lens = [128, 256, 512]   # 3 个请求的 chunk 长度
  prefix_lens = [1024, 2048, 4096]  # 各自的 cached prefix 长度
  tokens = sum(extend_lens)  # 总 token 数 = 896

  old_formula = tokens * (tokens + 1) / 2  # 错误：假设所有 token 之间都有因果对
  new_formula = prefill_attention_pairs(extend_lens, prefix_lens)

  print(f"旧公式: {old_formula:.0f} 对")
  print(f"新公式: {new_formula:.0f} 对")
  print(f"差异: {new_formula/old_formula:.2f}x")
  ```
- **预期结果**：你会看到新公式计算的 pair 数远小于旧公式（因为 prefix 已经被缓存，不需要重复计算 prefix 内部的注意力）。这解释了为什么正确的 FLOPs 估算对性能分析至关重要。

### 知识点 5：配置重构中的"读取棘轮"（Read Ratchet）与测试守护

- **是什么**：SGLang 用测试来"钉住"哪些代码仍然允许直接读 `server_args` 字段，防止重构过程中出现回退。这被称为"暴露棘轮"（exposure ratchet）——只允许减少，不允许增加。
- **为什么重要**：大型重构最怕的是"改了一部分，剩下的忘了改"。棘轮测试确保每次改动都朝着目标方向前进，不会引入新的违规读取。
- **动手试试**：
  ```python
  # 模拟读取棘轮测试的概念
  import ast
  import sys

  def find_server_args_reads(file_path):
      """静态分析：找出所有直接读取 server_args.field 的代码"""
      with open(file_path) as f:
          tree = ast.parse(f.read())
      
      violations = []
      for node in ast.walk(tree):
          if isinstance(node, ast.Attribute):
              # 检查是否是 server_args.xxx 的形式
              if isinstance(node.value, ast.Name) and node.value.id == 'server_args':
                  violations.append(f"行 {node.lineno}: server_args.{node.attr}")
      return violations

  # 示例：检查一个"违规"文件
  test_code = '''
  def example(server_args):
      # 应该改为 get_parallel().dp_size
      if server_args.dp_size > 1:
          print("DP mode")
  '''
  
  with open('/tmp/test_violation.py', 'w') as f:
      f.write(test_code)
  
  violations = find_server_args_reads('/tmp/test_violation.py')
  if violations:
      print("发现违规读取：")
      for v in violations:
          print(f"  {v}")
  else:
      print("无违规读取")
  ```
- **预期结果**：你会看到静态分析如何自动检测 `server_args.field` 的直接读取。这正是棘轮测试的基础——通过自动扫描确保重构的进度可追踪。
