### 知识点 1：投机解码与 MTP（Multi-Token Prediction）
- **是什么**：让一个小模型或一个模型的浅层模块一次性预测多个未来 token，大模型再验证这些预测，如果预测正确就能一次生成多个 token，大幅加速推理。
- **为什么重要**：这是当前 LLM 推理加速最热门的方向之一。今天有多个 commit 在完善 MTP 的 KV cache 支持和多模块支持，说明它正在成为主流模型的标配功能（如 DeepSeek、Qwen）。
- **动手试试**：
```python

    draft_model_config=None,  # MTP 不需要单独的 draft 模型

)
print(f"MTP 配置成功: {config.method}, 预测 {config.num_speculative_tokens} 个 token")
```
- **预期结果**：理解 MTP 是"自包含"的投机解码，不需要额外的小模型，而是用模型自身的浅层模块做预测。

### 知识点 2：量化格式与硬件支持矩阵
- **是什么**：FP8、NVFP4、MXFP4 等是不同精度的数值格式，不同 GPU 架构对它们的支持不同。比如今天新增的 B12X 后端专门为 NVIDIA SM120/SM121 GPU 提供 NVFP4 和 MXFP4 支持。
- **为什么重要**：选错量化格式可能导致 kernel 不支持或性能极差。理解硬件支持矩阵是部署高性价比推理服务的关键。

### 知识点 3：KV Cache 与注意力后端的协同
- **是什么**：KV cache 是存储历史 token 的 Key 和 Value 向量的缓存，注意力后端（如 FlashInfer、FlashAttention）负责高效利用它。今天有 commit 专门修复 FlashInfer 在 SM120 上处理"attention sinks"（初始 token 的特殊处理）的问题。
- **为什么重要**：KV cache 是 LLM 推理的内存瓶颈，注意力后端的选择直接影响显存占用和速度。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Triton Kernel Tile 配置调优
- **是什么**：Triton 编写 GPU kernel 时，通过 `BLOCK_SIZE_M/N/K` 等参数控制每个线程块计算的数据块大小，不同配置对性能影响巨大。
- **为什么重要**：默认配置通常不是最优的。错误的 tile 大小可能导致显存带宽利用率低或 SM 占用率不足，性能差距可达数倍。在 SGLang 中，社区通过自动调优为特定 GPU 和矩阵形状保存最佳配置。
- **动手试试**：运行 SGLang 的 kernel benchmark 脚本，对比不同 tile 配置下的性能：
  ```bash
  # 先安装 sglang (参考官方文档)
  # 运行一个已有的 kernel benchmark，例如 paged_mqa_metadata
  python benchmark/kernels/bench_paged_mqa_metadata.py

  # 如果想自己调优，可以修改 configs 目录下的 json 文件
  # 例如修改 BLOCK_SIZE_M 从 16 改为 32，然后重新跑 benchmark
  ```
- **预期结果**：你会看到不同 batch size 下，最优配置不同（如小 batch 用小块，大 batch 用大块）。这说明"自适应调度"的重要性，掌握后你就能为自己的模型找到最佳配置。

### 知识点 2：环境变量驱动的功能开关
- **是什么**：SGLang 通过大量环境变量（如 `SGLANG_FLASHINFER_MOE_FUSED_FINALIZE`）控制运行时行为，这些开关在 `environ.py` 中统一注册和管理。
- **为什么重要**：这些开关让用户无需改代码就能切换内核实现、启用/禁用优化。理解它们能帮你调试性能问题或绕过 bug。比如 Commit 7 新增的 `SGLANG_FLASHINFER_MOE_FUSED_FINALIZE` 控制是否使用 fused MoE finalize。
- **动手试试**：
  ```bash
  # 查看当前所有环境变量及其默认值
  python -c "from sglang.srt.environ import Envs; print(Envs.__dict__)"

  # 尝试启用某个优化开关（例如禁用 fused finalize 看是否影响性能/正确性）
  SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=false python -m sglang.launch_server --model-path meta-llama/Llama-2-7b-chat-hf --port 30000
  ```
- **预期结果**：你能看到所有环境变量的定义和默认值。通过设置不同值，你能在不改代码的情况下切换内核行为，这是排查问题的关键手段。

### 知识点 3：CUDA Graph 捕获与权重加载重叠
- **是什么**：`overlap` 模式让模型权重从磁盘加载（staging）与 CUDA graph 捕获并行执行，因为两者使用不同的硬件资源（I/O 与 GPU 计算）。
- **为什么重要**：服务启动时间直接决定用户体验。通过重叠，启动时间可减少约 30-50%。这是工程化大模型服务的重要优化手段。
- **动手试试**：
  ```bash
  # 1. 不用 overlap 模式启动，记录启动时间
  time python -m sglang.launch_server --model-path meta-llama/Llama-2-7b-chat-hf --port 30000 --startup-weight-load-mode serial

  # 2. 用 overlap 模式启动，对比启动时间
  time python -m sglang.launch_server --model-path meta-llama/Llama-2-7b-chat-hf --port 30001 --startup-weight-load-mode overlap
  ```
- **预期结果**：你会看到 `overlap` 模式启动时间明显缩短。理解启动流程（`init_model_worker` 中的阶段划分）后，你能明白为什么这两个阶段可以重叠。

### 知识点 4：KV Cache 事件合并（Coalescing）
- **是什么**：当连续存储多个 KV cache 块时，将它们合并为一个批量事件，而不是逐个入队，减少事件处理开销。
- **为什么重要**：KV cache 事件用于缓存管理（如 LRU 淘汰、前缀复用）。每生成一个 token 都可能触发多个事件，合并能显著降低开销。
- **动手试试**：
  ```bash
  # 运行 KV cache 事件测试，观察合并后的行为
  python test/manual/test_kv_events.py

  # 也可以写个小脚本，手动构造连续存储事件，查看队列长度
  python -c "
  from sglang.srt.mem_cache.events import KVCacheEventMixin, BlockStored
  import types
  mixin = KVCacheEventMixin()
  mixin.kv_event_queue = []
  mixin.enable_kv_cache_events = True
  # 模拟连续存储两个块
  e1 = BlockStored(block_hashes=[1], medium='GPU', lora_id=None, block_size=64, token_ids=[1,2,3], parent_block_hash=None)
  e2 = BlockStored(block_hashes=[2], medium='GPU', lora_id=None, block_size=64, token_ids=[4,5,6], parent_block_hash=1)
  mixin._enqueue_kv_event(e1)
  mixin._enqueue_kv_event(e2)
  print(f'队列长度: {len(mixin.kv_event_queue)}')  # 应该是 1，因为被合并了
  "
  ```
- **预期结果**：你会看到连续的同类型事件被合并为一条，队列长度保持为 1。这说明合并机制生效，能减少事件处理次数。

### 知识点 5：DCP 解码上下文并行
- **是什么**：将一条请求的 KV cache 按 token 位置切分到多个 GPU（如 rank 0 存第 0, 4, 8... 个位置），每个 GPU 只处理部分上下文，最后通过 all-to-all 合并注意力结果。
- **为什么重要**：单卡显存无法容纳超长上下文的 KV cache。DCP 让你用更多 GPU 扩展单请求的上下文长度，是长上下文推理的关键技术。
- **动手试试**：
  ```bash
  # 启动一个使用 DCP 的 DeepSeek-V3.1 服务（需要多卡）
  # 注意：这需要你有 8 张 GPU
  python -m sglang.launch_server \
    --model-path deepseek-ai/DeepSeek-V3.1 \
    --trust-remote-code \
    --tp-size 8 \
    --dcp-size 8 \
    --host 0.0.0.0 \
    --port 30000

  # 然后发送一个长上下文请求（如 100K tokens），观察是否成功
  ```
- **预期结果**：服务能正常处理超长上下文（单卡无法容纳的长度）。理解 DCP 的"分而治之"思想后，你就掌握了扩展上下文长度的核心思路。
