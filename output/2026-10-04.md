## 🧪 重要知识点 & 动手实验

- **知识点 1：音频数据的形状归一化（多模态方向）**
  - **是什么**：音频在内存里可能是 `(N,)`、`(1, N)`、`(N, 1)`，但模型只认 `(N,)` 单声道。归一化函数要把这些形状统一。
  - **为什么重要**：如果你不做归一化，`(1, N)` 传给模型会被当成"1 个样本、N 个声道"，直接报错或静默出错。这类 bug 在真实用户上传音频时特别常见。
  - **动手试试**：
    ```python
    import numpy as np
    import torch

    def normalize_mono(x):
        if x.ndim == 2 and x.shape[0] == 1:
            return x[0]
        if x.ndim == 2 and x.shape[1] == 1:
            return x[:, 0]
        return x

    for shape in [(3,), (1, 3), (3, 1), (1, 1)]:
        a = np.arange(max(shape), dtype=np.float32).reshape(shape)
        out = normalize_mono(a)
        print(shape, "->", out.shape, out)
    ```
  - **预期结果**：所有输入都输出 `(3,)` 或 `(1,)` 的 1D 数组，说明你理解了"显式声道轴"的处理。

- **知识点 2：引用计数与 pending 状态（分布式/KV Offload 方向）**
  - **是什么**：每个 KV block 有一个 `ref_cnt`，表示有多少个请求在用它。当请求被取消或缓存被 reset 时，必须把所有 pending 的引用释放掉，否则 block 永远无法回收。
  - **为什么重要**：不释放会导致显存/内存泄漏，长时间运行后 OOM；释放过早会导致正在使用的请求读到脏数据。
  - **动手试试**：
    ```python
    class Block:
        def __init__(self, id):
            self.id = id
            self.ref_cnt = 0
        def inc(self): self.ref_cnt += 1
        def dec(self): self.ref_cnt -= 1

    class Pool:
        def __init__(self):
            self.blocks = {}
            self.pending = {}
        def alloc(self, bid):
            b = Block(bid); b.inc(); self.blocks[bid] = b; return b
        def mark_pending(self, req, bids):
            self.pending[req] = bids
        def reset(self):
            for bids in self.pending.values():
                for bid in bids:
                    self.blocks[bid].dec()
            self.pending.clear()

    pool = Pool()
    b1, b2 = pool.alloc(1), pool.alloc(2)
    pool.mark_pending("req-1", [b1, b2])
    print("before reset:", b1.ref_cnt, b2.ref_cnt)
    pool.reset()
    print("after reset:", b1.ref_cnt, b2.ref_cnt)
    ```
  - **预期结果**：reset 前 `ref_cnt` 都是 1，reset 后都变成 0，说明 pending 引用被正确释放。

- **知识点 3：CUDA Graph 与内存池（性能优化方向）**
  - **是什么**：CUDA Graph 把一串 kernel 调用录制成图，重放时省去 CPU 启动开销。cuMem pool 是它使用的显存池。睡眠模式可以把整个池备份到 CPU 内存。
  - **为什么重要**：CUDA graph 能显著降低 decode 延迟，但它的显存占用不释放会阻碍多模型共存。理解 pool 的生命周期是性能调优的基础。
  - **动手试试**（需要 CUDA 环境）：
    ```python
    import torch

    # 简单演示 CUDA graph 捕获
    x = torch.randn(1024, device="cuda")
    y = torch.empty_like(x)

    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        y.copy_(x * 2)

    x.fill_(3.0)
    g.replay()
    print(y[:5])  # 应该全是 6.0
    ```
  - **预期结果**：输出 `tensor([6., 6., 6., 6., 6.], device='cuda:0')`，说明你成功捕获并重放了一个 CUDA graph。

- **知识点 4：分离式推理的 token-in/token-out 模式（服务架构方向）**
  - **是什么**：prefill 实例只负责算 KV cache，decode 实例负责逐 token 生成。它们之间传的是 token ID，不是文本，所以需要 `/inference/v1/generate` 这样的接口。
  - **为什么重要**：分离式部署能独立扩缩容 prefill 和 decode，是长上下文、大并发场景的标准做法。不懂这个模式就没法调优这类系统。
  - **动手试试**：

  - **预期结果**：返回 JSON 里只有 `token_ids`，没有 `text` 字段，说明 tokens-only 模式生效。

- **知识点 5：量化 GEMM 的 split-K 与数值精度（量化方向）**
  - **是什么**：split-K 是把 K 维度切分给多个线程块并行计算，最后用 atomic add 合并。fp16 累加会有精度损失，需要"精确分解形式"（拆成 fp32 的 y/z 对）来避免。
  - **为什么重要**：量化模型（W4A16）在 AMD RDNA3 上如果精度不对，输出会乱码或重复。理解 dequant 的数学是修这类 bug 的前提。
  - **动手试试**：
    ```python
    import torch

    # 模拟 fp16 累加 vs fp32 累加的差异
    torch.manual_seed(0)
    x = torch.randn(10000, dtype=torch.float32) * 100

    s16 = torch.zeros(1, dtype=torch.float16)
    for v in x:
        s16 += v.half()
    s32 = x.sum()

    print("fp16 sum:", s16.item())
    print("fp32 sum:", s32.item())
    print("diff:", abs(s16.item() - s32.item()))
    ```
  - **预期结果**：fp16 累加结果与 fp32 有明显偏差，说明为什么量化 kernel 需要小心处理累加精度。

- **关键词：AMD ROCm 生态适配**
  - **一句话通俗解释**：SGLang 正在把越来越多的推理算子（attention、QK norm、RoPE、MoE）接到 AMD 的 AITER 库上，让 AMD GPU 也能跑出接近 NVIDIA 的性能。

- **关键词：Context Parallel（上下文并行）**
  - **一句话通俗解释**：把一条超长序列切成几段，分给多张 GPU 同时算 attention，最后合起来，专门解决长文本推理的显存和延迟问题。

  - **对新手意味着什么**：分布式推理是 LLM 部署的核心技能。理解 DP/TP/PP/CP 四种并行的组合关系，是进阶必备。

- **关键词：HiCache 分层缓存**
  - **一句话通俗解释**：把 KV cache 从 GPU 显存卸载到主机内存（甚至 SSD），需要时再换回来，用空间换 GPU 显存。
  - **为什么社区在关注**：今天有 3 个 HiCache 相关 commit（host lock 归属、cgroup 内存核算、Mamba 侧状态搬运），说明分层缓存已经进入"修 bug 保正确性"的成熟阶段，而不是早期功能开发。
  - **对新手意味着什么**：缓存是推理系统的"第二战场"，学会 KV cache 的分配、淘汰、跨层搬运，比只会调参有价值得多。

- **关键词：PD 分离（Prefill/Decode Disaggregation）**
  - **一句话通俗解释**：把"读 prompt"（prefill，算力密集）和"逐字生成"（decode，显存带宽密集）拆到不同机器上跑，各自用最合适的硬件。
  - **为什么社区在关注**：Commit 7、8 都在修 PD 分离的 dp_rank 注册和测试参数问题，说明这套架构在生产环境里已经大量部署，边角 bug 开始浮现。
  - **对新手意味着什么**：PD 分离是当前大模型服务的主流架构，理解 KV 传输（Mooncake、NIXL）和路由是加分项。

- **关键词：Router 缓存感知路由**
  - **一句话通俗解释**：请求调度器记住"哪个 worker 缓存了哪些前缀"，把相同前缀的请求尽量路由到同一个 worker，避免重复 prefill。
  - **为什么社区在关注**：Commit 20 引入了"pending prefix"机制，在 KV 事件到达前就先把 worker"记账"，解决并发突发请求打散的问题。这是 cache-aware 路由的精细化。
  - **对新手意味着什么**：路由 + 缓存是推理网关的核心，如果你做后端/基础设施，这块是必学。

## 🧪 重要知识点 & 动手实验

- **知识点 1：Context Parallel 与 DP/TP 的组合（Commit 6）**
  - **是什么**：Context Parallel 把一条长序列按 token 切分到多张卡上做 attention。`interleave` 策略是按 `token_idx % cp_size` 分配，`zigzag` 是首尾配对分配。今天这个 commit 让 CP 可以和 attention DP 叠加：`tp_size / attn_dp_size` 就是每个 DP 组里的 CP 宽度。
  - **为什么重要**：长上下文（100K+ token）单卡放不下，CP 是唯一解。不懂 CP 和 DP 的组合关系，你会写出冲突的启动参数，服务直接起不来。
  - **动手试试**：
    ```bash
    # 8 卡，2 个 attention DP 组，每组 4 卡做 CP
    python -m sglang.launch_server \
      --model-path deepseek-ai/DeepSeek-V3.2 \
      --tp 8 --attn-dp-size 2 \
      --enable-prefill-cp --cp-strategy interleave \
      --moe-dense-tp-size 1
    ```
  - **预期结果**：服务正常启动，日志里能看到 `attn_dp_size=2`、`cp_size=4`。发一个长 prompt，观察 TTFT 比单卡 CP 更低，且没有报 "attn_dp_size > 1 与 CP 不兼容" 的错误。

- **知识点 2：Triton 写 FP8 量化 kernel（Commit 15）**
  - **是什么**：FP8 量化是把 bf16/fp16 数值压成 8 位浮点（E4M3 格式），显存减半、算力翻倍。rowwise 是"每一行算一个缩放因子"。
  - **为什么重要**：量化是推理加速的头号手段。但量化 kernel 很容易踩坑：舍入方式不对、溢出处理不当，结果就是精度崩了或输出 NaN。
  - **动手试试**：
    ```python
    import torch
    from sglang.kernels.ops.diffusion import fp8_rowwise, can_use_fp8_rowwise

    x = torch.randn(128, 4096, dtype=torch.bfloat16, device="cuda")
    if can_use_fp8_rowwise(x):
        q, scale = fp8_rowwise(x)
        # 反量化验证
        deq = q.to(torch.float32) * scale.unsqueeze(1)
        print("max error:", (deq - x.float()).abs().max().item())
    ```
  - **预期结果**：`max error` 应该在 0.01 量级（E4M3 的精度极限），说明量化-反量化往返正确。如果 error 很大或出现 NaN，说明缩放因子或舍入有问题。

- **知识点 3：cgroup 内存核算与 HiCache 自动 sizing（Commit 17）**
  - **是什么**：cgroup 是 Linux 的容器资源隔离机制，`memory.stat` 里有 `file`（页缓存）等字段。HiCache 要根据容器实际可用内存决定卸载多少 KV cache。
  - **为什么重要**：在 Kubernetes 里跑推理，如果 HiCache 按宿主机内存算而不按 cgroup 限制算，就会 OOM 被 kill。这是生产环境的经典坑。
  - **动手试试**：
    ```bash
    # 查看当前 cgroup 内存信息
    cat /sys/fs/cgroup/memory.stat | head -20
    cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes

    # 在 Docker 里限制内存跑 SGLang，观察 HiCache 日志
    docker run --memory=32g --gpus all sglang/sglang:latest \
      python -m sglang.launch_server --model-path <model> --enable-hicache
    ```
  - **预期结果**：日志里 HiCache 报的可用内存应该接近 32g 减去预留，而不是宿主机的几百 G。如果发现它按宿主机算，就说明 cgroup 发现失败，需要设置 `SGLANG_HICACHE_HOST_MEMORY_BYTES`（注意：这个 commit 正在移除这个环境变量，改用自动发现）。

- **知识点 4：FlashInfer A2A 与 MoE 通信（Commit 4）**
  - **是什么**：MoE（混合专家）模型里，每个 token 要发给它选中的专家所在的 GPU。A2A（All-to-All）是这种"每个 GPU 发不同数据给所有 GPU"的通信模式。以前 prefill 用 AllGather + ReduceScatter，现在换成 FlashInfer 的 A2A，更省带宽。
  - **为什么重要**：MoE 模型的瓶颈往往不在计算而在通信。选错通信原语，GPU 利用率可能只有 30%。
  - **动手试试**：
    ```bash
    # 用 DeepSeek-V3 这类 MoE 模型，对比 A2A 和 AG+RS
    python -m sglang.launch_server \
      --model-path deepseek-ai/DeepSeek-V3 \
      --tp 8 --ep-size 8 \
      --moe-a2a-backend flashinfer   # 新路径
    # 对比 --moe-a2a-backend deepep  # 旧路径
    ```
  - **预期结果**：用 `nvidia-smi dmon` 或 `rocm-smi` 观察 GPU 利用率，A2A 路径下 prefill 阶段的通信开销应该更低，吞吐更高。注意需要 FlashInfer 版本支持。

- **知识点 5：Router 的 Pending Prefix 缓存记账（Commit 20）**
  - **是什么**：KV 事件是 worker 告诉 router"我缓存了这段前缀"的消息，但有延迟。Pending prefix 是 router 在发出请求后，立刻先"预记账"，认为这个 worker 有这个前缀，TTL 到期或 KV 事件到达后转为正式记录。
  - **为什么重要**：并发突发（比如 RL rollout、并行采样）时，多个请求共享同一冷前缀，如果等 KV 事件才路由，会全部打散到不同 worker，每个都重复 prefill。
  - **动手试试**：
    ```bash
    # 启动带 pending prefix 的 router
    ./sgl-router \
      --policy cache_aware \
      --cache-prefix-provider radix_tree \
      --cache-pending-prefix-ttl-ms 2000

    # 用相同前缀并发打 10 个请求
    for i in $(seq 1 10); do
      curl -s http://localhost:30000/generate \
        -d '{"text": "很长很长且完全相同的前缀...", "max_new_tokens": 10}' &
    done
    wait
    ```
  - **预期结果**：查看 `sgl_router_cache_pending_prefix_hits_total` 指标，应该大于 0。日志里应该看到这 10 个请求大多落到同一个 worker，而不是分散。
