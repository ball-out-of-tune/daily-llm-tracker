- **知识点 3：采样掩码（Sampling Mask）与 GPU 压缩**

  - **为什么重要**：这能显著减少 CPU 和 GPU 之间的数据拷贝，提升吞吐量。对于 `logprobs` 和 `sampling_mask` 这类功能，理解其底层实现有助于你进行高级 API 调用。

- **关键词：异构硬件适配（AMD ROCm / Intel XPU）**
  - **一句话通俗解释**：同一套推理框架，在不同品牌的 GPU（AMD、Intel）上都能高效运行，而不只是 NVIDIA。
  - **为什么社区在关注**：今日 20 个 commits 中有 6 个直接涉及 AMD 或 Intel 平台优化，这说明推理框架正在从"单芯片绑定"走向"多平台覆盖"。云厂商和多卡集群越来越多地采用混合硬件，谁能适配更多芯片谁就赢得市场。

- **关键词：算子融合（Kernel Fusion）**
  - **一句话通俗解释**：把多个小矩阵运算合并成一个大运算，减少数据搬运次数，让 GPU 算得更快。
  - **为什么社区在关注**：Commit 1（Kimi-K3 投影融合）和 Commit 12（删除自研 CuTe DSL 改用 FlashInfer）都在做同一件事——用更少的算子调用榨干硬件性能。GPU 算力已经够强，瓶颈在于"喂数据"的速度，融合就是为了减少喂数据的次数。
  - **对新手意味着什么**：理解"带宽受限 vs 计算受限"是性能优化的分水岭。学内核优化时，先学会判断瓶颈在哪，再决定是否融合。

- **关键词：量化精度与推理质量平衡**
  - **一句话通俗解释**：模型权重用低精度（如 FP4/FP8）存储以省显存，但关键步骤要"临时升级"到高精度以保质量。
  - **为什么社区在关注**：Commit 2（GPT-OSS MXFP4）和 Commit 20（Cosmos3 首尾步高精度）都在做同一件事——量化不能一刀切。社区共识是"关键计算步骤必须保持精度"。这直接关系到量化模型能否落地到生产环境。
  - **对新手意味着什么**：学习量化时不要只学"怎么压"，要学"哪里不能压"。

- **关键词：框架内部重构（CP V1 弃用、自研代码下放）**
  - **一句话通俗解释**：框架在清理旧接口、删重复代码，把维护成本转移给上游库。
  - **为什么社区在关注**：Commit 12（删掉 7000+ 行自研代码）和 Commit 15（CP V1 弃用）说明项目正在走向成熟——不再"什么都自己造"，而是信任成熟上游库。这是开源项目生命周期的自然演进。

## 🧪 重要知识点 & 动手实验

### 知识点 1：环境变量驱动的运行时行为开关
- **是什么**：通过 `SGLANG_ROCM_K3_FUSE_KDA_INPROJ` 这类环境变量，在运行时切换代码路径，而不用改代码。
- **为什么重要**：这是生产级推理框架的核心设计模式——同一份代码支持多种硬件/场景，用户通过环境变量调优。不懂这个模式，读代码时会被各种 `if envs.XXX.get()` 搞晕。
- **动手试试**：
  ```bash
  # 在 sglang 任意启动命令前加环境变量
  SGLANG_ROCM_K3_FUSE_KDA_INPROJ=false python -m sglang.srt.server \
    --model-path deepseek-ai/DeepSeek-V3 --tp 2
  # 对比默认 true 时的启动日志差异
  ```
- **预期结果**：你会看到日志中关于 KDA 投影层的初始化路径不同（融合 vs 分离）。掌握后，遇到性能问题时第一反应是"查环境变量文档"，而不是改代码。

### 知识点 2：带宽受限 vs 计算受限（Kernel Fusion 的决策依据）
- **是什么**：GPU 运算要么卡在"等数据"（带宽受限），要么卡在"算太久"（计算受限）。融合算子只在带宽受限时有收益。
- **为什么重要**：Commit 1 中特意加了 `MAX_TOKENS=256` 的开关——超过 256 个 token 后 GEMM 变成计算受限，融合反而变慢。不懂这个原理，盲目融合会得到负优化。
- **动手试试**：
  ```bash
  # 用 nsys 或 ncu 分析一个 GEMM kernel
  ncu --metrics gpu__time_duration.avg,dram__throughput.avg.pct_of_peak_sustained_elapsed \
      python your_gemm_test.py
  # 如果 dram throughput > 80%，说明带宽受限，适合融合
  ```
- **预期结果**：你会看到不同 token 数下 DRAM 利用率的变化。理解后，你就能解释"为什么某些优化在小 batch 有效、大 batch 无效"。

### 知识点 3：分页 KV Cache 与注意力掩码的相互作用
- **是什么**：KV Cache 按页存储，注意力计算需要知道"哪些页属于哪个序列"，分页大小会影响注意力窗口的对齐。
- **为什么重要**：Commit 3 修复了 Llama 4 分页 KV Cache 下局部注意力崩溃的问题。原因是分页导致注意力 chunk 边界与页边界不对齐，索引越界。这是生产环境中极隐蔽的 bug。
- **动手试试**：
  ```python
  # 模拟分页对 chunk 对齐的影响
  page_size = 16
  attn_chunk_size = 32
  seq_len = 50
  # 旧逻辑：effective_chunk = min(32, 50) = 32，然后对齐到 16 的倍数
  effective_chunk = (min(attn_chunk_size, seq_len) // page_size) * page_size
  print(f"旧逻辑 chunk={effective_chunk}")  # 32
  # 新逻辑 preserve=True 时直接用原始 chunk，不做对齐
  print(f"新逻辑 chunk={attn_chunk_size}")  # 32，但 seq_len=50 会越界！
  ```
- **预期结果**：你会理解为什么需要 `preserve_attn_chunk_size` 参数来控制是否做对齐。掌握后，遇到注意力相关 bug 时能快速定位是否与分页有关。

### 知识点 4：请求生命周期管理（dispatched vs pending）
- **是什么**：一个请求从客户端发出到完成，要经历多个状态：pending（排队）、dispatched（已发给调度器）、aborted（中止）。不同状态下失败，清理方式不同。
- **为什么重要**：Commit 10 修复了"客户端断开后请求仍占内存"的泄漏 bug。核心区分是：还没发出去的请求可以直接丢弃，已发出去的必须发 abort 信号让调度器清理。
- **动手试试**：
  ```python
  # 在 tokenizer_manager.py 中加日志观察状态流转
  # 找到 _mark_state_dispatched 调用处，加一行：
  logger.info(f"Request {rid} dispatched, state.dispatched={state.dispatched}")
  # 启动服务，发起一个请求，中途 Ctrl+C 断开客户端
  ```
- **预期结果**：你会看到日志中请求先标记 dispatched，断开后触发 `_release_req_states_on_failure` 而不是简单丢弃。理解后，你就能看懂为什么"abort 和 discard"是两套不同逻辑。

### 知识点 5：FP4/FP8 量化中的"关键步骤保精度"
- **是什么**：模型大部分层用低精度（FP4/FP8）跑，但第一个和最后一个去噪步骤临时把权重"解量化"到高精度（BF16）再算。
- **为什么重要**：Commit 20 的 Cosmos3 实现表明，量化误差在迭代式生成（如扩散模型）的首尾步会被放大。不懂这个模式，你会在量化模型上看到"质量崩坏"却不知道为什么。
- **动手试试**：
  ```bash
  # 用环境变量关闭混合精度，对比输出质量
  SGLANG_DIFFUSION_ENABLE_COSMOS3_STEP_MIXED_PRECISION=false \
    python your_cosmos3_inference.py
  # 再开回来对比
  SGLANG_DIFFUSION_ENABLE_COSMOS3_STEP_MIXED_PRECISION=true \
    python your_cosmos3_inference.py
  ```
- **预期结果**：你会看到关闭混合精度后，生成视频的细节明显变差（尤其是运动场景）。掌握后，你会理解"量化不是二选一，而是按需切换"。
