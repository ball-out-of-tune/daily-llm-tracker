## 🧪 重要知识点 & 动手实验

### 知识点 1：张量并行（TP）下的列切分——从 ReplicatedLinear 到 ColumnParallelLinear

- **是什么**：在多卡推理中，一个大的线性层可以按"输出维度"切分到多张卡上，每张卡只计算一部分输出。这叫**列并行（Column Parallel）**。与之相对的是**复制（Replicated）**——每张卡都算完整结果，浪费显存和算力。
- **为什么重要**：Commit 4 把 Engram 的 `wkv` 投影从 `ReplicatedLinear` 改成 `ColumnParallelLinear`。如果不懂这个区别，你会在多卡部署时发现显存莫名爆炸，或者吞吐上不去。更关键的是，**序列并行（Sequence Parallel）** 场景下不能用列切分（因为每张卡只看自己那部分 token），所以代码里加了 `disable_tp=use_sequence_parallel` 这个开关——这是 TP 和 SP 互斥的典型例子。
- **动手试试**：
  ```python
  # 对比两种线性层的参数量（假设 TP=2）
  import torch
  from vllm.model_executor.layers.linear import (
      ReplicatedLinear, ColumnParallelLinear
  )
  # 假设输入 1024 维，输出 4096 维
  # ReplicatedLinear: 每张卡都有 1024*4096 参数
  # ColumnParallelLinear: 每张卡只有 1024*2048 参数（输出维度除以 TP）
  print("Replicated per-GPU params:", 1024 * 4096)
  print("ColumnParallel per-GPU params:", 1024 * 4096 // 2)
  ```
  然后启动一个 TP=2 的 vLLM 服务，用 `nvidia-smi` 观察两张卡的显存占用是否均衡。
- **预期结果**：你会看到 ColumnParallel 每卡参数量减半，显存占用更均衡。如果改成 Replicated，两张卡会各存一份完整权重，浪费一半显存。

### 知识点 2：量化配置的"覆盖"与"混合精度"

- **是什么**：量化就是把 FP16/BF16 的权重压缩成 FP8/FP4 等低精度格式。**混合精度**指不同层用不同量化方案（比如注意力用 FP8，专家层用 FP4）。**Quark** 是 AMD 的量化工具链，它导出的配置里每个层可能有独立的量化规格。
- **为什么重要**：Commit 2 的核心 bug 是：`DeepseekV4FP8Config.from_config` 会把 Quark 的混合精度配置"压平"成一个全局 FP8 方案，导致每层的精细配置丢失，加载权重时对不上号。新手常犯的错误就是"以为量化配置是全局的"——实际上现代量化方案越来越细粒度。
- **动手试试**：
  ```python
  # 模拟一个混合精度配置的结构
  quant_config = {
      "global_quant_config": {
          "weight": {"dtype": "fp4", "qscheme": "per_group", "group_size": 32}
      },
      "layer_quant_config": {
          "layers.0.attn.wkv": {
              "weight": {"dtype": "fp8_e4m3", "qscheme": "per_block",
                         "block_size": [32, 32]}
          }
      },
      "quant_method": "quark",
  }
  # 思考：如果 from_config 只读 global_quant_config，
  # 那么 layers.0.attn.wkv 的 per_block FP8 配置就丢了
  print("全局方案:", quant_config["global_quant_config"]["weight"]["dtype"])
  print("层专属方案:", quant_config["layer_quant_config"]["layers.0.attn.wkv"]["weight"]["dtype"])
  ```
- **预期结果**：你会理解为什么"层专属配置"不能被全局配置覆盖。跑一个混合精度模型时，如果日志里出现 "fallback to global spec"，就是这个 bug 的信号。

### 知识点 3：NCCL M2N——两个独立 GPU 网格之间的权重重分片

- **是什么**：NCCL 是 NVIDIA 的集合通信库。**M2N** 是它的一个扩展，允许一个 M 卡的网格（训练器）把权重"重分片"发给 N 卡的网格（推理引擎），即使两边的并行策略完全不同（比如训练用 FSDP，推理用 TP）。
- **为什么重要**：Commit 3 新增了 `nccl_m2n` 后端。传统做法是训练器先把完整张量 gather 起来再发，这在超大模型上很昂贵。M2N 让训练器直接发自己的本地分片，推理端负责重组。这是 RL 训练闭环的关键基础设施。
- **动手试试**：

  然后尝试用 `backend="nccl_m2n"` 启动一个 LLM 实例（需要安装 `nccl-extensions`）。
- **预期结果**：你会看到 M2N 的配置项和它与其他后端（ipc、sparse_nccl、sharded_rdt）的对比表。理解"何时该用哪个后端"是分布式系统的核心判断力。

### 知识点 4：字符串切片的隐藏 O(N²) 陷阱

- **是什么**：在 Python 中，`s[i:i+n] == prefix` 每次都会创建一个长度为 n 的新字符串。如果放在循环里，总复杂度是 O(N×n)。而 `s.startswith(prefix, i)` 不创建新字符串，是 O(n) 单次、O(N) 总量。
- **为什么重要**：Commit 9 修复了 Gemma4 解析器中的这个模式。在解析长文本（比如模型输出的 JSON 参数）时，O(N²) 会让解析时间随输出长度平方增长——用户感知就是"模型越说越慢"。
- **动手试试**：
  ```python
  import time

  s = "x" * 100_000
  prefix = "xyz"

  # 慢：切片
  t0 = time.perf_counter()
  for i in range(len(s) - 3):
      _ = s[i:i+3] == prefix
  t1 = time.perf_counter()

  # 快：startswith
  t2 = time.perf_counter()
  for i in range(len(s) - 3):
      _ = s.startswith(prefix, i)
  t3 = time.perf_counter()

  print(f"切片: {t1-t0:.4f}s, startswith: {t3-t2:.4f}s")
  ```
- **预期结果**：你会看到 `startswith` 明显更快（通常 2-5 倍）。在 100 万字符的文本上差距会更夸张。这就是"API 选择决定复杂度"的经典案例。

### 知识点 5：张量别名（Aliasing）——为什么元组赋值会交换失败

- **是什么**：在 Python/NumPy/PyTorch 中，`t[i1], t[i2] = t[i2], t[i1]` 看似交换两行，实际上右侧先求值得到两个**视图（view）**，然后赋值时两个视图指向同一块内存，导致两行都变成第二行的内容。
- **为什么重要**：Commit 8 修复了 `InputBatch.swap_states` 中 `allowed_token_ids_mask` 的别名 bug。这会导致请求的 token 约束"丢失"——用户设置了 `allowed_token_ids`，但交换后约束消失了，模型可能输出非法 token。
- **动手试试**：
  ```python
  import torch

  t = torch.zeros(2, 5)
  t[0] = 1  # 第一行全是 1
  t[1] = 2  # 第二行全是 2

  # 错误做法：元组赋值
  t_bad = t.clone()
  t_bad[0], t_bad[1] = t_bad[1], t_bad[0]
  print("元组赋值结果:\n", t_bad)
  # 两行都变成 2！

  # 正确做法：花式索引
  t_good = t.clone()
  t_good[[0, 1]] = t_good[[1, 0]]
  print("花式索引结果:\n", t_good)
  # 正确交换
  ```
- **预期结果**：你会亲眼看到元组赋值导致两行"塌缩"成同一行。这是 PyTorch 新手最容易踩的坑之一，记住：**交换张量行要用花式索引或 `.clone()`**。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Setwise Scoring —— 用 CausalLM 给多个候选打分

- **是什么**：传统打分是"query + 一个 item"算一次分。Setwise 是"query + 一整块候选 + 每个候选后放一个特殊 token"，模型在这些特殊 token 位置读出 logprob 作为分数，一次前向就得到 N 个候选的分数。
- **为什么重要**：RAG 里 rerank 10 个文档，逐个打分要 10 次前向；setwise 只要 1 次。不懂这个，你的 rerank 延迟会高一个数量级。
- **动手试试**：
  ```python
  import requests
  # 假设你已启动 sglang server，且模型支持 score 接口
  payload = {
      "model": "your-model",
      "query": "什么是量子纠缠？",
      "items": ["量子纠缠是一种量子力学现象...", "苹果是一种水果...", "纠缠指两个粒子状态关联..."],
      "score_extraction_token": "▁A",  # 特殊 token，每个候选后放一个
      "label_token_ids": [1234, 5678],  # 你关心的标签 token id
  }
  r = requests.post("http://localhost:30000/v1/score", json=payload)
  print(r.json())  # scores 是 [N x num_labels] 的矩阵
  ```
- **预期结果**：你会拿到一个嵌套列表，每个候选对应一行分数。分数高的候选就是模型认为更相关的。

### 知识点 2：KV Cache 的"驱逐游标"为什么要分开记

- **是什么**：KV cache 里有些 token 会被"淘汰"（比如滑动窗口只保留最近 N 个）。旧代码用一个 `swa_evicted_seqlen` 记录淘汰到哪了；新代码用 `component_evicted_seqlens: dict[ComponentType, int]`，每种组件（SWA、Mamba）各记各的。
- **为什么重要**：混合模型里 SWA 和 Mamba 的淘汰策略不同，共用一个游标会导致"以为淘汰了其实没淘汰"或反之，最终表现为输出错乱或内存泄漏。
- **动手试试**：
  ```python
  from dataclasses import dataclass, field
  from enum import Enum

  class ComponentType(Enum):
      SWA = "swa"
      MAMBA = "mamba"

  @dataclass
  class ReqKvInfo:
      component_evicted_seqlens: dict = field(default_factory=dict)

      @property
      def max_evicted_seqlen(self):
          return max(self.component_evicted_seqlens.values(), default=0)

  kv = ReqKvInfo()
  kv.component_evicted_seqlens[ComponentType.SWA] = 128
  kv.component_evicted_seqlens[ComponentType.MAMBA] = 64
  print(kv.max_evicted_seqlen)  # 128
  ```
- **预期结果**：能看到不同组件独立记账，`max_evicted_seqlen` 取最大值用于判断"是否整体释放"。

### 知识点 3：Page-level KV View —— 把 token 级索引翻译成页级索引

- **是什么**：KV cache 按"页"分配（比如每页 64 个 token）。某个 kernel 需要页级视图（每页首地址 + 每页长度），但内存里存的是 token 级索引。这个 commit 写了一个转换函数。
- **为什么重要**：GPU kernel 对内存访问模式很敏感，页级连续访问比 token 级随机访问快得多。不懂这个，你写的 attention kernel 会慢好几倍。
- **动手试试**：
  ```python
  import torch

  def build_paged_kv_view(kv_indices, seq_lens_cpu, page_size):
      seq_lens = seq_lens_cpu.to(torch.int64)
      pages = (seq_lens + page_size - 1) // page_size
      page_indptr = torch.zeros(pages.numel() + 1, dtype=torch.int32)
      page_indptr[1:] = torch.cumsum(pages, dim=0)
      tok_base = torch.zeros(pages.numel() + 1, dtype=torch.int64)
      tok_base[1:] = torch.cumsum(seq_lens, dim=0)
      within = torch.arange(int(page_indptr[-1]), dtype=torch.int64) - \
               torch.repeat_interleave(page_indptr[:-1].to(torch.int64), pages)
      gather = torch.repeat_interleave(tok_base[:-1], pages) + within * page_size
      page_ids = (kv_indices[gather] // page_size).to(torch.int32)
      last_page_len = ((seq_lens - 1) % page_size + 1).to(torch.int32)
      return page_indptr, page_ids, last_page_len

  # 假设 2 个序列，长度 100 和 30，page_size=64
  kv_indices = torch.arange(200)  # 模拟 token 槽位
  seq_lens = torch.tensor([100, 30])
  indptr, ids, last_len = build_paged_kv_view(kv_indices, seq_lens, 64)
  print("page_indptr:", indptr)   # [0, 2, 3]
  print("page_ids:", ids)          # 页号
  print("last_page_len:", last_len)  # [36, 30]
  ```
- **预期结果**：第一个序列占 2 页，第二个占 1 页，最后一页的实际长度正确。

### 知识点 4：符号链接 vs 复制的坑 —— 覆写配置文件不能污染缓存

- **是什么**：模型下载后放在 HF cache 里，overlay 机制用硬链接把文件"挂"到工作目录。但如果某个步骤要改写 `config.json`，通过硬链接写会直接改掉 cache 里的原始 blob。
- **为什么重要**：这是分布式训练/推理里非常隐蔽的 bug——你以为只改了自己的副本，结果把共享缓存改坏了，下一个用户加载模型就报错。
- **动手试试**：
  ```python
  import os, shutil, tempfile

  tmp = tempfile.mkdtemp()
  src = os.path.join(tmp, "config.json")
  with open(src, "w") as f:
      f.write('{"source": true}')

  # 用硬链接
  dst_link = os.path.join(tmp, "linked.json")
  os.link(src, dst_link)
  with open(dst_link, "w") as f:
      f.write('{"source": false}')
  print("源文件被污染:", open(src).read())  # {"source": false} ← 危险！

  # 用复制
  dst_copy = os.path.join(tmp, "copied.json")
  shutil.copy2(src, dst_copy)
  with open(dst_copy, "w") as f:
      f.write('{"source": true}')
  print("源文件安全:", open(src).read())  # {"source": true}
  ```
- **预期结果**：硬链接写会污染源文件，复制不会。sglang 的修复是"小于 64MB 的文件一律复制"。

### 知识点 5：用 `all_gather_single` 替代已废弃的 `all_gather_into_tensor`

- **是什么**：PyTorch 新版把 `dist.all_gather_into_tensor` 改名为 `all_gather_single`，旧名字会有 deprecation warning。
- **为什么重要**：日志里一堆 warning 会淹没真正的错误；而且未来 PyTorch 版本可能直接删掉旧名字，导致代码崩溃。
- **动手试试**：
  ```python
  # 兼容写法：优先用新名字，回退到旧名字
  try:
      from torch.distributed import all_gather_single as _all_gather_single
      from torch.distributed import reduce_scatter_single as _reduce_scatter_single
  except ImportError:
      from torch.distributed import all_gather_into_tensor as _all_gather_single
      from torch.distributed import reduce_scatter_tensor as _reduce_scatter_single

  all_gather_single = _all_gather_single
  reduce_scatter_single = _reduce_scatter_single
  print("使用:", all_gather_single.__name__)
  ```
- **预期结果**：在任意 PyTorch 版本下都能正确导入，且不产生 deprecation warning。

- **对你有什么影响**：使用 DP attention + pooled indexer + breakable CUDA graph 的用户，之前可能遇到 "unexpected top-k shape" 报错，现在修复了。
