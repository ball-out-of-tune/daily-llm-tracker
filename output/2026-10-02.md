## 🧪 重要知识点 & 动手实验

### 知识点 1：投机解码（Speculative Decoding）

- **是什么**：用一个便宜的小模型（draft model）一次猜出 4-8 个 token，然后让大模型（target model）一次性验证这些 token 对不对，对的就接受，错的就回退。因为大模型一次 forward 可以验证多个 token，所以总体速度提升。
- **为什么重要**：这是当前 LLM 推理加速的"标配"技术。不懂它，你就看不懂为什么 vLLM 有 `num_speculative_tokens` 这个参数，也不知道为什么 MTP（Multi-Token Prediction）接受率会"崩"。
- **动手试试**：
  ```bash
  # 用 vLLM 启动一个带投机解码的服务
  vllm serve meta-llama/Llama-3.1-8B-Instruct \
      --speculative-config '{"model": "meta-llama/Llama-3.2-1B-Instruct", "num_speculative_tokens": 5}' \
      --port 8000
  ```
  然后发一个请求，观察输出的 `usage` 里是否有 `spec_decode_stats`。
- **预期结果**：你会看到吞吐量比不开投机解码时高 1.5-2 倍，但如果你把 `num_speculative_tokens` 设得太大（比如 10），接受率反而会下降，速度可能还不如不开。

### 知识点 2：KV Cache 与 PagedAttention

- **是什么**：KV Cache 是 Transformer 推理时缓存的 Key/Value 矩阵。PagedAttention 把 KV Cache 切成固定大小的"页"（block），像操作系统管理内存一样管理它。
- **为什么重要**：不懂 KV Cache，你就无法理解为什么 vLLM 能比 HuggingFace 快 10 倍，也不知道 `block_size`、`gpu_memory_utilization` 这些参数在调什么。
- **动手试试**：
  ```python
  # 跑一个简单的 vLLM 推理，观察 KV Cache 使用情况
  from vllm import LLM, SamplingParams
  llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct", gpu_memory_utilization=0.5)
  outputs = llm.generate(["Hello, my name is"], SamplingParams(max_tokens=50))
  print(outputs[0].outputs[0].text)
  # 启动时日志会打印 "GPU KV cache size: XXX tokens"
  ```
- **预期结果**：你会看到日志里有一行 `GPU KV cache size: 12345 tokens`，这就是你的显卡能同时缓存多少 token 的历史。调大 `gpu_memory_utilization` 这个数字会变大。

### 知识点 3：NCCL 与分布式通信

- **是什么**：NCCL 是 NVIDIA 的集合通信库，负责在多张 GPU 之间同步数据（比如 all-reduce、broadcast）。张量并行（TP）就是靠 NCCL 把每张卡算出的部分结果汇总起来。
- **为什么重要**：不开 NCCL，你就没法做多卡推理。不懂 all-reduce，你就看不懂为什么 batch invariance 会跟通信顺序有关。
- **动手试试**：
  ```python
  # 单机双卡跑一个 all-reduce
  import torch
  import torch.distributed as dist
  dist.init_process_group("nccl", rank=0, world_size=1)
  x = torch.ones(4, device="cuda")
  dist.all_reduce(x)
  print(x)  # tensor([1., 1., 1., 1.])
  ```
  然后试试用 `torchrun --nproc_per_node=2` 跑两个进程。
- **预期结果**：单卡时 all-reduce 就是原值；双卡时如果两个进程都传 `ones(4)`，结果会是 `tensor([2., 2., 2., 2.])`。

### 知识点 4：权重热更新（Weight Transfer）

- **是什么**：推理服务正在跑的时候，把新的模型权重传进去替换旧的，不用重启进程。
- **为什么重要**：RLHF 训练中，policy model 每训练几步就要更新到推理服务里做 rollout。如果每次重启，浪费的时间比训练还长。
- **动手试试**：
  ```python
  # 启动一个 vLLM 实例，开启权重传输
  from vllm import LLM
  llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct", enable_weight_transfer=True)
  # 然后通过 weight_transfer API 推送新权重
  ```
  具体 API 可以参考 `docs/training/weight_transfer/` 下的文档。
- **预期结果**：你会看到推理服务不中断，但模型的输出风格变了（因为权重被替换了）。

### 知识点 5：Transformers 后端迁移

- **是什么**：vLLM 原来为每个模型手写一份实现，现在越来越多直接用 HuggingFace Transformers 的模型定义。
- **为什么重要**：手写实现容易跟 HF 上游不同步，导致 bug。用 HF 后端后，只要 HF 支持新模型，vLLM 基本就能跑。
- **动手试试**：
  ```bash
  # 用 Transformers 后端跑一个模型
  vllm serve zai-org/glm-4-9b-chat-hf --model-impl transformers
  ```
- **预期结果**：模型能正常跑，但可能比 vLLM 原生实现慢一点（因为少了专门的 kernel 优化）。你可以对比 `--model-impl vllm` 和 `--model-impl transformers` 的速度差异。

## 💡 今日关键词

- **关键词：统一内存池 (unified-memory / page-major KV layout)**
  - **一句话解释**：把原来按层分开存放的 KV cache / Mamba state 合并到一个大 buffer 里，按 token 槽位统一排布，让显存可以在 KV 和 state 之间动态伸缩。
  - **为什么社区在关注**：今天 7 个 commit（#40326~#40331 系列）都在围绕这个特性做重构，说明 SGLang 正在把"混合模型（Mamba+Attention）显存利用率低"这个痛点系统性地解决。这类重构通常意味着一个新特性即将成熟。
  - **对新手意味着什么**：如果你在学推理引擎，这是理解"KV cache 布局"和"内存池设计"的绝佳案例——从 shape 推导地址改成 stride 推导地址，是高性能 kernel 的通用套路。

- **关键词：MXFP4 / NVFP4 低精度量化**
  - **一句话解释**：用 4 bit 表示模型权重和激活，显存占用降到原来的 1/4 左右，但对 kernel 支持有严格要求。
  - **为什么社区在关注**：今天有 3 个 commit 涉及 FP4（MiMo-V2 SM100/SM90 修复、MegaMoE W13 布局、GLM-5.3-Flash MXFP4 on AMD），说明 FP4 已经从"能跑"进入"跑得对、跑得快"的精细化阶段。
  - **对新手意味着什么**：量化不再是"调个参数"，而是要对每种量化格式的 kernel 兼容性、权重布局（W13 vs W31）有深入理解——这是当前非常吃香的技能。

- **关键词：AMD ROCm 适配**
  - **一句话解释**：让 SGLang 在 AMD Instinct GPU（MI300X/MI355X）上也能高效推理。
  - **为什么社区在关注**：今天有 3 个 commit 专门针对 ROCm（MLA 融合 kernel、MoE router、GLM-5.3-Flash on gfx950），说明 AMD 生态正在被认真对待，不再是"能跑就行"。
  - **对新手意味着什么**：异构计算（NVIDIA + AMD + TPU + NPU）是确定性趋势，掌握 CUDA 之外还能看懂 Triton/ROCm 代码，会显著增加你的竞争力。

- **关键词：投机解码 (Speculative Decoding / EAGLE / NEXTN)**

- **关键词：Triton kernel 的 int32 溢出**
  - **一句话解释**：当张量元素数超过 2^31（约 21 亿）时，用 32 位整数算地址会溢出，导致读写错位置。

## 🧪 重要知识点 & 动手实验

- **知识点 1：KV Cache 的 stride vs shape——为什么布局重构这么重要**
  - **是什么**：一个张量除了 shape（形状）还有 stride（每一步跨多少元素）。传统代码用 `view(-1, page_size, heads, dim)` 假设内存是连续排布的；新的统一内存池里，每层的数据是"交错"排布的，必须用 stride 来定位。
  - **为什么重要**：如果你写 kernel 时假设 `tensor.view()` 一定成功，在统一内存池或 page-major 布局下会直接崩溃或读到错误数据。Commit #40326 就是把这些 `view()` 全部改成 stride-aware 的 `paged_view()`。
  - **动手试试**：
    ```python
    import torch
    # 连续的 2x3 张量
    a = torch.arange(6).reshape(2, 3)
    print("contiguous:", a.stride())  # (3, 1)
    print(a.view(-1))  # 可以

    # 切片后不再是连续的
    b = a[:, ::2]  # 取第 0、2 列
    print("sliced:", b.stride())  # (3, 2)，注意 stride 变了
    try:
        b.view(-1)  # 会报错
    except RuntimeError as e:
        print("view 失败:", e)
    print("reshape 可以:", b.reshape(-1))  # reshape 会拷贝
    ```
  - **预期结果**：你会看到 `view()` 要求内存连续，而切片后的张量 stride 变了，`view()` 报错。理解这一点，你就明白为什么 SGLang 要引入 `paged_view` 这样的辅助函数。

- **知识点 2：Triton kernel 中的 int32 溢出**
  - **是什么**：Triton 默认用 int32 算索引。当张量元素数超过 `2^31 ≈ 21.4 亿` 时，`pid * stride` 这类计算会溢出成负数，导致读写错位。
  - **为什么重要**：长序列（几十万 token）+ 多头 attention 很容易突破这个界限。Commit #41965 就是把这个 bug 修了，并加了 48GB 显存的回归测试。
  - **动手试试**：
    ```python
    import numpy as np
    # 模拟 int32 溢出
    n = 2**31 + 10
    print("int32 结果:", np.int32(n))          # 溢出成负数
    print("int64 结果:", np.int64(n))          # 正确

    # 一个 491520 x 56 x 128 的 bf16 张量有多少元素？
    shape = (1, 491_520, 56, 128)
    total = int(np.prod(shape))
    print("元素总数:", total, "> 2^31?", total > 2**31)
    ```
  - **预期结果**：你会看到 int32 溢出成负数，而元素总数确实超过 2^31。以后写 kernel 时，遇到大张量记得 `.to(tl.int64)`。

- **知识点 3：MoE 权重布局——W13 vs W31**
  - **是什么**：MoE 层每个 expert 有两个矩阵：gate/up 投影（w1、w3）和 down 投影（w2）。FlashInfer 等后端要求 w1 和 w3 交错成 `[gate, up]` 顺序（即 W13），而有些后端要求 `[up, gate]`（W31）。
  - **为什么重要**：Commit #39388 就是修复 MegaMoE 在 NVFP4 下错误地把权重按 FlashInfer 布局重排，导致精度问题。布局搞错不会报错，只会静默地算错结果。
  - **动手试试**：
    ```python
    import torch
    # 假设 2 个 expert，每个 expert 的 w1 和 w3 各 4x4
    w1 = torch.arange(16).reshape(2, 4, 4)
    w3 = torch.arange(100, 116).reshape(2, 4, 4)

    # W13 布局：沿 dim=1 拼接 [w1; w3]
    w13 = torch.cat([w1, w3], dim=1)
    print("W13 shape:", w13.shape)  # (2, 8, 4)

    # 如果错误地按 W31 拼接
    w31 = torch.cat([w3, w1], dim=1)
    print("W13 和 W31 相同吗?", torch.equal(w13, w31))  # False
    ```
  - **预期结果**：你会看到两种布局数值完全不同。这解释了为什么 commit 要显式区分 `use_flashinfer_trtllm_weight_layout`。

- **知识点 4：投机解码中的 draft-verify 流程**
  - **是什么**：先用小模型（draft）快速生成 N 个候选 token，再用大模型（target）一次前向验证这 N 个 token，接受匹配的前缀。Commit #41175 把"验证"和"下一轮 draft 输入准备"融合进一个 kernel。
  - **为什么重要**：这是推理加速的核心技术。draft 和 verify 之间的数据传递如果处理不好，会成为性能瓶颈。
  - **动手试试**：
    ```python
    # 概念模拟：draft 猜 4 个 token，target 验证
    draft_tokens = [100, 200, 300, 400]
    target_tokens = [100, 200, 999, 400]  # 第 3 个位置不一致

    accept_len = 0
    for d, t in zip(draft_tokens, target_tokens):
        if d == t:
            accept_len += 1
        else:
            break
    print(f"接受了 {accept_len} 个 token")
    # 实际中还会接受 target 的第 accept_len 个 token 作为 bonus
    ```
  - **预期结果**：你会看到只接受了前 2 个。真实系统中，target 会额外输出一个"bonus token"，所以一轮能推进 `accept_len + 1` 个 token。

- **知识点 5：量化配置的"混合"陷阱**
  - **是什么**：一个模型的 config 里可能同时声明 `quant_method=fp8` 和 FP4 experts（比如 MiMo-V2 的混合 checkpoint）。只看 `quant_method` 会选错 runner。
  - **为什么重要**：Commit #41668 和 #42172 就是修复这个问题——SM100 上选 `flashinfer_mxfp4`，SM90 上选 `marlin`。选错 runner 会导致 kernel 读不了 packed MXFP4，直接报错或精度崩坏。
  - **动手试试**：
    ```python
    # 模拟配置检查逻辑
    def pick_runner(platform, quant_method, is_fp4_experts, a2a_backend):
        if platform == "sm100" and quant_method == "fp8":
            if is_fp4_experts:
                return "flashinfer_mxfp4" if a2a_backend == "none" else "auto"
            return "flashinfer_trtllm"
        if platform == "sm90" and is_fp4_experts:
            return "marlin"
        return "auto"

    print(pick_runner("sm100", "fp8", True, "none"))   # flashinfer_mxfp4
    print(pick_runner("sm90", "fp8", True, "none"))    # marlin
    print(pick_runner("sm100", "fp8", False, "none"))  # flashinfer_trtllm
    ```
  - **预期结果**：你会看到同一个 `quant_method=fp8` 的模型，根据 `is_fp4_experts` 和平台，选中完全不同的 runner。这就是为什么"看 config 选后端"不能只看一个字段。
