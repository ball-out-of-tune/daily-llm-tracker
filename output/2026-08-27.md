### 知识点 1：KV Cache 与 Padding
- **是什么**：KV Cache 是推理时存储已计算 Key/Value 张量的显存区域，有时候需要 padding（填充）对齐到固定大小，就像给一排座位加空椅子让队伍整齐。
- **为什么重要**：如果 padding 没处理好，会导致显存浪费、越界访问甚至崩溃。今天 Commit 3 就是修 GPU cache 存储尾部 padding 导致的 bug。

### 知识点 2：Sparse NCCL 权重同步
- **是什么**：训练好的模型权重通过 NCCL 广播给推理引擎，sparse 模式只传输"变化的部分"（delta），而不是全量参数。
- **为什么重要**：大模型动辄几十 GB，全量同步太慢。稀疏同步只传改变的部分，大幅降低通信开销，让训练和推理可以实时协作。
- **动手试试**：
```python
# 模拟创建稀疏补丁并发送（伪代码，展示核心 API）
from vllm.distributed.weight_transfer.sparse_nccl_engine import SparseWeightPatch

patch = SparseWeightPatch(
    name="model.layers.0.self_attn.q_proj.weight",
    full_shape=[4096, 4096],
    flat_indices=[0, 1, 2],  # 只更新前 3 个元素
    values=[0.1, 0.2, 0.3],
)
print(f"补丁大小: {len(patch.values)} 个元素，而不是 4096*4096 个")
```
- **预期结果**：你会看到补丁只包含 3 个值，对比全量 1600 万个值，理解稀疏更新的效率。

### 知识点 3：CUDA Graph 内存释放
- **是什么**：CUDA Graph 把一串 GPU 操作"录制成视频"然后快速重放，提升性能。但录制时占用的临时显存必须在分配 KV Cache 前释放。
- **为什么重要**：如果不释放，会导致显存不足（OOM），服务启动失败。今天 Commit 16 就是修这个顺序问题。

### 知识点 4：多模态 Padding 对齐
- **是什么**：SigLIP 这类模型训练时文本必须 padding 到固定长度，否则文本和图像的嵌入向量无法对齐。
- **为什么重要**：如果忘记 padding，得到的文本嵌入是错误的，导致检索、分类等下游任务结果完全不对。
- **动手试试**：
```python

tokenizer = AutoTokenizer.from_pretrained("google/siglip-so400m-patch14-384")

text = "Hello"
unpadded = tokenizer(text)["input_ids"]
padded = tokenizer(text, padding="max_length", max_length=64)["input_ids"]

print(f"未 padding: {len(unpadded)} tokens → {unpadded}")
print(f"padding 后: {len(padded)} tokens → 前几个值 {padded[:5]}")
```
- **预期结果**：你会看到 unpadded 只有几个 token，而 padded 变成了 64 个 token（后面全是填充符）。这解释了为什么 Commit 1 要求 padding。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 内存分配与越界问题（Commit 1）
- **是什么**：KV cache 是 LLM 推理中缓存历史 token 的 Key 和 Value 向量的内存区域。当可用内存页不足时，分配逻辑可能出错，导致越界读取（Out of Bounds）。
- **为什么重要**：KV cache 分配是推理服务稳定性的关键。如果分配逻辑有 bug，可能导致服务崩溃或返回错误结果。理解 KV cache 的分配策略有助于诊断推理服务的性能瓶颈和稳定性问题。
- **动手试试**：
  ```bash
  # 查看你的 GPU 显存大小
  nvidia-smi
  # 启动一个 SGLang 服务，设置较小的 KV cache 内存比例，模拟内存紧张场景
  python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct --mem-fraction-static 0.1
  # 发送多个并发请求，观察是否会触发内存分配问题
  python -m sglang.bench_serving --backend sglang --num-prompts 100 --request-rate 50
  ```
- **预期结果**：如果内存分配逻辑正确，服务应该能正常处理请求，即使内存紧张也不会崩溃。如果出现越界错误，你会看到类似 `IndexError` 或 `CUDA error` 的报错。

### 知识点 2：进程管理与资源清理（Commit 8）
- **是什么**：`kill_process_tree` 函数用于终止一个进程及其所有子进程。修改后默认会等待子进程被完全回收（reap），避免资源泄漏。
- **为什么重要**：在分布式推理中，服务可能启动多个子进程（如调度器、worker 等）。如果进程清理不彻底，GPU 显存、端口等资源会一直被占用，导致后续服务启动失败。理解进程管理是运维推理服务的基本功。
- **动手试试**：
  ```python
  import multiprocessing
  import time
  import os
  from sglang.srt.utils import kill_process_tree

  def child_process():
      print(f"Child PID: {os.getpid()}")
      time.sleep(10)

  if __name__ == "__main__":
      p = multiprocessing.Process(target=child_process)
      p.start()
      time.sleep(1)
      print(f"Parent PID: {os.getpid()}")
      # 使用默认参数（wait_timeout=60），会等待子进程被回收
      kill_process_tree(p.pid)
      print("Process tree killed and reaped")
  ```
- **预期结果**：你会看到子进程被终止，并且 `kill_process_tree` 函数会等待子进程完全退出后才返回。

### 知识点 3：投机解码（Speculative Decoding）与 MTP（Commit 10, 13）
- **是什么**：投机解码是一种加速 LLM 生成的技术，用一个小的 draft 模型快速生成多个候选 token，再用大模型一次性验证。MTP（Multi-Token Prediction）是其中一种实现方式。
- **为什么重要**：投机解码可以显著提升推理吞吐量（2-3 倍），但配置复杂，需要根据硬件和模型调整参数。理解投机解码有助于优化推理服务的性能。
- **动手试试**：
  ```bash

    --speculative-algorithm EAGLE \
    --speculative-num-steps 3 \
  ```

- **预期结果**：开启投机解码后，你会看到吞吐量（output token/s）显著提升，但首 token 延迟可能会略有增加。

### 知识点 4：多模态处理与并发（Commit 12）

- **是什么**：CUDA Graph 是一种把一系列 GPU 操作预编译成图然后重复执行的技术，可以大幅减少 kernel 启动开销。这个 commit 优化了 speculative adaptive 场景下 CUDA graph 的内存占用。
- **为什么重要**：CUDA Graph 是提升推理性能的关键技术，但内存占用可能很大。理解 CUDA Graph 的工作原理和优化方法有助于开发高性能推理服务。
