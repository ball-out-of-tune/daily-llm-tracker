## 🧪 重要知识点 & 动手实验

### 知识点 1：投机解码（Speculative Decoding）中的 MTP 与 KV Cache 分组

- **是什么**：MTP（Multi-Token Prediction）是一种让模型一次预测多个 token 的技术，配合投机解码可以加速生成。每个 draft 模型需要自己的 KV cache，vLLM 需要正确地把这些 KV cache "分组"管理。
- **为什么重要**：如果 KV cache 分组错了，draft 模型会读到错误的缓存，导致生成结果乱码或性能暴跌。Commit 17 修的就是这个 bug——在混合模型（如 Qwen3.5 的 GDN + full attention）路径下，MTP draft 的 KV cache 组没被正确标记。
- **动手试试**：
  ```bash
  # 用 Qwen3.5 模型测试 MTP 投机解码
  python -m vllm.entrypoints.openai.api_server \
      --model Qwen/Qwen3.5-0.8B \
      --speculative-config '{"method": "mtp", "num_speculative_tokens": 1}' \
      --enforce-eager
  ```
  然后发一个请求：
  ```bash
  curl http://localhost:8000/v1/completions \
      -H "Content-Type: application/json" \
      -d '{"model": "Qwen/Qwen3.5-0.8B", "prompt": "The capital of France is", "max_tokens": 20}'
  ```
- **预期结果**：正常返回补全结果，且日志中能看到 `spec_decode` 相关统计（接受的 draft token 数）。如果 KV cache 分组错误，会看到输出乱码或启动失败。

### 知识点 2：Sleep Mode 与参数保留（RLHF 场景）

- **是什么**：vLLM 的 sleep mode 允许在推理空闲时把权重和 KV cache 从 GPU 显存释放到 CPU 内存。Level-2 sleep 会释放权重，今天新增的 `sleep_preserve_parameter_names` 允许你指定哪些参数"冻结"不释放。
- **为什么重要**：在 RLHF 训练中，reference model 的权重是冻结的，不需要每次 wake up 都重新加载。保留这些权重能显著加快训练-推理切换速度。
- **动手试试**：
  ```python
  from vllm import LLM
  
  llm = LLM(
      model="Qwen/Qwen2.5-0.5B",
      enable_sleep_mode=True,
      sleep_preserve_parameter_names=["model.embed_tokens.*"],  # 保留 embedding
  )
  
  # 先跑一次推理
  llm.generate(["Hello"])
  
  # 进入 level-2 sleep（释放权重）
  llm.sleep(level=2)
  
  # 唤醒权重（保留的参数不会重新加载）
  llm.wake_up(tags=["weights"])
  
  # 再跑一次推理验证
  llm.generate(["Hello again"])
  ```
- **预期结果**：第二次推理结果正常，且唤醒速度比不保留参数时更快。可以对比 `sleep_preserve_parameter_names=[]` 的耗时。

### 知识点 3：调度器的 long_prefill_token_threshold 行为

- **是什么**：当一个 prompt 很长时，调度器可以把它切成多个 chunk 分批处理（chunked prefill），避免阻塞其他请求。`long_prefill_token_threshold` 控制这个切分的阈值。
- **为什么重要**：如果只有一个长请求，切分反而增加开销；如果有多个请求，切分能改善公平性。Commit 19 让调度器更聪明——只有存在其他请求时才应用阈值。
- **动手试试**：
  ```python
  from vllm import LLM, SamplingParams
  
  llm = LLM(
      model="Qwen/Qwen2.5-0.5B",
      max_num_batched_tokens=1024,
      long_prefill_token_threshold=400,
  )
  
  # 单个长请求：应该一次性调度 1024 个 token
  long_prompt = "Hello " * 2000
  out = llm.generate([long_prompt], SamplingParams(max_tokens=10))
  print("Single request OK")
  
  # 长请求 + 短请求：长请求应该被限制在 400 token
  out = llm.generate([long_prompt, "Hi"], SamplingParams(max_tokens=10))
  print("Mixed requests OK")
  ```
- **预期结果**：两种情况都能正常生成。可以通过开启 `VLLM_LOGGING_LEVEL=DEBUG` 查看调度日志，观察 `num_scheduled_tokens` 的差异。

### 知识点 4：Rust 前端的工具调用语法（Structural Tag）

- **是什么**：结构化输出（structured output）通过语法约束让模型输出符合特定格式（如 JSON）。Rust 前端新增了 `parallel_tool_calls` 支持，让工具调用的语法能正确反映"是否允许并行调用"。
- **为什么重要**：工具调用（Function Calling）是 Agent 应用的基础。如果语法约束不尊重 `parallel_tool_calls=False`，模型可能一次输出多个工具调用，导致下游解析失败。
- **动手试试**：
  ```bash

  ./target/release/vllm-rs serve --model Qwen/Qwen2.5-0.5B &

      -H "Content-Type: application/json" \
      -d '{
          "model": "Qwen/Qwen2.5-0.5B",
          "messages": [{"role": "user", "content": "What is the weather in Paris?"}],
          "tools": [{"type": "function", "function": {"name": "get_weather", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}}}}],
          "parallel_tool_calls": false
      }'
  ```
- **预期结果**：模型最多输出一个工具调用。如果把 `parallel_tool_calls` 改成 `true`，可能输出多个。

### 知识点 5：DFlash 投机解码的 profiling batch 上限

- **是什么**：DFlash/DSpark 是一种投机解码方法，在 profiling 阶段（测量显存和性能）需要跑一个 dummy batch。如果 batch 太大，会浪费显存甚至 OOM。

## 🧪 重要知识点 & 动手实验

- **知识点 1：KDA 线性注意力中的 beta sigmoid**
  - **是什么**：KDA（Kimi Delta Attention）里有个 `beta` 参数，模型输出的是"原始 logits"，需要先过 sigmoid 变成 0~1 的门控值再喂给内核。PTX 内核之前漏了这一步，导致数值错误。
  - **为什么重要**：内核和 PyTorch 参考实现"看起来一样"但结果不同，是深度学习工程里最阴险的 bug。不懂 `use_beta_sigmoid_in_kernel` 这类开关，你会花几天 debug 却发现是"签名对不上"。
  - **动手试试**：
    ```python
    import torch
    beta_raw = torch.tensor([-2.0, 0.0, 2.0])
    print("raw:", beta_raw)
    print("sigmoid:", torch.sigmoid(beta_raw))
    # 内核里如果不做 sigmoid，直接用 raw，会得到负数/超过1的门控
    ```
  - **预期结果**：看到 sigmoid 后值域压缩到 (0,1)，理解为什么"忘了 sigmoid"会导致状态更新方向反了。

- **知识点 2：CUDA Graph 与"流爆炸"**
  - **是什么**：CUDA Graph 把一串 GPU 操作录制成"图"，之后一键重放，省去 CPU 启动开销。但如果每条流都单独建图，会创建成千上万个流，把驱动搞崩。
  - **为什么重要**：投机解码的 draft 模型每步形状不同，最容易触发这个问题。不懂 CUDA Graph 的捕获边界，你的服务会在高并发下莫名 OOM 或崩溃。
  - **动手试试**：
    ```python
    import torch
    # 演示：同一个 stream 上重复 capture 会报错
    g = torch.cuda.CUDAGraph()
    s = torch.cuda.Stream()
    with torch.cuda.stream(s):
        x = torch.randn(4, device="cuda")
        y = x * 2
    with torch.cuda.graph(g, stream=s):
        y = x * 2
    g.replay()
    print("graph replay ok:", y)
    ```
  - **预期结果**：理解 graph 必须绑定固定 stream 和固定形状；看 commit #40658 里为什么把 `is_hip()` 判断去掉就能修好流爆炸。

- **知识点 3：量化中的 `exclude_modules`（排除清单）**
  - **是什么**：量化配置里可以列出"这些层不量化，保持 BF16"。但如果排除清单只写了单专家名（`experts.0.down_proj`），而代码里已经把专家融合成 `experts`，就会误量化，加载时维度对不上。
  - **为什么重要**：这是量化模型部署最常见的"加载失败"原因。不懂融合命名规则，你会以为模型文件坏了。
  - **动手试试**：
    ```python
    # 模拟 commit #39317 的修复逻辑
    def should_ignore(layer_name, ignore_list):
        if layer_name in ignore_list:
            return True
        if layer_name.endswith(".experts"):
            prefix = layer_name + "."
            return any(t.startswith(prefix) for t in ignore_list)
        return False

    ignore = ["model.layers.6.mlp.experts.0.down_proj"]
    print(should_ignore("model.layers.6.mlp.experts", ignore))  # True
    print(should_ignore("model.layers.7.mlp.experts", ignore))  # False
    ```
  - **预期结果**：看到前缀匹配的精确性——`experts.` 不会误伤 `experts2`，也不会漏掉融合模块。

- **知识点 4：客户端断连时的引擎 Abort**
  - **是什么**：用户关掉网页后，HTTP 连接断开，但服务端还在傻傻地跑推理。Rust router 现在会在连接断开时，主动 POST `/abort_request` 给后端引擎。
  - **为什么重要**：不做这个，GPU 会浪费在"没人要的结果"上，高并发时吞吐直接腰斩。
  - **动手试试**：
    ```bash
    # 启动一个 sglang server，然后发请求后立刻 Ctrl+C
    # 观察日志里是否出现 abort 相关记录
    curl -N http://localhost:30000/v1/chat/completions \
      -H "Content-Type: application/json" \
      -d '{"model":"...","messages":[{"role":"user","content":"写一篇一万字小说"}],"stream":true}'
    # 按 Ctrl+C 中断，看 server 端日志
    ```
  - **预期结果**：看到 server 日志中请求被标记为 aborted，GPU 利用率立刻下降。

- **知识点 5：PD 分离下的 DCP KV 打包**
  - **是什么**：PD（Prefill/Decode）分离时，KV 缓存要从 prefill 节点传到 decode 节点。DCP（Decode Context Parallel）会把 KV 按 head 切片，传输时需要把"切片"重新打包成连续内存。
  - **为什么重要**：不做打包，每个 head slice 单独发一次 RDMA，延迟爆炸；打包后一次传完。
  - **动手试试**：
    ```python
    import torch
    # 模拟：3 个 head slice，每个 4 行，每行 8 字节
    slices = [torch.arange(4*8, dtype=torch.uint8) + i*100 for i in range(3)]
    pack = torch.empty(3*4*8, dtype=torch.uint8)
    offset = 0
    for s in slices:
        pack[offset:offset+s.numel()] = s.flatten()
        offset += s.numel()
    print("packed shape:", pack.shape)
    ```
  - **预期结果**：理解 commit #40500 里 `src_row_stride` 为什么要单独传——因为源切片可能不是紧密排列的。
