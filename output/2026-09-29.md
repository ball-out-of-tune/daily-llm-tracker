## 🧪 重要知识点 & 动手实验

- **知识点 1：JSON Schema 的 `$defs` 与 `$ref` 引用（结构化输出）**
  - **是什么**：JSON Schema 允许你先定义可复用的"零件"（放在 `$defs` 里），然后用 `$ref` 引用它们。就像写代码时先定义函数，再在别处调用。
  - **为什么重要**：模型输出工具调用参数时，如果 schema 里有嵌套引用，解析器必须把 `$defs` "提升"（hoist）到能被正确解析的位置。commit 1 修的就是这个——不修的话，带嵌套定义的 Cohere 工具调用会直接报错。
  - **动手试试**：
    ```python
    import json
    schema = {
        "$defs": {
            "Location": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            }
        },
        "type": "object",
        "properties": {"location": {"$ref": "#/$defs/Location"}},
        "required": ["location"],
    }
    print(json.dumps(schema, indent=2))
    # 试着把 $defs 提到顶层，观察 $ref 路径如何变化
    ```
  - **预期结果**：你会看到 `$ref` 的路径是 `#/$defs/Location`。理解这个路径规则后，你就能看懂 commit 1 里 `collect_tool_schema` 为什么要做"提升"。

- **知识点 2：多模态预处理的 CPU vs GPU 归一化**
  - **是什么**：图像送进模型前要做 `(pixel - mean) / std` 归一化。传统做法在 CPU 上做，vLLM 现在支持在 GPU 上做（`mm_device_do_normalize`）。
  - **为什么重要**：CPU 归一化会产生大量数据搬运（CPU→GPU），成为瓶颈。GPU 端归一化省掉这次搬运，吞吐量能提升明显。commit 17 还专门去掉了"回退到 processor 对象"的逻辑，让参数解析更可靠。
  - **动手试试**：
    ```python
    import torch
    # 模拟 CPU 归一化
    img_cpu = torch.rand(3, 224, 224)
    mean = torch.tensor([0.481, 0.458, 0.408]).view(3, 1, 1)
    std = torch.tensor([0.269, 0.261, 0.276]).view(3, 1, 1)
    out_cpu = (img_cpu - mean) / std

    # 模拟 GPU 归一化
    if torch.cuda.is_available():
        img_gpu = img_cpu.cuda()
        out_gpu = (img_gpu - mean.cuda()) / std.cuda()
        print("max diff:", (out_cpu - out_gpu.cpu()).abs().max().item())
    ```
  - **预期结果**：`max diff` 接近 0，说明两种方式数学等价。但 GPU 版省掉了把 `img_cpu` 搬上 GPU 的那一步。

- **知识点 3：FlashInfer 的 CUDA toolkit 检测**
  - **是什么**：FlashInfer 是一个高性能注意力库，它运行时会 JIT 编译，需要找到 `nvcc`（CUDA 编译器）和 `ninja`（构建工具）。commit 13 让 vLLM 的 `has_flashinfer()` 用和 FlashInfer 一样的方式找这些工具。
  - **为什么重要**：如果检测方式和实际使用方式不一致，会出现"vLLM 以为 FlashInfer 可用，但实际 JIT 失败"的情况，导致运行时崩溃。这是个典型的"环境检测陷阱"。
  - **动手试试**：
    ```bash
    # 看看你的环境里 nvcc 和 ninja 在哪
    which nvcc || echo "nvcc not on PATH"
    which ninja || echo "ninja not on PATH"
    ls /usr/local/cuda/bin/nvcc 2>/dev/null || echo "no /usr/local/cuda"
    ```
  - **预期结果**：你会发现 `nvcc` 常常不在 PATH 上（尤其在容器里），而在 `/usr/local/cuda/bin/`。这就是 commit 13 要处理的情况。

- **知识点 4：进程组超时（分布式容错）**
  - **是什么**：分布式训练/推理时，多个进程通过 process group 通信。如果某个进程挂了，其他进程不能无限等待，需要设置超时。commit 20 修的是"容错场景下超时没被正确传递"。
  - **为什么重要**：没有超时，一个进程卡死会让整个集群 hang 住，浪费大量 GPU 时间。超时配置必须从高层配置（`ParallelConfig`）一路传到低层（`init_gloo_process_group`）。
  - **动手试试**：
    ```python
    from datetime import timedelta
    # 模拟配置传递
    class ParallelConfig:
        cpu_distributed_timeout_seconds = 30
        @property
        def cpu_distributed_timeout(self):
            return timedelta(seconds=self.cpu_distributed_timeout_seconds)

    cfg = ParallelConfig()
    print(cfg.cpu_distributed_timeout)  # 0:00:30
    ```
  - **预期结果**：你会看到超时被转换成 `timedelta`。理解这个模式后，就能看懂为什么 commit 20 要在 `stateless_init_dp_group` 里显式传 `timeout`。

- **知识点 5：torch.compile 的 STOCK_TORCH_COMPILE 模式**
  - **是什么**：PyTorch 2.x 的 `torch.compile` 能把模型编译成更快的计算图。vLLM 原来有自己的编译模式，commit 19 增加了"原生 torch.compile 模式"（STOCK）。
  - **为什么重要**：原生模式让 vLLM 能直接受益于 PyTorch 上游的编译优化，不用自己维护一套。但需要处理 V1/V2 model runner 的兼容性（commit 19 加了 `use_v2_model_runner` 参数化测试）。
  - **动手试试**：
    ```python
    import torch

    @torch.compile
    def f(x):
        return x.sin().cos()

    x = torch.randn(1000, device="cuda" if torch.cuda.is_available() else "cpu")
    print(f(x)[:3])
    ```
  - **预期结果**：第一次调用会慢（编译），之后会快。这就是 `torch.compile` 的"先编译后执行"模式。

## 🧪 重要知识点 & 动手实验

### 知识点 1：条件缓存（Conditioning Cache）——扩散模型跨请求复用

- **是什么**：扩散模型在生成前需要把 prompt 和参考图编码成条件向量（text embedding、vision feature、VAE posterior）。如果多个请求用同样的输入，可以直接复用这些编码结果，跳过编码器前向。
- **为什么重要**：多轮图像编辑、批量生成变体时，编码阶段可能占到 30%+ 的端到端时间。不缓存就会白白重复计算；缓存键设计错了（比如只用文件路径）会读到过期数据。
- **动手试试**：
  ```bash
  # 启动 Qwen-Image 2.1 服务，开启默认条件缓存
  sglang serve --model-path Qwen/Qwen-Image-2.1 \
      --conditioning-cache-max-size-mb 1024

  # 连续发两次相同 prompt 的请求，观察第二次的延迟
  curl -X POST http://localhost:30000/generate \
      -H 'Content-Type: application/json' \
      -d '{"prompt": "a cat on a mat", "num_inference_steps": 20}'
  ```
  再对比用 `--disable-conditioning-cache` 启动时的第二次延迟。
- **预期结果**：开启缓存时，第二次相同请求的编码阶段耗时明显下降（尤其 encoder 被 layerwise offload 时）；关闭缓存时两次延迟几乎相同。你会看到日志里出现 cache hit 相关字段。

### 知识点 2：W4A16 量化与 int4pack——为什么 4bit 权重能跑得动

- **是什么**：W4A16 指权重 4bit、激活 16bit。int4 每两个值打包进一个 uint8，再通过 `_convert_weight_to_int4pack` 转成硬件友好的布局。compressed-tensors 的 uint4b8 格式把每个 int4 值加 8 偏置，所以反量化时要减 8（代码里 `_UINT4B8_ZERO_POINT = 8`）。
- **为什么重要**：4bit 量化能把显存占用降到 1/4，是本地部署大模型的关键。但 unpack/pack 顺序、group_size、zero-point 处理错一个，输出就会全乱。
- **动手试试**：
  ```python
  import torch
  # 模拟 compressed-tensors 的 uint4b8 打包
  codes = torch.randint(0, 16, (4, 8), dtype=torch.uint8)  # 每行 8 个 int4
  # 两个 int4 打包成一个 uint8：低 4 位 + 高 4 位
  packed = (codes[:, 0::2] & 0xF) | ((codes[:, 1::2] & 0xF) << 4)
  print("packed shape:", packed.shape)  # [4, 4]

  # 反解
  low = packed & 0xF
  high = (packed >> 4) & 0xF
  print("roundtrip ok:", torch.equal(low, codes[:, 0::2]) and torch.equal(high, codes[:, 1::2]))
  ```
- **预期结果**：打印 `roundtrip ok: True`。你就理解了 int4pack 的本质就是位运算，以及为什么 zero-point 要单独存。

### 知识点 3：PCIe-IPC all-reduce——没有 NVLink 时怎么做集合通信

- **是什么**：在没有 NVLink、没有多播的机器上，GPU 之间只能走 PCIe 根复合体。朴素的 all-to-all 写入会互相打爆带宽。FlashInfer 的 PCIe-IPC 内核用"staging"让每个 rank 同时只有一个出站和一个入站流。
- **为什么重要**：8 卡 SM120 主机上，decode 阶段的 all-reduce 是 TPOT 的瓶颈。用 NCCL 会慢 30 倍以上。
- **动手试试**：
  ```bash
  # 检查你的机器有没有 NVLink
  nvidia-smi topo -m
  # 如果看到 PIX/PXB 而不是 NV#，说明走 PCIe

  # 开启 PCIe-IPC all-reduce（仅 SM120 无 NVLink 主机）
  export SGLANG_ENABLE_PCIE_IPC_ALLREDUCE=1
  export SGLANG_PCIE_IPC_MAX_NUMEL=0   # 自动从 decode batch 推导

  # 启动一个 TP=8 的服务，观察 TPOT
  sglang serve --model-path Qwen/Qwen3-8B --tp 8
  ```
- **预期结果**：decode 阶段 TPOT 明显下降（commit 里实测从 21.14ms 降到 13.62ms）。注意：prefill 阶段不要用这个 workspace，否则 TTFT 会退化。

### 知识点 4：层边界契约（Layer Boundary Contract）——理解 SGLang 新架构

- **是什么**：每个 decoder layer 被拆成"注意力阶段"和"FFN 阶段"，两者之间有一个"边界"，负责把残差流、行布局、all-reduce 融合等状态正确传递。`StageDecl` 描述一个阶段的输入/输出，`EdgeDecl` 描述两个阶段之间的契约。
- **为什么重要**：不懂边界契约，你就看不懂为什么 `--boundary-reduction` 能同时影响 dense 和 MoE FFN，也看不懂 TBO（two-batch overlap）为什么能拆分残差流。
- **动手试试**：
  ```bash
  # 读官方新文档
  open docs/docs/developer_guide/layer_boundary.mdx

  # 跑边界相关的单元测试，看它怎么验证契约
  python -m pytest test/registered/unit/layer_boundary/test_boundary_output_contracts.py -v
  ```
- **预期结果**：测试全部通过。你会看到测试如何构造 `DecoderLayerSides`、调用 `decoder_layer_edges`、断言 `EdgeDecl` 的字段。这就是"契约即测试"的范本。

### 知识点 5：PD 分离的失败快速失败（Fail Fast）——ctypes 调用 ibverbs

- **是什么**：PD 分离测试里，如果 RDMA 设备在 sysfs 里存在，但 ibverbs 打不开（比如容器里 `/dev/infiniband` 没挂载），传输后端会静默回退到 TCP，压测时才崩。新代码用 `ctypes` 直接调 `libibverbs.so.1` 检测。
- **为什么重要**：分布式系统的静默降级是最危险的 bug。学会在 setup 阶段主动探测依赖，能省掉几小时的 debug。
- **动手试试**：
  ```python
  import ctypes
  lib = ctypes.CDLL("libibverbs.so.1")
  lib.ibv_get_device_list.restype = ctypes.POINTER(ctypes.c_void_p)
  lib.ibv_get_device_list.argtypes = [ctypes.POINTER(ctypes.c_int)]
  lib.ibv_get_device_name.restype = ctypes.c_char_p
  lib.ibv_get_device_name.argtypes = [ctypes.c_void_p]

  num = ctypes.c_int(0)
  devices = lib.ibv_get_device_list(ctypes.byref(num))
  if not devices:
      print("ibverbs 打不开任何设备")
  else:
      names = [lib.ibv_get_device_name(devices[i]).decode() for i in range(num.value)]
      print("可用 RDMA 设备:", names)
  ```
- **预期结果**：在有 RDMA 的机器上打印设备名（如 `mlx5_0`）；在容器里没挂载 `/dev/infiniband` 时打印"打不开任何设备"。这就是 fail-fast 的底层原理。
