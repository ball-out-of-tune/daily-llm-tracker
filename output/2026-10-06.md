## 🧪 重要知识点 & 动手实验

- **知识点 1：Mamba 状态检查点（State Checkpoint）**
  - **是什么**：Mamba 模型在扫描序列时会分段计算，每段结束时的"状态"可以存下来复用。
  - **为什么重要**：长序列推理时，前缀缓存命中后可以从检查点续跑，避免重复计算。不懂这个，你写的缓存逻辑会算错状态。
  - **动手试试**：阅读 `tests/kernels/mamba/test_mamba2_checkpoint_state.py`，跑一下：
    ```bash
    pytest tests/kernels/mamba/test_mamba2_checkpoint_state.py -v
    ```
  - **预期结果**：看到"检查点状态 == 独立重算前缀的状态"的断言通过，理解"中间状态可复现"这一核心契约。

- **知识点 2：分布式 P2P 通信的 group-local rank**
  - **是什么**：在分布式训练/推理中，每个进程有全局 rank 和组内 rank，P2P 传输要用组内 rank 才不会传错。
  - **为什么重要**：EPLB（专家负载均衡）跨 PP stage 传权重时用错 rank，数据会发到别的 stage，导致 silent bug。
  - **动手试试**：看 `vllm/distributed/eplb/eplb_communicator.py` 的 `add_send`，对比 `dst_rank` 和 `group_peer=dst_rank` 的写法。跑测试：
    ```bash
    pytest tests/distributed/test_eplb_execute.py::test_eplb_communicator_pipeline_parallel -v
    ```
  - **预期结果**：看到 world_size=2 和 4 都通过，理解"全局 rank ≠ 组内 rank"这个常见坑。

- **知识点 3：Triton 内核的字节指针技巧**
  - **是什么**：把权重指针声明为 `uint8` 字节指针，按字节做内存拷贝，绕开 Triton 对某些 dtype 的降级限制。
  - **为什么重要**：FP8 E4M3FN 在 SM89 以下 Triton 无法直接处理，用字节拷贝就能兼容所有硬件。
  - **动手试试**：看 `vllm/models/qwen4_exp/common/ngram_embedding.py` 里 `_lookup_ple_embedding_from_pinned_kernel` 的改动，把 `embedding_dim` 换成 `row_bytes`。
  - **预期结果**：理解"用字节偏移代替元素偏移"是一种通用兼容技巧，在写跨硬件 Triton 内核时非常有用。

- **知识点 4：KV 缓存 FP8 量化与 descale**
  - **是什么**：KV 缓存存成 FP8，读取时乘以 `k_descale`/`v_descale` 恢复数值。
  - **为什么重要**：非 2 的幂次的 scale（如 0.3、0.7）能测试舍入边界，这是量化正确性的关键。
  - **动手试试**：跑：
    ```bash
    pytest tests/kernels/attention/test_triton_unified_attention_diffkv.py -k "kv_cache_dtype" -v
    ```
  - **预期结果**：看到 FP8 KV 缓存与 PyTorch 参考实现在容差内一致，理解"量化-反量化"闭环。

- **知识点 5：CUDA Graph 捕获与回放**
  - **是什么**：把一段 GPU 计算录制成图，之后用 `graph.replay()` 一键重放。
  - **为什么重要**：DeepSeek-V4.1 的 decoder replay 层用 CUDA Graph 加速，但图捕获时不能有动态 shape，需要 padding 到固定大小。
  - **动手试试**：看 `tests/models/test_deepseek_v41_decoder_replay_layers.py::test_replay_graph_matches_eager`，理解"图模式输出 == eager 模式输出"的验证思路。
  - **预期结果**：理解 CUDA Graph 的"录制-回放"模型，以及为什么需要 `BatchDescriptor` 描述批次大小。

## 🧪 重要知识点 & 动手实验

- **知识点 1：反序列化安全与网络绑定**
  - **是什么**：Python 的 `pickle.loads` 能执行任意代码，如果它监听在 `0.0.0.0`，任何人都能发恶意数据让你执行。
  - **为什么重要**：很多推理框架内部用 pickle 传张量，一旦暴露公网就是 RCE（远程代码执行）漏洞。不懂这个，你的服务可能已经被入侵了还不知道。
  - **动手试试**：
    ```bash
    # 观察你的服务监听在哪个地址
    # 启动一个 sglang 服务后执行：
    ss -tlnp | grep python
    # 或者
    netstat -tlnp | grep python
    ```
    然后修改启动参数加上 `--host 0.0.0.0`，再观察内部 ZMQ 端口是否仍绑定在 `127.0.0.1`。
  - **预期结果**：HTTP 服务端口监听 `0.0.0.0`，但内部调度器 ZMQ 端口只在 `127.0.0.1` 上，说明安全隔离生效。

- **知识点 2：GPU 显存缓存与 empty_cache**
  - **是什么**：PyTorch 的 caching allocator 会缓存已释放的显存，避免频繁向驱动申请，但缓存太多会占着不用。
  - **为什么重要**：Commit 9 的核心洞察是——每个请求结束就 `empty_cache()` 会导致下一个请求重新 malloc，产生抖动；正确做法是等服务器真正空闲再释放。
  - **动手试试**：
    ```python
    import torch
    # 分配后释放，观察缓存是否归还
    x = torch.randn(1000, 1000, device='cuda')
    del x
    print(torch.cuda.memory_reserved() / 1e6, "MB reserved")
    torch.cuda.empty_cache()
    print(torch.cuda.memory_reserved() / 1e6, "MB reserved after empty_cache")
    ```
  - **预期结果**：`del` 后 reserved 不变（缓存保留），`empty_cache()` 后 reserved 明显下降。

- **知识点 3：稀疏注意力与 top-k 索引**
  - **是什么**：普通注意力每个 query 看全部 key；稀疏注意力只看被 indexer 选出的 top-k 个 key。
  - **为什么重要**：长上下文（128K+）下，全注意力是 O(n²)，稀疏化后接近 O(n·k)，这是能跑起来和跑不起来的区别。
  - **动手试试**：
    ```python
    import torch
    # 模拟 top-k 稀疏注意力
    q = torch.randn(1, 8, 128, 64)      # batch, heads, seq, dim
    k = torch.randn(1, 8, 1024, 64)     # 1024 个历史 token
    topk = 64
    scores = q @ k.transpose(-2, -1)     # [1,8,128,1024]
    _, idx = scores.topk(topk, dim=-1)   # 只保留 64 个
    print("全注意力计算量:", scores.numel())
    print("稀疏后计算量:", 128 * topk * 8)
    ```
  - **预期结果**：稀疏后计算量减少约 16 倍，你会直观感受到长上下文加速的来源。

- **知识点 4：跨平台条件导入**
  - **是什么**：`from sgl_kernel import xxx` 在非 CUDA 平台会直接 ImportError，需要用 `if _is_cuda:` 包起来。
  - **为什么重要**：Commit 6 就是这个 bug——AMD/NPU 用户一启动就崩。这是异构部署最常见的坑。
  - **动手试试**：
    ```python
    # 模拟条件导入的写法
    import torch
    _is_cuda = torch.cuda.is_available()
    if _is_cuda:
        from sgl_kernel import merge_state_v2
        print("CUDA kernel 可用")
    else:
        print("回退到 Triton 实现")
    ```
  - **预期结果**：在无 GPU 机器上不报错，优雅回退，这就是"平台抽象"的价值。

- **知识点 5：请求重试与 worker 排除**
  - **是什么**：请求失败后，路由器记录"这个请求已经在 worker A 上失败过"，重试时不再选 A。
  - **为什么重要**：Commit 5 引入 `excluded: &[WorkerId]`，没有它重试可能又打回坏节点，永远失败。
  - **动手试试**（伪代码理解逻辑）：
    ```python
    failed_workers = set()
    def pick_worker(all_workers):
        candidates = [w for w in all_workers if w.id not in failed_workers]
        return candidates[0] if candidates else None

    workers = [{"id": "A"}, {"id": "B"}, {"id": "C"}]
    failed_workers.add("A")
    print("重试选中:", pick_worker(workers))  # 应该是 B
    ```
  - **预期结果**：输出 `B`，说明失败节点被正确跳过。
