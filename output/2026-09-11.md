## 🧪 重要知识点 & 动手实验

- **知识点 1：注意力后端的"解码 vs 预填充"路径差异**
  - **是什么**：LLM 推理分两个阶段——Prefill（处理整个 prompt）和 Decode（逐 token 生成）。两者的计算模式完全不同：Prefill 是"多 query 对一个 KV"，Decode 是"单 query 对长 KV"。所以高性能推理引擎会为两个阶段写不同的 CUDA 核函数。
  - **为什么重要**：如果你不知道这个区别，看到代码里 `num_decode_tokens`、`num_prefill_tokens`、`max_query_len == 1` 这些判断会一头雾水，也没法理解为什么一个 bugfix 只影响 decode 不影响 prefill。
  - **动手试试**：
    ```bash
    pip install vllm
    python -c "
    from vllm import LLM, SamplingParams
    llm = LLM(model='Qwen/Qwen2.5-0.5B-Instruct', enforce_eager=True)
    # 第一个请求触发 prefill，后续请求触发 decode
    out = llm.generate(['你好', '再见'], SamplingParams(max_tokens=5))
    for o in out:
        print(o.outputs[0].text)
    "
    ```
  - **预期结果**：你会看到两个请求的输出。在日志里能看到 prefill 和 decode 分别走了不同的 kernel。如果打开 `VLLM_LOGGING_LEVEL=DEBUG`，还能看到每个 attention backend 的选择。

- **知识点 2：KV Cache 在 P/D 分离架构下如何传输**
  - **是什么**：P/D 分离把 Prefill 和 Decode 放在不同机器上。Prefill 算完 KV Cache 后，要通过网络传给 Decode 节点。Mooncake、LMCache 就是干这个的。今天 commit 9 修的就是"PP（流水线并行）场景下，消费者有多个 stage，生产者要等所有 stage 都拉完才能释放 KV"。
  - **为什么重要**：如果生产者提前释放 KV，消费者拉到的是垃圾数据，输出就会乱码。这类 bug 非常隐蔽，只在特定并行配置下复现。
  - **动手试试**：
    ```bash
    # 单机模拟 P/D 分离（需要 2 张 GPU）
    # 终端 1：Prefill 实例
    vllm serve Qwen/Qwen2.5-0.5B-Instruct \
      --port 8100 --kv-transfer-config '{"kv_connector":"MooncakeConnector","kv_role":"kv_producer"}'
    # 终端 2：Decode 实例
    vllm serve Qwen/Qwen2.5-0.5B-Instruct \
      --port 8200 --kv-transfer-config '{"kv_connector":"MooncakeConnector","kv_role":"kv_consumer"}'
    ```
  - **预期结果**：两个实例启动后，通过代理把请求先发给 Prefill 再转发给 Decode，能正常输出。如果 KV 传输有问题，Decode 端会出现乱码或报错。

- **知识点 3：LoRA 的缩放因子（scaling factor）**
  - **是什么**：LoRA 在原始权重上加一个低秩增量 `ΔW = B @ A * scaling`。标准 LoRA 的 scaling = alpha / rank；rsLoRA（rank-stabilized LoRA）的 scaling = alpha / sqrt(rank)。今天 commit 8 修的就是 MoE 打包时用了错误的公式。
  - **为什么重要**：scaling 算错，模型输出会偏；rank 越大偏差越明显。而且这个 bug 只在"MoE + rsLoRA"组合下出现，普通 LoRA 不受影响，非常隐蔽。
  - **动手试试**：
    ```python
    import math
    rank, alpha = 16, 32
    standard = alpha / rank          # 2.0
    rslora   = alpha / math.sqrt(rank)  # 8.0
    print(f"standard={standard}, rslora={rslora}")
    # 差 4 倍！如果模型按 rslora 训练，推理时用 standard 就会输出偏
    ```
  - **预期结果**：你会看到两个数值差很多，理解为什么"用错公式"会导致模型行为异常。

- **知识点 4：多模态输入中的"dummy profiling"**
  - **是什么**：vLLM 启动时会用假数据（dummy input）跑一遍模型，测量显存占用、编译 CUDA graph。对于多模态模型，假视频的形状必须是 `(num_frames, height, width, 3)`，今天 commit 4 修的就是 H/W 写反了。
  - **为什么重要**：形状写反会导致 profiling 时显存估算错误，实际推理时可能 OOM。而且 H 和 W 经常数值相近，肉眼很难发现。
  - **动手试试**：
    ```python
    import numpy as np
    # 正确：视频帧是 (T, H, W, C)
    video_ok = np.full((8, 224, 448, 3), 255, dtype=np.uint8)
    # 错误：H/W 写反
    video_bad = np.full((8, 448, 224, 3), 255, dtype=np.uint8)
    print(video_ok.shape, video_ok.nbytes, video_bad.shape, video_bad.nbytes)
    # 虽然总字节数一样，但后续 resize/crop 会按错误的 H/W 处理
    ```
  - **预期结果**：两个数组字节数相同，但语义不同。多模态预处理链会按 shape 的第 1/2 维解释为 H/W，写反就全错了。

- **知识点 5：ROCm 下的符号可见性（RTLD_LOCAL vs RTLD_GLOBAL）**
  - **是什么**：Linux 动态链接器加载 .so 时，`RTLD_LOCAL` 表示符号只在当前库内可见，`RTLD_GLOBAL` 表示全局可见。今天 commit 20 修的就是：libtorch_cpu.so 用 RTLD_LOCAL 加载，导致 rocprofiler 找不到 `rocprofiler_configure` 符号，GPU profiling 静默失效。
  - **为什么重要**：这类问题不报错，只是"profiler 里没有 GPU 记录"，非常难排查。理解动态链接的符号作用域是排查这类问题的关键。
  - **动手试试**：
    ```bash

    python -c "import torch; print(torch.__file__)"
    # 找到 libtorch_cpu.so，然后用 nm 看符号
    nm -D $(python -c "import torch,os;print(os.path.join(os.path.dirname(torch.__file__),'lib','libtorch_cpu.so'))") | grep rocprofiler_configure
    # 如果有输出，说明符号存在；但能否被 rocprofiler 找到取决于加载方式
    ```
  - **预期结果**：你会看到符号确实在 .so 里，但只有用 `ctypes.CDLL(..., mode=ctypes.RTLD_GLOBAL)` 预加载后，rocprofiler 才能找到它。

## 🧪 重要知识点 & 动手实验

- **知识点 1：FP8 量化与 UE8M0 缩放格式**
  - **是什么**：FP8 用 8 位存浮点数（如 `e4m3fn` 是 4 位指数 + 3 位尾数）。UE8M0 是一种"无符号指数 + 无尾数"的缩放因子格式，专门用来存 block-wise 的 scale。
  - **为什么重要**：不懂缩放格式，加载 DeepSeek 这类 FP8 权重时会遇到数值爆炸或全为 0 的 bug——正是 Commit 1 修复的问题。
  - **动手试试**：
    ```python
    import torch
    # 模拟一个 FP8 权重和 UE8M0 scale
    w = torch.randn(4, 8, dtype=torch.float32)
    scale = torch.tensor([1.0, 2.0, 0.5, 4.0])  # 每行一个 scale
    w_fp8 = (w / scale[:, None]).to(torch.float8_e4m3fn)
    # 反量化
    w_deq = w_fp8.to(torch.float32) * scale[:, None]
    print("原始:", w[0, :3])
    print("反量化:", w_deq[0, :3])
    print("误差:", (w - w_deq).abs().max().item())
    ```
  - **预期结果**：误差在 1e-2 量级以内，说明你理解了 block-wise 量化的基本原理。

- **知识点 2：msgspec.Struct 替代 dataclasses**
  - **是什么**：`msgspec` 是一个用 C 实现的序列化库，`Struct` 类似 `dataclass` 但更快，且支持 JSON 零拷贝。
  - **为什么重要**：sglang 的 `ServerArgs` 已迁移到 msgspec，如果你还在用 `dataclasses.asdict` 会直接报错（Commit 20 就是修这个）。
  - **动手试试**：
    ```python
    import msgspec
    from dataclasses import dataclass, asdict

    @dataclass
    class A:
        x: int = 1
        y: str = "hi"

    class B(msgspec.Struct):
        x: int = 1
        y: str = "hi"

    print("dataclass:", asdict(A()))
    print("msgspec:", msgspec.structs.asdict(B()))
    print("json:", msgspec.json.encode(B()))
    ```
  - **预期结果**：两者输出结构相同，但 msgspec 还能直接编码成 JSON 字节流。

- **知识点 3：自定义 Logit Processor 与 batch 展开**
  - **是什么**：Logit Processor 是在采样前修改 logits 的钩子（比如强制某些 token、加惩罚）。当一次 batch 里每个请求生成多个 token 时，参数需要按 token 复制。
  - **为什么重要**：Commit 16 修的就是 `num_tokens_in_batch > 1` 时参数错位的 bug，会导致采样结果错乱。
  - **动手试试**：
    ```python
    import torch
    batch_indices = [0, 2]
    num_tokens_in_batch = 2
    params = [{"v": 1.0}, {"v": 2.0}, {"v": 3.0}]
    custom_params = [params[i] for i in batch_indices for _ in range(num_tokens_in_batch)]
    print(custom_params)
    # 预期: [{'v': 1.0}, {'v': 1.0}, {'v': 3.0}, {'v': 3.0}]
    ```
  - **预期结果**：看到每个请求的参数被重复了 `num_tokens_in_batch` 次，正是修复后的行为。

- **知识点 4：注意力掩码的因果性（causal vs non-causal）**
  - **是什么**：因果注意力只能看前面的 token（自回归生成），非因果可以看全部（如 encoder 或双向注意力）。
  - **为什么重要**：Commit 9 修的就是 XPU 后端把 ENCODER_ONLY 层错误地当成因果注意力，会导致 DFLASH draft 模型输出错误。
  - **动手试试**：
    ```python
    import torch
    import torch.nn.functional as F
    q = torch.randn(1, 4, 8)
    k = torch.randn(1, 4, 8)
    # 因果掩码
    causal_mask = torch.triu(torch.ones(4, 4), diagonal=1).bool()
    attn = q @ k.transpose(-2, -1) / (8 ** 0.5)
    attn_causal = attn.masked_fill(causal_mask, float("-inf"))
    print("因果注意力第 0 行:", F.softmax(attn_causal[0, 0], dim=-1))
    print("非因果第 0 行:", F.softmax(attn[0, 0], dim=-1))
    ```
  - **预期结果**：因果版本第 0 行只有第 0 个位置非零，非因果版本所有位置都有权重。

- **知识点 5：设备无关 API（`get_device()`）**
  - **是什么**：把硬编码的 `"cuda"` 替换成能自动识别当前设备的函数。
  - **为什么重要**：Commit 13 把测试和工具里的 `device="cuda"` 换成 `get_device()`，让同一份代码在 AMD/Intel 上也能跑。
  - **动手试试**：
    ```python
    import torch
    def get_device():
        if torch.cuda.is_available():
            return "cuda"
        if hasattr(torch, "xpu") and torch.xpu.is_available():
            return "xpu"
        return "cpu"
    dev = get_device()
    print("当前设备:", dev)
    x = torch.randn(3, 3, device=dev)
    print(x.device)
    ```
  - **预期结果**：输出你机器上可用的设备名，且张量创建成功。
