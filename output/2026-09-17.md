## 🧪 重要知识点 & 动手实验

- **知识点 1：EPLB 与专家并行负载均衡**
  - **是什么**：MoE 模型里，每个 token 被路由到 top-k 个专家。如果某些专家被大量 token 选中，对应 GPU 就会成为瓶颈。EPLB 通过复制热门专家（redundant experts）把负载摊开。
  - **为什么重要**：不懂 EPLB，MoE 推理吞吐会被单个热点专家拖垮，GPU 利用率可能只有 30%。今天 commit #44987（XPU EPLB）和 #57236（EPLB + SharedExpert Overlap + DeepEPv2）都是围绕这个。
  - **动手试试**：
    ```bash
    # 1. 安装 vllm 最新版
    pip install -U vllm
    # 2. 启动一个 MoE 模型（如 Mixtral 或 DeepSeek-V2-Lite），开启 EPLB
    vllm serve mistralai/Mixtral-8x7B-Instruct-v0.1 \
      --tensor-parallel-size 2 \
      --enable-expert-parallel \
      --enable-eplb
    # 3. 观察日志里是否出现 "EPLB" 相关统计
    ```
  - **预期结果**：日志里会打印每个专家的负载分布和冗余副本数，你会看到热门专家被复制成多份。

- **知识点 2：KV Cache 前缀缓存与 MLA 行压缩**
  - **是什么**：前缀缓存让相同 prompt 前缀的请求共享 KV；MLA（Multi-head Latent Attention）是 DeepSeek 系列用的压缩注意力，KV 存储更紧凑。今天 commit #56799 修复了 MLA 在 canonical layout 下按 TP 切分不一致的问题。
  - **为什么重要**：不懂前缀缓存，多轮对话/Agent 场景会重复计算，浪费 50%+ 算力；不懂 MLA 布局，TP 切换时缓存会错位，导致输出乱码。
  - **动手试试**：
    ```bash
    # 启动服务并打开前缀缓存和详细统计
    vllm serve Qwen/Qwen2.5-7B-Instruct \
      --enable-prefix-caching \
      --enable-prompt-tokens-details
    # 用 curl 发两次相同前缀的请求，观察 metrics
    curl http://localhost:8000/metrics | grep prefix_cache
    ```
  - **预期结果**：第二次请求的 `vllm:prefix_cache_hits_total` 会增加，`prefix_cache_queries_total` 也会增加，命中率 > 0。

- **知识点 3：流式 API 的字段省略契约**
  - **是什么**：SSE 流式响应中，可选的字段（如 `usage`、`logprobs`）应该在不存在时被**省略**，而不是序列化成 `null`。今天 commit #57264 和它的 revert #57302 就是在讨论这个契约。
  - **为什么重要**：很多 OpenAI 兼容客户端会判断 `"usage" in chunk`，如果服务器返回 `"usage": null` 就会误判。这是典型的 API 兼容性坑。
  - **动手试试**：
    ```python

    client = OpenAI(base_url="http://localhost:8000/v1", api_key="x")
    stream = client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct",
        messages=[{"role": "user", "content": "hi"}],
        stream=True,
    )
    for chunk in stream:
        d = chunk.model_dump(exclude_none=True)
        print(d.keys())  # 观察 usage/logprobs 是否出现
    ```
  - **预期结果**：中间 chunk 里通常没有 `usage` 字段，只有最后一个 chunk 才带上 usage。

- **知识点 4：EngineCore 握手时的阻塞 RPC 问题**
  - **是什么**：vLLM 启动时 EngineCore 会和 worker 做一次握手（handshake），确认能力。今天 commit #57226 修复了在**没有配置 weight transfer** 时仍然发起阻塞 RPC 的问题。
  - **为什么重要**：启动阶段的阻塞调用会拖慢冷启动时间，在多实例部署时尤其明显。不懂这个，你的服务启动会莫名慢几秒。

- **知识点 5：MoE 的 Shared Expert Overlap 与通信后端**
  - **是什么**：MoE 里通常有"共享专家"（所有 token 都走）和"路由专家"（按 top-k 走）。Overlap 就是把共享专家计算和 all-to-all 通信重叠起来，节省时间。今天 commit #57236 把 `deepep_v2` 加入了安全后端列表。
  - **为什么重要**：不重叠的话，通信时间就是纯等待；重叠后吞吐能提升 10-20%。但并不是所有通信后端都安全，选错会出正确性问题。
  - **动手试试**：
    ```bash

    VLLM_USE_DEEPEP_V2=1 vllm serve deepseek-ai/DeepSeek-V2-Lite \
      --enable-expert-parallel \
      --all2all-backend deepep_v2
    # 观察日志里是否出现 overlap 相关提示
    ```
  - **预期结果**：日志会显示 shared expert 和 dispatch 在时间上重叠，吞吐相比不重叠有提升。

## 🧪 重要知识点 & 动手实验

### 知识点 1：HiCache 的"空闲让出"机制（来自 Commit 11）

- **是什么**：当 GPU 没有 batch 要跑时，调度器会空转轮询。如果开了 HiCache 存储，这种空转会把 Python 的 GIL 占满，导致后台 I/O 线程拿不到 CPU 时间，确认消息发不回来，整个系统卡死。修复方法就一行：`time.sleep(0)`。
- **为什么重要**：多线程 Python 程序里，一个死循环轮询就能饿死后台线程。不懂这个，你写的异步服务会莫名其妙"卡住但不报错"。
- **动手试试**：
```python
# 对比实验：轮询 vs 让出 GIL
import threading, time

def worker():
    time.sleep(0.5)
    print("后台线程完成")

def spin_no_yield():
    t = threading.Thread(target=worker)
    t.start()
    start = time.time()
    while time.time() - start < 1.0:
        pass  # 纯空转，不给 GIL 机会
    t.join()

def spin_with_yield():
    t = threading.Thread(target=worker)
    t.start()
    start = time.time()
    while time.time() - start < 1.0:
        time.sleep(0)  # 主动让出 GIL
    t.join()

print("=== 不让出 ==="); spin_no_yield()
print("=== 让出 ==="); spin_with_yield()
```
- **预期结果**：第一种情况下"后台线程完成"会在主循环结束后才打印（被饿死）；第二种情况下会在 0.5 秒时就打印。你会亲身感受到 GIL 调度的影响。

### 知识点 2：多进程共享目录的静默数据损坏（来自 Commit 13）

- **是什么**：8 张 GPU 各自跑一个进程，如果它们把 SSD 缓存写到同一个目录，文件名可能撞车，而写入用的是 `O_CREAT|O_TRUNC`（有则清空），于是 A 进程把 B 进程的数据截断了，但双方都不知道。
- **为什么重要**：这是分布式存储的经典陷阱。任何"多进程写同一路径"的设计都要问一句：文件名能保证全局唯一吗？
- **动手试试**：
```bash
# 模拟两个进程写同一文件
mkdir -p /tmp/shared_cache && cd /tmp/shared_cache
python3 -c "
import os, time
def writer(name, data):
    for i in range(100):
        # O_TRUNC 会清空已有内容
        with open('bucket_0', 'w') as f:
            f.write(data * 10)
        time.sleep(0.001)
import multiprocessing as mp
p1 = mp.Process(target=writer, args=('A', 'A'))
p2 = mp.Process(target=writer, args=('B', 'B'))
p1.start(); p2.start(); p1.join(); p2.join()
print('最终文件长度:', os.path.getsize('bucket_0'))
"
```
- **预期结果**：文件长度远小于 `10 * 100`，说明写入被互相截断。修复思路就是 commit 里做的——给每个 rank 一个私有子目录 `rank_0_0_0_0/`。

### 知识点 3：Mamba 检查点深度必须落在"绝对网格"上（来自 Commit 2）

- **是什么**：Mamba 类模型需要定期保存中间状态（checkpoint）。原来的代码用"相对前缀的长度"算对齐位置，但如果前缀本身就没落在页边界上，算出来的位置根本不存在，会读到错误的状态。
- **为什么重要**：缓存复用是推理加速的核心，一旦状态错位，输出会莫名其妙地错误，而且只在特定输入长度下复现。
- **动手试试**：
```python
# 演示"相对对齐"vs"绝对对齐"的差异
checkpoint_grid = 512   # 检查点粒度
prefix_len = 64         # 前缀长度（非网格对齐）
extend_len = 512        # 本次新增

# 旧逻辑：相对前缀对齐
old = prefix_len + (extend_len // checkpoint_grid) * checkpoint_grid
# 新逻辑：绝对位置对齐
seq_end = prefix_len + extend_len
new = (seq_end // checkpoint_grid) * checkpoint_grid

print(f"序列总长: {seq_end}")
print(f"旧逻辑对齐到: {old}  (在网格上? {old % checkpoint_grid == 0})")
print(f"新逻辑对齐到: {new}  (在网格上? {new % checkpoint_grid == 0})")
print(f"新逻辑是否超出前缀? {new > prefix_len}")
```
- **预期结果**：旧逻辑得到 576（不是 512 的倍数），新逻辑得到 512（合法网格点）。你会明白为什么"对齐基准"选错会导致读到不存在的状态。

### 知识点 4：用 `if constexpr` 让 CUDA-only 代码在 ROCm 上"能编译但不可用"（来自 Commit 20）

- **是什么**：DeepSeek V4.1 的 KV 布局是 CUDA 专有的，但调用它的代码在 ROCm 上也要能编译通过（因为 `if constexpr` 的废弃分支仍会被解析）。解决方法是提供一个"能解析、但一实例化就报错"的模板桩。
- **为什么重要**：跨平台代码的常见需求——"这个功能在 A 平台可用，在 B 平台要编译通过但运行时禁止调用"。
- **动手试试**：
```cpp
// 保存为 test.cpp，用 g++ -std=c++17 test.cpp -o test
#include <cstdio>

template <typename T>
inline constexpr bool dependent_false_v = false;

// 桩函数：能解析，实例化即报错
template <typename T>
void cuda_only_impl(T) {
    static_assert(dependent_false_v<T>, "此功能仅 CUDA 可用");
}

template <typename T>
void caller(T x) {
    if constexpr (sizeof(T) == 4) {
        cuda_only_impl(x);  // 分支被丢弃，但仍需解析
    }
}

int main() {
    // caller<double>(1.0);  // 取消注释会编译失败
    printf("编译通过，但 cuda_only_impl 未被实例化\n");
    return 0;
}
```
- **预期结果**：程序正常编译运行。如果取消注释 `caller<double>`，会看到 `static_assert` 报错"此功能仅 CUDA 可用"。这就是"延迟到实例化才报错"的技巧。

### 知识点 5：推测解码 + 流水线并行的约束检查（来自 Commit 8）

- **是什么**：PP（流水线并行）把模型切成多段放在不同 GPU 上，推测解码需要一个"草稿模型"来猜词。两者组合时有一堆限制：不能用 overlap schedule、不能用 DP attention、必须单层 EAGLE 等，代码里用一串 `assert` 把这些约束写死。
- **为什么重要**：分布式推理的组合不是"打开两个开关"那么简单，理解这些约束能帮你避免踩坑。
- **动手试试**：
```python
# 模拟约束检查器
def validate_pp_spec(disable_overlap, algorithm, enable_dp_attn, adaptive):
    errors = []
    if not disable_overlap:
        errors.append("PP+spec 需要 --disable-overlap-schedule")
    if algorithm != "EAGLE":
        errors.append(f"只支持单层 EAGLE，当前是 {algorithm}")
    if enable_dp_attn:
        errors.append("PP+spec 与 DP attention 不兼容")
    if adaptive:
        errors.append("PP+spec 与 --speculative-adaptive 不兼容")
    return errors

# 场景1：正确配置
print("场景1:", validate_pp_spec(True, "EAGLE", False, False) or "✓ 通过")
# 场景2：忘记关 overlap
print("场景2:", validate_pp_spec(False, "EAGLE", False, False))
# 场景3：用了 DP attention
print("场景3:", validate_pp_spec(True, "EAGLE", True, False))
```
- **预期结果**：场景 1 通过，场景 2、3 报出具体错误。你会理解"参数组合校验"在生产代码里有多重要。
