## 🧪 重要知识点 & 动手实验

### 知识点 1：张量并行（Tensor Parallelism）下的设备分配

- **是什么**：把一个模型切到多张 GPU 上时，每张卡负责一部分计算，但"当前设备"必须精确指定为 `cuda:N` 而不是笼统的 `cuda`。
- **为什么重要**：Commit #3 修复了一个 bug：`safetensors` 加载模型时，如果传入 `"cuda"` 而不是 `"cuda:2"`，它会默认加载到 `cuda:0`，导致 TP rank 2 的 worker 加载到错误的设备上，模型直接崩溃。这是分布式训练/推理最常见的坑之一。
- **动手试试**：
```python
import torch

# 模拟 TP rank = 2 的 worker
# 错误写法：safetensors 会加载到 cuda:0
# device = "cuda"

# 正确写法：明确指定当前 rank 对应的设备
device = f"cuda:{torch.cuda.current_device()}"
print(f"加载到设备: {device}")

# 验证：在多卡机器上，current_device() 会返回当前进程绑定的 GPU
if torch.cuda.device_count() > 1:
    torch.cuda.set_device(2)
    print(f"设置后 current_device = {torch.cuda.current_device()}")
```
- **预期结果**：你会看到 `current_device()` 返回你设置的设备编号。在多卡环境下，`set_device` 后所有未指定设备的操作都会落在正确的卡上。这就是为什么代码里必须用 `cuda:{rank}` 而不是裸 `cuda`。

### 知识点 2：量化——用更少的比特存权重

- **是什么**：NVFP4 是 NVIDIA 的一种 4-bit 浮点格式，能把模型权重压缩到原来的 1/4（相比 FP16），大幅减少显存占用和带宽需求。
- **为什么重要**：Commit #13 把 NVFP4 支持扩展到纯 PyTorch 后端，意味着不需要专门的 kernel 库也能跑 NVFP4 模型。量化是当前 LLM 推理加速的核心手段——不理解量化，你会在部署大模型时遇到"显存不够"的墙。
- **动手试试**：
```python
import torch

# 模拟量化过程：FP16 -> 4-bit 的思想
x = torch.randn(8, 8, dtype=torch.float16)
print(f"原始 FP16 大小: {x.element_size() * x.numel()} bytes")

# 量化第一步：缩放（scale）
scale = x.abs().max() / 7  # 4-bit 有符号整数范围 -8~7
x_scaled = x / scale

# 量化第二步：取整到 4-bit 范围
x_quant = torch.clamp(torch.round(x_scaled), min=-8, max=7).to(torch.int8)
print(f"量化后每个元素只用 4-bit（但这里用 int8 模拟）")

# 反量化：还原近似值
x_dequant = x_quant.float() * scale
error = (x - x_dequant).abs().mean()
print(f"量化误差（越小越好）: {error.item():.4f}")
```
- **预期结果**：你会看到量化后的数值和原始值存在一定误差，但整体分布保持。这就是为什么量化模型需要微调（calibration）来减少精度损失。理解这个"缩放-取整-反缩放"过程，你就理解了所有量化方案的核心。

### 知识点 3：多流（Multi-stream）与异步拷贝

- **是什么**：GPU 上有多个执行流（stream），可以并行执行不同的操作。数据拷贝（CPU↔GPU）可以在单独流上异步进行，不阻塞计算流。
- **为什么重要**：Commit #14 增强了 CPU↔GPU 同步检查，可以检测出哪些"异步"拷贝其实是同步的（比如非页锁定内存的拷贝会悄悄变回同步）。在 EC Connector 和 KV Connector 中，异步拷贝是性能关键——如果不知道哪些操作会同步阻塞，性能分析时会被假异步骗到。
- **动手试试**：
```python
import torch
import time

# 页锁定内存（pinned memory）：真正的异步拷贝需要它
pinned = torch.zeros(1024 * 1024, dtype=torch.float32).pin_memory()
gpu_tensor = torch.zeros(1024 * 1024, device="cuda")

# 非页锁定内存（普通 CPU 内存）
normal = torch.zeros(1024 * 1024, dtype=torch.float32)

# 比较两种拷贝的时间
torch.cuda.synchronize()
start = time.time()
gpu_tensor.copy_(normal, non_blocking=True)  # 实际上是同步的（pageable）
torch.cuda.synchronize()
print(f"Pageable 拷贝耗时: {time.time() - start:.4f}s")

torch.cuda.synchronize()
start = time.time()
gpu_tensor.copy_(pinned, non_blocking=True)  # 真正的异步
torch.cuda.synchronize()
print(f"Pinned 拷贝耗时: {time.time() - start:.4f}s")
```
- **预期结果**：`pin_memory()` 创建的张量在 `non_blocking=True` 下能真正异步执行，而普通内存的"异步"拷贝实际上是同步的。在数据加载管道中，使用 pinned memory 是避免 CPU 预处理阻塞 GPU 计算的关键。

### 知识点 4：工具调用解析（Tool Call Parsing）

- **是什么**：LLM 输出不只是文本，还可能包含结构化的工具调用（比如调用天气 API）。解析器需要从模型输出中提取出"调用哪个函数、传什么参数"。
- **为什么重要**：Commit #12 修复了一个 bug：DeepSeek 模型在长上下文下偶尔会省略 `<DSML|tool_calls>` 包装标签，直接输出 `<DSML|invoke>`。如果解析器只认完整格式，就会把工具调用当作普通文本泄漏给用户。Agent 应用的可靠性完全依赖这类解析。
- **动手试试**：
```python
import re

# 模拟 DeepSeek V4 的工具调用输出（省略了 tool_calls 包装）
model_output = """我来帮你查天气。
<|DSML|invoke name="get_weather" parameter name="location" parameter type="string">NYC</|DSML|invoke>
"""

# 关键：用 invoke 标签本身来锚定检测，而不是依赖外层 wrapper
invoke_pattern = r'<\|DSML\|invoke name="(\w+)"(.*?)>\s*(.*?)\s*</\|DSML\|invoke>'

match = re.search(invoke_pattern, model_output, re.DOTALL)
if match:
    func_name = match.group(1)
    raw_params = match.group(2)
    value = match.group(3)
    
    # 提取参数名
    param_name = re.search(r'parameter name="(\w+)"', raw_params).group(1)
    print(f"检测到工具调用: {func_name}({param_name}={value!r})")
    
    # 注意：invoke 之前的内容是正常回复
    prefix = model_output[:match.start()].strip()
    print(f"正常回复内容: {prefix!r}")
```
- **预期结果**：即使缺少外层 wrapper，只要 invoke 标签存在就能正确提取函数名和参数。这就是修复的核心思路——用最内层的锚点做检测，而不是假设模型总是输出完整格式。

### 知识点 5：FP8 块缩放量化（FP8 Block Scales）

- **是什么**：FP8 的一种变体，不是对整个权重矩阵用一个缩放因子，而是按小块（如 128 个元素）分别缩放，精度更高。
- **为什么重要**：Commit #20 修复了混合精度检查点中 MTP（多 token 预测）层使用 FP8 块缩放时的层索引映射错误。在量化模型中，不同层可能用不同量化方案（如 NVFP4 和 FP8 混合），需要精确映射每层的量化参数。
- **动手试试**：
```python
import torch

def block_quantize(x, block_size=128):
    """按块做 FP8 量化（模拟）"""
    orig_shape = x.shape
    x_flat = x.reshape(-1)
    
    # 填充到 block_size 的整数倍
    pad = (-x_flat.numel()) % block_size
    if pad:
        x_flat = torch.nn.functional.pad(x_flat, (0, pad))
    
    # 按块计算 scale
    x_blocks = x_flat.reshape(-1, block_size)
    scales = x_blocks.abs().max(dim=1).values / 127.0  # FP8 范围 -127~127
    x_quant = torch.clamp(torch.round(x_blocks / scales.unsqueeze(1)), 
                         min=-127, max=127).to(torch.int8)
    
    # 反量化
    x_dequant = (x_quant.float() * scales.unsqueeze(1)).reshape(-1)[:orig_shape[0]]
    return x_dequant.reshape(orig_shape)

# 对比：全局缩放 vs 块缩放
x = torch.randn(256, 256) * torch.rand(256, 1) * 10  # 不均匀分布

# 全局量化
scale = x.abs().max() / 127.0
x_global_deq = torch.clamp(torch.round(x / scale), -127, 127).float() * scale

# 块量化
x_block_deq = block_quantize(x)

print(f"全局量化误差: {(x - x_global_deq).abs().mean().item():.4f}")
print(f"块量化误差:   {(x - x_block_deq).abs().mean().item():.4f}")
```
- **预期结果**：块量化的误差显著小于全局量化，因为不同区域的数值范围差异被局部缩放处理了。这就是为什么现代量化方案（如 FP8_BLOCK_SCALES）倾向于块缩放而不是全局缩放。

## 🧪 重要知识点 & 动手实验

### 知识点 1：理解性能优化中"位精确 (Bit-Exact)"的重要性

- **是什么**：在优化一个算子时（比如融合两个操作），优化后的结果和优化前的结果在二进制级别上必须完全一致，不能有哪怕一位的误差。这被称为"位精确"。
- **为什么重要**：在图像/视频生成中，一个微小的数值误差可能会在迭代中被放大，导致最终生成图像出现奇怪的噪点或颜色偏差。所以，SGLang 在融合算子（如 LayerNorm + 调制）时，会用一个"融合门"（BitExactFusionGate）来验证新内核的输出是否与老的、未经优化的实现完全一致。如果不一致，就自动回退到老的实现。
- **动手试试**：你可以在 Python 中模拟这个"验证"过程：
```python
import torch

# 模拟一个优化后的算子，它可能会引入微小误差
def optimized_op(x):
    # 假设这里是一个优化的、可能不精确的矩阵乘法
    return x @ torch.eye(x.shape[0], dtype=x.dtype) + 1e-7

# 模拟原始算子
def reference_op(x):
    return x @ torch.eye(x.shape[0], dtype=x.dtype)

# 验证
x = torch.randn(8, 8, dtype=torch.float64)
optimized_out = optimized_op(x)
reference_out = reference_op(x)

if torch.equal(optimized_out, reference_out):
    print("结果位精确，可以安全替换！")
else:
    print("结果有差异，需要回退到原始实现。")
```
- **预期结果**：你会看到 "结果有差异，需要回退到原始实现。"，因为 `optimized_op` 中加了 `1e-7`。这让你直观理解了为什么需要"位精确"门控。

### 知识点 2：解析 CUDA Graph 的"可打断 (Breakable)"模式

- **是什么**：CUDA Graph 可以把一系列 GPU 内核启动打包成一个图，减少 CPU 启动开销。但传统图是"非打断"的，一旦启动就必须完整执行。而"可打断 CUDA Graph"(BCG) 允许图在执行到某个点后暂停，回到 CPU 处理其他逻辑（比如查看是否需要提前退出），然后再继续执行图的剩余部分。
- **为什么重要**：在扩散模型采样循环中，每一步都需要执行 DiT（Diffusion Transformer）模型。如果每次迭代都启动一次新图，开销很大。BCG 允许你只启动一次图，然后在图的内部循环执行，每次迭代后都可以"打断"出来检查是否满足停止条件（如达到指定步数），从而避免重复启动图的开销。
- **动手试试**：这个功能需要特定的硬件和模型支持，无法本地模拟。但你可以通过阅读 FLUX.1-dev 的文档来理解其用法：
```bash
# 这是在 H200 上启用 BCG 的命令（摘录自 Commit 2）
CUDA_VISIBLE_DEVICES=0,1 sglang generate \
  --model-path black-forest-labs/FLUX.1-dev \
  --backend sglang \
  --num-gpus 2 --tp-size 2 \
  --enable-breakable-cuda-graph \
  --warmup-resolutions 1024x1024 \
  --quality lossless \
  # ... 其他参数
```
- **预期结果**：运行命令后，日志中会出现 `[Diffusion BCG] captured`，表示图捕获成功。后续请求如果分辨率匹配，将复用这个图，从而降低延迟。

### 知识点 3：探索显存调度的"组件驻留 (Component Residency)"模式

- **是什么**：这是 SGLang 为多模态生成模型设计的一种显存管理策略。它允许你为模型的每个组件（如 `dit`、`vae`、`text_encoder`）分别指定其在显存中的驻留方式。
- **为什么重要**：不同的组件使用频率和显存占用差异巨大。例如，`text_encoder` 只在处理输入时用一次，而 `dit` 在生成时反复使用。通过 `--component-residency` 参数，你可以精细控制：
    - `resident`: 一直留在 GPU 显存（适合 `dit`）。
    - `component-offload`: 平时在 CPU，用的时候搬到 GPU，用完再搬回（适合 `text_encoder`）。
    - `snapshot-offload`: 在 GPU 上运行时，保留一份 CPU 参数快照，结束时直接恢复，避免昂贵的 GPU->CPU 拷贝（适合 `vae`，能显著提速）。
- **动手试试**：你可以尝试在 `sglang generate` 命令后添加 `--help` 来查看这个参数，然后对比不同模式下的显存占用和首次请求延迟（假设你有一张 GPU）：
```bash
# 查看帮助
sglang generate --help | grep component-residency

# 理论上的命令示例（需要真实模型）
# sglang serve --model-path <your-model> --component-residency vae=snapshot-offload
```
- **预期结果**：你会看到这个参数可以重复指定，例如 `--component-residency dit=resident --component-residency vae=snapshot-offload`。这让你明白，显存管理不是"一刀切"，而是可以精细到每个模块的。

### 知识点 4：认识 MoE 路由层的性能瓶颈与优化

- **是什么**：混合专家模型（MoE）有一个"路由"（Router）模块，它决定每个 token 由哪些"专家"（Expert）处理。这个路由计算通常是一个很小的矩阵乘（GEMV），但因为是串行依赖，容易成为性能瓶颈。
- **为什么重要**：Commit 20 专门为 AMD GPU 优化了这个 GEMV 操作。它发现 AMD 的矩阵库在处理小矩阵时效率极低，于是用 Triton 重写了一个"split-K"内核，把计算分给多个计算单元，最后在一个内核里完成合并，避免了多次启动内核的开销。在 AMD 上性能提升了 100 多倍。
- **动手试试**：你可以用 PyTorch 观察一个简单的 GEMV 操作在 CPU 和 GPU（如果你有）上的耗时，理解其计算模式：
```python
import torch
import time

M, K, N = 8, 4096, 128  # 模拟 8 个 token，4096 维输入，128 个专家
x = torch.randn(M, K, device='cuda')
w = torch.randn(N, K, device='cuda')

# GEMV: 对每个专家权重矩阵与输入向量做点积
start = time.time()
out = torch.einsum('mk,nk->mn', x, w)
torch.cuda.synchronize()
print(f"GEMV 耗时: {(time.time() - start) * 1000:.2f} ms")
```
- **预期结果**：你会看到这个操作本身很快，但在真实推理中，它可能因为启动开销或与其他操作的串行依赖而成为瓶颈。这个实验能帮你理解为什么开发者会为这种"小算子"费尽心思。
