## 🧪 重要知识点 & 动手实验

- **知识点 1：cgroup 内存限制与 SHM 预检（来自 Commit 1）**
  - **是什么**：Linux 用 cgroup 限制一个容器能用多少内存。vLLM 在申请共享内存（SHM）前，会先检查 cgroup 还剩多少额度，不够就直接报错而不是让系统 OOM。
  - **为什么重要**：在 K8s/Docker 里跑推理服务时，如果不检查 cgroup，程序以为有 64GB 可用，实际容器只给 8GB，一申请就崩。这是生产环境的常见坑。
  - **动手试试**：
    ```bash
    # 查看当前 cgroup 内存限制（v2）
    cat /sys/fs/cgroup/memory.max
    cat /sys/fs/cgroup/memory.current
    # 手动算一下剩余额度
    python3 -c "
    limit = int(open('/sys/fs/cgroup/memory.max').read().strip())
    used = int(open('/sys/fs/cgroup/memory.current').read().strip())
    print(f'剩余: {(limit-used)/1024**3:.2f} GiB')
    "
    ```
  - **预期结果**：看到容器的真实内存上限和已用量，理解为什么"物理机有 64G 但容器只有 8G"。

- **知识点 2：GPU 同步检查与 torch.compile（来自 Commit 7）**
  - **是什么**：GPU 是异步执行的，CPU 发指令后不等 GPU 完成。有时需要强制同步（比如调试时）。vLLM 有个调试工具会拦截 `.to()` 等操作检查是否意外同步，但这个拦截会破坏 `torch.compile` 的图追踪。
  - **为什么重要**：`torch.compile` 是 PyTorch 加速的核心手段，任何"猴子补丁"都可能让编译失败。理解"编译期 vs 运行期"的区别是性能调优的关键。
  - **动手试试**：
    ```python
    import torch
    def f(x, like):
        return x.to(device=like.device, dtype=like.dtype)
    compiled = torch.compile(f, fullgraph=True)
    a = torch.ones(4, device="cuda", dtype=torch.float64)
    b = torch.ones(4, device="cuda", dtype=torch.float32)
    print(compiled(a, b).dtype)  # 应该是 float32
    ```
  - **预期结果**：编译成功并输出 `torch.float32`。如果报错说"unsupported"，说明有东西挡住了图追踪。

- **知识点 3：MXFP8 量化的 scale 计算（来自 Commit 16）**
  - **是什么**：MXFP8 把数据按每 32 个一组分块，每块算一个共享的 scale（缩放因子）。scale 用 E8M0 格式存（只有指数没有尾数），必须考虑目标 E4M3 格式的最大值 448。
  - **为什么重要**：scale 算错会导致小数值下溢成 0，模型输出直接崩坏。这类"数值精度"bug 非常隐蔽。
  - **动手试试**：
    ```python
    import torch
    # 模拟：一个块里有大值和小值
    block = torch.tensor([448.0, 0.001], dtype=torch.float32)
    amax = block.abs().max()
    # 错误做法：直接用 amax 算 scale
    sb_wrong = torch.floor(torch.log2(amax)) + 127
    # 正确做法：考虑 E4M3 的最大值
    FP8_MAX = 448.0
    sb_right = torch.ceil(torch.log2(amax / FP8_MAX)) + 127
    print(f"错误 scale: {sb_wrong}, 正确 scale: {sb_right}")
    ```
  - **预期结果**：看到两种算法给出的 scale 不同，理解为什么后者能保住小数值。

- **知识点 4：Rust 前端的容错设计（来自 Commit 12）**
  - **是什么**：当 logprob 是 NaN（非数字）时，Rust 前端不再直接报错，而是保留这个值继续处理，让同一个批次里其他正常请求不受影响。
  - **为什么重要**：分布式系统里"一个坏请求不能拖垮整批"。这种"局部失败不影响全局"的设计思想是生产级系统的必备素质。
  - **动手试试**：
    ```python
    # 模拟 NaN 在排序中的行为
    import math
    probs = [float('nan'), -1.0, -0.5, float('-inf')]
    selected = probs[0]
    # 引擎的排名逻辑：统计有多少个 >= selected
    rank = sum(1 for p in probs if p >= selected)
    print(f"NaN 的排名是: {rank}")  # NaN 比较总是 False，所以 rank=0
    ```
  - **预期结果**：看到 NaN 导致排名为 0，理解为什么需要特殊处理。

- **知识点 5：Rust 的 per-request 指标（来自 Commit 18）**
  - **是什么**：给每个请求记录"被抢占了几次"（preemption），并输出成 Prometheus 直方图，方便监控。
  - **为什么重要**：可观测性是运维的基础。知道"哪些请求被反复抢占"能帮你定位显存压力问题。
  - **动手试试**：
    ```bash
    # 启动 vLLM 后，用 curl 拉取指标
    curl -s http://localhost:8000/metrics | grep preemption
    ```
  - **预期结果**：看到 `vllm:request_num_preemptions_sum` 等指标，理解 Prometheus 指标的命名规范（`_sum`、`_count` 后缀）。

## 🧪 重要知识点 & 动手实验

- **知识点 1：为什么 benchmark 里必须用 spawn 而不是 fork？**
  - **是什么**：`multiprocessing` 有两种启动子进程的方式：`fork`（复制父进程内存）和 `spawn`（重新启动一个 Python 解释器）。
  - **为什么重要**：CUDA/XPU 上下文一旦在父进程初始化，`fork` 出来的子进程无法重新初始化 GPU 上下文，会直接崩溃或挂死。这是很多"benchmark 脚本莫名其妙卡住"的根因。
  - **动手试试**：
    ```python
    # demo.py
    import multiprocessing, torch

    def child():
        print("child cuda available:", torch.cuda.is_available())

    if __name__ == "__main__":
        torch.zeros(1, device="cuda")  # 父进程先初始化 CUDA
        ctx = multiprocessing.get_context("spawn")   # 改成 "fork" 试试
        p = ctx.Process(target=child)
        p.start(); p.join()
    ```
  - **预期结果**：用 `spawn` 能正常打印；改成 `fork` 后大概率报 CUDA 相关错误或直接卡死。这就是 commit #6 修的问题。

- **知识点 2：block-wise FP8 量化的 scale 粒度**
  - **是什么**：FP8 只有 8 位，必须配一个"缩放因子"。这个因子是按整张权重（per-tensor）、按行（per-channel）、还是按 128×128 的小块（block-wise）来算，精度和性能差别巨大。
  - **为什么重要**：`[1, 128]` 和 `[128, 128]` 是最常见的两种 block 形状。选错会导致要么精度掉、要么 kernel 走不到最优路径。commit #18 就是在 XPU 上专门处理这两种形状的存储布局。
  - **动手试试**：
    ```python
    import torch
    # 模拟一个 [N, K] 的权重
    w = torch.randn(512, 1024)
    block_n, block_k = 128, 128
    # 按块求 scale
    w_blocks = w.view(w.shape[0]//block_n, block_n,
                      w.shape[1]//block_k, block_k)
    scale = w_blocks.abs().amax(dim=(1,3)) / 448.0  # FP8 e4m3 最大值
    print("scale shape:", scale.shape)   # [4, 8]
    ```
  - **预期结果**：你会看到 scale 的形状是 `[N/128, K/128]`，而不是 `[N, K]`。理解这一点，就能看懂所有 block-FP8 kernel 的接口。

- **知识点 3：CUDA Graph 与调度元数据**
  - **是什么**：CUDA Graph 把一串 GPU kernel 录制下来，之后一次 replay，省掉每个 kernel 的启动开销。但如果某个 kernel 的参数依赖运行时数据（比如每个请求的 top-k 长度），就没法直接录进去。
  - **为什么重要**：commit #2 里 FlashMLA 的 tile scheduler 元数据 kernel 就是这个问题——它原本在 critical path 上，现在被单独抽出来做成独立 kernel，可以提前算好。
  - **动手试试**：
    ```python
    import torch
    x = torch.randn(1024, device="cuda")
    y = torch.empty_like(x)

    # 普通执行
    for _ in range(100):
        y = x * 2

    # CUDA Graph
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        y = x * 2
    for _ in range(100):
        g.replay()
    ```
  - **预期结果**：用 `torch.cuda.synchronize()` 加计时，Graph 版本通常快 10%~30%（小 kernel 越多差距越大）。这就是为什么所有推理框架都在做 graph capture。

- **知识点 4：HTTP/2 明文模式（h2c）**
  - **是什么**：HTTP/2 通常跑在 TLS 上（h2），但也可以明文跑（h2c）。h2c 支持多路复用——一个 TCP 连接上同时跑多个请求，不会互相阻塞。
  - **为什么重要**：LLM 推理里，一个请求可能要跑几十秒，HTTP/1.1 下一个连接只能等一个请求，连接池压力巨大。h2c 让单连接并发成为可能，尤其适合内网 Router → Worker 的场景。
  - **动手试试**：
    ```bash
    # 用 curl 测 h2c（需要 curl 编译了 http2）
    curl --http2-prior-knowledge -v http://localhost:30000/healthz

    # 看响应头里是不是 HTTP/2
    # < HTTP/2 200
    ```
  - **预期结果**：如果服务端支持 h2c，你会看到 `< HTTP/2 200`；否则会 fallback 到 HTTP/1.1 或报错。commit #3 就是让 Router 两端都支持这个。

- **知识点 5：MoE 的量化方案选择（AITER vs Triton）**
  - **是什么**：MoE（混合专家）层有很多 kernel 实现：Triton 版通用但慢，AITER 版是 AMD 专门优化的，但要求特定的权重布局（shuffled）和 scale 粒度。
  - **为什么重要**：commit #20 里，代码根据"是否有 per-channel scale"来决定用哪个后端。选错了要么精度不对，要么性能腰斩。
  - **动手试试**：
    ```python
    # 看一个 MoE 权重的 scale 粒度
    import torch
    w13 = torch.randn(8, 2*2048, 4096)  # [num_experts, 2*inter, hidden]
    # per-tensor: 一个标量
    scale_pt = w13.abs().max() / 448.0
    # per-channel: [num_experts, 2*inter]
    scale_pc = w13.abs().amax(dim=-1) / 448.0
    print(scale_pt.shape, scale_pc.shape)  # () 和 (8, 4096)
    ```
  - **预期结果**：per-channel 的 scale 更细，精度更好，但 kernel 实现更复杂。这就是为什么 AITER 要求 per-channel，而 per-tensor 走不了 AITER 路径。
