### 知识点 1：整数溢出防护（Commit 1）
- **是什么**：当缓冲区大小超过 `INT32_MAX`（约21亿）时，用 `int32_t` 存储会溢出为负数，导致内存分配错误。
- **为什么重要**：大模型推理时，`token_num * topk_num * hidden_size` 很容易超过 21 亿。不修复会导致随机崩溃或内存损坏。
- **动手试试**：
  ```python
  import numpy as np
  # 模拟 int32 溢出
  token_num = 100000
  topk_num = 8
  hidden_size = 7168
  size_int32 = np.int32(token_num * topk_num * hidden_size)
  size_int64 = np.int64(token_num * topk_num * hidden_size)
  print(f"int32: {size_int32} (溢出为负数!)")
  print(f"int64: {size_int64} (正确)")
  ```
- **预期结果**：看到 `int32` 输出为负数，`int64` 输出正确值。理解为什么大模型代码必须用 `int64_t`。

### 知识点 1：RoPE 旋转位置编码的两种配对方式（Neox vs Interleaved）

- **是什么**：RoPE（旋转位置编码）需要对向量的维度进行两两配对旋转。Neox 风格是按 `(i, i + D/2)` 配对，Interleaved（GPT-J）风格是按 `(2i, 2i+1)` 配对。
- **为什么重要**：模型训练时用的是哪种配对方式，推理时就必须用哪种，否则位置信息完全错乱，输出 garbage。今天 Commit 19 就是给 DSpark 投机解码加了 `IS_NEOX` 开关来支持 LFM2 模型。
- **动手试试**：
```python
import torch

D = 8  # head_dim
half = D // 2

# Neox style: pairs (0,4), (1,5), (2,6), (3,7)
neox_off1 = torch.arange(half)
neox_off2 = torch.arange(half) + half

# Interleaved style: pairs (0,1), (2,3), (4,5), (6,7)
int_off1 = 2 * torch.arange(half)
int_off2 = 2 * torch.arange(half) + 1

print("Neox pairs:", list(zip(neox_off1.tolist(), neox_off2.tolist())))
print("Interleaved pairs:", list(zip(int_off1.tolist(), int_off2.tolist())))
```
- **预期结果**：你会看到两种完全不同的配对方式。如果你在加载一个用 Neox 训练的模型时用了 Interleaved 的 RoPE 实现，模型输出会完全不对。

### 知识点 2：CUDA Graph 的 Prefill 捕获与 Padding

- **是什么**：CUDA Graph 可以把一串 GPU 内核调用"录下来"重复播放，省去内核启动开销。但 prefill（预填充）阶段的 token 数不固定，需要用 padding（填充）把不同长度的请求对齐到固定 bucket。
- **为什么重要**：Commit 14 修复了一个 bug——非 gathered 的 FullCG（完整 CUDA Graph）路径下，`num_token_non_padded` 缓冲区没有正确填充，导致模型读到陈旧数据。如果你自己写 CUDA Graph 捕获，padding 逻辑是最容易出错的地方。
- **动手试试**：观察 SGLang 中 CUDA Graph 的 bucket 配置：

### 知识点 3：KV 缓存描述符（Memory Descriptor）的对齐

### 知识点 4：统一内存池的"虚拟页到物理页"翻译

- **是什么**：在统一内存池中，请求看到的是虚拟页号，实际存储位置是物理页号。内核需要一张 `v2p`（virtual-to-physical）映射表来翻译。
- **为什么重要**：Commit 1 和 2 在重构这个翻译逻辑——以前每个注意力后端各自翻译，现在统一在 `ForwardBatch` 构造时翻译一次。这能避免重复计算，但也意味着内核接口在变化。
- **动手试试**：模拟页表翻译：
```python
page_size = 16  # 每页 16 个 token
req_to_token = [101, 102, 103, 104]  # 每个请求的 token 起始页

# 给定一个全局 token 索引，找到它所在的物理页
def token_to_page(token_idx, req_id, page_size):
    page_offset = token_idx // page_size
    return req_to_token[req_id] + page_offset

# 给定一个页号，计算该页内所有 token 的物理位置
def page_to_tokens(page_id, page_size):
    return [page_id * page_size + i for i in range(page_size)]

print(f"Token 100 在请求 0 中的物理页: {token_to_page(100, 0, page_size)}")
print(f"物理页 101 包含的 token: {page_to_tokens(101, page_size)}")
```
- **预期结果**：你会理解为什么需要 `ENTRY_PAGE_SIZE` 这个参数——当源表是页粒度时，需要先除以页大小再取模才能得到正确的 token 索引。

### 知识点 5：投机解码（Speculative Decoding）的 Draft 模型 KV 管理

- **是什么**：投机解码用一个小的 draft 模型快速生成多个候选 token，再用大模型一次验证。draft 模型的 KV 缓存需要单独管理。
- **为什么重要**：Commit 4 将 draft token 容量从运行时状态中解耦，避免 adaptive 算法改变活跃宽度时容量不稳定。Commit 20 处理了 decode 端同时有 draft 和 target 模型 KV 时的描述符布局。
