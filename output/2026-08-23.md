### 知识点 1：投机解码（Speculative Decoding）与状态修复
- **是什么**：投机解码用一个小模型"猜测"大模型的输出，然后大模型一次性验证多个 token，从而加速推理。但猜测的 token 数量变化会破坏状态管理，比如 Mamba 模型的卷积状态。
- **为什么重要**：投机解码是当前 LLM 推理加速的核心技术之一，但实现细节非常容易出错。今天这个 commit 修复了短卷积（short_conv）模型在投机解码下的状态大小计算和更新逻辑，这类 bug 会导致推理结果错误。

### 知识点 2：Prefix Caching 与 Checkpoint
- **是什么**：Prefix caching 将已计算过的 prompt 前缀的 KV 状态缓存起来，下一次遇到相同前缀时直接复用，避免重复计算。FlashKDA 的优化是支持在缓存中保存"中间 checkpoint"，从而跳过部分前缀的计算。
- **为什么重要**：这是提升 TTFT（首 token 延迟）的关键技术，尤其对频繁使用相同系统提示词或文档前缀的场景（如 RAG、对话系统）收益巨大。这个 commit 显示 9%~25% 的 TTFT 提升。
- **动手试试**：

- **预期结果**：你会发现 checkpoint 允许在缓存中存储多个中间状态，而不仅仅是最终状态。这样当新请求的前缀与缓存部分匹配时，可以直接从最近的 checkpoint 开始计算。

### 知识点 2：文件映射（Memory-Mapped File）与匿名内存
- **是什么**：把文件内容直接映射到进程地址空间，读取时操作系统按需从磁盘加载，内存压力大时可以被回收。而匿名内存（如 `torch.Tensor`）则不可回收。
- **为什么重要**：Commit 2 把 VAE 权重的 dtype 转换结果从匿名内存改为文件缓存，这样内存不足时系统可以丢弃缓存，重新从磁盘读取，而不是直接 OOM。
- **动手试试**：
```python
import mmap
import os, tempfile

# 创建一个 100MB 的文件映射（模拟 safetensors 权重文件）
with tempfile.NamedTemporaryFile(delete=False) as f:
    f.write(b'\x00' * 100 * 1024 * 1024)
    path = f.name

# 映射文件到内存
with open(path, 'rb') as f:
    with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as mm:
        # 读取前 10 个字节
        print(f"读取到: {mm[:10]}")
        # 查看进程的 RSS（驻留内存）
        rss_kb = int(open('/proc/self/status').read().split('VmRSS:')[1].split()[0])
        print(f"当前 RSS: {rss_kb} KB")

os.unlink(path)
```
- **预期结果**：你会看到文件映射只占用极少的 RSS，因为数据按需从磁盘加载。这解释了为什么 SGLang 用文件缓存代替匿名内存可以显著降低内存压力。

### 知识点 3：GQA（分组查询注意力）与 KV 缓存
- **是什么**：传统 MHA（多头注意力）中每个查询头都有独立的 KV 头，内存开销大。GQA 让多个查询头共享一个 KV 头，大幅减少 KV 缓存。
- **为什么重要**：Commit 5 修复了 AMD 平台上 GQA 的 bug——之前代码错误地把单个 KV 头 expand 成多个，导致注意力计算变成 MHA，KV 流量增加 7 倍。正确的做法是让内核自动推导分组数。
- **动手试试**：
```python
import torch

# 模拟 GQA 的 K/V 张量：1 个 KV 头，8 个 Q 头
q = torch.randn(4, 8, 64)    # [seq, q_heads, head_dim]
k = torch.randn(4, 1, 64)    # [seq, kv_heads, head_dim]
v = torch.randn(4, 1, 64)

# 正确方式：不 expand，让推理引擎自动处理 GQA 分组
# 错误方式（commit 修复前）：
k_wrong = k.expand(-1, 8, -1)  # [4, 8, 64] 显式复制
print(f"错误方式 K 形状: {k_wrong.shape}, 显存: {k_wrong.numel() * 4 / 1024:.1f} KB")
print(f"正确方式 K 形状: {k.shape}, 显存: {k.numel() * 4 / 1024:.1f} KB")
```
- **预期结果**：错误方式显存是正确方式的 8 倍。在长上下文场景（如 128K tokens），这个差异会放大到 GB 级别，直接影响推理速度。

### 知识点 4：预热请求（Warmup Request）的帧数对齐
- **是什么**：视频生成模型对帧数有对齐要求（如必须是 8 的倍数），预热请求的帧数也必须对齐，否则 CUDA 图缓存不匹配。
- **为什么重要**：Commit 1 修复了 LTX-2.3 多 GPU 场景下预热帧数不足的问题。如果预热帧数与真实请求不匹配，推理时会重新编译 CUDA 图，导致首个请求极慢。
- **动手试试**：
```python
def align_frames(num_frames: int, alignment: int = 8) -> int:
    """将帧数向上对齐到 alignment 的倍数"""
    return ((num_frames + alignment - 1) // alignment) * alignment

# 模拟不同模型的预热帧数选择
for requested in [17, 25, 33]:
    generic = min(requested, 17)          # 通用上限 17 帧
    ltx2_multi_gpu = min(requested, 25)   # LTX-2.3 多 GPU 上限 25 帧
    aligned = align_frames(ltx2_multi_gpu)
    print(f"请求 {requested} 帧 -> 通用预热 {generic} 帧, LTX2 预热 {ltx2_multi_gpu} 帧 (对齐后 {aligned})")
```
- **预期结果**：你会看到不同模型的预热帧数上限不同，LTX-2.3 多 GPU 需要 25 帧来覆盖其 latent shape，而通用模型只需 17 帧。

### 知识点 5：抽象类与测试替身（Test Stub）
- **是什么**：Python 的 `abc` 模块可以定义抽象基类（ABC），子类必须实现所有抽象方法才能被实例化。测试时用桩（stub）类提供最小实现。
