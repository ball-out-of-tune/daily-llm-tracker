## 🧪 重要知识点 & 动手实验

### 知识点 1：M-RoPE 缓存为什么能省 4 倍显存

- **是什么**：多模态模型（如 Qwen3-VL）用 M-RoPE 编码位置，它的位置索引可能远超 token 数量，所以之前直接开 4 倍缓存。但新模型的位置不会超过 token 数，可以只开 1 倍。
- **为什么重要**：KV Cache 显存直接影响你能跑多长的上下文、batch 能开多大。省 4 倍缓存意味着可以多塞 4 倍的序列长度。
- **动手试试**：
```bash
# 查看当前模型的 max_position_embeddings
python -c "
from transformers import AutoConfig
cfg = AutoConfig.from_pretrained('Qwen/Qwen2.5-VL-7B-Instruct')
print('max_position_embeddings:', cfg.max_position_embeddings)
print('理论缓存大小:', cfg.max_position_embeddings * 4)
"
```
- **预期结果**：看到 `max_position_embeddings` 是 32768，之前 vLLM 会分配 131072 的 cos/sin 缓存，现在 Qwen3-VL 只分配 32768。

### 知识点 2：量化 KV Cache 与 NVFP4

- **是什么**：KV Cache 是推理时保存的注意力键值，占显存大头。NVFP4 是 NVIDIA 的 4 比特浮点格式，把 KV Cache 压到原来的 1/4。
- **为什么重要**：长上下文（如 128K token）时 KV Cache 能吃掉几十 GB 显存，量化后可以跑更长的上下文或更大的 batch。
- **动手试试**：
```bash
# 启动 vLLM 并指定量化 KV Cache（需要支持的 GPU）
vllm serve Qwen/Qwen3-8B \
    --kv-cache-dtype nvfp4 \
    --max-model-len 32768 \
    --gpu-memory-utilization 0.9
```
- **预期结果**：日志中会显示 `KV cache dtype: nvfp4`，同样的显存下 `max_model_len` 可以设得更大。

### 知识点 3：CUDA Graph 与 eager break

- **是什么**：CUDA Graph 把一串 GPU 操作录制下来重放，减少 kernel launch 开销。但有些算子（如 Mamba 的状态更新）形状动态，不能录进图里，需要"跳出"图以 eager 模式执行。
- **为什么重要**：不理解这点，你会看到奇怪的性能抖动或报错，比如"Mamba 模型开 CUDA Graph 后结果不对"。
- **动手试试**：
```python
# 观察 eager break 装饰器的作用

@eager_break_during_capture
def my_dynamic_op(x):
    # 这个函数在 CUDA Graph 捕获期间会以 eager 模式执行
    return x * 2

# 在 vLLM 中默认启用
import vllm
llm = vllm.LLM("Qwen/Qwen3-8B", compilation_config={"level": 3})
```
- **预期结果**：日志中会看到 `eager break` 相关提示，Mamba 模型在 CUDA Graph 下也能正确运行。

### 知识点 4：投机解码与辅助隐藏状态（EAGLE3）

- **是什么**：投机解码用一个"草稿模型"预测多个 token，主模型一次验证。EAGLE3 需要主模型输出中间层的隐藏状态给草稿模型用。
- **为什么重要**：Granite 现在支持 EAGLE3，意味着你可以用投机解码加速 Granite 推理，速度提升 2-3 倍。

- **预期结果**：日志中会显示 `Speculative decoding enabled`，吞吐量相比不用投机解码有显著提升。

### 知识点 5：LoRA 与 MoE 的混合格式

- **是什么**：LoRA 是低秩适配器，MoE 是混合专家。GPT-OSS 模型的 gate/up 投影在 LoRA 中有多种存储格式（2D 和 3D），混用时容易出错。

## 💡 今日关键词

- **关键词：LoRA 合并的精度陷阱**
  - **一句话通俗解释**：把一个小补丁（LoRA）合并到主模型权重里时，如果补丁太小，会被大模型的低精度（BF16）直接"四舍五入抹掉"。
  - **为什么社区在关注**：扩散模型（Diffusion）的蒸馏 LoRA 更新量极小，合并后性能反而崩塌，说明"合并"不是无脑优化，需要智能判断。
  - **对新手意味着什么**：学习数值精度（FP32 vs BF16）和 LoRA 原理时，不要只看公式，要理解"浮点数有效位数"这个底层约束。

- **关键词：模型加载加速（InstantTensor / 分布式预取）**
  - **一句话通俗解释**：大模型权重动辄几十 GB，从磁盘读进 GPU 很慢，用分布式并行加载 + 流水线预取可以把启动时间大幅缩短。
  - **为什么社区在关注**：推理服务的冷启动时间直接影响成本和用户体验，加载器优化成为新的竞争点。
  - **对新手意味着什么**：I/O 优化、流水线（pipeline）、分布式协调是工程落地的必备技能，不只是算法。

- **关键词：CUDA Graph 与动态形状**
  - **一句话通俗解释**：CUDA Graph 把一串 GPU 操作"录制成宏"，回放时省去启动开销；但 prefill 阶段 token 数不固定，所以要"分段录制"（piecewise）。

- **关键词：PD 分离与内存池**

- **关键词：新硬件适配（SM90 / GB300 / ROCm）**

## 🧪 重要知识点 & 动手实验

### 知识点 1：LoRA 合并的精度损失（BF16 舍入）
- **是什么**：LoRA 是一个低秩补丁 `ΔW = B @ A`，合并到主权重 `W` 时执行 `W + ΔW`。如果 `W` 是 BF16（约 8 位有效数字），而 `ΔW` 比 `W` 的最小可表示单位（ulp）还小，加上去就等于没加。
- **为什么重要**：蒸馏 LoRA（如 Larry Turbo）更新量常在 1e-4 量级，合并后 77%–97% 的更新被舍入掉，模型质量崩塌。不懂这个会误以为"合并只是加速，不影响效果"。
- **动手试试**：
  ```python
  import torch

  # 模拟一个 BF16 权重和一个极小的 LoRA 更新
  W = torch.randn(1024, 1024, dtype=torch.bfloat16)
  delta = torch.randn(1024, 1024, dtype=torch.float32) * 1e-4  # 蒸馏 LoRA 量级

  # 直接合并（BF16 精度）
  W_merged = (W.float() + delta).to(torch.bfloat16)
  lost = (W_merged.float() - (W.float() + delta))
  print("合并后丢失的更新范数占比:", (lost.norm() / delta.norm()).item())

  # 对比 FP32 合并
  W_fp32 = W.float() + delta
  print("FP32 合并保留完整更新")
  ```
- **预期结果**：会看到丢失比例接近 1.0（几乎全部丢失），说明小更新在 BF16 下被完全抹掉。这就是 commit #1 引入 `merge_rounding_norms` 检测的原因。

### 知识点 2：CUDA Graph 与 max_bs 的钳制
- **是什么**：CUDA Graph 需要预先捕获固定 batch size 的计算图。`max_bs` 是捕获的最大 batch，`max_running_requests` 是调度器允许的最大并发请求数。如果 `max_bs > max_running_requests`，就白白浪费显存捕获了永远不会用到的图。
- **为什么重要**：显存浪费会挤压 KV Cache 空间，降低吞吐。commit #3 把默认 `max_bs` 钳制到 `max_running_requests`，是个"小改动大收益"的典型。
- **动手试试**：
  ```bash
  # 启动一个 server，观察 CUDA Graph 捕获的 batch size 列表
  python -m sglang.launch_server \
    --model-path Qwen/Qwen2.5-0.5B-Instruct \
    --max-running-requests 8 \
    --cuda-graph-max-bs-decode 160 \
    2>&1 | grep -i "cuda graph\|capture"
  ```
- **预期结果**：日志里会显示实际捕获的 batch size 被限制在 8 以内，而不是 160，节省了显存。

### 知识点 3：msgspec 替代 pickle 做进程间通信
- **是什么**：`pickle` 能反序列化任意 Python 对象，包括执行代码，是安全漏洞。`msgspec` 用 msgpack 格式，只允许预定义的结构体（Struct），反序列化时严格校验字段。
- **为什么重要**：commit #10 指出 PP0 的 ZMQ socket 绑定在可路由地址且无认证，用 pickle 等于开了远程代码执行后门。任何跨进程/跨网络的通信都不该用 pickle。
- **动手试试**：
  ```python
  import msgspec

  class Op(msgspec.Struct, array_like=True, frozen=True):
      kind: int
      rank: int
      key: int

  enc = msgspec.msgpack.Encoder()
  dec = msgspec.msgpack.Decoder(Op)

  data = enc.encode(Op(kind=1, rank=2, key=42))
  print("编码后字节:", data)
  print("解码:", dec.decode(data))

  # 尝试解码一个畸形消息
  try:
      dec.decode(b'\x81\xa4evil')  # 不合法结构
  except Exception as e:
      print("拒绝畸形消息:", type(e).__name__)
  ```
- **预期结果**：正常消息能往返；畸形消息抛异常被丢弃，不会执行任意代码。

### 知识点 4：DeepGEMM 的 block32 量化
- **是什么**：FP8 量化通常用 128×128 的 block 计算缩放因子（scale）。DeepSeek V4.1 用 32×32 的更细粒度 block，精度更高但需要专门的 kernel。
- **为什么重要**：commit #20 为 SM90 引入 native block32 DeepGEMM，说明量化粒度对精度影响显著，硬件厂商在 kernel 层面做优化。
- **动手试试**：
  ```python
  import torch

  # 模拟 FP8 量化：不同 block size 对精度的影响
  W = torch.randn(256, 256, dtype=torch.float32)

  def quantize_fp8(W, block):
      W = W.clone()
      for i in range(0, W.shape[0], block):
          for j in range(0, W.shape[1], block):
              blk = W[i:i+block, j:j+block]
              scale = blk.abs().max() / 448.0  # FP8 E4M3 最大约 448
              W[i:i+block, j:j+block] = (blk / scale).clamp(-448, 448) * scale
      return W

  err128 = (quantize_fp8(W, 128) - W).abs().mean()
  err32  = (quantize_fp8(W, 32)  - W).abs().mean()
  print(f"block128 误差: {err128:.6f}")
  print(f"block32  误差: {err32:.6f}")
  ```
- **预期结果**：block32 的误差明显小于 block128，验证了细粒度量化的优势。

### 知识点 5：FlashAttention 的 mask_mod（自定义注意力掩码）
- **是什么**：`mask_mod` 是一个回调函数，在注意力计算时动态决定哪些 query-key 对可见。它比固定 mask 更灵活，但需要 FA4 支持。
- **为什么重要**：commit #17 为 Gemma4 启用 FA4 并支持 head-dim 512 的 mask_mod，说明长上下文、变长序列、稀疏注意力等场景需要更灵活的注意力控制。
- **动手试试**：
  ```python
  # 伪代码：理解 mask_mod 的作用
  def sliding_window_mask(q_idx, kv_idx, window=4):
      """只允许每个 query 看到前 window 个 key"""
      return kv_idx <= q_idx and kv_idx > q_idx - window

  # 在 FA4 中传入 mask_mod=sliding_window_mask
  # 效果：注意力计算时自动跳过窗口外的 key，节省计算
  ```
- **预期结果**：理解 mask_mod 是"运行时动态掩码"，比预生成 mask 张量更省显存，适合滑动窗口、因果变体等场景。
