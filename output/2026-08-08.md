### 知识点 1：MoE 中的 TopK 稀疏计算
- **是什么**：在 MoE 模型中，每个 token 只激活 top-k 个专家（如 k=2），而不是所有专家。TopK 操作是 MoE 推理的热点 kernel。

  ```python
  num_experts = 4
  top_k = 2
  
  # 每个 token 对每个专家的得分

  print("原始得分:", scores)

  ```

### 知识点 2：MXFP4 量化格式
- **是什么**：MXFP4 是 OCP 组织定义的微缩放格式，用 4 位存数据（e2m1：1 位符号、2 位指数、1 位尾数），配合 e8m0 格式的 per-block scale（每 32 个元素一个缩放因子）。相比 FP16，显存占用减少 75%。
- **为什么重要**：Commit 16 和 Commit 13 分别实现了 MXFP4 在线量化和 NVFP4 KV Cache 的 4-over-6 scale 搜索。这是当前最前沿的量化技术，能让你在同样显存下跑更大的模型。
- **动手试试**：

  ```bash
  pip install vllm --upgrade
  
  # 使用 MXFP4 量化运行模型（需要支持 MXFP4 的 GPU）
  vllm serve Qwen/Qwen3-4B --quantization mxfp4
  ```
  如果 GPU 不支持，可以尝试：
  ```python
  # 模拟 MXFP4 的 per-block scale 量化过程
  import torch
  
  def mxfp4_quantize(tensor, block_size=32):
      """模拟 MXFP4 量化：按 block 计算 scale，然后量化到 4bit"""
      orig_shape = tensor.shape
      flat = tensor.flatten()
      # 按 block_size 分块
      n_blocks = (flat.numel() + block_size - 1) // block_size
      padded = torch.zeros(n_blocks * block_size, dtype=flat.dtype)
      padded[:flat.numel()] = flat
      blocks = padded.view(n_blocks, block_size)
      
      # 计算每个 block 的 scale（取绝对值最大值）
      scales = blocks.abs().max(dim=1).values
      # 量化：除以 scale，然后四舍五入到最近的 e2m1 值（简化：用 4bit 表示）
      quantized = blocks / scales.unsqueeze(1)
      # 模拟 4bit 量化（这里用 8bit 代替演示）
      quantized_4bit = torch.round(quantized * 8) / 8
      
      # 反量化
      dequantized = quantized_4bit * scales.unsqueeze(1)
      return dequantized[:flat.numel()].reshape(orig_shape)
  
  # 测试
  x = torch.randn(64, 64)
  x_q = mxfp4_quantize(x)
  print(f"原始数据范围: {x.min():.4f} ~ {x.max():.4f}")
  print(f"量化后误差: {(x - x_q).abs().mean():.6f}")
  ```
- **预期结果**：你会看到量化带来的精度损失（约 0.01 量级），理解为什么需要 per-block scale 来减少损失。

### 知识点 3：ZMQ 端口 TOCTOU 竞态条件
- **是什么**：TOCTOU（Time-of-Check to Time-of-Use）竞态，指先检查端口是否可用，再绑定使用，中间可能有其他进程抢占了该端口。就像先看厕所没人，走过去发现被人占了。
- **为什么重要**：Commit 2 修复了分布式通信中一个隐蔽的端口冲突 bug。在分布式训练/推理中，多进程同时启动时端口冲突是常见问题，理解这个 bug 能帮你避免类似的分布式部署问题。
- **动手试试**：
  ```python
  import socket
  import threading
  import time
  
  # 模拟 TOCTOU 竞态
  def get_open_port():
      """检查一个可用端口（传统方式，有竞态风险）"""
      with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
          s.bind(("127.0.0.1", 0))
          port = s.getsockname()[1]
          # 模拟检查后到绑定前的延迟
          time.sleep(0.1)
          return port
  
  def bind_port(port):
      """尝试绑定指定端口"""
      try:
          with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
              s.bind(("127.0.0.1", port))
              print(f"成功绑定端口 {port}")
              time.sleep(0.5)
      except OSError as e:
          print(f"绑定端口 {port} 失败: {e}")
  
  # 两个线程同时获取端口并绑定
  # 正确做法：直接 bind 端口 0 让内核分配，避免竞态
  port1 = get_open_port()
  t1 = threading.Thread(target=bind_port, args=(port1,))
  t2 = threading.Thread(target=bind_port, args=(port1,))  # 拿到同一个端口
  t1.start()
  t2.start()
  t1.join()
  t2.join()
  ```
- **预期结果**：你会看到两个线程拿到同一个端口，其中一个绑定失败。这就是 TOCTOU 竞态。正确做法是直接 `bind(("127.0.0.1", 0))` 让内核分配唯一端口。

### 知识点 4：CUDA Graph 捕获
- **是什么**：CUDA Graph 将一系列 GPU kernel 调用"录制"成一个图，然后可以重复执行，减少 CPU 启动 kernel 的开销。就像把做菜的每个步骤录下来，以后一键自动完成。
- **为什么重要**：Commit 18 将 Blackwell GPU 的 CUDA Graph 默认捕获大小从 512 提升到 1024，Commit 8 优化了 DeepSeek V3.2 的捕获范围。理解 CUDA Graph 能帮你理解为什么 vLLM 在静态 shape 下推理这么快。
- **动手试试**：
  ```python
  import torch
  
  # 演示 CUDA Graph 的基本用法
  # 注意：需要 CUDA GPU
  
  if torch.cuda.is_available():
      # 固定输入 shape（CUDA Graph 要求静态 shape）
      N = 1024
      x = torch.randn(N, N, device="cuda")
      w = torch.randn(N, N, device="cuda")
      
      # 正常执行
      def compute(x, w):
          return torch.relu(x @ w)
      
      # 预热
      for _ in range(3):
          y = compute(x, w)
      
      # CUDA Graph 捕获
      g = torch.cuda.CUDAGraph()
      # 使用静态输入输出缓冲区
      static_x = x.clone()
      static_w = w.clone()
      static_y = torch.empty_like(static_x)
      
      with torch.cuda.graph(g):
          static_y = torch.relu(static_x @ static_w)
      
      # 重放（输入变化时复制到缓冲区）
      new_x = torch.randn(N, N, device="cuda")
      static_x.copy_(new_x)
      g.replay()
      print("CUDA Graph 重放完成，输出 shape:", static_y.shape)
  else:
      print("需要 CUDA GPU 才能体验 CUDA Graph")
  ```
- **预期结果**：如果你有 GPU，会看到 CUDA Graph 捕获和重放的过程。理解为什么输入必须放在固定缓冲区，以及为什么 vLLM 需要 padding 到固定长度。

### 知识点 5：序列并行（Sequence Parallelism）
- **是什么**：当单个序列太长放不进 GPU 显存时，把序列切分成多段，分别在不同 GPU 上处理，最后再拼接结果。就像把一篇长文章分给几个人同时翻译。
- **为什么重要**：Commit 5 优化了 DeepSeek V3.2 的序列并行实现。处理超长上下文（如 128K tokens）时，序列并行是必不可少的。
- **动手试试**：

  ```python
      world_size = 2
      seq_per_rank = 4
      
      # 每个 rank 的隐藏状态（简化：一维）
      # 实际中每个 rank 计算部分结果后需要 all-gather 再切片
      local_hidden = torch.randn(seq_per_rank)

  ```
- **预期结果**：你会看到序列并行中数据的切分和拼接过程，理解为什么需要通信操作（all-gather、reduce-scatter）。

## 🧪 重要知识点 & 动手实验

### 知识点 1：MoE 路由后端（MoE Runner Backend）
- **是什么**：MoE 模型在推理时，需要根据输入 token 动态选择激活哪些专家（expert）。负责这个"路由"和"专家计算"的底层实现，就是 MoE runner backend。
- **为什么重要**：不同的 backend（如 `triton_kernel`、`flashinfer_trtllm`）在不同硬件和模型上有不同的性能和兼容性。选择错误可能导致性能极差甚至无法运行。Commit 1 中，`InternS2Mobius` 模型被强制指定使用 `triton_kernel` 后端，因为它有 2560 个专家，只有这个后端经过验证。
- **动手试试**：
  ```bash
  # 查看当前支持哪些 MoE runner backend
  python -c "from sglang.srt.server_args import ServerArgs; print(ServerArgs.moe_runner_backend)"
  
  # 尝试用不同后端启动一个 MoE 模型（如果硬件支持）
  # 注意：这需要你有相应的 GPU 和模型
  # python -m sglang.launch_server --model-path Qwen/Qwen2-57B-A14B-Instruct --moe-runner-backend triton_kernel --tp 4
  # python -m sglang.launch_server --model-path Qwen/Qwen2-57B-A14B-Instruct --moe-runner-backend flashinfer_trtllm_routed --tp 4
  ```
- **预期结果**：你能看到 `moe_runner_backend` 的默认值（通常是 `auto`），并通过命令行参数覆盖它。如果硬件不支持某些后端，启动时会报错。理解了 `auto` 模式会根据模型配置自动选择后端的逻辑，你就掌握了这个知识点。

### 知识点 2：序列并行（Sequence Parallelism）—— Ulysses 与 Ring
- **是什么**：当序列长度太长，单张 GPU 放不下时，把序列切分成多段，分别在不同 GPU 上计算注意力，就是序列并行。Ulysses 按注意力头切分，Ring 按序列长度切分。
- **为什么重要**：这是处理超长上下文（如 256K、1M token）的关键技术。Commit 2 展示了如何在跨节点场景下组合使用 Ulysses（节点内）和 Ring（跨节点），以克服单节点 GPU 数量限制和跨节点通信瓶颈。
- **动手试试**：
  ```bash
  # 查看 sglang 中与序列并行相关的参数
  python -c "from sglang.srt.server_args import ServerArgs; print(ServerArgs.sp_degree, ServerArgs.ulysses_degree, ServerArgs.ring_degree)"
  
  # 阅读相关文档（如果已安装）
  # less docs/cookbook/diffusion/MiniMax/MiniMax-H3.mdx
  ```
- **预期结果**：你会看到 `sp_degree`（总序列并行度）、`ulysses_degree` 和 `ring_degree` 的默认值。理解 `sp_degree = ulysses_degree * ring_degree` 这个关系，以及它们如何配合 `--nnodes` 和 `--node-rank` 使用，你就掌握了跨节点序列并行的基本配置方法。

### 知识点 3：推测解码（Speculative Decoding）中的终止条件
- **是什么**：推测解码让一个小模型（draft model）快速生成多个候选 token，再由大模型（target model）一次验证。这样一次前向传播可以接受多个 token，加速生成。但这也给"何时停止"带来了复杂性。
- **为什么重要**：如果处理不当，生成的文本可能超出 `max_new_tokens` 限制，或者提前截断。Commit 13 修复了"在一次接受多个 token 的步骤中，如果同时命中了 EOS 和长度上限，如何正确判定终止原因"的 bug。
- **动手试试**：
  ```python
  # 模拟一个简单的场景：一次接受了 3 个 token，其中第 2 个是 EOS，同时总长度超过了 max_new_tokens
  max_new_tokens = 5
  output_ids = [1, 2, 3, 4, 5, 6]  # 已经生成了 6 个 token，超过限制
  new_accepted_tokens = [4, 5, 6]  # 这次接受的后 3 个 token
  
  # 旧逻辑：先检查长度，直接返回 length finish，忽略了 EOS
  # 新逻辑：先检查 EOS，发现 EOS 在超限位置，将 finish 降级为 length finish，并截断输出
  ```
- **预期结果**：你理解了新逻辑的顺序：先检查特殊 token（EOS/stop），再检查长度上限。如果 EOS 在超限位置之后，最终结果仍然是长度终止，但输出会被截断到 `max_new_tokens` 长度，避免输出超出限制。

### 知识点 4：Triton 内核加载诊断（Kernel Load Watch）
- **是什么**：Triton 内核在第一次被调用时才编译并加载到 GPU。如果这个"首次加载"发生在服务已经开始处理请求之后，可能导致延迟尖峰甚至 OOM（因为显存已被 KV cache 等占用）。
- **为什么重要**：Commit 15 引入了一个监控模块，可以在服务启动后检测到这种"迟到"的 Triton 内核加载，并发出警告或直接崩溃（在 CI 中用于强制保证所有内核都在启动时完成预热）。
- **动手试试**：

- **预期结果**：你了解了这些环境变量的作用。理解"启动预热（warmup）"的重要性，以及在 CI 中如何通过这种机制确保代码质量，你就掌握了这个知识点。

### 知识点 5：YaRN 旋转位置编码（RoPE）的缩放因子
- **是什么**：YaRN 是一种将模型上下文长度从训练长度外推（extrapolate）到更长长度的方法。它通过调整 RoPE 的缩放因子（mscale）来实现。
- **为什么重要**：如果缩放因子应用错误（比如重复应用），会导致模型输出质量严重下降。Commit 7 修复了一个这样的 bug，并添加了测试来防止回归。
- **动手试试**：
  ```python
  # 模拟修复前后的计算
  import math

  def yarn_get_mscale_simple(factor):
      # 这是 sglang 中 yarn.py 的简化版本
      return 0.1 * math.log(factor) + 1.0

  factor = 128.0
  attention_factor = 1.4852030263919618  # 模型配置中给出的最终 mscale

  # 旧逻辑（错误）：直接把 attention_factor 作为 attn_factor，而 sglang 内部会再乘一次 mscale_simple
  old_attn_factor = attention_factor
  old_effective_mscale = old_attn_factor * yarn_get_mscale_simple(factor)
  print(f"旧逻辑有效 mscale: {old_effective_mscale:.4f} (期望 {attention_factor:.4f})")

  # 新逻辑（正确）：除以 mscale_simple，避免双重应用
  new_attn_factor = attention_factor / yarn_get_mscale_simple(factor)
  new_effective_mscale = new_attn_factor * yarn_get_mscale_simple(factor)
  print(f"新逻辑有效 mscale: {new_effective_mscale:.4f} (期望 {attention_factor:.4f})")
  ```
- **预期结果**：你会看到旧逻辑计算出的有效 mscale 是期望值的平方（约 2.2），而新逻辑恢复了正确的值（约 1.485）。这直观地展示了"双重应用" bug 的危害和修复方法。
