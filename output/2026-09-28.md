### 知识点 1：CUDA Graph 与图回放微基准（来自 Commit 2 和 Commit 8）

- **是什么**：CUDA Graph 把"启动 kernel A → 启动 kernel B → 启动 kernel C"这一串操作录制成一张图，之后一次调用就能全部回放，省掉每个 kernel 几微秒的 CPU 启动开销。
- **为什么重要**：在 decode 阶段，每个 token 只算一次，kernel 很小但数量多，CPU 启动开销可能比 GPU 计算还大。不用 CUDA Graph，你的吞吐可能只有理论值的 50%。不懂它，你调不出高吞吐。
- **动手试试**：
  ```python
  import torch

  # 1. 普通执行：每次都要 CPU 逐个启动 kernel
  x = torch.randn(1024, 1024, device="cuda")
  y = torch.randn(1024, 1024, device="cuda")

  # 2. 用 CUDA Graph 录制
  g = torch.cuda.CUDAGraph()
  # 预热（必须先跑一次，因为 graph 捕获不能包含内存分配）
  for _ in range(3):
      z = x @ y
  torch.cuda.synchronize()

  with torch.cuda.graph(g):
      z = x @ y

  # 3. 回放
  import time
  torch.cuda.synchronize()
  t0 = time.perf_counter()
  for _ in range(1000):
      g.replay()
  torch.cuda.synchronize()
  t1 = time.perf_counter()
  print(f"graph replay: {(t1-t0)/1000*1e6:.2f} us/call")

  # 4. 对比普通执行
  torch.cuda.synchronize()
  t0 = time.perf_counter()
  for _ in range(1000):
      z = x @ y
  torch.cuda.synchronize()
  t1 = time.perf_counter()
  print(f"eager:        {(t1-t0)/1000*1e6:.2f} us/call")
  ```
- **预期结果**：graph replay 的单次调用时间明显低于 eager（小 kernel 时差距可达数倍）。你会看到 Commit 2 里提到的"用 graph replay + 轮转 buffer 让 L2 cache 冷启动"就是这个思路的延伸。

### 知识点 2：Triton 融合 kernel——把两次 RoPE 合成一次（来自 Commit 17）

- **是什么**：RoPE（旋转位置编码）原来要对 Q 和 K 各调用一次 kernel，现在把两个调用融合成一个 in-place kernel，直接在打包的 QKV buffer 上原地修改。
- **为什么重要**：融合 kernel 减少显存读写次数。原来 Q 和 K 各读一次写一次，现在一次读一次写。在 ViT 这种每层都要做 RoPE 的场景，收益累积起来很可观。不懂融合，你写的 kernel 永远比别人的慢一倍。
- **动手试试**：
  ```python
  # 先验证 Commit 17 的测试思路：融合 kernel 必须和逐张量路径逐位一致
  import torch
  from vllm.model_executor.layers.rotary_embedding.common import ApplyRotaryEmb
  from vllm.model_executor.layers.rotary_embedding.packed_qk_rope import packed_qk_rope_

  num_tokens, num_heads, head_dim = 257, 12, 128
  angles = torch.rand(num_tokens, head_dim // 2, device="cuda") * torch.pi
  freqs_cis = torch.polar(torch.ones_like(angles), angles)
  cos, sin = freqs_cis.real.contiguous(), freqs_cis.imag.contiguous()

  xqkv = torch.randn(num_tokens, 3, num_heads, head_dim,
                     dtype=torch.bfloat16, device="cuda")
  xqkv_ref = xqkv.clone()
  xq, xk, xv = torch.unbind(xqkv_ref, dim=-3)

  op = ApplyRotaryEmb(enforce_enable=True, is_neox_style=False,
                      enable_fp32_compute=True)
  xq_ref = op(xq, cos, sin)
  xk_ref = op(xk, cos, sin)

  packed_qk_rope_(xqkv, freqs_cis)
  torch.testing.assert_close(xqkv[:, 0], xq_ref, atol=0, rtol=0)
  torch.testing.assert_close(xqkv[:, 1], xk_ref, atol=0, rtol=0)
  torch.testing.assert_close(xqkv[:, 2], xv, atol=0, rtol=0)  # V 不动
  print("融合 kernel 逐位一致，V 未被污染")
  ```
- **预期结果**：三个 assert 全部通过，说明融合 kernel 在数学上等价于逐张量路径，而且没有误改 V 部分。这是所有融合 kernel 的黄金标准——**先保证正确性，再谈性能**。

### 知识点 3：MXFP4 量化与反量化（来自 Commit 19）

### 知识点 4：SSE 流式解析与状态机（来自 Commit 5 和 Commit 14）

- **是什么**：OpenAI 的流式响应是一串 `event: xxx\ndata: {...}\n\n` 格式的 SSE 消息。Responses API 比 Chat Completions 更复杂——reasoning 和 output 是分开的事件，最后还要等 `response.completed`。
- **为什么重要**：如果解析状态机写错，TTFT（首 token 延迟）和 ITL（token 间隔）就全错了。Commit 5 特别强调：reasoning delta 要算进 TTFT，因为服务端已经在解码了。不懂状态机，你测出来的性能数据全是假的。
- **动手试试**：
  ```python
  # 模拟 Responses API 的 SSE 流，手写一个最小解析器
  import json

  sse_stream = """
  event: response.reasoning_text.delta
  data: {"type":"response.reasoning_text.delta","delta":"思考中"}

  event: response.output_text.delta
  data: {"type":"response.output_text.delta","delta":"你好"}

  event: response.completed
  data: {"type":"response.completed","response":{"usage":{"input_tokens":10,"output_tokens":5}}}

  """.strip().split("\n\n")

  reasoning, output, usage = "", "", None
  for block in sse_stream:
      lines = block.split("\n")
      event = next(l.split(": ", 1)[1] for l in lines if l.startswith("event: "))
      data = json.loads(next(l.split(": ", 1)[1] for l in lines if l.startswith("data: ")))
      if event == "response.reasoning_text.delta":
          reasoning += data["delta"]
      elif event == "response.output_text.delta":
          output += data["delta"]
      elif event == "response.completed":
          usage = data["response"]["usage"]

  print(f"reasoning={reasoning!r}, output={output!r}, usage={usage}")
  ```
- **预期结果**：输出 `reasoning='思考中', output='你好', usage={'input_tokens': 10, 'output_tokens': 5}`。你会理解为什么 Commit 5 说"reasoning delta 要计入 TTFT"——因为它是服务端在真实解码时发出的。

### 知识点 5：多后端 block size 协商（来自 Commit 1）

- **是什么**：vLLM 里不同 attention backend（FlashAttention、FlashInfer、Triton）支持的 KV cache block size 不一样，有的是固定值，有的是"某个数的倍数"。启动时必须找到一个所有 backend 都能接受的公共 block size。
- **为什么重要**：如果报错信息只说"No common block size"，你根本不知道是哪个 backend 拖后腿。Commit 1 让错误信息列出每个 backend 的名字和支持的尺寸。**好的错误信息是工程质量的体现**。
- **动手试试**：
  ```python
  # 模拟 Commit 1 的 block size 协商逻辑
  from vllm.v1.attention.backend import MultipleOf

  def block_size_is_supported(backends, size):
      for b in backends:
          supported = b.get_supported_kernel_block_sizes()
          if not any(
              (isinstance(s, MultipleOf) and size % s.base == 0) or s == size
              for s in supported
          ):
              return False
      return True

  class Backend:
      def __init__(self, name, sizes):
          self.name, self.sizes = name, sizes
      def get_name(self): return self.name
      def get_supported_kernel_block_sizes(self): return self.sizes

  backends = [
      Backend("FlashAttention", [16, 32, 64]),
      Backend("Triton", [MultipleOf(16)]),
      Backend("Custom", [32, 64, 128]),
  ]
  kv_manager_block_size = 256
  for size in sorted([16, 32, 64, 128, 256], reverse=True):
      if block_size_is_supported(backends, size):
          print(f"选定 block size = {size}")
          break
  else:
      print("No common block size for", kv_manager_block_size, "(",
            "; ".join(f"{b.get_name()}: {b.get_supported_kernel_block_sizes()}"
                      for b in backends), ")")
  ```
- **预期结果**：输出 `选定 block size = 64`（因为 Custom 不支持 128，Triton 要求 16 的倍数，三者交集最大是 64）。如果全部失败，你会看到带 backend 名字的详细错误——这正是 Commit 1 的改进。

## 🧪 重要知识点 & 动手实验

- **知识点 1：Prefill Context Parallelism 的 Zigzag 切分策略**
  - **是什么**：把一条长 prompt 的 token 按 `2C` 块切分，第 `r` 号 GPU 拿第 `r` 块和倒数第 `r` 块，让因果注意力计算量均衡。
  - **为什么重要**：因果注意力下，越靠后的 token 计算量越大。如果简单均分，前面的 GPU 会提前空闲。Zigzag 让每张卡"一块轻 + 一块重"，负载均衡。不懂这个，你调 CP 参数时会发现 GPU 利用率上不去。
  - **动手试试**：
    ```python
    # 模拟 zigzag 切分
    C = 4  # CP 组大小
    tokens = list(range(16))
    block_size = len(tokens) // (2 * C)
    blocks = [tokens[i*block_size:(i+1)*block_size] for i in range(2*C)]
    for r in range(C):
        local = blocks[r] + blocks[2*C - 1 - r]
        print(f"Rank {r}: {local}")
    ```
  - **预期结果**：Rank 0 拿到 `[0,1,14,15]`，Rank 3 拿到 `[6,7,8,9]`。每张卡都有一块"早"（计算少）和一块"晚"（计算多），总计算量接近。

- **知识点 2：Chat Template 缓存键的顺序敏感性**
  - **是什么**：Jinja 模板渲染字典时，键的顺序会影响输出，所以缓存键不能排序。
  - **为什么重要**：`orjson.OPT_SORT_KEYS` 会把 `{"a":1,"b":2}` 和 `{"b":2,"a":1}` 视为相同，但模板渲染结果可能不同。这会导致用户拿到错误的渲染结果，而且极难复现。
  - **动手试试**：
    ```python
    import orjson
    d1 = {"system": "A", "user": "B"}
    d2 = {"user": "B", "system": "A"}
    print(orjson.dumps(d1, option=orjson.OPT_SORT_KEYS))
    print(orjson.dumps(d2, option=orjson.OPT_SORT_KEYS))  # 相同！有 bug
    print(orjson.dumps(d1))
    print(orjson.dumps(d2))  # 不同，正确
    ```
  - **预期结果**：前两行输出相同（这就是 bug），后两行不同（修复后的行为）。理解"缓存键必须包含所有影响输出的因素"。

- **知识点 3：CUDA Graph 与异步更新的执行顺序**
  - **是什么**：NPU 上用 CUDA Graph 加速推理时，输入更新和 graph 重放的顺序会影响性能。
  - **为什么重要**：Commit 11 把 `update_future.result()` 从 `replay()` 之前移到之后，让更新和重放并行，避免串行等待。这是典型的异步流水线优化。
  - **动手试试**（概念模拟）：
    ```python
    import time
    from concurrent.futures import ThreadPoolExecutor
    ex = ThreadPoolExecutor(1)
    def slow_update(): time.sleep(0.1); return "updated"
    # 串行
    t0 = time.time(); r = ex.submit(slow_update); r.result(); time.sleep(0.1)
    print("串行:", time.time()-t0)
    # 并行
    t0 = time.time(); r = ex.submit(slow_update); time.sleep(0.1); r.result()
    print("并行:", time.time()-t0)
    ```
  - **预期结果**：串行约 0.2s，并行约 0.1s。理解"两个不相关操作可以重叠"。

- **知识点 4：KV 缓存 offload 的竞态条件**
  - **是什么**：显存到内存的 KV 拷贝还在进行时，如果触发 retraction 释放显存，拷贝会读到无效数据。
  - **为什么重要**：异步操作的"完成"和"资源释放"之间必须有同步点。Commit 5 用 `all_reduce(MAX)` 在所有 rank 上检查是否有 pending 拷贝，有就拒绝 retraction。
  - **动手试试**：
    ```python
    # 模拟跨 rank 的 pending 检查
    import torch.distributed as dist
    # 单进程模拟
    pending_local = True  # 本 rank 还有拷贝
    pending = torch.tensor([pending_local], dtype=torch.int)
    # 实际代码里会 all_reduce(MAX)，任一 rank 有 pending 就拒绝
    if pending.item():
        raise RuntimeError("拒绝 retraction：还有拷贝在飞")
    ```
  - **预期结果**：抛出异常，保护数据一致性。理解"分布式系统中任一 rank 的问题都是全局问题"。

- **知识点 5：多任务 Diffusion 的 task_type 协商**
  - **是什么**：客户端可以显式指定 `task_type`，也可以省略让服务端根据输入推断。
  - **为什么重要**：一个 pipeline 可能同时支持 T2I、I2I、T2V、I2V，省略 task_type 时服务端要"猜"用户意图，猜不准就报 400。这是 API 设计中的"显式优于隐式"权衡。
  - **动手试试**：
    ```bash
    # 显式指定
    curl -X POST http://localhost:30010/v1/images/generations \
      -H "Content-Type: application/json" \
      -d '{"prompt": "a cat", "task_type": "t2i"}'
    # 省略，让服务端推断
    curl -X POST http://localhost:30010/v1/images/generations \
      -H "Content-Type: application/json" \
      -d '{"prompt": "a cat"}'
    ```
  - **预期结果**：两者都能工作，但显式指定更可靠。当输入有歧义（比如同时有图和视频）时，省略会报错要求明确。
