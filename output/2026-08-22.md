### 知识点 1：KV Cache 组规范（KVCacheGroupSpec）与统一类型解包
- **是什么**：KV Cache 不再是一个统一的大缓存，而是按层（layer）分组，每组有自己的缓存规范（如滑动窗口、MLA、Full Attention）。`UniformTypeKVCacheSpecs` 是一个包装器，内部包含多个同类型但参数不同的缓存规范，需要"解包"才能识别真实类型。
- **为什么重要**：DeepSeek-V4 这类模型有不同层使用不同注意力机制，如果代码用 `isinstance` 检查时没解包 `UniformTypeKVCacheSpecs`，就会找不到 full-attention 组，导致错误回退到默认组（gid=0），引发严重 bug。不懂这个，你在处理混合注意力模型时就会踩坑。
- **动手试试**：

    MLAAttentionSpec, SlidingWindowMLASpec,

### 知识点 2：MXFP8 块缩放指数计算
- **是什么**：MXFP8 量化中，每个块（如 32 个元素）有一个缩放因子（scale），用于将块内最大值映射到 FP8 的最大值。修复前的代码把块最大值映射到 1.0，导致小元素落入次正规数（subnormal）范围，精度丢失。修复后映射到 FP8 最大值（448.0）。
- **为什么重要**：量化精度直接影响模型输出质量。如果你在 AMD GPU 上跑量化模型遇到精度问题，这很可能就是原因之一。低精度推理是趋势，但"精度不翻车"是底线。
- **动手试试**：
```python
import torch
import triton
import triton.language as tl

@triton.jit
def _quantize_kernel(x_ptr, xq_ptr, scales_ptr, BLOCK_M: tl.constexpr):
    pid_m = tl.program_id(0)
    offs = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    x = tl.load(x_ptr + offs).to(tl.float32)
    
    # 修复前：amax 映射到 1.0
    amax_old = tl.max(tl.abs(x), axis=0)
    sb_old = tl.floor(tl.log2(amax_old)) + 127.0
    
    # 修复后：amax 映射到 FP8_MAX
    FP8_MAX = 448.0
    amax_new = tl.maximum(tl.max(tl.abs(x), axis=0), 1e-30)
    sb_new = tl.ceil(tl.log2(amax_new / FP8_MAX)) + 127.0
    
    tl.store(scales_ptr + pid_m, sb_new)

# 用一个小张量测试
x = torch.tensor([0.001, 0.002, 0.003, 400.0], dtype=torch.float32, device="cuda")
xq = torch.empty_like(x, dtype=torch.float8_e4m3fn)
scales = torch.empty(1, dtype=torch.float32, device="cuda")
_quantize_kernel[(1,)](x, xq, scales, BLOCK_M=4)
print(f"scale exponent: {scales.item()}")
```
- **预期结果**：你看到修复后的 scale 指数比修复前大（因为除以 FP8_MAX 后 log2 值更大），量化后的值更均匀，不会出现小值被压到次正规数的情况。

### 知识点 3：FlashAttention 元数据的"组几何"（Group Geometry）
- **是什么**：注意力元数据（如 num_heads）必须来自注意力层所在的 KV cache 组（group），而不是模型全局值。因为混合注意力模型中，不同层的 head 数可能不同。
- **为什么重要**：如果使用模型全局的 `get_num_attention_heads()`，对于每层 head 数不同的模型（如 Laguna），会导致 scratchpad 缓冲区过小，被索引越界，引发内存错误。这是典型的"看似小问题，实则大 bug"。

### 知识点 4：FlashInfer XQA 解码回退机制
- **是什么**：FlashInfer 的 XQA（eXecution-eXpert Attention）解码内核只支持 head_dim 在 [16, 256] 且能被 16 整除的情况。当 KV cache 组的 head_dim 超出这个范围（如 Gemma 4 的全局注意力组 head_dim=512），需要回退到原生 FlashInfer 解码。
- **为什么重要**：混合注意力模型（如 Gemma 4）有不同层使用不同 head_dim。如果不做回退，XQA 内核会用错误的 head_dim 处理数据，导致崩溃或错误结果。这是"优雅降级"的典型设计模式。
- **动手试试**：

### 知识点 5：自适应 TopK 宽度（Adaptive TopK Width）
- **是什么**：DeepSeek-V4 的稀疏 MLA 注意力中，topk 选择的宽度（每个 token 选多少个压缩 token）不再固定，而是根据当前序列长度自适应调整。序列越长，topk 宽度越大（但不超过上限）。
- **为什么重要**：固定 topk 宽度在小序列时浪费计算，在大序列时可能不够。自适应可以在保证质量的同时节省算力。但要注意 CUDA Graph 捕获时的稳定性——宽度变化不能影响捕获的地址和 stride。
- **动手试试**：
```python
import triton

# 模拟自适应 topk 宽度计算
def compute_topk_width(max_seq_len: int, compress_ratio: int, alignment: int = 64):
    base = max(max_seq_len // compress_ratio, 1)
    width = triton.next_power_of_2(base)
    return max(width, alignment)

# 测试不同序列长度
for seq_len in [128, 256, 512, 1024, 2048, 4096, 8192, 16384]:
    width = compute_topk_width(seq_len, compress_ratio=128)
    print(f"seq_len={seq_len:6d} -> topk_width={width}")

# 输出（示意）:
# seq_len=   128 -> topk_width=64
# seq_len=   256 -> topk_width=64
# seq_len=   512 -> topk_width=64
# seq_len=  1024 -> topk_width=64
# seq_len=  2048 -> topk_width=64
# seq_len=  4096 -> topk_width=64
# seq_len=  8192 -> topk_width=128
# seq_len= 16384 -> topk_width=128
```
- **预期结果**：你看到随着序列变长，topk 宽度从 64 增长到 128。这就是 commit 18 实现的自适应逻辑。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 的 CPU Offload（Commit 2）

- **是什么**：当GPU显存不足时，将KV Cache（注意力机制的中间结果）从GPU显存搬到CPU内存，需要时再搬回来，从而支持更长的上下文或更大的batch。
- **为什么重要**：这是处理超长上下文（如100K+ tokens）的关键技术。不懂这个，你可能会在跑长文本时遇到OOM（显存溢出）。MXFP8格式的KV Cache之前不支持CPU offload，这次补上了。
- **动手试试**：
```python
# 概念验证：模拟KV Cache的CPU offload
import torch
import time

# 模拟GPU上的KV Cache（假设是MXFP8格式，带scale）
k_buffer_gpu = torch.randn(1024, 128, dtype=torch.float8_e4m3fn, device='cuda')
k_scale_gpu = torch.randn(1024, 1, dtype=torch.float32, device='cuda')

# 模拟CPU offload：把数据搬到CPU，再搬回来
start = time.time()
k_buffer_cpu = k_buffer_gpu.to('cpu', non_blocking=True)
k_scale_cpu = k_scale_gpu.to('cpu', non_blocking=True)
torch.cuda.synchronize()
print(f"Offload to CPU: {time.time() - start:.4f}s")

start = time.time()
k_buffer_gpu_restored = k_buffer_cpu.to('cuda', non_blocking=True)
k_scale_gpu_restored = k_scale_cpu.to('cuda', non_blocking=True)
torch.cuda.synchronize()
print(f"Load back to GPU: {time.time() - start:.4f}s")

# 验证数据一致性
print(f"Data restored correctly: {torch.equal(k_buffer_gpu, k_buffer_gpu_restored)}")
```
- **预期结果**：你会看到数据在GPU和CPU之间成功往返，且数据保持一致。这说明了offload的基本原理。注意，真实场景中还需要处理scale（缩放因子），否则反量化会出错。

### 知识点 2：MoE 专家并行与计算重叠（Commit 14）

- **是什么**：MoE（Mixture of Experts）模型中有多个"专家"网络。DeepEP是一种专家并行通信库。计算重叠是指让共享专家（所有token都要经过的）和路由专家（只有部分token经过的）在不同的CUDA流上同时计算，从而隐藏延迟。
- **为什么重要**：这是提升MoE模型推理吞吐量的关键优化。不懂这个，你可能不知道为什么同一个模型在不同框架上性能差异巨大。
- **动手试试**：
```python
# 概念验证：CUDA Stream 重叠计算
import torch
import time

# 创建两个CUDA流
stream1 = torch.cuda.Stream()
stream2 = torch.cuda.Stream()

# 模拟两个可以并行计算的任务
a = torch.randn(4096, 4096, device='cuda')
b = torch.randn(4096, 4096, device='cuda')

# 串行执行
start = time.time()
c1 = torch.matmul(a, b)
c2 = torch.matmul(a, b)
torch.cuda.synchronize()
serial_time = time.time() - start

# 并行执行（使用两个流）
start = time.time()
with torch.cuda.stream(stream1):
    c1 = torch.matmul(a, b)
with torch.cuda.stream(stream2):
    c2 = torch.matmul(a, b)
torch.cuda.synchronize()
parallel_time = time.time() - start

print(f"Serial: {serial_time:.4f}s, Parallel: {parallel_time:.4f}s")
print(f"Speedup: {serial_time / parallel_time:.2f}x")
```
- **预期结果**：在GPU上，并行执行通常比串行快（但不是所有情况，因为GPU可能已经饱和）。这个实验让你理解CUDA Streams的基本用法，这是实现计算重叠的基础。

### 知识点 3：MXFP8 量化格式（Commit 2, 10）

- **是什么**：MXFP8是一种块浮点量化格式，将一组数值（如32个）共享一个缩放因子（scale），从而在保持精度的同时大幅减少存储。它把数据分成两半：存储FP8格式的数据主体 + 存储一个FP32的scale。
- **为什么重要**：MXFP8是NVIDIA Blackwell架构主推的量化格式，DeepSeek V4等新模型都在用。不懂这个，你可能看不懂模型配置，也不知道为什么某些硬件上跑不了。
- **动手试试**：
```python
# 概念验证：模拟MXFP8量化
import torch

# 原始数据（假设是FP32）
original = torch.randn(32, 128, dtype=torch.float32)

# 模拟MXFP8量化：按块（block）计算scale
block_size = 32
# 重塑为 [num_blocks, block_size, ...]
reshaped = original.view(-1, block_size, original.shape[1])
# 计算每个块的scale（最大值）
scales = reshaped.abs().max(dim=1, keepdim=True).values
# 量化到FP8（E4M3格式，范围约[-448, 448]）
quantized = (reshaped / scales).to(torch.float8_e4m3fn)

# 反量化
dequantized = (quantized.float() * scales).view(original.shape)

# 计算误差
mse = ((original - dequantized) ** 2).mean().item()
print(f"MXFP8 quantization MSE: {mse:.6f}")
print(f"Original dtype: {original.dtype}, Quantized dtype: {quantized.dtype}")
```
- **预期结果**：你会看到量化后的数据占用更少的内存（FP8 vs FP32），但会有一定的精度损失（MSE不为0）。这个实验让你理解MXFP8的核心思想：共享scale来减少存储开销。

### 知识点 4：LoRA 与投机解码（Commit 15）

- **是什么**：LoRA（Low-Rank Adaptation）是一种高效微调技术，只训练一小部分参数。投机解码（Speculative Decoding）是让一个小模型先草拟多个token，再用大模型并行验证，从而加速推理。这个commit让两者可以同时使用。
- **为什么重要**：这允许用户用LoRA微调模型，同时享受投机解码的加速效果。这在实际部署中非常实用，比如为特定任务微调模型并加速推理。
- **动手试试**：
```python
# 概念验证：LoRA 的矩阵分解思想
import torch

# 原始权重矩阵（假设是 4096x4096）
W = torch.randn(4096, 4096)

# LoRA 分解：W' = W + BA，其中 B 是 4096x16，A 是 16x4096
# 只训练 B 和 A，保持 W 不变
rank = 16
B = torch.randn(4096, rank, requires_grad=True)
A = torch.randn(rank, 4096, requires_grad=True)

# 模拟前向传播
x = torch.randn(1, 4096)
y = x @ W + x @ B @ A

# 计算LoRA参数量 vs 全量参数量
lora_params = B.numel() + A.numel()
full_params = W.numel()
print(f"LoRA parameters: {lora_params:,} (0.02% of full)")
print(f"Full parameters: {full_params:,}")
```
- **预期结果**：你会看到LoRA只需要训练极少量的参数（约0.02%），就能实现模型适配。这解释了为什么LoRA是高效微调的主流方法。

### 知识点 5：gRPC 协议适配（Commit 19）

- **是什么**：gRPC是一种高性能RPC框架，常用于微服务通信。SGLang通过gRPC Bridge提供与NVIDIA Triton推理服务器兼容的接口，让已有Triton客户端可以直接接入SGLang。
- **为什么重要**：这降低了从Triton迁移到SGLang的成本，让企业可以无缝切换后端。
- **动手试试**：
