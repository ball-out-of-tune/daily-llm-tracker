### 知识点 1：CUDA Graph 与自定义算子注册
- **是什么**：CUDA Graph 可以将一系列 GPU 操作捕获并重放，减少内核启动开销。自定义算子（Custom Op）则允许将自定义的 Triton/CUDA 内核注册到 PyTorch 中，使其能参与图捕获和自动微分。
- **为什么重要**：在模型部署中，图捕获可以显著降低延迟。如果不注册为自定义算子，你的高性能内核可能无法被 CUDA Graph 捕获，导致性能回退。
- **动手试试**：
  ```python

  from torch.fx.experimental.proxy_tensor import make_fx

  # 定义一个简单的自定义算子（模拟）
  def my_custom_gemm(a, b):
      return a @ b

  # 使用 FakeTensor 测试算子是否能被追踪（模拟注册后的行为）
  with FakeTensorMode():
      a = torch.empty((4, 256), device='cuda', dtype=torch.float16)
      b = torch.empty((256, 64), device='cuda', dtype=torch.float16)
      out = my_custom_gemm(a, b)
      print("Output shape:", out.shape)

      # 尝试用 make_fx 捕获计算图
      graph = make_fx(lambda a, b: my_custom_gemm(a, b))(a, b)
      print("Graph captured successfully")
  ```
- **预期结果**：你会看到输出 shape 和 "Graph captured successfully" 的提示。这模拟了 vLLM 中 `triton_w4a16_gemm` 注册为自定义算子后，能被 `make_fx` 和 CUDA Graph 正常处理的现象。

### 知识点 2：MoE 路由与 Padding
- **是什么**：在混合专家模型（MoE）中，Token 会被路由到不同的专家。为了批量处理，通常需要将路由结果"填充"（Padding）到统一大小。处理不当会导致计算错误或效率低下。
- **为什么重要**：理解 MoE 的 Padding 机制，是优化其性能的关键。错误的 Padding 处理会引入无效计算，甚至导致程序崩溃。
- **动手试试**：
  ```python
  import torch

  # 模拟一个 MoE 路由结果
  # 假设有 4 个 token，3 个专家，每个专家最多处理 2 个 token
  # 路由结果是 [专家1, 专家0, 专家2, 专家1]
  routing_map = torch.tensor([1, 0, 2, 1])

  # 计算每个专家的 token 数量（这相当于计算 input_offset_by_experts）
  num_tokens_per_expert = torch.bincount(routing_map, minlength=3)
  print("Tokens per expert:", num_tokens_per_expert)

  # 假设我们 padding 到每个专家 2 个 token
  # 那么 padding 后的总行数应该是 3 (专家数) * 2 (每专家最大token数) = 6
  # 但实际有效的 token 数是 4
  num_valid_rows = min(6, num_tokens_per_expert.sum().item())
  print("Valid rows to process:", num_valid_rows)

  # 在 CUDA kernel 中，你应该只处理前 num_valid_rows 行，跳过 padding 行
  # 这类似于 Commit 14 中修复的 `numValidRows` 计算
  ```
- **预期结果**：你会看到每个专家的 token 数，以及计算出的有效行数。这模拟了 CUTLASS MoE 中如何通过 `input_offset_by_experts[n_experts]` 避免处理 padding 行。

### 知识点 3：KV Cache 与分页
- **是什么**：KV Cache 是 LLM 推理中存储历史 Key 和 Value 张量的缓存，用于避免重复计算。分页（Paging）技术允许 KV Cache 存储在非连续的内存块中，提高内存利用率。
- **为什么重要**：高效管理 KV Cache 是提升吞吐量和支持长上下文的关键。理解其块分配、哈希和滑动窗口机制，是优化推理引擎的基础。

  ```python
  cpu_block.block_hash_num_tokens = gpu_block.block_hash_num_tokens
  ```

### 知识点 4：流式解析与状态机
- **是什么**：在处理 LLM 流式输出时，模型可能生成不完整的工具调用或结构化文本。流式解析器（如 DSML 解析器）通过维护状态机，来逐步解析这些不完整的片段。
- **为什么重要**：对于函数调用和 Agent 场景，必须能实时解析流式输出，否则会错过关键事件或产生错误。
- **动手试试**：

  ```python
  class SimpleParser:
      def __init__(self):
          self.state = 'idle'
          self.buffer = ''

      def feed(self, chunk):
          # 简单逻辑：遇到 <tag> 开始，遇到 </tag> 结束
          for char in chunk:
              if self.state == 'idle':
                  if char == '<':
                      self.state = 'in_tag'
                      self.buffer = ''
                  # 忽略其他字符
              elif self.state == 'in_tag':
                  if char == '>':
                      print(f"Parsed tag: {self.buffer}")
                      self.state = 'idle'
                  else:
                      self.buffer += char

  # 模拟不完整的流式输入
  parser = SimpleParser()
  parser.feed("<param name='a")
  parser.feed("'>value</param>")

  # 输出: Parsed tag: param name='a'
  # 这说明解析器能处理分块的输入
  ```
- **预期结果**：你会看到解析器输出了正确的标签。这模拟了 DeepSeek DSML 解析器处理流式参数时，如何隐含地关闭前一个参数并开始解析新参数。

### 知识点 1：投机解码 (Speculative Decoding) 与自适应策略
- **是什么**：一种加速LLM生成的技术。用一个快速的小模型（草稿模型）先猜测多个Token，再用大模型（目标模型）一次性验证这些猜测。如果猜对了，就能一次生成多个Token，速度翻倍。
- **为什么重要**：这是目前LLM推理中最重要的加速手段之一。自适应策略则更进一步，根据当前负载（如批次大小）动态调整猜测的步数，以求在效率和效果间达到最佳平衡。不懂这个，你可能会疑惑为什么SGLang有时快有时慢。
- **动手试试**：

### 知识点 2：SWA (Sliding Window Attention) 的释放机制
- **是什么**：SWA只保留最近固定窗口大小的KV Cache，以节省显存。但当一个请求结束时，释放KV Cache的时机和范围需要非常精确，尤其是当SWA和全注意力（Full Attention）混合使用时。
- **为什么重要**：如果释放逻辑出错，可能导致显存泄漏、数据错误或程序崩溃。这是系统稳定性中最容易出bug也最难调试的部分。比如Commit 3中提到的"SWA ownership at enqueue time"就是为了解决释放顺序问题。
- **动手试试**：

- **预期结果**：你理解了释放顺序对正确性的影响，并能解释为什么需要先释放SWA再释放全注意力。

### 知识点 3：CUDA Graph 容量解耦
- **是什么**：CUDA Graph是一种将一系列GPU内核调用打包并一次性重放的技术，用于减少内核启动开销。其捕获时需要指定最大请求数和最大Token数。过去，这两个数是绑定的（`max_bs * max_tokens_per_req`），导致资源浪费。
- **为什么重要**：解耦后，可以独立设置请求数和Token数，更灵活地利用显存和计算资源，尤其在处理变长请求时能提升性能。
- **动手试试**：
  1. 查看 `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py` 中关于 `max_num_token` 的设置逻辑。
  2. 搜索 `capture_num_tokens` 这个参数，看它是如何被传入并使用的。
  3. （概念实验）想象一个场景：如果最大批次是8，每个请求最多2048个Token，但实际平均每个请求只有512个Token。用旧的绑定方式，你需要为8*2048=16384个Token分配资源。用解耦方式，你可以设置`max_bs=8`，`capture_num_tokens=4096`，从而节省大量显存。
- **预期结果**：你能理解为什么解耦是合理的，并能解释`max_num_token`的计算方式变化带来的好处。

### 知识点 4：FP8 KV Cache (CPU)
- **是什么**：将KV Cache的数据类型从FP16/BF16降到FP8，以减少内存占用和带宽需求。这需要特定的指令集（如AVX512）和特殊的数据打包格式（如VNNI）来高效处理。
- **为什么重要**：内存带宽是CPU推理的主要瓶颈。FP8 KV Cache能显著提升CPU上的推理性能，是SGLang支持更多场景（如无GPU环境）的重要一步。
- **动手试试**：
  1. 阅读 `python/sglang/kernels/aot/csrc/cpu/decode.cpp` 中 `pack_vnni_Nx32` 函数的模板参数变化。
  2. 搜索 `mm512_load_vec` 这个函数，它根据是否有 `src_scale` 来决定是加载普通数据还是反量化的FP8数据。
  3. （概念实验）尝试用Python模拟一个简单的FP8量化过程：
  ```python
  import torch
  # 模拟原始FP16数据
  x = torch.randn(4, 4, dtype=torch.float16)
  # 模拟FP8量化（这里简化为缩放和取整）
  scale = x.abs().max() / 127.0
  x_fp8 = (x / scale).round().clamp(-127, 127).to(torch.int8)
  # 模拟反量化
  x_dequant = x_fp8.float() * scale
  print("Original:", x)
  print("Dequantized:", x_dequant)
  print("Error:", (x.float() - x_dequant).abs().mean())
  ```
- **预期结果**：你看到了FP8量化带来的精度损失，并理解了为什么需要`src_scale`来进行反量化。

### 知识点 5：PD分离 (Prefill-Decode Disaggregation) 中的"假"传输
- **是什么**：在PD分离架构中，Prefill和Decode在不同的GPU上运行。为了测试或模拟，有一种"假"PD模式，它跳过真实的KV传输，但需要一个"假"的Token来模拟交接过程。
- **为什么重要**：如果所有请求的"假"Token都一样（比如都是0），可能会在基准测试中引入偏差。这个commit通过哈希请求ID来生成多样化的Token，使测试更真实。
- **动手试试**：

  ```python
  class FakeReq:

          self.vocab_size = vocab_size

      return int.from_bytes(digest, byteorder="little") % req.vocab_size

  req2 = FakeReq("request-2")

  print(gen_fake_id(req2))
  ```
