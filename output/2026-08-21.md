### 知识点 1：投机解码（Speculative Decoding）
- **是什么**：用一个"小模型/草稿模型"先快速生成多个候选 token，再用"大模型/目标模型"一次性验证这些 token 是否正确，从而加速推理。
- **为什么重要**：这是当前 LLM 推理加速最热门的技术之一，可以显著提升吞吐量。不懂它，你就无法理解 vLLM 中大量关于 `spec_decode` 的代码和配置。
- **动手试试**：
  ```bash

  vllm serve meta-llama/Llama-3.1-8B-Instruct \

  ```
- **预期结果**：服务正常启动，日志中会显示投机解码相关的配置信息。你可以对比开启和关闭投机解码时的吞吐量。

### 知识点 2：CUDA Graph 与可中断 CUDA Graph
- **是什么**：CUDA Graph 将 GPU 操作录制为一张图，避免重复启动 kernel 的开销。可中断 CUDA Graph（Breakable CUDA Graph）允许在录制过程中动态插入条件判断，使图在不同输入下能"自适应"。
- **为什么重要**：MiniMax-M3 的 bug 就是因为 CUDA Graph 重放时，某些内存分配的地址发生了变化，导致 FP8 数据失效。理解 CUDA Graph 是优化推理性能的必备知识。
- **动手试试**：
  ```python
  # 查看你的 GPU 是否支持 CUDA Graph
  import torch
  print(torch.cuda.is_available())
  print(torch.cuda.get_device_capability())
  ```
- **预期结果**：输出 `True` 和一个类似 `(8, 0)` 的元组，表示你的 GPU 算力。

### 知识点 3：MoE（Mixture of Experts）模型
- **是什么**：将模型拆分为多个"专家"子网络，每个 token 只激活其中少数几个专家，从而在增加模型参数量的同时控制计算量。
- **为什么重要**：DeepSeek-V4、MiniMax-M3 等最新模型都采用了 MoE 架构。今天多个 commit 都在优化 MoE 的 kernel 和权重加载，说明这是当前模型架构的主流方向。
- **动手试试**：

  ```python
  config = AutoConfig.from_pretrained("deepseek-ai/DeepSeek-V3")

  print(f"激活专家数: {config.num_experts_per_tok}")
  print(f"共享专家数: {config.n_shared_experts}")
  ```
- **预期结果**：你会看到类似 `专家数量: 256`、`激活专家数: 8` 的输出，理解 MoE 的核心参数。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Radix Tree 前缀缓存（KV Cache 复用）

- **是什么**：Radix Tree 是一种树状数据结构，用于存储和复用 KV 缓存中相同的前缀部分。当多个请求共享相同的前缀（如系统提示词）时，只需计算一次，后续请求直接复用。
- **为什么重要**：KV 缓存是 LLM 推理中最大的内存开销之一。不理解 Radix Tree，就无法理解 SGLang 的核心性能优势，也无法调优缓存相关参数。
- **动手试试**：使用 SGLang 启动一个服务，发送两个共享前缀的请求，观察第二个请求的 `cached_tokens` 数量。
```bash
# 启动服务
python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct --port 30000

# 发送请求
curl http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/Llama-3.2-1B-Instruct",
    "messages": [{"role": "user", "content": "Hello, how are you? Tell me a story about a cat."}],
    "max_tokens": 50
  }'

# 再次发送相同请求，观察 meta_info 中的 cached_tokens 字段
# 第二次请求的 cached_tokens 应大于 0
```
- **预期结果**：第二次请求的响应中 `meta_info.cached_tokens` 大于 0，说明前缀缓存生效。

### 知识点 2：投机解码（Speculative Decoding）

- **是什么**：用小模型（草稿模型）快速生成多个候选 token，再用大模型（目标模型）并行验证。如果验证通过，一次前向传播可以产生多个 token，大幅提升吞吐。
- **为什么重要**：投机解码是当前 LLM 推理加速的最重要技术之一。不理解它，就无法理解 `--speculative-algorithm` 等参数，也无法解释为什么某些场景下推理速度能提升 2-3 倍。
- **动手试试**：对比开启和关闭投机解码时的吞吐差异。
```bash
# 不开启投机解码
python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct --port 30000

# 开启投机解码（用更小的草稿模型）
python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct \
  --speculative-algorithm EAGLE \
  --speculative-draft-model-path meta-llama/Llama-3.2-1B-Instruct \
  --speculative-num-draft-tokens 4 \
  --port 30001

# 用相同请求分别压测两个服务，对比吞吐
```
- **预期结果**：开启投机解码的服务吞吐显著高于未开启的服务。

### 知识点 3：P/D 分离部署（Prefill/Decode Disaggregation）

- **是什么**：将推理过程拆分为预填充（处理输入）和解码（生成输出）两个阶段，部署在不同的 GPU 节点上，各自独立扩展。
- **为什么重要**：预填充是计算密集型（大量并行），解码是访存密集型（低并行度）。混合部署时两者互相干扰，分离后可以各自优化。长上下文场景下收益尤其明显。
- **动手试试**：使用 SGLang 的 `--disaggregation-mode` 启动分离部署。
```bash
# 启动 Prefill 节点
python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct \
  --disaggregation-mode prefill \
  --port 30010

# 启动 Decode 节点（需要连接 prefill 节点）
python -m sglang.launch_server --model-path meta-llama/Llama-3.2-1B-Instruct \
  --disaggregation-mode decode \
  --prefill-node-url http://localhost:30010 \
  --port 30011

# 通过 decode 节点发送请求
curl http://localhost:30011/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "meta-llama/Llama-3.2-1B-Instruct", "messages": [{"role": "user", "content": "Hello"}], "max_tokens": 50}'
```
- **预期结果**：请求成功返回，且两个节点各司其职。

### 知识点 4：cgroup 内存限制检测

- **是什么**：cgroup 是 Linux 内核的资源隔离机制，容器运行时（如 Docker）用它限制进程的内存使用。正确读取 cgroup 信息，才能准确计算可用内存预算。
- **为什么重要**：SGLang 需要根据可用内存决定 KV 缓存池的大小。如果读取错误，可能导致 OOM 或内存利用率不足。在容器化部署场景中尤其关键。
- **动手试试**：在 Docker 容器中运行 Python，查看 SGLang 如何检测 cgroup 内存。
```bash
# 在容器中运行
docker run --memory=4g --rm -it python:3.11 bash

# 在容器内执行
python -c "
import os
# 查看当前进程的 cgroup
with open('/proc/self/cgroup') as f:
    print(f.read())
# 查看 cgroup 内存限制
print(open('/sys/fs/cgroup/memory.max').read())
print(open('/sys/fs/cgroup/memory.current').read())
"
```
- **预期结果**：`memory.max` 显示约 4GB（容器内存限制），`memory.current` 显示当前使用量。

### 知识点 5：MXFP4 量化与 MoE 推理

- **是什么**：MXFP4 是一种 4-bit 浮点量化格式，将模型权重压缩到原来的 1/4，同时保持较高精度。MoE（Mixture of Experts）模型通过路由选择部分专家网络，减少计算量。
- **为什么重要**：量化是部署大模型的必备技术，MoE 是当前超大模型的主流架构。理解两者的结合（量化 MoE 推理），才能理解 Kimi K3 等模型的部署优化。

- **预期结果**：如果检测到 SM100/SM103/SM107 且模型为 MXFP4 量化，输出 `flashinfer_mxfp4`。
