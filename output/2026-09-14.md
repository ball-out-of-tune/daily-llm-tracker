## 🧪 重要知识点 & 动手实验

- **知识点 1：CUDA Graph 与微批（Microbatch）**
  - **是什么**：CUDA Graph 是把一串 GPU 算子录制成图再回放；微批是把一个大 batch 拆成几个小 batch 交错执行（DBO，Dual Batch Overlap），让通信和计算重叠。
  - **为什么重要**：传统 CUDA Graph 假设输入 shape 固定，微批场景下每个 micro-batch 的输入是变化的，需要"持久化输入 buffer"才能让图正确回放。不懂这个，写出来的图会读到旧数据，输出全错。
  - **动手试试**：
    ```python
    import torch
    # 一个最简单的 CUDA Graph 捕获与回放
    x = torch.zeros(8, device="cuda")
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        y = x * 2 + 1
    x.copy_(torch.arange(8, device="cuda"))  # 更新输入 buffer
    g.replay()
    print(y)  # 应该输出 [1, 3, 5, 7, 9, 11, 13, 15]
    ```
  - **预期结果**：看到 `y` 用的是更新后的 `x`。这正对应 Commit 5 里"microbatched graph replay reads updated persistent input buffers"的核心思想。

- **知识点 2：命令行参数解析中的 `split` 陷阱**
  - **是什么**：Python 的 `str.split("=")` 默认会按所有 `=` 切分，如果路径里含 `=`（比如某些 URL 或带参数的路径），就会 split 出超过 2 段，直接报错。
  - **为什么重要**：Commit 1 修的就是这个 bug——`--lora-modules name=path` 中 path 含 `=` 时解析失败。新手写 CLI 工具最容易踩这个坑。
  - **动手试试**：
    ```python
    item = "my-lora=/models/foo=bar/lora"
    # 错误写法
    try:
        name, path = item.split("=")
    except ValueError as e:
        print("错误:", e)
    # 正确写法
    name, path = item.split("=", 1)
    print(name, "->", path)  # my-lora -> /models/foo=bar/lora
    ```
  - **预期结果**：错误写法抛 `ValueError: too many values to unpack`，正确写法输出 `my-lora -> /models/foo=bar/lora`。

- **知识点 3：base64 校验与安全边界**
  - **是什么**：`base64.b64decode` 默认对非法字符"宽容处理"（可能静默丢弃），加 `validate=True` 后遇到非法字符直接抛异常。
  - **为什么重要**：Commit 7 给视频 base64 载荷加了校验，跟图片/音频对齐。用户传了坏数据，早报错比晚崩溃好——否则可能变成一个诡异的解码错误，排查半天。
  - **动手试试**：
    ```python
    import base64
    bad = "SGVsbG8gV29ybGQh!!!"  # 含非法字符
    # 宽容模式
    print(base64.b64decode(bad))
    # 严格模式
    try:
        base64.b64decode(bad, validate=True)
    except Exception as e:
        print("严格模式捕获:", type(e).__name__)
    ```
  - **预期结果**：宽容模式可能返回乱码或部分数据，严格模式抛 `binascii.Error`。

- **知识点 4：分布式 rendezvous 与多节点 TP**
  - **是什么**：多个进程/节点要组成一个通信组，需要约定"谁是 rank 0、谁是 rank 1"以及"通过哪个地址互相找到"，这个约定过程叫 rendezvous。
  - **为什么重要**：Commit 10 让 weight cache daemon 支持多节点 TP，用 `--nnodes/--node-rank/--master-addr` 组织跨节点通信。不懂 rendezvous，多机部署就是玄学。
  - **动手试试**：
    ```bash
    # 用 torchrun 模拟一个 2 进程的 rendezvous（单机即可）
    cat > /tmp/rv.py <<'EOF'
    import os, torch.distributed as dist
    dist.init_process_group("gloo", init_method="env://")
    print(f"rank={dist.get_rank()} world={dist.get_world_size()}")
    dist.destroy_process_group()
    EOF
    torchrun --nproc_per_node=2 --master_port=29500 /tmp/rv.py
    ```
  - **预期结果**：看到两行输出，分别 rank=0 和 rank=1，world=2。这就是 rendezvous 成功的样子。

- **知识点 5：JIT 编译与并行预热**
  - **是什么**：JIT（Just-In-Time）编译是"用到才编译"，第一次调用会慢；预热（warmup）就是启动时把所有可能用到的编译 key 都提前编译好。
  - **为什么重要**：Commit 15 用 `par_compile` 并行编译 mHC 内核，把串行的 TileLang 编译变成多 worker 并行。Commit 19 更彻底，直接把 FA4 注意力改成预编译，不再 JIT。首字延迟（TTFT）就是这么一点点抠出来的。
  - **动手试试**：
    ```python
    import time, concurrent.futures
    def slow_compile(x):
        time.sleep(0.5)  # 模拟一次 JIT 编译
        return x * x
    keys = list(range(8))
    t0 = time.time()
    [slow_compile(k) for k in keys]
    print("串行:", round(time.time() - t0, 2), "秒")
    t0 = time.time()
    with concurrent.futures.ThreadPoolExecutor(max_workers=4) as ex:
        list(ex.map(slow_compile, keys))
    print("并行:", round(time.time() - t0, 2), "秒")
    ```
  - **预期结果**：串行约 4 秒，并行约 1 秒。这就是 Commit 15 想达到的效果。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 分层缓存（HiCache）——用 CPU 内存换显存

- **是什么**：GPU 显存有限，长对话的 KV 缓存放不下时，把不常用的部分挪到 CPU 内存（甚至 SSD），需要时再换回来。
- **为什么重要**：不做这个，长上下文（比如 128K token）要么跑不起来，要么并发数极低。不懂的话，你会疑惑"为什么我的 32K 上下文服务只能同时服务 2 个用户"。
- **动手试试**：
  ```bash
  # 启动一个带 HiCache 的服务（以 Qwen 模型为例）
  python -m sglang.launch_server \
    --model-path Qwen/Qwen2.5-7B-Instruct \
    --enable-hierarchical-cache \
    --hicache-ratio 1.5 \
    --hicache-write-policy write_through \
    --hicache-io-backend direct \
    --hicache-mem-layout page_first_direct \
    --port 30000
  ```
  然后发一个长请求：
  ```bash
  curl http://localhost:30000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{"model":"Qwen/Qwen2.5-7B-Instruct","messages":[{"role":"user","content":"'"$(python -c 'print("你好"*2000)')"'"}],"max_tokens":10}'
  ```
- **预期结果**：服务启动日志里会看到 `HiCache enabled, host tier size = 1.5x device KV cache`。第二次发相同前缀的请求时，日志会显示 `storage hit length` 大于 0，说明命中了主机层缓存。

### 知识点 2：投机解码的"验证-回滚"机制

- **是什么**：小模型先猜 N 个 token，大模型一次并行验证；猜对的保留，猜错的丢弃并从错误位置重新生成。关键是验证过程中不能污染模型状态（比如卷积状态、SSM 状态）。
- **为什么重要**：投机解码能提速 2-3 倍，但如果验证 kernel 写坏了状态，回滚就会出错，导致输出乱码或崩溃。
- **动手试试**：
  ```bash
  # 用 EAGLE 投机解码启动
  python -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --speculative-algorithm EAGLE \
    --speculative-draft-model-path lmsys/sglang-EAGLE-Llama-3.1-8B-Instruct \
    --speculative-num-steps 3 \
    --speculative-eagle-topk 1 \
    --speculative-num-draft-tokens 4 \
    --port 30000
  ```
  观察日志中 `accept length` 的分布。
- **预期结果**：你会看到类似 `accept_len_mean: 2.5` 的统计，说明平均每次猜中 2.5 个 token。如果 accept length 突然变成 0 或 1，可能是验证 kernel 状态被污染了。

### 知识点 3：Split-KV 注意力——长序列的并行化技巧

- **是什么**：把 KV 序列切成多段，每段由一个 thread block 独立计算注意力，最后再合并结果。适合"序列很长但 batch 很小"的场景。
- **为什么重要**：不做 split-KV，长序列注意力会变成一个 block 干完所有活，GPU 利用率极低。不懂的话，你会困惑"为什么 32K 上下文的 prefill 这么慢"。
- **动手试试**：
  ```python
  # 用 PyTorch 模拟 split-KV 的思想
  import torch
  import torch.nn.functional as F

  def split_kv_attention(q, k, v, num_splits=4):
      # q: [1, heads, 1, dim], k/v: [1, heads, seq, dim]
      seq_len = k.shape[2]
      chunk = seq_len // num_splits
      partial_out = []
      partial_lse = []
      for i in range(num_splits):
          k_chunk = k[:, :, i*chunk:(i+1)*chunk, :]
          v_chunk = v[:, :, i*chunk:(i+1)*chunk, :]
          # 简化的注意力计算
          scores = (q @ k_chunk.transpose(-2, -1)) / (q.shape[-1] ** 0.5)
          attn = F.softmax(scores, dim=-1)
          out = attn @ v_chunk
          partial_out.append(out)
          partial_lse.append(torch.logsumexp(scores, dim=-1))
      # 合并：用 logsumexp 归一化
      lse = torch.stack(partial_lse, dim=0).logsumexp(dim=0)
      out = sum(o * torch.exp(l - lse) for o, l in zip(partial_out, partial_lse))
      return out

  q = torch.randn(1, 8, 1, 64)
  k = torch.randn(1, 8, 1024, 64)
  v = torch.randn(1, 8, 1024, 64)
  out = split_kv_attention(q, k, v, num_splits=4)
  print("Output shape:", out.shape)
  ```
- **预期结果**：输出 shape 为 `[1, 8, 1, 64]`，与不分段的结果数值接近（误差在 1e-5 以内）。这说明你理解了 split-KV 的核心：分段计算 + logsumexp 合并。

### 知识点 4：多平台抽象层——一份代码跑多种芯片

- **是什么**：定义一个 `SRTPlatform` 接口，CUDA、ROCm、NPU、XPU 各自实现，上层代码只调用接口。
- **为什么重要**：不做抽象，每加一种芯片就要改一遍所有推理代码，维护成本爆炸。不懂的话，你会写出"只在 NVIDIA 上能跑"的代码。
- **动手试试**：
  ```python
  # 模拟平台抽象层的设计
  from abc import ABC, abstractmethod

  class SRTPlatform(ABC):
      @abstractmethod
      def get_device(self, local_rank: int): pass
      @abstractmethod
      def get_device_total_memory(self, device_id: int = 0) -> int: pass

  class CudaPlatform(SRTPlatform):
      def get_device(self, local_rank: int):
          import torch
          return torch.device("cuda", local_rank)
      def get_device_total_memory(self, device_id: int = 0) -> int:
          import torch
          return torch.cuda.get_device_properties(device_id).total_memory

  class NpuPlatform(SRTPlatform):
      def get_device(self, local_rank: int):
          import torch
          return torch.device("npu", local_rank)
      def get_device_total_memory(self, device_id: int = 0) -> int:
          import torch
          return torch.npu.get_device_properties(device_id).total_memory

  # 上层代码不关心具体平台
  def allocate_kv_cache(platform: SRTPlatform, size_gb: float):
      total = platform.get_device_total_memory(0)
      print(f"Device total memory: {total / 1e9:.1f} GB")
      print(f"Allocating {size_gb} GB for KV cache")

  allocate_kv_cache(CudaPlatform(), 20)
  ```
- **预期结果**：你会看到 `Device total memory: XX GB` 和 `Allocating 20 GB for KV cache`。这说明你理解了抽象层的核心：上层逻辑与底层实现解耦。

### 知识点 5：SSE 流式响应的可观测性——如何统计"流到一半断了"

- **是什么**：SSE（Server-Sent Events）是流式输出的协议，但一个 200 响应可能流到一半就断了（上游错误、客户端断开）。需要区分"正常结束"、"上游错误"、"客户端断开"。
- **为什么重要**：不区分的话，你会把"客户端主动断开"也算成"服务端失败"，导致监控告警误报。不懂的话，你的 SLA 统计会完全失真。
- **动手试试**：
  ```python
  # 用 Python 模拟 SSE 流的不同结束状态
  import asyncio
  from enum import Enum

  class StreamEnd(Enum):
      OK = "ok"
      STREAM_ERROR_EVENT = "stream_error_event"
      UPSTREAM_ERROR = "upstream_error"
      CLIENT_DISCONNECT = "client_disconnect"

  async def sse_pump(events, simulate_disconnect=False):
      try:
          for i, event in enumerate(events):
              if simulate_disconnect and i == 2:
                  print(f"[pump] client disconnected at event {i}")
                  return StreamEnd.CLIENT_DISCONNECT
              print(f"[pump] sending: {event}")
              await asyncio.sleep(0.1)
          return StreamEnd.OK
      except Exception as e:
          print(f"[pump] upstream error: {e}")
          return StreamEnd.UPSTREAM_ERROR

  async def main():
      events = ["data: hello", "data: world", "data: foo", "data: bar"]
      end = await sse_pump(events, simulate_disconnect=True)
      print(f"Stream ended with: {end.value}")

  asyncio.run(main())
  ```
- **预期结果**：你会看到 `Stream ended with: client_disconnect`。这说明你理解了流式响应的结束状态需要细分，不能简单用"成功/失败"二分。
