## 🧪 重要知识点 & 动手实验

- **知识点 1：Gumbel-max 采样与伪随机数独立性**
  - **是什么**：从 softmax 分布中采样 token 的经典技巧是 `argmax(logit_i + g_i)`，其中 `g_i` 是 Gumbel 噪声。今天 CPU 版本从"预生成大表 + 滑动窗口"改成了 `SplitMix64(seed, i)` 直接计算。
  - **为什么重要**：如果噪声生成有周期性（比如连续 seed 只是表指针平移 1），采样结果会出现系统性偏差，表现为"模型输出重复、多样性下降"，非常难 debug。
  - **动手试试**：
    ```python
    # 对比两种噪声生成方式的相关性
    import numpy as np
    def splitmix64(seed, i):
        x = (seed + i * 0x9E3779B97F4A7C15) & ((1<<64)-1)
        x = ((x ^ (x >> 30)) * 0xBF58476D1CE4E5B9) & ((1<<64)-1)
        x = ((x ^ (x >> 27)) * 0x94D049BB133111EB) & ((1<<64)-1)
        return (x ^ (x >> 31)) / (1<<64)
    # 观察 seed 连续变化时噪声是否独立
    for s in range(5):
        print([round(splitmix64(s, i), 3) for i in range(5)])
    ```
  - **预期结果**：每一行的数字看起来毫无规律，且相邻 seed 之间没有"整体平移"关系，说明噪声独立。

- **知识点 2：safetensors 头部读取与量化层识别**
  - **是什么**：safetensors 文件头部有 JSON 元数据，描述每个 tensor 的名字、dtype、shape。vLLM 靠它判断"哪些层被量化了"。
  - **为什么重要**：老 checkpoint 可能叫 `gptq_model-4bit-128g.safetensors` 而不是标准的 `model.safetensors`，如果读取失败会得到空列表，导致 vLLM 误以为"所有层都没量化"，进而用错误精度加载，输出垃圾。
  - **动手试试**：
    ```python
    from safetensors import safe_open
    # 下载一个小的量化模型，或自己造一个
    import json, struct
    header = {"layers.0.qweight": {"dtype":"I32","shape":[64],"data_offsets":[0,256]}}
    hb = json.dumps(header).encode()
    with open("fake.safetensors","wb") as f:
        f.write(struct.pack("<Q", len(hb))); f.write(hb); f.write(b"\0"*256)
    with safe_open("fake.safetensors","pt") as f:
        print(list(f.keys()))
    ```
  - **预期结果**：打印出 `['layers.0.qweight']`，理解 vLLM 是如何从头部推断量化层的。

- **知识点 3：ZeroDivisionError 与"未知元数据"的防御式编程**
  - **是什么**：视频采样时用 `fps` 计算帧间隔，如果解码器返回 `fps=0`（未知），就会除零崩溃。
  - **为什么重要**：真实世界的媒体文件元数据千奇百怪，防御式编程是工程必备素养。今天 vLLM 的做法是：fps=0 时按 HF 的约定假设 24fps，并把这个假设写回 metadata。
  - **动手试试**：
    ```python
    class VideoSource:
        def __init__(self, total_frames, original_fps, duration):
            self.total_frames_num = total_frames
            self.original_fps = original_fps
            self.duration = duration
    def prepare(source):
        if source.original_fps > 0:
            return source
        return VideoSource(source.total_frames_num, 24.0, source.duration)
    print(prepare(VideoSource(100, 0.0, 0.0)).original_fps)  # 24.0
    ```
  - **预期结果**：输出 `24.0`，理解"用合理默认值兜底"的模式。

- **知识点 4：HTTP 状态码语义与幂等重试**
  - **是什么**：上传文件时只判断 `status != 200` 会导致 201/204 这类成功响应被误判为失败并触发重试。
  - **为什么重要**：重试可能造成文件被写入两次、计费翻倍、日志污染。正确做法是判断 `200 <= status < 300`。
  - **动手试试**：
    ```python
    import requests
    # 用 httpbin 演示 201/204
    for code in [200, 201, 204]:
        r = requests.put(f"https://httpbin.org/status/{code}")
        ok = 200 <= r.status_code < 300
        print(code, "success" if ok else "fail")
    ```
  - **预期结果**：三种状态码都判为 success，理解 2xx 语义。

- **知识点 5：CUDA Graph 的"预算分桶"与贪心装箱**
  - **是什么**：多模态编码器有不同大小的输入，vLLM 预先为每个 token 预算（256/4096/8192）捕获一张 CUDA Graph，运行时把多个图像贪心打包进一个预算图里。
  - **为什么重要**：打包策略不好会导致"为了塞进一个大图而浪费算力"或"频繁切换小图"，今天 commit #58925 优化了"预算悬崖"的处理逻辑。
  - **动手试试**：
    ```python
    def greedy_pack(items, budgets):
        # items: [(idx, tokens)], budgets: 升序
        items = sorted(items, key=lambda x: x[1])
        packs = []
        cur, cur_sum = [], 0
        for idx, t in items:
            if cur_sum + t <= budgets[-1]:
                cur.append(idx); cur_sum += t
            else:
                packs.append((cur, cur_sum)); cur, cur_sum = [idx], t
        if cur: packs.append((cur, cur_sum))
        return packs
    print(greedy_pack([(0,4000),(1,200)], [256,4096,8192]))
    ```
  - **预期结果**：看到 `([(1,200)], 200)` 和 `([(0,4000)], 4000)` 分两批，理解"悬崖回避"。

## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 的虚拟页到物理页翻译（unified-memory 核心）

- **是什么**：推理时 KV cache 存在显存里，为了灵活管理，用"虚拟页号"记账，真正写入显存时再翻译成"物理页号"。统一内存池就是让草稿模型也走目标模型的翻译表。
- **为什么重要**：不懂这个，你会在长上下文或投机解码时遇到"显存爆了但明明还有空"或"读到别人的数据"的诡异 bug。
- **动手试试**：写一个最小模拟，把虚拟 token id 通过页表翻译成物理地址。

```python
import torch

PAGE_SIZE = 4
# 假设虚拟页 0 映射到物理页 3，虚拟页 1 映射到物理页 0
v2p = torch.tensor([3, 0, 1, 2], dtype=torch.long)

def translate(virtual_ids):
    i64 = virtual_ids.long()
    vpage = torch.where(i64 < 0, torch.zeros_like(i64), i64 // PAGE_SIZE)
    phys_page = v2p[vpage]
    return torch.where(i64 < 0, torch.zeros_like(i64),
                       torch.clamp(phys_page * PAGE_SIZE + i64 % PAGE_SIZE, min=0))

virtual = torch.tensor([0, 1, 5, 7, -1, -5])
print("虚拟 id:", virtual.tolist())
print("物理 id:", translate(virtual).tolist())
```

- **预期结果**：你会看到 `[0, 1, 21, 23, 0, 0]`。虚拟 id 0 落在物理页 3 的第 0 位 → 12？不对，我们期望的是 `v2p[0]*4+0=12`。看到输出后你会发现页表映射的语义，这就是 commit #37628 里 `_translate_token_ids` 干的事。

### 知识点 2：投机解码中"未提交槽位"必须被屏蔽

- **是什么**：投机解码会一次猜多个 token，但只有一部分会被接受。没被接受的槽位里的数据是"脏"的，查缓存时必须屏蔽掉。
- **为什么重要**：commit #42624 修的就是这个 bug —— 如果不屏蔽，未提交槽位里可能存着越界地址（如 `1<<40`），查表时会崩溃或读到垃圾。
- **动手试试**：模拟 commit 的修复逻辑。

```python
import torch

stride = 4
commit_lens = torch.tensor([2, 0])  # 第0行提交2个，第1行提交0个
col = torch.arange(stride).view(1, -1)
committed = col < commit_lens.view(-1, 1)
print("committed mask:\n", committed)

# 未提交的槽位必须用 0 索引，而不是用真实但越界的索引
req_to_token = torch.tensor([[10, 11, 12, 13], [20, 21, 22, 23]])
rows = torch.where(committed, torch.tensor([[0], [1]]), torch.zeros_like(committed, dtype=torch.long))
cols = torch.where(committed, torch.tensor([[0, 1, 2, 3], [0, 1, 2, 3]]), torch.zeros_like(committed, dtype=torch.long))
result = torch.where(committed, req_to_token[rows, cols], torch.zeros_like(req_to_token[rows, cols]))
print("安全查表结果:\n", result)
```

- **预期结果**：第 0 行前 2 个是真实值，后 2 个是 0；第 1 行全是 0。这就是 commit 里 `torch.where(committed, ..., 0)` 的核心思想。

### 知识点 3：Triton 内核中编译期常量（`tl.constexpr`）的作用

- **是什么**：Triton 是写 GPU 内核的 Python DSL。`tl.constexpr` 标记的参数在编译期就被固定下来，编译器和 Triton 可以据此做特化优化。
- **为什么重要**：commit #37628 里给 `generate_draft_decode_kv_indices` 加了 `TRANSLATE: tl.constexpr = False`，意味着"要不要翻译地址"在编译期决定，不需要翻译时零开销。
- **动手试试**：写一个带 `constexpr` 分支的 Triton 内核。

```python
import torch
import triton
import triton.language as tl

@triton.jit
def scale_kernel(x_ptr, y_ptr, n, FACTOR: tl.constexpr = 1.0):
    pid = tl.program_id(0)
    offs = pid * 128 + tl.arange(0, 128)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    tl.store(y_ptr + offs, x * FACTOR, mask=mask)

x = torch.randn(256, device="cuda")
y = torch.empty_like(x)
scale_kernel[(2,)](x, y, 256, FACTOR=3.0)
print("前5个:", y[:5].tolist())
```

- **预期结果**：输出是 x 的 3 倍。改 `FACTOR` 后重新调用会触发重新编译（Triton 按 constexpr 值缓存内核）。

### 知识点 4：Diffusion 管线的"stage"化设计

- **是什么**：把视频/图像生成拆成多个可复用阶段（文本编码、图像编码、去噪、VAE 解码），每个阶段是一个类。
- **为什么重要**：commit #42841、#42967、#34494 都在做这种"抽公共基类"的重构。理解 stage 组织方式，你才能读懂 diffusion 推理代码。
- **动手试试**：写一个极简的 stage 管线。

```python
class Stage:
    def __call__(self, x):
        raise NotImplementedError

class AddOne(Stage):
    def __call__(self, x):
        return x + 1

class MulTwo(Stage):
    def __call__(self, x):
        return x * 2

class Pipeline:
    def __init__(self, stages):
        self.stages = stages
    def run(self, x):
        for s in self.stages:
            x = s(x)
        return x

p = Pipeline([AddOne(), MulTwo(), AddOne()])
print("结果:", p.run(3))  # ((3+1)*2)+1 = 9
```

- **预期结果**：输出 9。这就是 SGLang diffusion 代码里 `PipelineStage` 的简化版。

### 知识点 5：CUDA Graph 与"可打断图"（Breakable CUDA Graph）

- **是什么**：普通 CUDA Graph 把整段计算录成一个图，中间不能插入 Python 逻辑。Breakable 允许在图的中间"断开"，执行一段 eager 代码，再继续录。
- **为什么重要**：commit #42286 重构了 `eager_on_graph` 装饰器，让 eager 段能绑定"当前活跃的 forward batch"。这在投机解码、MoE 路由等需要动态决策的场景非常关键。
- **动手试试**：用 PyTorch 体验最基础的 CUDA Graph 捕获与重放。

```python
import torch

def f(x, y):
    return x * x + y

x = torch.randn(4, device="cuda")
y = torch.randn(4, device="cuda")
static_x = torch.zeros(4, device="cuda")
static_y = torch.zeros(4, device="cuda")

# 预热
s = torch.cuda.Stream()
s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):
    for _ in range(3):
        f(static_x, static_y)
torch.cuda.current_stream().wait_stream(s)

g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    static_out = f(static_x, static_y)

static_x.copy_(x); static_y.copy_(y)
g.replay()
print("图输出:", static_out.tolist())
print("直接算:", f(x, y).tolist())
```

- **预期结果**：两次输出一致。你会看到图重放省掉了 Python 层调度，这就是推理引擎里"图捕获"的威力。
