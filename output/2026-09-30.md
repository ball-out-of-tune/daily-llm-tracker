## 🧪 重要知识点 & 动手实验

### 知识点 1：量化推理（W4A16 / AWQ）——把模型塞进小显存

- **是什么**：把权重从 16 位浮点压到 4 位整数，激活仍用 16 位（所以叫 W4A16），显存直接省 4 倍，精度损失很小。
- **为什么重要**：一张 24GB 显卡原本只能跑 7B 模型，用 W4A16 可以跑 30B+。不懂量化格式（group_size、zero_point、packed layout）就会在加载 checkpoint 时各种报错。
- **动手试试**：
  ```bash
  # 用 vLLM 跑一个 AWQ 量化模型
  pip install vllm
  python -m vllm.entrypoints.openai.api_server \
      --model TheBloke/Llama-2-7B-Chat-AWQ \
      --quantization awq \
      --dtype float16
  ```
  然后看日志里 `quantization=awq`、`load_format=...`，再对比非量化版本的显存占用。
- **预期结果**：显存占用从约 14GB 降到约 4-5GB，输出质量肉眼几乎无差别。你会看到 vLLM 自动选择了 AWQ 的 GEMM kernel。

### 知识点 2：CUDA Graph 与原地更新（in-place update）

- **是什么**：CUDA Graph 把 kernel 序列录制成一张"图"，之后每次用同一块内存地址重放，省掉 CPU 调度开销。但前提是**地址和 dtype 不能变**。
- **为什么重要**：Commit 9 的 bug 就是 `_causal_buf` 原来是 bool，被 `.to(torch.int32)` 转成了新张量，图还指向旧地址，导致 replay 时 mask 永远是 capture 那一刻的快照。这类 bug 不报错、只出错结果，极难排查。
- **动手试试**：
  ```python
  import torch
  # 模拟：图捕获后，原地更新 vs 重新赋值
  buf = torch.zeros(4, dtype=torch.int32, device='cuda')
  # 正确：原地写
  buf[:] = torch.tensor([1, 0, 1, 0], device='cuda')
  print(buf.data_ptr())  # 地址不变
  # 错误：重新赋值
  buf = torch.tensor([1, 0, 1, 0], device='cuda')
  print(buf.data_ptr())  # 地址变了！CUDA graph 会失效
  ```
- **预期结果**：你会看到两次 `data_ptr()` 一个相同一个不同。记住原则：**CUDA graph 捕获的 buffer 只能用 `.copy_()` 或切片赋值更新**。

### 知识点 3：MoE（混合专家）与稀疏激活

- **是什么**：模型有很多"专家"子网络，每个 token 只激活其中 2-4 个，所以参数量大但计算量小。DeepSeek、Mixtral 都是 MoE。
- **为什么重要**：Commit 2 在 AMD ROCm 上给 DeepSeek V4.1 加 FP4 激活的 MoE kernel，说明 MoE 是当下主流架构，且硬件厂商在争相优化。不懂 MoE 的路由（router）和专家并行（EP）就无法调优。
- **动手试试**：
  ```bash
  # 跑一个小 MoE 模型（Qwen1.5-MoE 或 Mixtral 的量化版）
  python -m vllm.entrypoints.openai.api_server \
      --model Qwen/Qwen1.5-MoE-A2.7B-Chat \
      --tensor-parallel-size 1
  # 观察日志里的 "num_experts" 和 "experts_per_token"
  ```
- **预期结果**：日志会显示 `num_experts=60, experts_per_token=4` 之类信息。你可以试着用 `--enforce-eager` 对比 CUDA graph 开启前后的吞吐差异。

### 知识点 4：Tool Calling / 结构化输出（JSON Schema 约束）

- **是什么**：让模型输出的工具调用参数必须符合 JSON Schema，比如强制是 `{"type": "object", "properties": {...}}`。
- **为什么重要**：Commit 7 修了一个 bug——当 `tool_choice` 强制指定某个工具且参数为空时，之前不约束输出，模型可能吐出一堆废话导致解析失败。生产环境里 Agent 调用工具失败率很大一部分来自这里。

### 知识点 5：RL 权重校验（Weight Checker）

- **是什么**：通过 SHA-256 哈希每个权重张量，比较训练端和推理端的权重是否一致，确保权重更新真的落到了每一张卡上。
- **为什么重要**：Commit 17 新增 `/weight_checker` 端点。分布式 RL 里权重同步经常"看起来成功但实际没生效"，没有校验会导致训练崩溃或策略漂移。
- **动手试试**：
  ```bash

  VLLM_SERVER_DEV_MODE=1 python -m vllm.entrypoints.openai.api_server \
      --model facebook/opt-125m

  curl -X POST http://localhost:8000/weight_checker \
      -H 'Content-Type: application/json' \
      -d '{"action":"checksum"}' | head -c 300
  ```
- **预期结果**：返回类似 `{"checksums": {"dp0:pp0:pcp0:tp0:model.decoder.embed_tokens.weight": "a1b2..."}}` 的 JSON，每个张量一个哈希。你可以 reset 后再 checksum，看到哈希全变。

- **新手概念课堂**：采样就像"从一堆糖果里按概率抓一颗"。传统做法是先算每颗糖被选中的概率，再模拟一次随机抽签；融合算子相当于直接把"概率+抽签+选最大"打包成一个动作，减少中间搬运。
- **对你有什么影响**：CPU 上跑小模型时，采样阶段可能从毫秒级降到微秒级，尤其是大词表（128k）和高并发 batch 场景，端到端延迟明显下降。

### 2. [ROCm][Perf] Add opt-in a4w4 (FP4 activation) MoE for DeepSeek V4.1 on AITER (#58819)
- **代码层面**：在 `vllm/_aiter_ops.py` 和 MoE 配置里新增 `VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4` 环境变量开关，只在 `deepseek_v41` 模型类型上允许启用，否则抛错。
- **新手概念课堂**：a4w4 指激活和权重都用 4 位浮点（FP4），比 W4A16 更激进。因为 FP4 动态范围小，换错模型会导致权重布局（ATOM SEPARATED vs INTERLEAVE）不匹配，输出直接乱码——所以必须"白名单"式 opt-in。

- **新手概念课堂**：sleep mode 是 RL 场景里"暂停推理、腾出显存给训练"的机制。多个引擎时，只要有一个没醒，整个 wake_up 就该失败——这就像叫醒一屋子人，只要有一个人还在睡，就不能说"全员起床"。
- **对你有什么影响**：RL 用户调用 `/wake_up` 时会拿到更准确的返回，避免"以为醒了实际没醒"导致的请求挂起。

- **关键词：DCP（Decode Context Parallel，解码上下文并行）**
  - **一句话通俗解释**：把一条很长的序列切成几段，由多张卡同时负责解码阶段的计算，每张卡只算自己那一段，最后把结果拼起来。
  - **为什么社区在关注**：今天 Commit 1 专门为华为 NPU 上的 DeepSeek DSA 模型加了 DCP 支持，还在 PD 分离（Prefill/Decode 拆开部署）里新增了 `ascend` 传输后端。这说明长上下文推理已经不能靠单卡硬扛，必须做"切段并行"，而且国产硬件正在被认真适配。
  - **对新手意味着什么**：如果你学分布式推理，DCP 是继 TP/PP/EP/DP 之后必须补上的一块拼图。掌握"序列维度切分 + 跨卡通信"的思路，能直接迁移到任何长文本场景。

## 🧪 重要知识点 & 动手实验

### 知识点 1：序列并行与 DCP（分布式方向）

- **是什么**：把一条长序列沿 token 维度切成 N 份，N 张卡各算一份，需要时通过通信把跨段的信息交换回来。DCP 特指在解码（decode）阶段做这件事。
- **为什么重要**：长上下文（比如 128K）单卡放不下 KV cache，也来不及算。不懂序列并行，你就没法部署真正的大上下文模型。踩坑点在于：切分后 attention 的 softmax 需要跨卡归约，写错了结果就是错的，而且很难发现。
- **动手试试**：先理解概念，用 PyTorch 模拟"分段 softmax"：
```python
import torch
# 模拟：把一整行 logits 切成两段，分别算 softmax 再合并
logits = torch.randn(1, 8)
part1, part2 = logits[:, :4], logits[:, 4:]

# 朴素做法：直接对全量做 softmax（正确结果）
full = torch.softmax(logits, dim=-1)

# 分块做法：各自算 max 和 sum，再合并
m1, m2 = part1.max(-1, keepdim=True).values, part2.max(-1, keepdim=True).values
m = torch.maximum(m1, m2)
e1, e2 = torch.exp(part1 - m), torch.exp(part2 - m)
denom = e1.sum(-1, keepdim=True) + e2.sum(-1, keepdim=True)
merged = torch.cat([e1, e2], dim=-1) / denom

print("最大误差:", (full - merged).abs().max().item())
```
- **预期结果**：误差接近 0（约 1e-7）。你就掌握了 flash-attention / 序列并行里最核心的"在线 softmax 归约"技巧——这正是 DCP 跨卡通信要解决的问题。

### 知识点 2：Kernel 融合与 Triton（性能优化方向）

- **是什么**：把多个独立的小 GPU 算子（kernel）合并成一个，减少"启动开销 + 中间结果读写显存"的浪费。
- **为什么重要**：GPU 上每次 kernel 启动都有固定开销，中间张量写回显存再读出来更是带宽杀手。Commit 8 把"KV 准备"和"稀疏块展开"融合，就是典型例子。不懂融合，你的推理速度可能只有别人的一半。
- **动手试试**：用 Triton 写一个"加法 + 乘常数"的融合 kernel，对比 PyTorch 两步操作：
```python
import torch, triton, triton.language as tl

@triton.jit
def fused_add_mul(x_ptr, y_ptr, out_ptr, n, c, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, (x + y) * c, mask=mask)

n = 1 << 20
x, y = torch.randn(n, device="cuda"), torch.randn(n, device="cuda")
out = torch.empty_like(x)
grid = lambda meta: (triton.cdiv(n, meta["BLOCK"]),)
fused_add_mul[grid](x, y, out, n, 2.0, BLOCK=1024)
print("与 (x+y)*2 一致:", torch.allclose(out, (x + y) * 2))
```
- **预期结果**：输出 `True`。你已经写出第一个融合 kernel。可以进一步用 `torch.cuda.Event` 计时，对比 `(x+y)*2` 的两步版本，通常能看到 20%~40% 的加速。

### 知识点 3：低精度存储（fp8）与量化（量化方向）

- **是什么**：用 8 位浮点（fp8，e4m3 格式）代替 16 位来存 KV cache 或中间结果，显存直接砍半。
- **为什么重要**：Commit 7 给 QSA 索引缓存加了可选 fp8 存储。显存是推理的硬瓶颈，低精度存储是"免费"的容量翻倍。踩坑点：精度损失可能导致模型输出质量下降，需要评估。
- **动手试试**：用 PyTorch 模拟 fp8 量化误差：
```python
import torch
x = torch.randn(1024, 128)

# 模拟 e4m3：先缩放到合适范围，再四舍五入到 8 位
scale = x.abs().max() / 448.0  # e4m3 最大值约 448
x_scaled = x / scale
# 粗粒度模拟量化：保留 3 位尾数
x_q = torch.round(x_scaled * 8) / 8
x_deq = x_q * scale

print("原始范围:", x.abs().max().item())
print("量化误差 (MSE):", ((x - x_deq) ** 2).mean().item())
print("相对误差:", ((x - x_deq).abs() / (x.abs() + 1e-6)).mean().item())
```
- **预期结果**：相对误差大约在 1%~5% 量级。你会直观感受到"省一半显存，代价是几个百分点的精度"——这正是所有量化方案的核心权衡。

### 知识点 4：CUDA Graph 与显存预留（部署方向）

- **是什么**：CUDA Graph 把一串 GPU 操作录制成一个"图"，之后每次重放，省去逐个启动的开销。但录制时会一次性占住所有中间显存。
- **为什么重要**：Commit 2、3 的崩溃根源就是 MTP 多捕获了几个 graph，导致 Triton kernel 首次加载时没有显存可放。不懂 graph 的显存特性，你会遇到"明明还有 112GB 空闲却 OOM"的诡异现象。
- **动手试试**：观察 graph capture 前后的显存变化：
```python
import torch

def some_work(x):
    for _ in range(10):
        x = torch.relu(x @ x.T)
    return x

x = torch.randn(256, 256, device="cuda")
torch.cuda.synchronize()
print("capture 前:", torch.cuda.memory_allocated() / 1e6, "MB")

g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    y = some_work(x)

print("capture 后:", torch.cuda.memory_allocated() / 1e6, "MB")
g.replay()
torch.cuda.synchronize()
print("replay 后:", torch.cuda.memory_allocated() / 1e6, "MB")
```
- **预期结果**：你会看到 capture 后显存明显上升（graph 占住了中间张量），而 replay 不再增加。这就解释了为什么"多捕获几个 graph"会吃掉大量显存。

### 知识点 5：抽象层重构与"残差流"（架构设计方向）

- **是什么**：把模型层与层之间传递的"隐藏状态 + 残差"封装成一个有状态的对象（ResidualStream），用统一接口管理"何时求和、何时通信、何时归一化"。
- **为什么重要**：Commit 12/16/18/19 把七八个模型统一到这套协议上。这是大型框架从"每个模型手写一遍"进化到"声明式组合"的关键。理解它，你就能看懂现代推理引擎的骨架。
- **动手试试**：用 Python 类模拟一个简化版残差流：
```python
class ResidualStream:
    def __init__(self):
        self.residual = None
        self.pending = None

    def record(self, contribution):
        """生产者留下一个待求和的贡献"""
        self.pending = contribution

    def fold(self, hidden):
        """把待求和的贡献折进残差"""
        if self.pending is not None:
            hidden = hidden + self.pending
            self.pending = None
        self.residual = hidden
        return hidden

    def read(self):
        return self.residual

# 模拟两层
stream = ResidualStream()
h = 1.0
stream.record(0.5)          # 第一层留下贡献 0.5
h = stream.fold(h)          # 折进去 -> 1.5
print("残差:", stream.read())  # 1.5
stream.record(0.25)
h = stream.fold(h)          # -> 1.75
print("残差:", stream.read())  # 1.75
```
- **预期结果**：输出 `1.5` 和 `1.75`。你已经理解了残差流的核心状态机——真实框架里只是把"加法"换成了"跨卡通信 + 融合归一化"。
