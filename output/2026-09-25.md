## 🧪 重要知识点 & 动手实验

- **知识点 1：Triton 内核调度器（Kernel Dispatcher）**
  - **是什么**：一个注册表，允许你在运行时把某个 `@triton.jit` 函数替换成自己的实现，所有调用点自动生效。
  - **为什么重要**：在真实场景里，不同 GPU（NVIDIA/AMD/Intel）需要不同的内核实现。不懂这套机制，你就只能改源码；懂了，你可以写一个插件包直接替换。
  - **动手试试**：
    ```python
    # 先看 dispatcher 的接口
    from vllm.triton_utils.dispatcher import KernelOverride, register_kernels
    print(KernelOverride, register_kernels)

    # 跑一下官方测试，看它怎么替换内核
    # pytest tests/model_executor/test_triton_dispatcher.py -v
    ```
  - **预期结果**：你会看到测试里用 `_FakeTritonKernel` 冒充真内核，注册后调用点拿到的是 `KernelOverride` 实例而不是原始 `JITFunction`，说明替换成功。

- **知识点 2：MXFP8 与 32×32 block scale**
  - **是什么**：权重用 FP8 存，但每 32×32 个元素共享一个缩放因子（scale），比"整行一个 scale"更精细。
  - **为什么重要**：精度和速度的平衡点。如果 scale 太粗（比如整张量一个），大模型精度会掉；太细（每元素一个）又浪费显存。32×32 是硬件友好的折中。
  - **动手试试**：
    ```bash
    # 跑 MXFP8 内核选择测试（需要 CUDA GPU）
    pytest tests/kernels/quantization/test_mxfp8_kernel_selection.py -v
    # 跑 Marlin tile padding 测试（含新加的 32x256 形状）
    pytest tests/kernels/quantization/test_marlin_tile_padding.py -v -k mxfp8
    ```
  - **预期结果**：你会看到不同形状 (32,256)、(96,256)、(130,256) 都能正确地 padding 到 tile 大小并 round-trip 回原值，说明 block scale 路径没丢精度。

- **知识点 3：CUDA Graph 内存池与 weak_ref_tensor**
  - **是什么**：CUDA Graph 用固定内存池录制，重放时复用；`weak_ref_tensor` 只持有弱引用，不阻止内存被回收。
  - **为什么重要**：如果你把 tensor 传给一个异步流（side stream），但 tensor 是临时从池里借的，下一段 graph 可能把它复用掉，结果读到垃圾数据。这是典型的"偶发 bug"。
  - **动手试试**：
    ```python
    import torch
    from vllm.utils.torch_utils import weak_ref_tensor

    x = torch.arange(8, device="cuda")
    w = weak_ref_tensor(x)
    del x
    torch.cuda.empty_cache()
    # w 现在可能指向已释放的内存，访问结果未定义
    print(w)  # 可能出错或读到垃圾
    ```
  - **预期结果**：你会看到 `w` 在 `x` 被释放后不再安全。Commit 17 的修复就是给这类 tensor 单独开一块不会被池复用的内存。

- **知识点 4：分布式 all-reduce / reduce-scatter 与 NVLink multimem**
  - **是什么**：多卡训练/推理时，把各卡的数据求和（all-reduce）或求和后分发（reduce-scatter）。NVLink multimem 是 SM100 上的一种硬件加速广播/归约路径。
  - **为什么重要**：通信是分布式推理的瓶颈。低 SM 占用的 reduce-scatter 意味着计算内核有更多 SM 可用，整体吞吐更高。
  - **动手试试**：
    ```bash
    # 需要 8 卡 SM100 环境
    python -m torch.distributed.run --standalone --nproc-per-node=8 \
        benchmarks/kernels/benchmark_multimem_reduce_scatter.py \
        --message-bytes 16M 32M 64M --dtype bf16
    ```
  - **预期结果**：你会看到 multimem 候选在 16M~96M 消息大小下的延迟，对比传统 all-reduce 有明显优势（尤其是大消息）。没有 8 卡环境的话，读脚本里的 `Candidate` 数据结构也能理解对比方法。

- **知识点 5：Lark 语法与结构化输出**
  - **是什么**：Lark 是一种语法描述语言，比 EBNF 更易读，支持正则、别名、`%import`。xgrammar 后端现在能直接解析 Lark。
  - **为什么重要**：结构化输出（让模型只输出 JSON/特定格式）依赖语法约束。支持 Lark 意味着你可以直接抄 HuggingFace / Codex 工具定义里的语法。
  - **动手试试**：
    ```python
    from vllm.sampling_params import SamplingParams, StructuredOutputsParams

    lark = """
    start: "id=" NUMBER tag? LF?
    tag: " #" /[a-z]+/ -> label
    NUMBER: /[0-9]+/
    %import common.LF
    """
    params = SamplingParams(structured_outputs=StructuredOutputsParams(grammar=lark))
    print(params.structured_outputs.grammar)
    # 跑官方测试
    # pytest tests/v1/structured_output/test_backend_xgrammar_lark.py -v
    ```
  - **预期结果**：测试会验证 Lark 语法在请求校验和编译两个阶段都能被原生解析，不再被改写成 EBNF。

## 🧪 重要知识点 & 动手实验

### 知识点 1：int32 偏移溢出（来自 Commit 1）

- **是什么**：Triton kernel 里用 `int32` 存字节偏移，超过 2 GiB 就会变成负数，写到缓冲区外面去。
- **为什么重要**：KV cache 单层就可能超过 2 GiB，尤其是长上下文 + 大 head_dim。不修就是内存越界写，轻则结果错，重则崩进程。
- **动手试试**：
  ```python
  import numpy as np
  # 模拟 int32 溢出
  offset = np.int32(2**31 - 1)
  print("max int32:", offset)
  print("overflow:", np.int32(offset + 1))  # 变成负数
  # 正确做法：用 int64
  offset64 = np.int64(2**31 - 1)
  print("int64 safe:", offset64 + 1)
  ```
- **预期结果**：你会看到 int32 加 1 后变成 `-2147483648`，而 int64 正常。这就是为什么 Triton kernel 里要把 `.to(tl.int32)` 改成 `.to(tl.int64)`。

### 知识点 2：推测解码的 mask 构造（来自 Commit 7）

- **是什么**：XQA 后端在 verify 阶段需要构造一个 bitmask，告诉注意力 kernel 每个 draft token 只能看到哪些位置。
- **为什么重要**：推测解码的 verify 是"一次前向验证多个 draft token"，如果 mask 错了，draft token 会看到不该看的位置，结果全错。
- **动手试试**：
  ```python
  import torch
  draft_len = 5
  words_per_row = (draft_len + 31) // 32 * 2
  row = torch.arange(draft_len, dtype=torch.int32)[:, None]
  word = torch.arange(words_per_row, dtype=torch.int32)[None, :]
  bits = (row + 1 - 16 * word).clamp(0, 16)
  mask = ((1 << bits) - 1).to(torch.uint16)
  print("bits:\n", bits)
  print("mask:\n", mask)
  ```
- **预期结果**：你会看到一个下三角形状的位掩码，每个 draft token 只允许看到自己和之前的位置。这就是 causal mask 在推测解码里的位压缩表示。

### 知识点 3：懒加载与 `functools.cache`（来自 Commit 5）

- **是什么**：把"导入即加载"改成"第一次用到才加载"，并用 `@cache` 缓存结果。
- **为什么重要**：启动时少导入一个重库，可能省几秒。对于需要频繁重启的开发和 CI 场景，体验差别巨大。
- **动手试试**：
  ```python
  from functools import cache
  import time

  @cache
  def load_heavy():
      print("loading...")
      time.sleep(1)
      return {"data": 42}

  t0 = time.time()
  load_heavy()
  print("first call:", time.time() - t0)
  t0 = time.time()
  load_heavy()
  print("second call:", time.time() - t0)
  ```
- **预期结果**：第一次调用打印 "loading..." 并耗时约 1 秒，第二次瞬间返回。这就是 `@cache` 的威力。

### 知识点 4：DP 并行中的 gather slot（来自 Commit 4）

- **是什么**：数据并行（DP）下，每个 rank 要把自己的 token 数告诉别人，需要一个"槽位"来对齐。
- **为什么重要**：推测解码的 draft 模型会复用 target 的 DP 通信，如果 slot 算错，draft 会读到错误的 token 数，导致 padding 错乱。
- **动手试试**：
  ```python
  # 模拟 DP gather：4 个 rank 各自的 token 数
  global_num_tokens = [10, 20, 15, 5]
  # 每个 rank 需要知道自己该看哪个位置
  def dp_slot_in(global_num_tokens, rank):
      # 简化版：rank 直接对应索引
      return rank
  for rank in range(4):
      slot = dp_slot_in(global_num_tokens, rank)
      print(f"rank {rank} reads slot {slot} -> {global_num_tokens[slot]} tokens")
  ```
- **预期结果**：每个 rank 读到自己的 token 数。真实代码里 slot 可能因为 elastic scale-up 而偏移，所以要用 `dp_gather_slot()` 而不是直接 `attn_dp_rank`。

### 知识点 5：安全默认值设计（来自 Commit 2）

- **是什么**：新功能默认关闭，用户必须显式开启才能用。
- **为什么重要**：请求里自带 `chat_template` 可能被用来注入任意模板，绕过服务端的 prompt 约束。默认拒绝是防御性编程。
- **动手试试**：
  ```python
  class ServerConfig:
      trust_request_chat_template = False  # 默认关闭

  def validate_request(request, config):
      if request.get("chat_template") and not config.trust_request_chat_template:
          return "Request-supplied chat_template is not allowed."
      return None

  config = ServerConfig()
  req = {"chat_template": "{{ evil }}"}
  print(validate_request(req, config))  # 拒绝
  config.trust_request_chat_template = True
  print(validate_request(req, config))  # 允许
  ```
- **预期结果**：默认情况下请求被拒绝，开启信任后才允许。这就是"secure by default"。
