### 知识点 1：CUDA Graph 与权重回放（Commit 1）

- **是什么**：CUDA Graph 是 NVIDIA 提供的一种把一系列 GPU kernel 调用"录制"成一张图、然后反复"重放"的技术。但录制时 kernel 会记住张量的**内存地址**，如果之后权重被重新加载到新地址，图就会失效。

- **为什么重要**：在模型做 sleep/wake 或 checkpoint 恢复时，如果权重存储被替换，CUDA Graph 重放就会崩溃或产生错误结果。这个 commit 就是修复 ROCm 平台上 MoE 层在 CUDA Graph 捕获后权重被替换的问题。

- **动手试试**：
```python
import torch

# 模拟 CUDA Graph 捕获
x = torch.randn(4, 4, device='cuda')
w = torch.randn(4, 4, device='cuda')

# 录制计算图
g = torch.cuda.CUDAGraph()
# 预热
for _ in range(3):
    y = x @ w
torch.cuda.synchronize()
with torch.cuda.graph(g):
    y = x @ w

# 重放
g.replay()
print(y)  # 正常

# 关键：替换权重 w 的内存（模拟权重回放）
w_new = torch.randn(4, 4, device='cuda')
w.data = w_new.data  # 注意：这不会改变 w 的地址！
# 但如果做 w = w_new，w 的地址变了，graph 重放就会用旧地址
print(y)  # 仍然是旧 w 的结果
```

- **预期结果**：你会看到即使 `w.data = w_new.data`，`y` 不变（因为地址没变）；但如果直接 `w = w_new`，graph 重放还是会用旧地址。这解释了为什么 commit 中强调"post-load processing 不能替换参数存储"。

### 知识点 2：Triton Kernel 编写规范（Commit 5、6）

- **是什么**：Triton 是一种类 Python 的 GPU 编程语言，比 CUDA 更易用。vLLM 为 AI Agent 编写了专门的"技能文件"来指导如何写 Triton kernel。

- **为什么重要**：Triton 有很多"坑"——比如 grid 维度限制 65535、int32 溢出、JIT 编译的特化问题等。不懂这些，写的 kernel 可能在特定形状下崩溃或性能极差。

- **动手试试**：
```python
import triton
import triton.language as tl
import torch

@triton.jit
def add_kernel(x_ptr, y_ptr, output_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(output_ptr + offsets, x + y, mask=mask)

# 注意：BLOCK_SIZE 必须是 2 的幂
x = torch.randn(10000, device='cuda')
y = torch.randn(10000, device='cuda')
output = torch.empty_like(x)

# grid[0] 可以很大，但 grid[1] 和 grid[2] 不能超过 65535
grid = (triton.cdiv(10000, 1024),)
add_kernel[grid](x, y, output, 10000, BLOCK_SIZE=1024)
print(torch.allclose(output, x + y))  # True
```

- **预期结果**：kernel 能正确执行。然后试试把 `BLOCK_SIZE` 改成 1000（不是 2 的幂），会报错——这说明了 Triton 对编译时常量的约束。

### 知识点 3：int32 vs int64 索引（Commit 19）

- **是什么**：在 GPU 计算中，索引数组用 int32 还是 int64 会影响内存占用和性能。int32 只用 4 字节，int64 用 8 字节，但 int32 最大只能表示约 21 亿。

- **为什么重要**：这个 commit 把 NIXL（NVIDIA 的通信库）的索引从 int64 改为 int32，避免了中间类型转换，提升了性能。但对新手来说，关键是理解：**什么时候可以用 int32，什么时候必须用 int64**。

- **动手试试**：
```python
import numpy as np

# int32 溢出问题
a = np.array([2_000_000_000], dtype=np.int32)
b = np.array([500_000_000], dtype=np.int32)
print(a + b)  # 溢出！结果是负数

# 但如果先转 int64 再算就没问题
a64 = a.astype(np.int64)
b64 = b.astype(np.int64)
print(a64 + b64)  # 正确

# 在 GPU kernel 中，索引超过 2^31 就需要 int64
# 例如 KV cache 地址计算：num_layers * num_heads * seq_len * head_dim
num_layers, num_heads, seq_len, head_dim = 80, 8, 131072, 128
kv_cache_size = num_layers * num_heads * seq_len * head_dim
print(kv_cache_size)  # 远超 2^31，必须用 int64 计算！
```

- **预期结果**：看到 int32 溢出的危害，理解为什么 commit 中说"Cast operands before multiplication or addition so an intermediate does not overflow in 32-bit arithmetic"。

### 知识点 4：多模态缓存哈希按模态隔离（Commit 20）

- **是什么**：多模态模型（如同时处理图片和视频的模型）在处理输入时，会把预处理参数（如图片尺寸、视频帧数）哈希成缓存键。这个 bug 修复让**不同模态的参数变更不会互相影响缓存**。

- **为什么重要**：如果图片尺寸变了导致整个缓存失效（包括视频的），会造成大量不必要的重复预处理，浪费计算资源。这也是缓存设计中"关注点分离"的经典问题。

- **动手试试**：
```python
# 模拟缓存键设计
def make_cache_key(image_size=None, video_frames=None):
    """好的设计：按模态分开"""
    parts = []
    if image_size is not None:
        parts.append(f"img:{image_size}")
    if video_frames is not None:
        parts.append(f"vid:{video_frames}")
    return "|".join(parts) if parts else "empty"

# 坏的设计：所有参数混在一起
def bad_cache_key(**kwargs):
    return str(sorted(kwargs.items()))

# 测试：只改图片尺寸，视频缓存应该仍然有效
cache = {}
# 第一次请求：图片 224，视频 4 帧
key1 = make_cache_key(image_size=224, video_frames=4)
cache[key1] = "processed_result"

# 第二次请求：图片改成 448，视频还是 4 帧
key2 = make_cache_key(image_size=448, video_frames=4)
print(f"Video cache hit: {key2 in cache}")  # False，因为 key2 != key1

# 但如果设计成按模态分开缓存：
image_cache = {}
video_cache = {}
image_cache[224] = "img_processed"
video_cache[4] = "vid_processed"

# 图片变了只影响图片缓存
image_cache[448] = "img_processed_new"
print(f"Video cache still valid: {4 in video_cache}")  # True！
```

- **预期结果**：理解为什么 commit 中要把 `media_io_kwargs` 和 `hf_processor_mm_kwargs` 按模态隔离——这样改图片参数不会让视频缓存失效。

### 知识点 5：量化容差与原子操作不确定性（Commit 12）

- **是什么**：FP8 量化（8位浮点）相比 BF16（16位）精度更低。在 GPU 上做 split-K 归约时使用原子操作，**原子操作的非确定性执行顺序**会导致结果在相邻的 BF16 值之间波动（1 ULP 的差异）。

- **为什么重要**：测试中的容差设置不能太紧，否则会因为硬件的不确定性导致测试随机失败（flaky test）。这也是为什么 commit 中把相对误差从 0.002 放宽到 0.003。

- **动手试试**：
```python
import torch

# 模拟 split-K 归约中的原子操作不确定性
def splitk_reduce(x, num_splits=4):
    """模拟多个 split 并行计算后原子累加"""
    split_size = x.shape[0] // num_splits
    results = []
    for i in range(num_splits):
        part = x[i*split_size:(i+1)*split_size]
        results.append(part.sum())
    
    # 模拟原子操作：结果取决于累加顺序
    # 不同顺序可能产生不同的舍入误差
    total_1 = results[0] + results[1] + results[2] + results[3]
    total_2 = results[3] + results[2] + results[1] + results[0]
    total_3 = results[1] + results[3] + results[0] + results[2]
    
    return total_1, total_2, total_3

# 用 BF16 测试
x = torch.randn(1024, dtype=torch.bfloat16, device='cuda') * 100
r1, r2, r3 = splitk_reduce(x)
print(f"不同累加顺序的结果差异: {(r1-r2).abs().item():.6f}")
print(f"是否完全一致: {torch.allclose(r1, r2, rtol=1e-6)}")
```

- **预期结果**：不同累加顺序可能在 BF16 下产生微小差异（约 1 ULP）。这解释了为什么测试容差不能设得太紧，也解释了为什么 commit 12 同时提高了容差并加强了余弦相似度要求。

## 🧪 重要知识点 & 动手实验

### 知识点 1：Radix Tree（基数树）前缀匹配优化
- **是什么**：一种用于存储字符串/序列前缀的树结构，SGLang 用它管理 KV Cache 的复用。
- **为什么重要**：在推理中，多个请求共享相同的前缀 token 时，Radix Tree 能避免重复计算。理解它有助于理解 SGLang 的 prefix caching 机制。
- **动手试试**：
```python
# 模拟 RadixKey 的 match 行为（简化版）
class FakeRadixKey:
    def __init__(self, tokens):
        self.tokens = tokens
    def match_at(self, other, offset):
        # 返回从 offset 开始与 other 的公共前缀长度
        n = min(len(self.tokens), len(other.tokens) - offset)
        count = 0
        for i in range(n):
            if self.tokens[i] == other.tokens[offset + i]:
                count += 1
            else:
                break
        return count

# 测试：两个请求共享前缀 "hello world"
req1 = FakeRadixKey(list("hello world, how are you?"))
req2 = FakeRadixKey(list("hello world, I'm fine."))
print(f"共享前缀长度: {req1.match_at(req2, 0)}")  # 应输出 12
```
- **预期结果**：输出 `12`，说明你理解了前缀匹配的基本逻辑，这对理解 SGLang 的 Radix Cache 工作原理有帮助。

### 知识点 2：广播（Broadcast）在分布式推理中的作用
- **是什么**：一种集体通信操作，将一份数据从某个 rank 发送到所有其他 rank。
- **为什么重要**：PP 动态 chunk 修复中，所有 rank 必须同步禁用/启用某个功能，否则会出现死锁或行为不一致。
- **动手试试**：
```python
import torch
import torch.distributed as dist

# 初始化（假设已有 2 个进程）
dist.init_process_group("gloo", rank=0, world_size=2)

# 只有 rank 0 有数据
data = [1, 2, 3] if dist.get_rank() == 0 else None
print(f"广播前 rank {dist.get_rank()}: {data}")

# 广播：从 rank 0 发给所有人
data = dist.broadcast_object_list([data], src=0)[0]
print(f"广播后 rank {dist.get_rank()}: {data}")
```
- **预期结果**：两个进程都输出 `[1, 2, 3]`，说明你理解了 broadcast 的语义——它保证了所有 rank 看到相同的数据，是分布式系统中"一致性"的基础。

### 知识点 3：CUDA Graph 捕获与重放
- **是什么**：将一系列 GPU 内核启动录制为一张图，之后可以以极低的 CPU 开销重放。
- **为什么重要**：SGLang 的 decode 阶段大量使用 CUDA Graph 来降低延迟。提交 #37329 改进了其输出处理逻辑。
- **动手试试**：
```python
import torch

# 创建一个简单的 CUDA Graph 示例
x = torch.randn(4096, device="cuda")
y = torch.empty_like(x)

# 捕获
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    y = x * 2.0 + 1.0

# 重放（不需要重新启动内核，开销极低）
g.replay()
print(y[:5])  # 输出 x*2+1 的结果
```
- **预期结果**：输出 `x * 2 + 1` 的值。理解 CUDA Graph 是理解 SGLang 高性能推理的关键一步。

### 知识点 4：MXFP8/FP8 量化与精度处理
- **是什么**：将模型权重/激活从 FP16/BF16 压缩到 FP8（8位浮点），以节省显存和带宽。
- **为什么重要**：提交 #37489 修复了 SM107 上 FP32 输入被错误量化的问题。新手在部署量化模型时容易忽略 dtype 匹配问题。
- **动手试试**：
```python
import torch

# 模拟 FP32 到 FP8 的转换
x_fp32 = torch.randn(4, 32, dtype=torch.float32)
print(f"FP32 range: [{x_fp32.min():.3f}, {x_fp32.max():.3f}]")

# 转换为 FP8（e4m3 格式）
x_fp8 = x_fp32.to(torch.float8_e4m3fn)
print(f"FP8 range: [{x_fp8.float().min():.3f}, {x_fp8.float().max():.3f}]")

# 观察精度损失
error = (x_fp8.float() - x_fp32).abs().mean()
print(f"平均绝对误差: {error:.4f}")
```
- **预期结果**：看到 FP8 转换后的数值范围被截断，误差非零。这提醒你：量化是有损的，且不同 dtype 的输入需要走不同的量化路径。

### 知识点 5：环境变量控制 JIT 编译行为
- **是什么**：通过环境变量让运行时决定是否允许动态编译。
- **为什么重要**：生产环境希望"预先编译好，启动时不编译"，避免冷启动抖动。提交 #36615 新增 `SGLANG_CRASH_ON_JIT_COMPILE` 强制这一行为。
- **动手试试**：
```bash
# 先正常启动，观察 JIT 编译日志
python -c "import sglang; print('ok')"

# 设置禁止 JIT 编译的环境变量
SGLANG_CRASH_ON_JIT_COMPILE=1 python -c "import sglang; print('ok')"
```
- **预期结果**：第二条命令如果遇到未缓存的编译，会抛出 `RuntimeError` 并提示你 "forbids compiling at runtime"。这让你理解生产环境如何通过环境变量控制编译策略。
