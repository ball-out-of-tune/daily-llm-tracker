## 🧪 重要知识点 & 动手实验

### 知识点 1：Pooling 模型为什么不能预留"生成 token"的位置

- **是什么**：聊天模型每步会生成一个新 token，所以调度器要预留一个 context slot；但 pooling 模型（embedding/rerank）只做前向传播，不生成 token，所以不能预留。
- **为什么重要**：如果不区分，pooling 请求在 chunked prefill 时最后一个 chunk 会少算一个 token，导致 embedding 结果错误或请求卡住。
- **动手试试**：
  ```python
  # 模拟调度器行为（简化版）
  max_model_len = 8
  max_num_batched_tokens = 4
  prompt_len = 8

  # 生成式模型：每步预留 1 个 token 给采样
  num_sampled = 1
  # 非生成式模型：不预留
  num_sampled_pooling = 0

  def chunks(prompt_len, chunk_size, reserve):
      remaining = prompt_len
      result = []
      while remaining > 0:
          # 关键：chunk 大小要减去预留的 slot
          take = min(chunk_size - reserve, remaining)
          result.append(take)
          remaining -= take
      return result

  print("生成式:", chunks(prompt_len, max_num_batched_tokens, num_sampled))
  print("Pooling:", chunks(prompt_len, max_num_batched_tokens, num_sampled_pooling))
  ```
- **预期结果**：生成式会输出 `[3, 3, 2]`（最后一块少一个 token），pooling 输出 `[4, 4]`（正好覆盖全部 8 个 token）。这解释了为什么 pooling 请求必须用 `num_sampled_tokens_per_step = 0`。

### 知识点 2：NonUvaBuffer 的 `non_blocking=True` 为什么能避免 stream sync

- **是什么**：把数据从 CPU 内存拷到 GPU 时，如果 CPU 内存是"pinned"（锁页）的，可以用异步拷贝；如果不是，PyTorch 默认会同步等待。
- **为什么重要**：每次同步都会让 GPU 空转，在推理服务里累积起来就是明显的延迟。
- **动手试试**：
  ```python
  import torch
  import numpy as np

  # 模拟 NonUvaBuffer 的行为
  size = 8
  cpu_tensor = torch.from_numpy(np.arange(size, dtype=np.int32))
  gpu_tensor = torch.empty(size, dtype=torch.int32, device="cuda")

  # 开启同步检测模式（如果发生隐式同步会报错）
  torch.cuda.set_sync_debug_mode("error")
  try:
      # 非阻塞拷贝：要求源 tensor 是 pinned 的
      gpu_tensor.copy_(cpu_tensor, non_blocking=True)
      print("non_blocking=True 拷贝成功，没有触发同步")
  except RuntimeError as e:
      print("触发同步:", e)
  finally:
      torch.cuda.set_sync_debug_mode(0)

  torch.cuda.synchronize()
  print("结果:", gpu_tensor.tolist())
  ```
- **预期结果**：如果 `cpu_tensor` 不是 pinned 的，`non_blocking=True` 可能仍然触发同步；vLLM 的 `NonUvaBuffer` 内部用 pinned 内存，所以能真正异步。你会看到"拷贝成功"且不报错。

### 知识点 3：n-gram 推测解码是怎么"猜"token 的

- **是什么**：n-gram 推测解码不看模型，而是直接在已生成的文本里找"之前出现过相同 n 个 token 的片段"，把后面跟着的 token 当作猜测。
- **为什么重要**：它不需要额外的小模型，几乎零成本，特别适合代码补全、文档续写这类重复性强的任务。
- **动手试试**：
  ```python
  def ngram_propose(context, n=3, max_draft=4):
      """在 context 里找最近一次出现的 n-gram，返回它后面的 token 作为草稿。"""
      if len(context) < n:
          return []
      suffix = tuple(context[-n:])
      # 从右往左找最近一次匹配
      for i in range(len(context) - n - 1, -1, -1):
          if tuple(context[i:i+n]) == suffix:
              # 返回匹配点后面的 max_draft 个 token
              return context[i+n : i+n+max_draft]
      return []

  context = [1, 2, 3, 4, 5, 1, 2, 3, 9, 8, 7]
  draft = ngram_propose(context, n=3, max_draft=3)
  print("草稿 token:", draft)
  # 期望：找到 [1,2,3] 后面跟的是 [4,5,1]，所以草稿是 [4,5,1]
  ```
- **预期结果**：输出 `[4, 5, 1]`。如果大模型验证后接受这些 token，就省下了 3 次前向传播。GPU 版（commit 17）把"找最近匹配"这一步并行化到 GPU 上，速度更快。

### 知识点 4：为什么要把 `cur_token * stride` 转成 int64

- **是什么**：在 GPU kernel 里计算输出地址时，`cur_token * output_tensor_stride0` 可能超过 32 位整数上限（约 21 亿），导致地址溢出。
- **为什么重要**：当模型很大（hidden_size=6144）且 batch 很大时，输出张量的行偏移会超过 2^31，用 int32 算地址就会写到错误的位置，产生静默错误。
- **动手试试**：
  ```python
  import numpy as np

  hidden_size = 6144
  # 模拟超过 int32 上限的行号
  output_row = (1 << 31) // hidden_size + 1
  print(f"output_row = {output_row}")

  # int32 计算（会溢出）
  stride = hidden_size
  int32_result = np.int32(output_row) * np.int32(stride)
  print(f"int32 结果: {int32_result} (可能为负或错误)")

  # int64 计算（正确）
  int64_result = np.int64(output_row) * np.int64(stride)
  print(f"int64 结果: {int64_result} (正确)")
  ```
- **预期结果**：int32 结果会溢出变成负数或错误值，int64 结果正确。这就是 commit 8 把 `cur_token` 转成 `tl.int64` 的原因。

### 知识点 5：量化 kernel 的"优先级列表"是怎么工作的

- **是什么**：vLLM 为每种量化格式维护一个 kernel 候选列表，按平台（CUDA/ROCm）和能力（SM80/SM90）排序，运行时选第一个支持的。
- **为什么重要**：不同 kernel 在同一个 GPU 上性能可能差 2-3 倍，选错就是白白浪费算力。
- **动手试试**：
  ```python
  # 模拟 vLLM 的 kernel 选择逻辑
  class Kernel:
      def __init__(self, name, min_cc):
          self.name = name
          self.min_cc = min_cc

  kernels = [
      Kernel("MarlinFP8", 80),
      Kernel("HummingFP8", 90),
      Kernel("CutlassFP8", 89),
  ]

  def select(kernels, cc):
      # 按列表顺序选第一个满足能力要求的
      for k in kernels:
          if cc >= k.min_cc:
              return k.name
      return None

  print("SM80:", select(kernels, 80))
  print("SM90:", select(kernels, 90))

  # commit 20 做的事情：在 SM90 上把 Humming 提到 Marlin 前面
  def prioritize_humming(kernels, cc):
      if cc < 90:
          return kernels
      humming = [k for k in kernels if "Humming" in k.name]
      rest = [k for k in kernels if "Humming" not in k.name]
      return humming + rest

  print("SM90 重排后:", select(prioritize_humming(kernels, 90), 90))
  ```
- **预期结果**：SM80 选 Marlin，SM90 原本也选 Marlin（因为它在列表前面），重排后 SM90 选 Humming。这就是 commit 20 的核心逻辑。

## 🧪 重要知识点 & 动手实验

### 知识点 1：量化中的 SwiGLU 激活与 clamp 限制

- **是什么**：SwiGLU 是 MoE 模型常用的激活函数，公式大致是 `swish(x) * gate(x)`。有些量化 checkpoint 会带一个 `swiglu_limit`（也叫 `gemm1_clamp_limit`），用来把激活值裁剪到某个范围，防止量化溢出。
- **为什么重要**：Commit 12 修的就是这个 bug——Quark W4A4 MXFP4 的 MoE 声明了 `activation="silu"` 但实际带了 `gemm1_clamp_limit`，如果不把 clamp 传给 AITER 的 SwiGLU kernel，专家网络会静默地跑成普通 SiLU，输出全是垃圾。这种 bug 不会报错，只会让模型"看起来能跑但结果乱"。
- **动手试试**：
  ```python
  import torch
  import torch.nn.functional as F

  def swiglu_plain(x, gate):
      return F.silu(x) * gate

  def swiglu_clamped(x, gate, limit):
      x = x.clamp(-limit, limit)
      gate = gate.clamp(-limit, limit)
      return F.silu(x) * gate

  torch.manual_seed(0)
  x = torch.randn(4, 8) * 10
  gate = torch.randn(4, 8) * 10
  limit = 7.0

  out_plain = swiglu_plain(x, gate)
  out_clamped = swiglu_clamped(x, gate, limit)
  print("max diff:", (out_plain - out_clamped).abs().max().item())
  print("plain  :", out_plain[0, :4])
  print("clamped:", out_clamped[0, :4])
  ```
- **预期结果**：你会看到 `max diff` 很大（因为输入乘了 10，超出了 limit），说明 clamp 与否结果完全不同。如果你在部署量化 MoE 时忘了传 `swiglu_limit`，就会得到 `out_plain` 这种错误结果。

### 知识点 2：位级一致的 sigmoid 实现

- **是什么**：`sigmoid(x) = 1 / (1 + exp(-x))`。听起来简单，但不同实现（`tl.sigmoid`、`torch.sigmoid`、手写 `libdevice.exp`）在浮点层面结果可能不同。
- **为什么重要**：Commit 13 把 Triton kernel 里的 `tl.sigmoid` 换成了 `tl.div_rn(1.0, 1.0 + libdevice.exp(-b_beta))`，就是为了和 PyTorch 的 `beta.float().sigmoid()` 位级一致。在 KDA（一种线性注意力）里，beta 是门控系数，位级不一致会导致长序列累积误差，最终输出对不上。
- **动手试试**：
  ```python
  import torch

  # 用 float32 模拟 bf16 输入
  beta = torch.tensor([-10.0, -1.0, 0.0, 1.0, 10.0], dtype=torch.float32)

  # 方式 1：torch.sigmoid
  s1 = torch.sigmoid(beta)

  # 方式 2：手写 exp
  s2 = 1.0 / (1.0 + torch.exp(-beta))

  # 方式 3：用 float64 作为"真值"
  s3 = torch.sigmoid(beta.double()).float()

  print("torch.sigmoid :", s1)
  print("manual exp    :", s2)
  print("float64 truth :", s3)
  print("diff s1 vs s2 :", (s1 - s2).abs())
  print("diff s1 vs s3 :", (s1 - s3).abs())
  ```
- **预期结果**：你会发现 `torch.sigmoid` 和手写 `exp` 在 float32 下就有细微差异（尤其在 `x=±10` 附近）。这就是为什么 kernel 作者要用 `libdevice.exp` + `div_rn`——它们和 PyTorch 的 CUDA 实现走的是同一条指令路径。

### 知识点 3：CUDA Graph 与"为什么融合能提速"

- **是什么**：CUDA Graph 把一串 GPU kernel 调用"录制"成一张图，之后每次执行只需要一次 launch，而不是每个 kernel 都从 CPU 发一次指令。算子融合则是把多个小 kernel 合并成一个，减少 kernel launch 和显存读写。
- **为什么重要**：Commit 11（Anima AdaLN 融合）和 Commit 17（DiffusionGemma FA4 + CUDA graphs）都是这个思路。在 diffusion 这种要跑几十步去噪的场景里，每步省几毫秒，50 步就是几百毫秒。
- **动手试试**：
  ```python
  import torch
  import time

  def small_ops(x):
      x = x * 1.5
      x = x + 0.5
      x = torch.tanh(x)
      x = x / 2.0
      return x

  x = torch.randn(1024, 1024, device="cuda")

  # 预热
  for _ in range(10):
      small_ops(x)
  torch.cuda.synchronize()

  # 普通执行
  t0 = time.perf_counter()
  for _ in range(1000):
      y = small_ops(x)
  torch.cuda.synchronize()
  t1 = time.perf_counter()
  print(f"eager: {(t1 - t0) * 1000:.2f} ms")

  # CUDA Graph 捕获
  g = torch.cuda.CUDAGraph()
  static_x = x.clone()
  with torch.cuda.graph(g):
      static_y = small_ops(static_x)

  t0 = time.perf_counter()
  for _ in range(1000):
      g.replay()
  torch.cuda.synchronize()
  t1 = time.perf_counter()
  print(f"graph: {(t1 - t0) * 1000:.2f} ms")
  ```
- **预期结果**：你会看到 graph 版本明显更快（通常快 2-5 倍），因为省掉了 4 次 kernel launch 的 CPU 开销。这就是为什么 sglang 在 decode 阶段大量使用 CUDA Graph。

### 知识点 4：契约测试——用测试约束重构

- **是什么**：契约测试（contract test）不测"功能对不对"，而是测"每个字段/每个分支是否被显式处理"。比如 Commit 2 要求 `ComponentData` 的每个字段都必须在 split hook 里被分类为 copy/divide/reset/migrate。
- **为什么重要**：MemCache 的 SWA 组件曾经两次忘记处理 `host_lock_ref`（#38138 和 #38480），导致正在写 L3 的 host slice 被驱逐回收。这种 bug 靠人工 review 很难发现，但契约测试一加就再也跑不掉了。
- **动手试试**：
  ```python
  import dataclasses
  import unittest

  @dataclasses.dataclass
  class ComponentData:
      value: int = 0
      host_value: int = 0
      lock_ref: int = 0
      host_lock_ref: int = 0

  # 契约：每个字段必须被分类
  SPLIT_POLICY = {
      "value": "divide",
      "host_value": "divide",
      "lock_ref": "copy",
      "host_lock_ref": "copy",
  }

  class TestContract(unittest.TestCase):
      def test_all_fields_classified(self):
          fields = {f.name for f in dataclasses.fields(ComponentData)}
          classified = set(SPLIT_POLICY.keys())
          missing = fields - classified
          self.assertEqual(missing, set(), f"未分类字段: {missing}")

  # 模拟：如果新增一个字段但忘了分类
  @dataclasses.dataclass
  class ComponentDataV2:
      value: int = 0
      host_value: int = 0
      lock_ref: int = 0
      host_lock_ref: int = 0
      new_field: int = 0  # 新字段

  class TestContractV2(unittest.TestCase):
      def test_all_fields_classified(self):
          fields = {f.name for f in dataclasses.fields(ComponentDataV2)}
          classified = set(SPLIT_POLICY.keys())
          missing = fields - classified
          self.assertEqual(missing, set(), f"未分类字段: {missing}")

  # 运行
  unittest.main(argv=[""], exit=False)
  ```
- **预期结果**：第一个测试通过，第二个测试失败并提示 `未分类字段: {'new_field'}`。这就是契约测试的威力——你新增字段时，测试会强制你去更新分类表。
