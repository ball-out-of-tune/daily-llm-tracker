## 🧪 重要知识点 & 动手实验

### 知识点 1：算子融合（以 Fused WO-A + Inverse RoPE + FP8 Quant 为例）

- **是什么**：DeepSeek V4.1 的注意力输出投影（WO-A）本来要分三步做：反向 RoPE 旋转 → 矩阵乘 → FP8 量化。融合后一个 kernel 全干完。
- **为什么重要**：每多一个 kernel，就要把中间结果写回显存再读出来，带宽是瓶颈。融合后能省 2/3 的显存往返，小 batch 场景下延迟能降一大截。不懂这个，你写的推理代码永远比人家的慢。
- **动手试试**：
  ```bash
  # 在 vllm 仓库根目录
  pytest tests/kernels/test_fused_inv_rope_fp8_quant.py -v -k "dsv41"
  ```
  如果没有 SM100/SM103 显卡，可以看测试代码里 `_FUSED_WO_A_KERNEL` 的调用签名，理解输入输出关系：
  ```python
  q, sf = _FUSED_WO_A_KERNEL(
      x=x, positions=positions, rope=rope, weight=wq, weight_scale=ws
  )
  ```
- **预期结果**：测试通过说明融合 kernel 和"三步分开做"的结果误差 < 3e-3。你会看到融合 kernel 的输出 `q` 和参考实现的 `ref` 数值几乎一致，且 padding 的 scale 行被清零。

### 知识点 2：批不变性（Batch Invariance）

- **是什么**：同一个 prompt，batch size = 1 和 batch size = 32，输出 token 序列完全一样。
- **为什么重要**：很多业务（比如 RLHF 训练、A/B 测试、缓存命中）依赖"输入相同 → 输出相同"。如果 batch 一变结果就变，缓存就废了，用户也会投诉。
- **动手试试**：
  ```bash
  # 开启批不变模式
  VLLM_BATCH_INVARIANT=1 python -m vllm.entrypoints.openai.api_server \
      --model Qwen/Qwen2.5-0.5B-Instruct
  # 然后分别用 batch=1 和 batch=8 发同样的请求，对比输出
  ```
  观察启动日志里有没有 `Disabling sequence parallelism and async TP` 的 warning。
- **预期结果**：日志会打印 `Disabling sequence parallelism and async TP (pass_config.enable_sp / fuse_gemm_comms) when VLLM_BATCH_INVARIANT is enabled`。这说明 vLLM 为了正确性主动牺牲了性能优化。

### 知识点 3：KV Cache 的 condense 与掩码清理

- **是什么**：`InputBatch.condense()` 会把空闲的 slot 挤掉，让请求索引连续。但如果某个请求有 `allowed_token_ids` 白名单，挤走后旧行的掩码没清，下一个用这行的新请求就会"继承"错误的限制。
- **为什么重要**：这类 bug 极其隐蔽——只在特定请求顺序下触发，且表现为"模型莫名其妙只输出某些 token"。不懂 slot 复用机制，你根本查不出来。
- **动手试试**：
  ```bash
  pytest tests/v1/worker/test_gpu_input_batch.py::test_condense_clears_stale_allowed_token_ids_mask -v
  ```
  然后打开 `vllm/v1/worker/gpu_input_batch.py` 的 `condense()`，找到新增的那一行：
  ```python
  self.allowed_token_ids_mask_cpu_tensor[last_req_index].fill_(False)
  ```
- **预期结果**：测试通过，说明 condense 后旧行的掩码被清零，新请求不会被误限制。你可以试着把这行注释掉，测试会失败，亲眼看到 bug 复现。

### 知识点 4：EPLB（Expert Parallel Load Balancer）与弹性扩缩容

- **是什么**：MoE 模型里不同专家被分到不同 GPU 上。EPLB 负责在负载不均时把专家搬来搬去。扩缩容时如果统计信息是旧的，就会搬错。
- **为什么重要**：MoE 模型动辄几百个专家，负载均衡做不好，某些 GPU 会成瓶颈。弹性扩缩容（加机器/减机器）时统计信息必须一致，否则整个集群会抖。
- **动手试试**：
  ```bash
  # 看这个 commit 改的核心逻辑
  grep -n "use_last_expert_load" vllm/distributed/eplb/eplb_state.py
  ```
  你会发现 `last_expert_load` 是一个 `(num_moe_layers, num_logical_experts)` 的 int64 张量，初始化为全 1（表示"假设均匀负载"）。
- **预期结果**：你能理解为什么扩缩容时要传 `use_last_expert_load=True`——因为新 rank 还没有自己的负载统计，只能用上一次 reshuffle 时保存的全局统计。

### 知识点 5：错误信息脱敏（Message Sanitization）

- **是什么**：把异常信息里的内存地址（`0x7a95e299e750`）、文件路径（`/home/user/secret.py`）、traceback 都替换成占位符再返回。
- **为什么重要**：攻击者能从错误信息里推断出你的目录结构、Python 版本、甚至某些库的版本，进而找漏洞。这是 Web 安全的基本功。
- **动手试试**：
  ```python

  print(sanitize_message("<PIL.Image.Image image mode=RGB size=2x2 at 0x7D52EAF07BF0>"))
  # 输出: <PIL.Image.Image image mode=RGB size=2x2>
  print(sanitize_message("File \"/home/user/app.py\", line 42, in foo"))
  # 输出: 空字符串
  ```
- **预期结果**：地址和路径都被擦掉。注意今天这个 commit 把正则从 `[0-9a-f]+` 改成 `[0-9a-fA-F]+`，因为有些地址是大写十六进制——你可以构造一个含大写地址的字符串验证。

## 🧪 重要知识点 & 动手实验

- **知识点 1：KV 缓存页对齐与分片（Commit 1）**
  - **是什么**：KV 缓存按"页"（page）为单位分配，分片时要保证每个分片的边界对齐到页，否则会碎片化。
  - **为什么重要**：不对齐会导致显存浪费和分配失败。理解 `page_size`、`shard_size`、`granule` 的关系，是调试 OOM 问题的基础。
  - **动手试试**：
    ```python
    # 模拟页对齐计算
    page_size = 16
    shard_size = 4
    prefix_len = 100

    # 计算需要多少个页
    prefix_pages = -(-prefix_len // page_size)  # 向上取整
    # 每个分片需要多少页
    pages_per_shard = -(-prefix_pages // shard_size)
    total_pages = shard_size * pages_per_shard * page_size
    print(f"prefix_len={prefix_len}, 对齐后需要 {total_pages} tokens 的空间")
    # 输出: prefix_len=100, 对齐后需要 112 tokens 的空间
    ```
  - **预期结果**：你会看到 100 个 token 实际占用了 112 个 token 的空间。这就是"页对齐"的代价，也是为什么分片要谨慎设计。

- **知识点 2：GPU 内核的 num_warps 调优（Commit 11 & 20）**
  - **是什么**：`num_warps` 是一个 CUDA 内核启动时用的线程束数量。太少会浪费 GPU，太多会争抢资源。不同 GPU 架构最优值不同。
  - **为什么重要**：Commit 11 发现 RTX 4090（低于 Hopper 架构）上 MXFP4 MoE 需要固定 `num_warps`；Commit 20 发现 B200 上 Mamba2 用 8x1 配置比 4x4 快 2 倍。调错参数性能可能差几倍。
  - **动手试试**：
    ```python
    # 用 Triton 写一个简单的向量加法，测试不同 num_warps
    import torch
    import triton
    import triton.language as tl

    @triton.jit
    def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
        pid = tl.program_id(0)
        offs = pid * BLOCK + tl.arange(0, BLOCK)
        mask = offs < n
        x = tl.load(x_ptr + offs, mask=mask)
        y = tl.load(y_ptr + offs, mask=mask)
        tl.store(out_ptr + offs, x + y, mask=mask)

    x = torch.randn(1024*1024, device='cuda')
    y = torch.randn(1024*1024, device='cuda')
    out = torch.empty_like(x)
    for nw in [1, 2, 4, 8, 16]:
        grid = lambda meta: (triton.cdiv(x.numel(), meta['BLOCK']),)
        add_kernel[grid](x, y, out, x.numel(), BLOCK=1024, num_warps=nw)
        # 用 torch.cuda.Event 计时对比
    ```
  - **预期结果**：你会发现不同 `num_warps` 下耗时不同，通常在 4-8 之间有个最优点。这解释了为什么 SGLang 要针对不同架构硬编码参数。

- **知识点 3：LMCache 组件游标（Commit 8）**
  - **是什么**：多组件缓存（SWA 滑动窗口、Mamba 状态、C128）各自有独立的"已驱逐位置"游标，不能混用。
  - **为什么重要**：之前代码用单一的 `swa_evicted_seqlen` 字段，导致不同组件的游标互相污染。修复后引入 `ComponentType` 枚举和 `component_evicted_seqlens` 字典。
  - **动手试试**：
    ```python
    from enum import Enum

    class ComponentType(Enum):
        FULL = 0
        SWA = 1
        MAMBA = 2
        C128 = 3

    # 模拟多组件游标管理
    class ReqKvInfo:
        def __init__(self):
            self.component_evicted_seqlens = {ct: 0 for ct in ComponentType}

        def set_evicted_seqlen(self, ct, val):
            self.component_evicted_seqlens[ct] = val

        def get_evicted_seqlen(self, ct):
            return self.component_evicted_seqlens[ct]

    kv = ReqKvInfo()
    kv.set_evicted_seqlen(ComponentType.SWA, 100)
    kv.set_evicted_seqlen(ComponentType.MAMBA, 50)
    print(kv.component_evicted_seqlens)
    # 输出: {FULL: 0, SWA: 100, MAMBA: 50, C128: 0}
    ```
  - **预期结果**：每个组件独立记录自己的驱逐位置，互不干扰。这就是"组件化"设计的好处。

- **知识点 4：ROCm 与 CUDA 的 API 差异（Commit 6 & 10）**
  - **是什么**：AMD 的 HIP API 与 NVIDIA 的 CUDA API 大多一一对应，但有些细节不同。比如 `cudaDevAttrMaxSharedMemoryPerBlock` 对应 `hipDeviceAttributeMaxSharedMemoryPerBlock`。
  - **为什么重要**：移植代码时经常卡在这些细节上。Commit 10 就是通过 `#define` 宏把 HIP 名字映射成 CUDA 名字，让代码两边都能编译。
  - **动手试试**：
    ```cpp
    // 查看你的 CUDA/HIP 头文件里的属性枚举
    // CUDA: /usr/local/cuda/include/driver_types.h
    // HIP:  /opt/rocm/include/hip/hip_runtime_api.h

    // 用 grep 查找对应的属性
    // grep "cudaDevAttrMaxSharedMemoryPerBlock" /usr/local/cuda/include/*.h
    // grep "hipDeviceAttributeMaxSharedMemoryPerBlock" /opt/rocm/include/hip/*.h
    ```
  - **预期结果**：你会发现两个 API 的名字和数值基本对应，但偶尔有差异（如 `hipDeviceAttributeSharedMemPerBlockOptin` 少了 "Max"）。这就是移植时的坑。

- **知识点 5：滑动窗口注意力（SWA）的驱逐策略（Commit 9）**
  - **是什么**：SWA 只保留最近 N 个 token 的 KV，更早的会被驱逐。驱逐时机和粒度影响性能和正确性。
  - **为什么重要**：Commit 9 把驱逐逻辑从 scheduler 抽到 `tree_cache.evict_sliding_windows()`，支持辅助窗口（auxiliary SWA）。这是为了支持更复杂的缓存结构。
  - **动手试试**：
    ```python
    # 模拟滑动窗口驱逐
    def evict_sliding_window(seq_len, window_size, eviction_interval=1):
        """返回应该保留的 token 范围"""
        if seq_len <= window_size:
            return (0, seq_len)
        # 窗口左边界
        left = seq_len - window_size
        # 按 interval 对齐
        left = (left // eviction_interval) * eviction_interval
        return (left, seq_len)

    print(evict_sliding_window(1000, 512))       # (488, 1000)
    print(evict_sliding_window(1000, 512, 4))    # (488, 1000)
    print(evict_sliding_window(100, 512))        # (0, 100)
    ```
  - **预期结果**：你会看到窗口外的 token 被驱逐，窗口内的保留。`eviction_interval` 控制驱逐的粒度对齐。
