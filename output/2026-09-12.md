## 🧪 重要知识点 & 动手实验

- **知识点 1：用 asyncio 让 prefill 和 decode 并发跑（分离式推理入门）**
  - **是什么**：以前代码是"先等 prefill 全部完成，再开始 decode"，现在改成两个协程同时跑，用 `asyncio.create_task` 起一个后台任务。
  - **为什么重要**：分离式推理的核心价值就是让两台机器并行工作；如果串行等待，等于白拆。不懂 async 就会写出"看起来拆了、实际还是串行"的假分离。
  - **动手试试**：
    ```python
    import asyncio, time

    async def prefill():
        await asyncio.sleep(1)
        print("prefill done")

    async def decode():
        for i in range(3):
            await asyncio.sleep(0.3)
            print(f"decode chunk {i}")

    async def main():
        task = asyncio.create_task(prefill())
        async for _ in decode_gen():
            pass
        await task

    async def decode_gen():
        for i in range(3):
            await asyncio.sleep(0.3)
            yield f"chunk {i}"

    asyncio.run(main())
    ```
  - **预期结果**：你会看到 decode 的 chunk 和 prefill 交错打印，总耗时约 1 秒，而不是 1.9 秒——这就是并发的价值。

- **知识点 2：用 `gpu_sync_allowed()` 上下文管理 GPU 同步（性能调试必备）**
  - **是什么**：`.item()` 会把 GPU 上的数拉回 CPU，强制同步，破坏 CUDA Graph 捕获；`gpu_sync_allowed()` 是一个"允许同步"的开关，只在预热/构建阶段打开。
  - **为什么重要**：在捕获 CUDA Graph 时，任何隐式同步都会导致捕获失败或性能崩塌。这个模式是 vLLM 里非常常见的护栏。
  - **动手试试**：
    ```python
    import torch
    from contextlib import contextmanager

    _allow = False

    @contextmanager
    def gpu_sync_allowed():
        global _allow
        old = _allow
        _allow = True
        try:
            yield
        finally:
            _allow = old

    def safe_item(t):
        if not _allow:
            raise RuntimeError("GPU sync not allowed here!")
        return t.item()

    x = torch.tensor([3.0], device="cuda")
    with gpu_sync_allowed():
        print(safe_item(x))  # OK
    try:
        safe_item(x)
    except RuntimeError as e:
        print("blocked:", e)
    ```
  - **预期结果**：上下文里能拿到值，外面直接报错——这就是"显式声明同步点"的工程实践。

- **知识点 3：Triton kernel 里 `tl.constexpr` 的取舍（冷启动 vs 特化）**
  - **是什么**：`tl.constexpr` 告诉 Triton"这个参数是编译期常量，可以为它生成专用 kernel"；但每个不同取值都会触发一次编译，产生"冷编译抖动"。
  - **为什么重要**：Commit 16 把 `NUM_TOKENS` 等从 constexpr 改成普通参数，就是为了避免每次 shape 变化都重新编译。理解这点能帮你判断"该不该特化"。
  - **动手试试**：
    ```python
    import torch, triton, triton.language as tl

    @triton.jit
    def add_const(x_ptr, y_ptr, N: tl.constexpr):
        i = tl.program_id(0)
        tl.store(y_ptr + i, tl.load(x_ptr + i) + N)

    @triton.jit
    def add_runtime(x_ptr, y_ptr, n):
        i = tl.program_id(0)
        tl.store(y_ptr + i, tl.load(x_ptr + i) + n)

    x = torch.arange(8, device="cuda", dtype=torch.float32)
    y = torch.empty_like(x)
    add_const[(8,)](x, y, 10)   # 编译一次
    add_const[(8,)](x, y, 20)   # 又编译一次！
    add_runtime[(8,)](x, y, 10) # 只编译一次，n 可复用
    ```
  - **预期结果**：用 `add_const` 换 N 会重复编译（慢），`add_runtime` 不会——这就是"冷编译抖动"的来源。

- **知识点 4：非连续张量（non-contiguous）导致的 kernel 崩溃**
  - **是什么**：张量在内存里的排列可能"跳着走"（比如转置后），CUDA kernel 如果假设它是连续的就会读错地址甚至崩溃。
  - **为什么重要**：Commit 10 就是给 `state_indices` 加 `.contiguous()` 修 ROCm 崩溃。这是新手最容易踩的坑之一。
  - **动手试试**：
    ```python
    import torch
    a = torch.arange(6).reshape(2, 3)
    b = a.t()  # 转置，非连续
    print("b.is_contiguous():", b.is_contiguous())
    print("b.stride():", b.stride())
    c = b.contiguous()
    print("c.is_contiguous():", c.is_contiguous())
    ```
  - **预期结果**：`b` 非连续、stride 是 `(1, 3)`；`c` 连续、stride 是 `(3, 1)`——传给 kernel 前先 `.contiguous()` 是安全习惯。

- **知识点 5：KV 缓存磁盘对齐与 O_DIRECT**
  - **是什么**：`O_DIRECT` 是绕过操作系统页缓存、直接读写磁盘的模式，要求地址和长度按块大小（通常 4096）对齐；普通带缓存 I/O 没这个要求。
  - **为什么重要**：Commit 18 修的就是"混合模型 block 大小是 512 对齐但不是 4096 对齐，导致磁盘卸载无法启动"。理解对齐能帮你排查 I/O 报错。
  - **动手试试**：
    ```python
    import os
    BLOCK = 4096
    size = 3 * 512  # 1536 字节
    print("对齐 4096?", size % BLOCK == 0)  # False
    print("对齐 512? ", size % 512 == 0)    # True
    # O_DIRECT 会拒绝 1536 字节的读；buffered I/O 可以
    ```
  - **预期结果**：看到 1536 只满足 512 对齐、不满足 4096 对齐——这正是 Commit 18 里"应该只在 O_DIRECT 下断言"的原因。

## 🧪 重要知识点 & 动手实验

### 知识点 1：稀疏注意力的 gather 越界（Commit 1 & 16）

- **是什么**：稀疏注意力会把"选中的 KV 行"从显存池里 gather（收集）出来。如果索引算错了一格，就会读到别的请求的数据，或者直接越界崩溃。
- **为什么重要**：这类 bug 不会稳定复现，只在特定 batch 形状、特定序列长度下炸，线上表现为"偶发输出乱码"或"CUDA illegal memory access"。不懂的人会以为是模型问题。
- **动手试试**：
  ```python
  import torch
  # 模拟一个 KV 池：10 行，每行 4 维
  pool = torch.arange(40).reshape(10, 4)
  # 假设选中的行索引是 [3, 7, 12]（12 越界了！）
  idx = torch.tensor([3, 7, 12])
  # 错误做法：直接 gather
  try:
      print(pool[idx])
  except IndexError as e:
      print("越界:", e)
  # 正确做法：clamp 到有效范围（Commit 1 的做法）
  idx_clamped = idx.clamp_max(pool.shape[0] - 1)
  print("clamp 后:", pool[idx_clamped])
  ```
- **预期结果**：直接索引会报错或读到垃圾数据；clamp 之后索引变成 `[3, 7, 9]`，全部合法。你会明白"防御性 clamp"为什么在 kernel 里是标配。

### 知识点 2：量化权重的设备一致性（Commit 4）

- **是什么**：`torch.zeros(...)` 不指定 `device` 时默认在 CPU 上分配，如果后面要把它和 GPU 上的张量做运算，就会触发隐式的 CPU↔GPU 拷贝，甚至报错。
- **为什么重要**：在线权重量化（比如 LoRA 热更新、动态量化）不一定在 CUDA 上下文里跑，此时 `torch.zeros` 就会落到 CPU，导致后续 kernel 失败。
- **动手试试**：
  ```python
  import torch
  if torch.cuda.is_available():
      scale = torch.ones(4, 4, device="cuda")
      # 错误写法（Commit 4 修复前）
      bad = torch.zeros(4, 4, dtype=scale.dtype)
      print("bad device:", bad.device)  # cpu
      try:
          bad += scale  # 会报错或隐式拷贝
      except RuntimeError as e:
          print("报错:", e)
      # 正确写法
      good = torch.zeros(4, 4, dtype=scale.dtype, device=scale.device)
      print("good device:", good.device)  # cuda:0
      good += scale
      print("OK")
  ```
- **预期结果**：你会亲眼看到 `device` 不匹配时 PyTorch 的报错，从此养成"分配张量必带 device"的习惯。

### 知识点 3：会话空闲超时与请求被拒（Commit 13）

- **是什么**：会话（session）有一个"最后活跃时间"，超过阈值就被回收。如果请求被拒（比如超过最大长度）时也更新了这个时间，会话就会永远不超时，泄漏资源。
- **为什么重要**：这是典型的"状态机边界"问题：什么时候该更新状态，什么时候不该。在长连接服务里，一个漏掉的清理逻辑能拖垮整个服务。
- **动手试试**：
  ```python
  import time

  class Session:
      def __init__(self, timeout=2.0):
          self.last_active = time.monotonic()
          self.timeout = timeout

      def handle(self, ok: bool):
          if ok:
              self.last_active = time.monotonic()  # 只有成功才刷新
              return "accepted"
          return "rejected"  # 被拒时不刷新

      def expired(self):
          return time.monotonic() - self.last_active > self.timeout

  s = Session(timeout=1.0)
  print(s.handle(ok=False))  # rejected
  time.sleep(1.2)
  print("过期了吗:", s.expired())  # True，因为被拒不刷新
  ```
- **预期结果**：被拒的请求不会延长会话寿命，资源能正常回收。反过来如果把 `last_active` 更新放在函数开头，`expired()` 永远是 False。

### 知识点 4：NCCL Graph 注册导致死锁（Commit 18）

- **是什么**：NCCL 会把 CUDA Graph 里捕获的通信缓冲区"注册"起来，让对端直接 DMA 读写。但如果这些缓冲区是图内存池的临时地址（会被复用），注册就会失效，导致一个 rank 卡在 `ncclDevKernel_SendRecv` 里等死。
- **为什么重要**：这是分布式推理最阴间的一类 bug——只在"请求突发、各 DP rank 步调不一致"时出现，日志里什么都看不到，就是整个集群 hang 住。
- **动手试试**：
  ```bash
  # 复现思路（需要多卡环境）：
  # 1. 开启 NCCL_GRAPH_REGISTER=1（默认）
  # 2. 用 tp=4 dp=4 起服务，开 CUDA Graph
  # 3. 用脚本瞬间打 100 个并发请求，让各 rank 步调错开
  # 观察：部分 rank 卡住，nvidia-smi 显示 GPU 利用率 100% 但无输出
  # 修复：设置 NCCL_GRAPH_REGISTER=0 后重跑，hang 消失
  export NCCL_GRAPH_REGISTER=0
  ```
- **预期结果**：开启注册时集群在突发流量下死锁，关闭后恢复正常。你会理解"环境变量有时比代码更关键"。

### 知识点 5：DFlash Mamba 状态在 checkpoint 边界对齐（Commit 11）

- **是什么**：Mamba 类模型的状态是"滚动累积"的，投机解码验证时，如果按验证前的序列长度去判断"是否到了 checkpoint 边界"，就会算错，导致状态提交到错误的槽位。
- **为什么重要**：Mamba/线性注意力的状态管理比 Transformer 的 KV 复杂得多，一个 off-by-one 会让后续所有解码全部错乱。
- **动手试试**：
  ```python
  # 模拟：checkpoint 间隔为 8，验证前长度 7，验证接受了 3 个 token
  interval = 8
  seq_pre = 7
  commit = 3
  seq_post = seq_pre + commit  # 10

  # 错误做法：用 seq_pre 判断边界
  wrong_track = (seq_pre // interval) != (seq_pre // interval)
  print("错误判断是否跨边界:", wrong_track)  # False

  # 正确做法：用 seq_post 判断
  right_track = (seq_pre // interval) != (seq_post // interval)
  print("正确判断是否跨边界:", right_track)  # True（7//8=0, 10//8=1）
  ```
- **预期结果**：用验证后的长度判断，才能正确识别"这一步跨过了 checkpoint 边界"，状态才会被正确保存。你会明白"状态机里用哪个时刻的值"是门学问。
