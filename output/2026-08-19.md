## 🧪 重要知识点 & 动手实验

### 知识点 1：KV Cache 哈希的确定性
- **是什么**：vLLM 用哈希算法为 KV Cache 块生成内容哈希，用于跨进程复用缓存。以前默认用随机种子，现在改为固定默认种子，保证不同进程对相同内容生成相同哈希。
- **为什么重要**：如果你在多机部署 vLLM 并共享 KV Cache（比如通过共享文件系统或对象存储），以前必须手动设置 `PYTHONHASHSEED` 才能让哈希一致，否则缓存无法命中。现在默认就一致了。
- **动手试试**：
```bash
# 启动两个 vLLM 实例，共享同一个 KV Cache 目录
# 以前必须这样：
PYTHONHASHSEED=0 vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --kv-offload-dir /shared/kv_cache --kv-offload-tier filesystem

# 现在直接这样就行：
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --kv-offload-dir /shared/kv_cache --kv-offload-tier filesystem
```
- **预期结果**：两个实例对相同 prompt 生成相同的缓存文件名，第二个实例能直接命中第一个实例的缓存，响应速度显著提升。

### 知识点 2：XGrammar 结构化输出的终止处理
- **是什么**：XGrammar 是 vLLM 用于结构化输出（如 JSON schema 约束）的语法引擎。修复后，当语法匹配到终止 token（如 EOS）后，后续 token 会被忽略而不是报错。
- **为什么重要**：在强化学习或推理场景中，模型可能生成 EOS 后又生成额外 token。以前这会导致语法引擎报错或状态错乱，现在能优雅处理。
- **动手试试**：
```python

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct")
params = SamplingParams(
    max_tokens=100,
    guided_json='{"type": "object", "properties": {"name": {"type": "string"}}}'
)
# 强制模型在 JSON 完成后继续生成（模拟异常情况）
output = llm.generate("Give me a name", params)
print(output[0].outputs[0].text)
```
- **预期结果**：输出仍然是合法的 JSON，即使模型在 JSON 结束后又生成了额外内容，也不会导致崩溃或错误。

### 知识点 4：前缀缓存哈希算法的选择
- **是什么**：vLLM 支持多种哈希算法（`sha256`、`xxhash` 等）用于前缀缓存。`xxhash` 性能更好但种子是随机的，`sha256` 是确定性的但更慢。
- **为什么重要**：如果你需要跨进程共享 KV Cache，使用 `xxhash` 时必须手动设置 `PYTHONHASHSEED`；使用 `sha256`（默认）则不需要。选错会导致缓存无法命中。
- **动手试试**：
```bash
# 查看当前使用的哈希算法
vllm serve meta-llama/Llama-3.1-8B-Instruct --prefix-caching-hash-algo sha256

# 如果要用 xxhash 并跨进程共享缓存，必须设置种子
PYTHONHASHSEED=42 vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --prefix-caching-hash-algo xxhash --kv-offload-dir /shared/kv_cache
```
- **预期结果**：使用 `sha256` 时无需设置种子即可跨进程共享缓存；使用 `xxhash` 时设置相同种子才能命中。

## 🧪 重要知识点 & 动手实验

### 知识点 1：页面大小（Page Size）与内存对齐
- **是什么**：KV Cache 按固定大小（如 256 tokens）分页管理，分配内存时如果请求的长度不是页面的整数倍，最后一页就会浪费。
- **为什么重要**：Commit 17、19、20 都在修复“未对齐分配导致显存泄漏”的 bug。不懂这个，你在做推理引擎开发时可能会遇到“显存越用越多”的诡异问题。
- **动手试试**：
  ```python
  page_size = 256
  committed_len = 100  # 已提交的 token 数
  reserve = 64  # 需要预留的 token 数
  
  # 错误的做法：直接相加
  wrong = committed_len + reserve  # 164，不是页面的整数倍
  
  # 正确的做法：向上取整到页面大小
  right = (committed_len + reserve + page_size - 1) // page_size * page_size  # 512
  print(f"错误分配: {wrong}, 正确分配: {right}")
  ```
- **预期结果**：你会看到错误分配是 164，而正确分配是 512。这说明如果你不按页面对齐，系统会少分配内存，导致后续越界或泄漏。

### 知识点 2：投机解码（Speculative Decoding）
- **是什么**：用小模型（draft model）快速生成多个候选 token，再用大模型（target model）一次性验证。如果小模型猜对了，大模型一次前向就能确认多个 token，速度翻倍。
- **为什么重要**：Commit 12 和 19 都在优化 DFlash 投机解码的效率和内存分配。这是当前最热门的推理加速技术之一。
- **动手试试**：
  ```python
  # 用 transformers 的辅助生成（assisted decoding）感受投机解码
  from transformers import AutoModelForCausalLM, AutoTokenizer, AssistedGenerationMixin
  
  tokenizer = AutoTokenizer.from_pretrained("gpt2")
  draft_model = AutoModelForCausalLM.from_pretrained("gpt2")  # 小模型
  target_model = AutoModelForCausalLM.from_pretrained("gpt2-xl")  # 大模型
  
  inputs = tokenizer("The capital of France is", return_tensors="pt")
  outputs = target_model.generate(
      **inputs,
      assistant_model=draft_model,  # 指定辅助模型
      max_new_tokens=20,
  )
  print(tokenizer.decode(outputs[0]))
  ```
- **预期结果**：你会看到生成速度快于只用大模型，且输出质量几乎相同。这让你直观感受到“先猜后验”的威力。

### 知识点 3：CUDA Graph 内存池复用
- **是什么**：CUDA Graph 会把一系列 GPU 内核调用“录制”成一个图，然后反复重放。它的内存池是图执行时的专用显存区域。
- **为什么重要**：Commit 15 让 EAGLE 采样借用 CUDA Graph 的内存池，避免单独分配显存。这是显存优化的高级技巧。
- **动手试试**：
  ```python
  import torch
  
  # 创建一个 CUDA Graph
  g = torch.cuda.CUDAGraph()
  static_x = torch.zeros((1024, 1024), device="cuda")
  static_y = torch.zeros((1024, 1024), device="cuda")
  
  # 录制
  with torch.cuda.graph(g):
      static_y = static_x * 2
  
  # 重放（无需重新调度内核）
  static_x.fill_(1.0)
  g.replay()
  print(static_y[0, 0])  # 输出 2.0
  ```
- **预期结果**：你会看到重放后 `static_y` 的值是 2.0。这说明 CUDA Graph 的“录制-重放”模式确实能复用内存并减少调度开销。

### 知识点 4：量化（Quantization）与硬件能力检查
- **是什么**：把模型权重从 FP16 压缩到 FP4/INT8，大幅减少显存占用和计算量。但低精度计算需要特定硬件支持（如 Blackwell 支持 FP4）。
- **为什么重要**：Commit 7 和 8 强调了量化前必须检查硬件能力，否则会在运行时报出难以理解的 CUDA 错误。
- **动手试试**：
  ```python

  import torch
  
  capability = torch.cuda.get_device_capability()
  print(f"GPU Compute Capability: {capability[0]}.{capability[1]}")
  
  # Blackwell (SM100) 支持 FP4，Ampere (SM80) 不支持
  if capability[0] >= 10:
      print("你的 GPU 支持 NVFP4 量化！")
  else:
      print("你的 GPU 不支持 NVFP4，请使用 FP8 或 BF16。")
  ```
- **预期结果**：你会看到你的 GPU 计算能力版本，从而判断是否支持 FP4 量化。这让你在部署量化模型前就能避免踩坑。

### 知识点 5：Docker 虚拟环境隔离
- **是什么**：在 Docker 镜像中创建 Python 虚拟环境（venv），而不是直接安装到系统路径，避免包冲突。
- **为什么重要**：Commit 13 将 SGLang 从系统路径迁移到 `/opt/sglang` 虚拟环境，这是工程化的最佳实践。
- **动手试试**：

  ```bash
      python -m venv /opt/myenv
      source /opt/myenv/bin/activate
      pip install numpy
      python -c 'import numpy; print(numpy.__version__)'
      # 退出虚拟环境后 numpy 不再可用
      deactivate
      python -c 'import numpy' 2>&1 | head -1
  "
  ```
- **预期结果**：你会看到在虚拟环境中可以正常导入 numpy，退出后导入失败。这展示了虚拟环境如何隔离依赖。
