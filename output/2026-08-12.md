## 🧪 重要知识点 & 动手实验

### 知识点 1：constexpr 优化（来自 Commit 3）

- **是什么**：`constexpr` 是 C++/Triton 中的编译期常量，告诉编译器"这个值在编译时就确定了"，从而让编译器生成更优化的代码。
- **为什么重要**：在 GPU kernel 中，把常量标记为 `constexpr` 可以让编译器在编译时就展开计算，避免运行时判断，显著提升性能。不懂这个，写 kernel 时可能无意间降低性能。
- **动手试试**：
  ```python
  # 在一个 Triton kernel 中，尝试以下两种写法对比性能
  import triton
  import triton.language as tl

  # 写法 A：不用 constexpr
  @triton.jit
  def kernel_a(x, y, min_val, max_val, BLOCK: tl.constexpr):
      val = tl.load(x)
      val = tl.clamp(val, min_val, max_val)  # 运行时比较
      tl.store(y, val)

  # 写法 B：用 constexpr
  @triton.jit
  def kernel_b(x, y, min_val: tl.constexpr, max_val: tl.constexpr, BLOCK: tl.constexpr):
      val = tl.load(x)
      val = tl.clamp(val, min_val, max_val)  # 编译期确定
      tl.store(y, val)
  ```
- **预期结果**：用 `triton.testing.do_bench` 比较两个 kernel 的执行时间，你会看到写法 B 更快。掌握后，写 kernel 时应尽量把不会改变的值标记为 `constexpr`。

### 知识点 2：GPU↔CPU 同步（来自 Commit 6）

- **是什么**：GPU 和 CPU 之间的数据同步需要"同步点"，这会阻塞执行流水线，是性能杀手。
- **为什么重要**：每次同步都意味着 GPU 要停下来等 CPU，或者 CPU 要停下来等 GPU。在推理路径上，一次不必要的同步可能让延迟增加数倍。
- **动手试试**：
  ```python
  import torch
  import time

  # 场景：把 numpy 数组转到 GPU
  device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
  
  # 不好的做法：多次小批量拷贝
  start = time.time()
  for i in range(100):
      x = torch.tensor([i], device=device)  # 每次都是同步操作
  print(f"多次小批量: {time.time() - start:.4f}s")

  # 好的做法：一次大批量拷贝
  start = time.time()
  data = torch.arange(100, device=device)  # 一次完成
  print(f"一次大批量: {time.time() - start:.4f}s")
  ```
- **预期结果**：你会看到"一次大批量"远快于"多次小批量"。理解这个原理后，在写推理代码时应该尽量减少 GPU↔CPU 的往返次数。

### 知识点 3：KV Cache 布局与混合模型（来自 Commit 16、18）

- **是什么**：KV Cache 是推理时缓存历史 token 的 key/value 张量，不同模型（如混合了 attention 和 Mamba 的模型）需要不同的缓存布局。
- **为什么重要**：KV Cache 是推理时显存占用的大头，布局不合理会导致显存浪费或 kernel 无法执行。
- **动手试试**：
  ```python
  # 查看模型各层的 KV cache 规格
  from vllm.v1.kv_cache_interface import FullAttentionSpec, MambaSpec
  
  # Attention 层的 cache 规格
  attn_spec = FullAttentionSpec(
      block_size=16,
      num_kv_heads=8,
      head_size=128,
      dtype=torch.float32,
  )
  print(f"Attention cache 每页大小: {attn_spec.page_size_bytes} bytes")
  
  # Mamba 层的 cache 规格
  mamba_spec = MambaSpec(
      block_size=16,
      shapes=((64,),),
      dtypes=(torch.float32,),
  )
  print(f"Mamba cache 每页大小: {mamba_spec.page_size_bytes} bytes")
  ```
- **预期结果**：你会看到不同层类型有不同的 page_size_bytes。理解 KV Cache 布局是优化推理显存使用的基础。

### 知识点 4：MoE 权重加载与转置（来自 Commit 20）

- **是什么**：MoE 模型的权重（如 Qwen3-VL）可能以转置形式存储，加载时需要正确还原方向。
- **为什么重要**：权重方向错误会导致推理结果完全错误，而且是"静默错误"——不报错但输出垃圾。
- **动手试试**：
  ```python
  import torch
  
  # 模拟一个 MoE 权重，形状为 [experts, hidden, intermediate]
  weight = torch.randn(8, 1024, 2048)
  
  # 检查权重方向
  def orient_weight(w, is_transposed):
      if is_transposed:
          return w.transpose(-1, -2)
      return w
  
  # 正确的方向
  w_correct = orient_weight(weight, False)
  print(f"正确方向 shape: {w_correct.shape}")
  
  # 错误的转置
  w_wrong = orient_weight(weight, True)
  print(f"错误转置 shape: {w_wrong.shape}")
  ```
- **预期结果**：你会看到转置前后 shape 的变化。理解权重方向问题后，在加载自定义模型权重时就能避免踩坑。

## 🧪 重要知识点 & 动手实验

### 知识点 1：CPU Offload（CPU 卸载）—— 显存不够时的救命稻草

- **是什么**：当 GPU 显存不足以容纳整个模型时，把暂时用不到的模型组件（比如文本编码器、部分 DiT 层）从 GPU 显存搬到 CPU 内存，等需要时再搬回来。
- **为什么重要**：这是在没有更多 GPU 的情况下运行大模型的唯一方法。不懂这个，你可能会因为 OOM（显存溢出）而无法运行任何稍大的模型。今天的 commit #34391 引入了统一的 `--cpu-offload-components` 参数，简化了这一过程。
- **动手试试**：如果你有一张 8GB 显存的 GPU，尝试运行一个约 5GB 的文生图模型（如 `Wan-AI/Wan2.1-T2V-1.3B-Diffusers`），先不带 offload 参数，观察 OOM；然后加上 `--cpu-offload-components dit text_encoder`，观察能否成功运行。
  ```bash
  # 先尝试不带 offload（预期 OOM 或极慢）
  sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers --num-gpus 1
  
  # 再尝试带 offload
  sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers --num-gpus 1 --cpu-offload-components dit text_encoder
  ```
- **预期结果**：第一个命令可能报 `CUDA out of memory`；第二个命令能成功启动，但推理速度会明显变慢（因为需要从 CPU 搬运数据）。你看到了"用时间换空间"的效果，就掌握了这个知识点。

### 知识点 2：Bit-exact 验证 —— 优化不等于可以乱改结果

- **是什么**：在替换一个算子（比如把两个独立的 PyTorch 操作融合成一个 Triton 内核）时，必须验证新算子的输出和旧算子在二进制层面上完全一致（`torch.equal` 返回 `True`）。
- **为什么重要**：今天的 commit #34412 专门为 bit-exact 失败增加了诊断信息。如果不做这个验证，你优化的模型生成结果可能和原始模型有细微但不可接受的差异，这在金融、医疗等对准确性要求极高的场景是灾难性的。
- **动手试试**：用 `torch.equal` 对比 PyTorch 原生 `F.silu(a) * b` 和今天 commit #34314 里实现的自定义 Triton 内核 `fused_silu_mul_bitexact` 的输出。
  ```python
  import torch
  from sglang.kernels.ops.diffusion.triton.silu_mul_bitexact import fused_silu_mul_bitexact
  
  torch.manual_seed(42)
  a = torch.randn(1024, dtype=torch.bfloat16, device='cuda')
  b = torch.randn(1024, dtype=torch.bfloat16, device='cuda')
  
  # 原始 eager 计算
  ref = torch.nn.functional.silu(a) * b
  
  # 自定义 Triton 内核
  out = fused_silu_mul_bitexact(a, b)
  
  # 验证 bit-exact
  print(f"Bit-exact: {torch.equal(ref, out)}")  # 应该打印 True
  ```
- **预期结果**：打印 `Bit-exact: True`。你看到 `True` 就说明你理解了"优化后的代码必须和原代码在数值上完全一致"这一概念。

### 知识点 3：SM120 架构感知的 Kernel 调优 —— 不同 GPU 需要不同的启动配置

- **是什么**：GPU 的微架构（如 NVIDIA 的 Hopper SM90 vs. Blackwell SM120）会影响内核的最佳启动参数（如 `num_warps`、每块处理的行数 `rows`）。今天的 commit #34349 专门为 RTX 5090（SM120）调整了 QK LayerNorm 的配置。
- **为什么重要**：一个在内核上精心调优的启动配置，换到另一个架构上可能性能反而下降。这就是为什么推理框架需要"架构感知"的代码路径。
- **动手试试**：如果你有 RTX 5090（SM120），对比不同 `rows` 参数下 `fused_qk_head_layernorm` 的性能；如果没有，可以在 H100 上运行，观察默认配置（`rows=64, num_warps=2`）的表现。
  ```python
  import torch
  from sglang.kernels.ops.diffusion.triton.layernorm_modulate import fused_qk_head_layernorm
  
  # 模拟一个典型的 QK 头
  q = torch.randn(1, 4360, 32, 128, dtype=torch.bfloat16, device='cuda')
  k = torch.randn(1, 4360, 32, 128, dtype=torch.bfloat16, device='cuda')
  w = torch.randn(128, dtype=torch.bfloat16, device='cuda')
  b = torch.randn(128, dtype=torch.bfloat16, device='cuda')
  
  # 用默认配置运行
  q_out, k_out = fused_qk_head_layernorm(q, k, w, b)
  print(f"Output shape: {q_out.shape}")  # 和输入相同
  ```
- **预期结果**：内核正常执行并返回相同形状的输出。你看到了"同样的操作，不同架构可能需要不同参数"这一概念，可以尝试修改 `rows` 参数（需要直接改源码）观察性能差异。

### 知识点 4：MoE 专家权重行步长填充（L3 Cache Aliasing）—— 硬件层面的性能陷阱

- **是什么**：在 Intel XPU（如 BMG）上，当 MoE 专家权重的行大小（字节数）恰好落在 L3 缓存的某个别名模式上时，会导致缓存抖动（thrashing），性能骤降。解决办法是给行步长加一些填充字节，打破这种别名。
- **为什么重要**：这是一个非常典型的"硬件特性影响软件性能"的例子。如果你不了解目标硬件的缓存结构，你写的代码可能在某个特定形状上莫名慢 30% 以上。
- **动手试试**：运行以下 Python 代码，模拟 `xpu_moe_ld_padding_elems` 函数对不同 K 维度的判断。
  ```python
  # 直接调用今天 commit #33905 中新增的函数
  from sglang.srt.layers.moe.utils import xpu_moe_ld_padding_elems
  
  # bf16 类型，每个元素 2 字节
  itemsize = 2
  
  for k_dim in [1024, 2048, 3072, 4096, 7168]:
      padding = xpu_moe_ld_padding_elems(k_dim, itemsize)
      print(f"K={k_dim}: padding={padding} elements ({padding * itemsize} bytes)")
  ```
- **预期结果**：你会看到 `K=3072` 和 `K=7168` 返回非零 padding（如 32 个元素），而 `K=1024`、`K=2048`、`K=4096` 返回 0。你理解了"某些特定形状会触发硬件缓存问题，需要特殊处理"这一概念。

### 知识点 5：PD 分离（Prefill-Decode Disaggregation）—— 大模型服务的架构演进

- **是什么**：将处理用户请求的"预填充"阶段（处理完整 prompt）和"解码"阶段（逐 token 生成回复）分离到不同的 GPU 集群上，各自独立扩缩容。
- **为什么重要**：预填充是计算密集型（大量矩阵乘法），解码是访存密集型（逐个 token 读取权重）。两者混在一起会导致 GPU 利用率不均。今天的 commit #34450 调整了 PD 分离场景下 ZMQ 通信的 socket 上限，说明这个架构正在大规模部署中。
- **动手试试**：阅读 SGLang 文档中关于 PD 分离的配置，尝试启动一个简单的 prefill 和一个 decode 实例。
  ```bash
  # 启动 prefill 实例（假设 master 地址为 127.0.0.1:30000）
  sglang serve --model-path meta-llama/Llama-3.2-1B-Instruct --port 30000 --role prefill
  
  # 启动 decode 实例
  sglang serve --model-path meta-llama/Llama-3.2-1B-Instruct --port 30001 --role decode --pd-master-url http://127.0.0.1:30000
  ```
- **预期结果**：两个实例都成功启动，decode 实例会连接到 prefill 实例。当你通过 API 发送请求时，日志会显示 token 在两者之间传输。你理解了"将服务拆分成不同角色以优化资源利用"这一架构模式。
