## 🧪 重要知识点 & 动手实验

- **知识点 1：结构化输出与 JSON Schema 约束**
  - **是什么**：通过语法（grammar）约束解码，让模型只能生成符合 Schema 的 token 序列。
  - **为什么重要**：Agent 调工具时，如果模型吐出非法 JSON，整个链路就崩了。不懂这个会踩"模型偶尔不按格式输出"的坑。
  - **动手试试**：
    ```bash
    pip install vllm
    vllm serve Qwen/Qwen2.5-1.5B-Instruct --guided-decoding-backend xgrammar
    ```
    然后用 curl 发一个带 `response_format` 的请求：
    ```bash
    curl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
      "model": "Qwen/Qwen2.5-1.5B-Instruct",
      "messages": [{"role": "user", "content": "给我一个人的信息"}],
      "response_format": {"type": "json_object", "schema": {
        "type": "object",
        "properties": {"name": {"type": "string"}, "age": {"type": "integer"}},
        "required": ["name", "age"]
      }}
    }'
    ```
  - **预期结果**：你会看到输出永远是合法 JSON，字段类型也对。如果 Schema 里加了 `pattern` 和 `maxLength` 组合，今天 commit 1 告诉你 xgrammar 会拒绝这种组合（静默丢弃长度约束是 bug），这就是"边界条件对齐"的价值。

- **知识点 2：FP8 量化的数值对齐**
  - **是什么**：FP8 是 8 位浮点，能表示的范围比 BF16 小很多，量化时要用一个"缩放因子"把数值压进 FP8 范围。
  - **为什么重要**：如果你自己写量化 kernel，用了错误的 max 值（比如用 `torch.finfo(dtype).max` 而不是框架统一的 `get_fp8_min_max()`），会出现数值溢出或精度损失，模型输出会变垃圾。
  - **动手试试**：
    ```python
    import torch
    from vllm.model_executor.layers.quantization.utils.quant_utils import get_fp8_min_max
    print(get_fp8_min_max())  # 看框架统一用的 FP8 范围
    print(torch.finfo(torch.float8_e4m3fn).max)  # 对比 torch 默认值
    ```
  - **预期结果**：两个值可能不同。今天 commit 8 就是把 ROCm 上的 Kimi-K3 从"用 torch 默认 max"改成"用 vLLM 统一 max"，避免跨后端数值不一致。

- **知识点 3：异步拷贝与缓冲区别名陷阱**
  - **是什么**：`tensor.to("cpu", non_blocking=True)` 是异步拷贝，返回的 numpy 数组可能还指向原 GPU 缓冲区。
  - **为什么重要**：如果这个缓冲区会被复用（比如下一步推理又写进去），你拿到的"快照"就变成脏数据了。这是异步编程最经典的坑。
  - **动手试试**：
    ```python
    import torch, numpy as np
    buf = torch.zeros(4, dtype=torch.int64)
    snap = buf.to("cpu", non_blocking=True).numpy()  # 没有 copy=True
    buf.fill_(1)
    print(snap)  # 可能会变成 [1,1,1,1] 而不是 [0,0,0,0]
    ```
  - **预期结果**：如果你在 CPU 上跑，可能看不出问题；在 GPU 上跑，`snap` 会跟着 `buf` 变。今天 commit 18 就是加 `copy=True` 修复这个 bug。测试代码在 `tests/v1/worker/test_gpu_model_runner_v2.py::test_async_copy_to_np_does_not_alias_reused_buffer`。

- **知识点 4：多模态输入按模态排序以提升吞吐**
  - **是什么**：一次请求里可能有图片、视频、音频，把它们按模态分组编码，能减少 kernel 切换和 padding 浪费。
  - **为什么重要**：不排序的话，编码器要在不同模态间反复横跳，GPU 利用率低。这是多模态推理的性能关键。
  - **动手试试**：
    ```python
    # 模拟：输入顺序是 [video, image, video, image]
    mm_kwargs = [("video", 0), ("image", 1), ("video", 2), ("image", 3)]
    # 排序后：[image, image, video, video]
    sorted_items = sorted(mm_kwargs, key=lambda x: x[0])
    print(sorted_items)
    ```
  - **预期结果**：看到同模态聚在一起。今天 commit 16 在 `encoder_runner.py` 里做了这件事，并且保证输出顺序还原成输入顺序（用 index 映射）。

- **知识点 5：LoRA 适配器的格式校验**
  - **是什么**：LoRA 是在大模型上挂小矩阵做微调。MoE 模型有"2D 每专家"和"3D 融合"两种权重布局，搞混了就加载错。
  - **为什么重要**：以前 vLLM 信任用户声明的 `is_3d_lora_weight`，声明错了不报错但输出垃圾。今天 commit 19 加了加载前校验，直接抛 `ValueError`。
  - **动手试试**：
    ```python

    # 关键：manager._enable_mixed_moe_lora_format = False
    #       adapter.is_3d_lora_weight = False
    #       module 是 FusedMoEWithLoRA（2D wrapper）
    # 期望：抛 ValueError，消息里包含 "enable_mixed_moe_lora_format=True"
    ```
  - **预期结果**：你会看到错误消息明确告诉你需要打开哪个开关、设置哪个字段，而不是静默产生错误输出。

## 🧪 重要知识点 & 动手实验

### 知识点 1：CUDA Stream 隔离与工作区缓存（对应 Commit 5）

- **是什么**：GPU 上可以同时跑多个"任务流"（stream），每个流里的操作按顺序执行，但不同流之间可以并行。如果你把所有流共用一块临时缓冲区，就会发生"你写我读"的数据竞争。
- **为什么重要**：FlashAttention 4 的 sheared-bias 需要一块很大的临时显存。原来代码按"设备"缓存这块内存，假设同一设备上的调用是串行的。但在多流场景下，两个流可能同时用同一块 buffer，结果就是数值错误——而且是那种"偶发、难复现"的 bug，最让人头疼。
- **动手试试**：
```python
import torch

# 创建两个 stream
s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

# 模拟竞争：两个流同时写同一块 buffer
buf = torch.zeros(1024, device="cuda")

def worker(stream, value):
    with torch.cuda.stream(stream):
        for _ in range(1000):
            buf.fill_(value)
            torch.cuda.synchronize()

# 如果 buf 是共享的，结果会不确定
# 正确做法：每个 stream 一个 buf
bufs = {s1: torch.zeros(1024, device="cuda"),
        s2: torch.zeros(1024, device="cuda")}
print("每个 stream 独立 buffer，避免竞争")
```
- **预期结果**：你会理解为什么 Commit 5 要把 `_shear_bias_workspace` 的 key 从 `device` 改成 `(device_index, stream_ptr)`。

### 知识点 2：int32 溢出——大张量下的隐形杀手（对应 Commit 17）

- **是什么**：int32 最大只能表示约 21 亿。当张量元素数超过这个值，用 int32 计算偏移量就会"绕回"负数，导致读写错位。
- **为什么重要**：扩散模型的 QKV 张量动辄几十 GB。Commit 17 的测试里，`rows=119024, heads=56, head_size=128`，总元素数就超过了 2^31。如果不处理，kernel 会读到错误的内存地址，产生垃圾输出甚至崩溃。
- **动手试试**：
```python
import numpy as np

# 模拟 int32 溢出
max_i32 = 2**31 - 1
print(f"int32 最大值: {max_i32}")

# 一个超过 2^31 的偏移
offset = 2**31 + 100
print(f"原始偏移: {offset}")
print(f"转成 int32: {np.int32(offset)}")  # 变成负数！

# 验证：大张量的元素数
rows, heads, head_size = 119024, 56, 128
total = rows * heads * head_size
print(f"总元素数: {total}, 是否超过 int32: {total > max_i32}")
```
- **预期结果**：你会看到 `np.int32(2**31+100)` 输出一个负数，明白为什么 kernel 里要用 `tl.int64`。

### 知识点 3：base64 解码的性能陷阱（对应 Commit 15）

- **是什么**：base64 是把二进制数据编码成文本的格式。Python 里逐字符解码 14.5MB 的 base64 数据，要花 3.5 秒——这在 HTTP 请求路径上是灾难。
- **为什么重要**：很多人以为"Python 慢"是玄学，其实慢在"每个字符一次解释器循环"。正确做法是用正则先判断"这是纯 base64"，然后按大块（chunk）解码，让 C 层的 `base64.b64decode` 一次性处理几千个字符。
- **动手试试**：
```python
import base64
import time

data = b"x" * 10_000_000  # 10MB
encoded = base64.b64encode(data)

# 方法 1：逐字符（慢）
start = time.time()
result = bytearray()
for ch in encoded:
    result.extend(base64.b64decode(bytes([ch]) + b"=="))
print(f"逐字符: {time.time() - start:.2f}s")

# 方法 2：分块（快）
start = time.time()
CHUNK = 4096
result = bytearray()
for i in range(0, len(encoded), CHUNK):
    chunk = encoded[i:i+CHUNK]
    result.extend(base64.b64decode(chunk + b"=" * (-len(chunk) % 4)))
print(f"分块: {time.time() - start:.2f}s")
```
- **预期结果**：分块版本通常快几十倍。这就是 Commit 15 的核心思想。

### 知识点 4：CUDA Graph 捕获与张量缓存陷阱（对应 Commit 14）

- **是什么**：CUDA Graph 把一串 GPU 操作录制成图，之后重放。但"录制"时如果某个函数内部有缓存（比如 `prepare_chunk_offsets` 用了 tensor_cache），重放时就会用录制时的旧值，而不是新输入。
- **为什么重要**：这是 CUDA Graph 最经典的坑。Commit 14 的修复是：允许调用方传入 `chunk_offsets`，绕过内部缓存。如果你在写需要 graph capture 的 kernel，一定要检查所有"缓存"和"全局状态"。
- **动手试试**：
```python
import torch

# 模拟：一个带缓存的函数
_cache = {}

def compute_offset(x):
    key = x.shape[0]
    if key not in _cache:
        _cache[key] = x.sum()  # 录制时算一次
    return _cache[key]

# 正常调用
x1 = torch.tensor([1.0, 2.0])
print(compute_offset(x1))  # 3.0

# 换数据但 shape 相同
x2 = torch.tensor([10.0, 20.0])
print(compute_offset(x2))  # 还是 3.0！缓存陷阱

# 正确做法：显式传入，不走缓存
def compute_offset_safe(x, offset=None):
    if offset is not None:
        return offset
    return x.sum()
print(compute_offset_safe(x2, offset=x2.sum()))  # 30.0
```
- **预期结果**：你会看到缓存返回了错误的值，理解为什么 graph capture 场景下要禁用缓存。

### 知识点 5：MoE 小批量排序的专家数门槛（对应 Commit 8）

- **是什么**：MoE（混合专家）模型里，每个 token 要被路由到几个专家。小批量时，排序这些路由结果有专门的小 kernel。但"小 kernel"并不总是更快——当专家数很多时，它反而比通用 kernel 慢。
- **为什么重要**：Commit 8 发现，在 gfx950 上，当专家数 E=129 时小排序更快，但 E=513 时反而更慢。所以加了 `num_experts <= 256` 的门槛。这是典型的"经验性调优"——没有理论公式，只能靠 benchmark。
- **动手试试**：
```python
import torch
import time

def small_sort(topk_ids):
    # 模拟小排序：简单循环
    return topk_ids.sort(dim=-1).indices

def big_sort(topk_ids):
    # 模拟通用排序
    return torch.argsort(topk_ids, dim=-1)

for num_experts in [128, 256, 512, 1024]:
    topk_ids = torch.randint(0, num_experts, (8, 10), device="cuda")
    
    torch.cuda.synchronize()
    start = time.time()
    for _ in range(1000):
        small_sort(topk_ids)
    torch.cuda.synchronize()
    t_small = time.time() - start
    
    torch.cuda.synchronize()
    start = time.time()
    for _ in range(1000):
        big_sort(topk_ids)
    torch.cuda.synchronize()
    t_big = time.time() - start
    
    print(f"E={num_experts}: small={t_small:.4f}s, big={t_big:.4f}s")
```
- **预期结果**：你会看到随着专家数增加，小排序的优势逐渐消失甚至反转。这就是 Commit 8 加门槛的原因。
