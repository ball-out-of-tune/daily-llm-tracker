### 知识点 1：结构化工具调用与 strict 级别（来自 Commit 4）

- **是什么**：通过语法约束（grammar）强制模型输出的工具调用符合 JSON Schema，而不是事后解析。
- **为什么重要**：Agent 场景下，模型"少写一个引号"或"把数字写成字符串"就会让整个流程崩溃。不懂 strict 级别，你会以为模型"不够聪明"，其实是没做约束。
- **动手试试**：
  ```bash
  # 启动一个支持工具调用的 vLLM 服务，开启服务端严格级别
  vllm serve Qwen/Qwen2.5-7B-Instruct \
    --tool-call-parser hermes \
    --tool-strict-level function

  # 另一个终端发请求
  curl http://localhost:8000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
      "model": "Qwen/Qwen2.5-7B-Instruct",
      "messages": [{"role": "user", "content": "北京天气怎么样？"}],
      "tools": [{
        "type": "function",
        "function": {
          "name": "get_weather",
          "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
          }
        }
      }],
      "tool_choice": "auto"
    }'
  ```
- **预期结果**：即使你没有在 tools 里写 `strict: true`，因为服务端设了 `--tool-strict-level function`，模型输出也会被约束成合法的函数调用结构。把级别改成 `parameter` 后，连参数 schema 也会被强制。你会看到 `tool_calls` 字段里的 JSON 永远合法。

### 知识点 2：KV Cache 的"只释放缓存、保留权重"（来自 Commit 15）

- **是什么**：一个新的 `release_kv_cache_memory()` API，可以把 KV Cache 占的显存还回去，但模型权重还留在 GPU 上。
- **为什么重要**：权重加载很慢（几十 GB），KV Cache 是动态的。多租户场景下，用户 A 空闲时释放 KV Cache，用户 B 来了立刻用，不用重新加载模型。
- **动手试试**：
  ```python
  from vllm import LLM

  llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct", enable_sleep_mode=True)

  # 先跑一次推理
  llm.generate(["你好"])

  # 进入 level 0 睡眠（暂停调度，保留权重）
  llm.sleep(level=0, mode="keep")

  # 只释放 KV Cache 显存
  llm.release_kv_cache_memory()

  # 唤醒 KV Cache，继续推理
  llm.wake_up(tags=["kv_cache"])
  print(llm.generate(["再问一次"]))
  ```
- **预期结果**：调用 `release_kv_cache_memory()` 后，用 `nvidia-smi` 看显存会明显下降（KV Cache 部分被释放），但模型权重还在。`wake_up` 后又能正常推理，不用重新加载权重。

### 知识点 3：稀疏注意力的 NaN 陷阱（来自 Commit 11）

- **是什么**：在稀疏注意力里，候选 block 的分数可能因为 warmup 阶段是 NaN。如果代码用 `value > -inf` 判断，NaN 会被误判为"有效"，导致选出垃圾 block。
- **为什么重要**：这是经典的浮点陷阱。NaN 和任何数比较都返回 False，所以 `NaN > -inf` 是 False，但 `NaN != -inf` 是 True。一个符号之差，模型输出就从"正常"变成"乱码"。
- **动手试试**：
  ```python
  import torch

  # 模拟 warmup 阶段的分数
  logits = torch.tensor([[0.5, float("nan"), 0.3, float("-inf")]])

  # 错误写法：NaN 会被当成 padding 丢掉
  wrong = logits > float("-inf")
  print("错误写法:", wrong)

  # 正确写法：只有 -inf 才是 padding
  correct = logits != float("-inf")
  print("正确写法:", correct)
  ```
- **预期结果**：`错误写法` 输出 `[True, False, True, False]`——NaN 被误杀了。`正确写法` 输出 `[True, True, True, False]`——NaN 被保留，后续 kernel 会正确处理。这就是 Commit 11 改的那一行。

### 知识点 4：共享 token-to-request 映射（来自 Commit 6）

- **是什么**：多个 KV Cache group（比如 MLA 和 Mamba 混合）需要知道"每个 token 属于哪个请求"。以前每个 group 各算一遍，现在算一次共享。
- **为什么重要**：混合架构（MLA + Mamba）越来越常见，如果每个 group 都重复计算映射，会浪费 CPU 时间和内存带宽。
- **动手试试**：
  ```python
  import torch

  # 模拟：4 个请求，token 数分别是 2, 3, 1, 2
  num_tokens_per_req = [2, 3, 1, 2]
  token_to_req = torch.cat([
      torch.full((n,), i) for i, n in enumerate(num_tokens_per_req)
  ])
  print("token_to_req:", token_to_req)
  # 输出: tensor([0, 0, 1, 1, 1, 2, 3, 3])

  # 这个映射可以给所有 KV cache group 复用
  # 而不是每个 group 都重新构造一遍
  ```
- **预期结果**：你会看到一个"扁平化"的映射数组。理解它之后，再看 `build_attn_metadata` 里的 `_token_to_req_indices_cache` 就知道为什么能省时间了。

### 知识点 5：ROCm 上的算子别名（来自 Commit 5）

- **是什么**：在 AMD GPU 上，某个算子没有专门的 HIP 实现，就把 `forward_cuda` 直接指向 `forward_native`（PyTorch 原生实现）。
- **为什么重要**：跨平台代码里，"优雅降级"比"报错崩溃"重要得多。GLM-5.3-Flash 在 ROCm 上启动就崩，就是因为缺少这个别名。
- **动手试试**：
  ```python
  class MyKernel:
      def forward_native(self, x):
          return x * 2

      def forward_cuda(self, x):
          # 假设这是 CUDA 专用优化
          return x * 2

      # ROCm 上没有专门实现，直接复用 native
      forward_hip = forward_native

  k = MyKernel()
  print(k.forward_hip(torch.tensor([1, 2, 3])))
  ```
- **预期结果**：`tensor([2, 4, 6])`。这个模式在 vLLM 里到处都是：`forward_native` 是兜底，`forward_cuda`/`forward_hip`/`forward_xpu` 是平台优化。新手读代码时，看到 `forward_xxx` 就知道是平台分发。

## 🧪 重要知识点 & 动手实验

### 知识点 1：量化推理与 MXFP4 格式

- **是什么**：MXFP4 是一种 4 位浮点格式（e2m1：2 位指数 + 1 位尾数），配合 e8m0 的共享缩放因子，把模型权重压缩到原来的 1/4 大小。

- **为什么重要**：大模型动辄几百 GB，不量化根本塞不进单卡。但量化会掉精度，所以需要针对不同硬件（H100、H200、B200）验证"这个量化格式能不能跑、精度够不够"。不懂量化，你就无法在生产环境部署大模型。

- **动手试试**：
```bash
# 1. 查看 SGLang 支持哪些量化格式
python -c "from sglang.srt.layers.quantization import __all__; print(__all__)"

# 2. 用一个量化模型启动服务（需要先有 GPU）
python -m sglang.launch_server \
  --model-path inclusionAI/Ling-3.0-flash-VL-fp4 \
  --tp 1 \
  --moe-runner-backend flashinfer_mxfp4 \
  --port 30000

# 3. 发一个请求验证
curl http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "default", "messages": [{"role": "user", "content": "你好"}]}'
```

- **预期结果**：服务能正常启动并返回响应。如果看到 `flashinfer_mxfp4` 相关的日志，说明 MoE 层用了 MXFP4 后端。如果报错说权重加载失败，说明该硬件不支持这个格式——这正是 commit #39419 要解决的问题。

---

### 知识点 2：调度策略与最短 Prefill 优先

- **是什么**：调度策略决定"队列里哪个请求先跑"。FCFS 是先来先服务，"最短 prefill 优先"是优先处理输入短、缓存命中少的请求。

- **为什么重要**：想象餐厅排队，如果先服务点 100 道菜的大桌，后面点 1 道菜的小桌要等很久，平均等待时间爆炸。同理，长 prefill 会阻塞短请求，导致 TTFT（首 token 延迟）飙升。短任务优先能显著降低平均延迟。

- **动手试试**：
```bash
# 启动服务时指定调度策略
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --schedule-policy shortest-prefill-first \
  --port 30000

# 同时发一个长请求和一个短请求，观察谁先返回
# 用两个终端分别执行：
# 终端 1（长请求）：
curl http://localhost:30000/v1/completions \
  -d '{"prompt": "'"$(python -c 'print("hello "*500)')"'", "max_tokens": 10}'

# 终端 2（短请求）：
curl http://localhost:30000/v1/completions \
  -d '{"prompt": "hi", "max_tokens": 10}'
```

- **预期结果**：短请求会明显更快返回。查看服务日志，会看到 `Experimental shortest-prefill-first: queue=... shortest_uncached=...` 的调试信息。对比默认 `fcfs` 策略，短请求的 TTFT 会下降。

---

### 知识点 3：JIT vs AOT 内核编译

- **是什么**：AOT（Ahead-Of-Time）是安装时就编译好所有 GPU 算子；JIT（Just-In-Time）是运行时按需编译。

- **为什么重要**：AOT 启动快但不够灵活——换个 GPU 架构、改个参数就得重新编译整个包，CI 时间爆炸。JIT 灵活但首次运行慢（要编译）。SGLang 把投机采样内核从 AOT 迁到 JIT（#40033），就是为了让不同硬件（CUDA、ROCm、MUSA）共用一套源码。

- **动手试试**：
```bash
# 1. 看看 JIT 内核的源码长什么样
ls python/sglang/kernels/jit/include/sgl_kernel/speculative/

# 2. 查看采样内核的 CDF 边界修复（commit #35798）
grep -A 3 "has_target_mass" python/sglang/kernels/jit/include/sgl_kernel/speculative/sampling.cuh

# 3. 运行投机采样的测试
python -m pytest test/registered/kernels/ops/speculative/test_speculative_sampling.py -v
```

- **预期结果**：你能看到 `sampling.cuh` 里新增的 `has_target_mass` 判断——这是修复 CDF 边界 bug 的关键。测试通过说明投机采样的接受/拒绝逻辑正确。

### 知识点 4：Radix Cache 与前缀缓存

- **是什么**：Radix Cache 是一种树形数据结构，把多个请求共享的 prompt 前缀缓存起来，避免重复计算。比如 100 个请求都以"请翻译以下内容"开头，这段只算一次。

- **为什么重要**：前缀缓存能大幅降低 prefill 计算量，是推理框架的标配。但如果清理逻辑不对（比如没插入缓存的请求没有正确释放 KV 内存），就会内存泄漏。Commit #35204 就是修这个。

- **动手试试**：
```bash
# 1. 启动服务时开启前缀缓存（默认开启）
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --enable-prefix-caching \
  --port 30000

# 2. 发两个前缀相同的请求，观察第二个的 prefill 时间
# 第一次
curl http://localhost:30000/v1/completions \
  -d '{"prompt": "The capital of France is", "max_tokens": 5}'
# 第二次（相同前缀）
curl http://localhost:30000/v1/completions \
  -d '{"prompt": "The capital of France is", "max_tokens": 5}'

# 3. 查看缓存命中率
curl http://localhost:30000/metrics | grep cache
```

- **预期结果**：第二次请求的 `prompt_tokens` 计算量会显著减少（日志里会显示 cache hit）。如果看到 `cache_hit_rate` 指标上升，说明前缀缓存生效了。

---

### 知识点 5：投机采样的 CDF 边界处理

- **是什么**：投机采样中，小模型生成候选 token，大模型用概率分布决定"接受还是拒绝"。判断接受与否要用累积分布函数（CDF），边界情况（概率为 0 或 1）容易出 bug。

- **为什么重要**：如果 CDF 边界处理错了，会导致采样结果偏差——本该被拒绝的 token 被接受，模型输出质量下降。这种 bug 很隐蔽，只有极端概率分布才能触发。Commit #35798 就是修这个。

- **动手试试**：
```python
# 运行边界测试用例
import subprocess
subprocess.run([
    "python", "-m", "pytest",
    "test/registered/kernels/ops/speculative/test_speculative_sampling.py::test_target_only_sampling_cdf_boundaries",
    "-v"
])
```

- **预期结果**：5 个边界用例（零质量零阈值、零质量默认阈值、内部边界、下端点、上端点）全部通过。如果修复前运行，`zero-mass-zero-threshold` 这类用例会失败——因为概率为 0 的 token 被错误接受了。
