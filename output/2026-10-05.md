## 🧪 重要知识点 & 动手实验

- **知识点 1：INT4 KV Cache 与非 2 的幂 head size**
  - **是什么**：KV cache 量化到 INT4 时，会做一个叫 Hadamard 变换的旋转操作。这个变换原本要求 head size 是 2 的幂（如 64、128），现在支持任意偶数（如 Phi-3 的 96）。
  - **为什么重要**：Phi-3、Gemma 等模型 head size 不是 2 的幂，如果不支持，这些模型就没法用 INT4 KV cache，显存直接翻倍。不懂这个，你部署 Phi-3 时会遇到"backend 选择失败"的报错。
  - **动手试试**：
    ```bash
    # 安装 vllm 后，运行这个测试
    pytest tests/kernels/attention/test_attention_selector.py::test_int4_per_token_head_head_size_selection -v
    ```
    如果你想手动验证 head_size=96 的模型能否用 INT4：
    ```python
    from vllm.v1.attention.ops.int4_per_token_head import single_rht
    import torch
    x = torch.randn(4, 96, dtype=torch.float16, device="cuda")
    y = single_rht(x)  # 现在不会报错了
    print(y.shape)  # torch.Size([4, 96])
    ```
  - **预期结果**：测试全部通过，`single_rht` 在 96 维上正常工作，输出形状不变。

- **知识点 2：批次不变性与确定性归约**
  - **是什么**：GPU 上多个线程同时累加时，谁先加谁后加会影响浮点结果。批次不变性要求：不管 batch 里有多少请求，累加顺序固定。
  - **为什么重要**：如果你的应用需要"同一输入永远同一输出"（如金融、医疗、A/B 测试），原子加法（atomics）会导致结果抖动。今天 LoRA shrink 改成"固定 8 路 K 切分 + 固定顺序求和"就是为了这个。
  - **动手试试**：
    ```bash
    # 跑批次不变性测试
    pytest tests/v1/determinism/test_lora_shrink_batch_invariant.py -v -s
    ```
    手动观察差异：
    ```python
    import torch
    torch.manual_seed(0)
    a = torch.randn(1000, device="cuda")
    # 顺序求和
    s1 = a.sum()
    # 分 8 块求和再相加（模拟 split-K）
    s2 = sum(a[i::8].sum() for i in range(8))
    print(s1.item(), s2.item())  # 可能不同！这就是为什么需要固定顺序
    ```
  - **预期结果**：测试通过，说明 vLLM 在开启 batch invariance 后，不同 batch size 下 LoRA 输出完全一致。

- **知识点 3：ROCm 上的显存 profiling 与配置上下文**
  - **是什么**：vLLM 启动时会跑一次"假请求"来测量模型占多少显存，从而决定 KV cache 能分多少。这个过程中需要知道 `max_num_seqs` 等配置。
  - **为什么重要**：如果 profiling 时拿不到配置，ROCm 的 decode workspace 会按最大 token 数（32768）预留显存，1M 上下文下直接吃掉 128 GiB，OOM 崩溃。
  - **动手试试**：

    ```
  - **预期结果**：测试验证了 profiling 期间配置可见，退出后配置被清理，不会污染全局状态。

- **知识点 4：KV Cache 卸载的抢占恢复**
  - **是什么**：当 GPU 显存不够时，调度器会"抢占"某些请求，把它们的 KV cache 挪到 CPU。请求恢复时，需要重新分配 GPU block，旧的存储游标必须清零。
  - **为什么重要**：如果游标没清零，恢复后的请求会以为"我已经存了 2 个 block"，结果漏存尾部 block，导致后续推理读到错误的 KV，输出乱码。
  - **动手试试**：

    ```
    这个测试参数化了 `use_v2_model_runner` 和 `same_output`，覆盖 4 种抢占路径。
  - **预期结果**：4 个组合全部通过，证明抢占后恢复的请求能正确存下尾部 block。

- **知识点 5：流式响应中的错误传播**
  - **是什么**：SSE（Server-Sent Events）流式返回时，如果模型还没吐出第一个 token 就报错，客户端可能收不到任何错误信息，只看到连接关闭。
  - **为什么重要**：用户看到"连接中断"会以为是网络问题，实际是模型加载失败或 prompt 太长。今天 Commit 11 保证错误在首个 chunk 就返回。
  - **动手试试**：

## 🔥 重要更新

1. **Commit 8（LoRA split-K=8 确定性归约）**：这是批次不变性在 LoRA 上的关键补全。之前 LoRA 的 K 维归约用原子加法，导致不同 batch size 下输出抖动。现在改成固定 8 路切分 + 固定顺序求和，生产环境可复现性大幅提升。**做 A/B 测试或多轮对话一致性要求的团队必须关注**。

2. **Commit 2（ROCm 显存 profiling 保留配置）**：修的是 AMD GPU 上 1M 上下文直接 OOM 的严重 bug。原因是 profiling 时拿不到 `max_num_seqs`，workspace 按 32768 token 预留了 128 GiB。**所有在 AMD 上跑长上下文的用户受益**。

3. **Commit 3（INT4 KV cache 支持非 2 的幂 head size）**：解锁了 Phi-3（head_size=96）等模型使用 INT4 KV cache 的能力。之前这些模型会被 backend selector 直接拒绝。**显存敏感场景下，Phi-3 的 KV cache 能省一半**。

4. **Commit 12（对齐 KV block size 检查所有 attention backend）**：之前只检查主 backend，混合模型（如 Mamba + Attention）的兄弟 backend 可能拒绝对齐后的 block size，导致运行时才报错。现在提前在 platform 层检查。**混合架构模型部署更稳**。

- **新手概念课堂**：混合模型（如 Mamba + Attention）有多个 attention backend。平台层为了对齐 block size，可能把 16 改成 32，但某个 backend 只接受 16。之前只检查主 backend，现在检查所有兄弟。就像"一家人出门，不能只问爸爸同不同意，要问所有家庭成员"。
- **对你有什么影响**：部署混合架构模型（如 Jamba、Bamba）时，block size 不匹配会在启动时明确报错，而不是运行时崩溃。

- **代码层面**：`rocm_attn.py` 中修正 sliding window 的边界计算，确保窗口 W 包含当前 token 和前 W-1 个 token。测试新增 `test_rocm_backend_sliding_window_includes_boundary_token`，参数化 `sliding_window=[None, 1, 4]` 和 `query_len=[1, 3]`。
- **新手概念课堂**：sliding window attention 就像"只看最近 W 个 token"。如果窗口是 4，当前 token 是第 8 个，应该看第 5、6、7、8 个。之前 ROCm 实现可能漏看了第 5 个（差一错误），导致输出偏差。

### 14. [Bugfix][XPU] Make DeepSeek V4 FP8 sparse decode graph-capturable (#59159)
- **代码层面**：`xpu_sparse_decode_fp8.py` 中重构 workspace 布局——topk 行在前、SWA 行在后，用 shape 推导宽度而不是 `max().item()` 主机同步。去掉 `topk_buf`/`swa_buf` 中间缓冲，直接写入 workspace 切片。
- **新手概念课堂**：CUDA Graph 捕获要求"每次执行的算子序列和内存地址完全一样"。如果代码里有 `int(tensor.max().item())`，会把 GPU 数据拷回 CPU，打断 graph 捕获。这个 commit 把"动态宽度"改成"固定 shape 推导"，让 graph 能捕获。就像拍电影，演员走位必须固定，不能每次即兴发挥。
- **对你有什么影响**：Intel XPU 上跑 DeepSeek V4 FP8 稀疏解码时，可以用 CUDA Graph 加速，decode 阶段吞吐提升。

## 🧪 重要知识点 & 动手实验

- **知识点 1：算子融合（Kernel Fusion）—— 把 FP8 量化塞进搬运 kernel**
  - **是什么**：本来要"读数据 → 量化 → 写数据"三步走，现在合成一个 kernel：读进来的同时就量化好写出去。
  - **为什么重要**：每次 kernel launch 都有固定开销（几十微秒），小算子多了就是灾难。KV cache 搬运是每步都要做的，融合能直接省掉一次读写和一次 launch。
  - **动手试试**：用 `torch.profiler` 看看一个简单模型的 kernel launch 数量：
    ```python
    import torch
    from torch.profiler import profile, ProfilerActivity
    x = torch.randn(4096, 4096, device="cuda", dtype=torch.bfloat16)
    with profile(activities=[ProfilerActivity.CUDA]) as prof:
        for _ in range(10):
            y = x / 2.0
            z = y.to(torch.float8_e4m3fn)
            w = z.to(torch.bfloat16)
    print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=10))
    ```
  - **预期结果**：你会看到 `div`、`to(fp8)`、`to(bf16)` 分别是独立的 kernel，每个都有 launch 开销。如果把它们写成一个 Triton kernel（就像 commit #40785 做的），launch 数量从 3 降到 1。

- **知识点 2：序列并行（Sequence Parallelism）与 Attention Mask**
  - **是什么**：一条长序列被切成几段，分给不同 GPU 各算一段 attention，但每段末尾会"多算一点"补 padding，需要 mask 掉这些无效部分。
  - **为什么重要**：如果 mask 用错，模型会看到"未来的 token"或"填充的垃圾"，输出直接崩。但如果 mask 是纯 pad 造成的，其实可以省掉，换来更快的 dense attention。
  - **动手试试**：模拟 SP 场景，对比有无 mask 的 attention 输出：
    ```python
    import torch
    torch.manual_seed(0)
    q = torch.randn(1, 4, 8, 64, device="cuda", dtype=torch.bfloat16)
    k = torch.randn(1, 4, 8, 64, device="cuda", dtype=torch.bfloat16)
    v = torch.randn(1, 4, 8, 64, device="cuda", dtype=torch.bfloat16)
    # 假设最后 2 个位置是 padding，用 mask 屏蔽
    mask = torch.ones(8, 8, device="cuda", dtype=torch.bool)
    mask[:, 6:] = False
    out_masked = torch.nn.functional.scaled_dot_product_attention(q, k, v, attn_mask=mask)
    out_dense = torch.nn.functional.scaled_dot_product_attention(q, k, v)
    print("max diff:", (out_masked - out_dense).abs().max().item())
    ```
  - **预期结果**：diff 不为 0，说明 mask 确实改变了结果。但如果 padding 位置本来就是零，两种结果会一致——这就是 commit #33855 允许"关掉 mask 走 dense 路径"的前提。

- **知识点 3：MoE 的 Expert Parallel Dispatch（All-to-All 通信）**
  - **是什么**：每个 token 会被路由到 top-k 个专家，专家分布在不同 GPU 上，所以 token 需要"快递"到目标 GPU，算完再"快递"回来。
  - **为什么重要**：通信量 = token 数 × hidden 维度 × 2（去 + 回），是 MoE 推理最大的开销。DeepEP 就是专门优化这个通信的库。
  - **动手试试**：用 PyTorch 模拟一次 all-to-all：
    ```python
    import torch
    import torch.distributed as dist
    # 需要先初始化进程组：
    # torchrun --nproc_per_node=2 your_script.py
    if dist.is_initialized():
        rank = dist.get_rank()
        # 每个 rank 有 4 个 token，要发给另一个 rank
        send = torch.full((4, 8), float(rank), device="cuda")
        recv = torch.empty_like(send)
        dist.all_to_all_single(recv, send)
        print(f"rank {rank} received: {recv[:,0].tolist()}")
    ```
  - **预期结果**：rank 0 收到全 1，rank 1 收到全 0，验证了 token 在 GPU 间的搬运。DeepEP 做的就是把这个过程压缩成一次高效 kernel。

- **知识点 4：数值精度与舍入模式（Rounding Mode）**
  - **是什么**：BF16/FP8 转换时，浮点数无法精确表示，需要选择"四舍五入"（RTNE）、"远离零"（RTNA）还是"向零取整"（RTZ）。
  - **为什么重要**：不同舍入模式累积误差不同，在 attention 这种大量累加的场景下，可能影响最终输出质量。commit #28650 把 gfx942 上的默认从 RTNA 改成 RTZ，就是实测发现 RTZ 更稳。
  - **动手试试**：对比不同舍入模式对累加误差的影响：
    ```python
    import torch
    x = torch.tensor([1.0009765625, 1.0009765625, 1.0009765625], dtype=torch.float32)
    # BF16 只有 8 位尾数，1.0009765625 无法精确表示
    bf16 = x.to(torch.bfloat16)
    print("原值:", x.tolist())
    print("BF16:", bf16.to(torch.float32).tolist())
    print("误差:", (bf16.to(torch.float32) - x).tolist())
    ```
  - **预期结果**：你会看到每个值都被舍入到最近的 BF16 可表示值。当大量这样的值累加时，误差方向（偏大/偏小）会导致系统性偏差，这就是为什么需要选对舍入模式。

- **知识点 5：层边界抽象（Layer Boundary）**
  - **是什么**：把模型的一层显式拆成"注意力阶段"和"FFN 阶段"，用声明式 API 描述它们的连接关系，框架自动处理残差、TP all-reduce、流水线通信等。
  - **为什么重要**：不同模型的残差结构差异很大（普通残差、mHC、IHC、gated 等），硬编码会导致大量重复代码。抽象后，新模型适配只需声明阶段，不用管底层通信。
  - **动手试试**：看 SGLang 文档里的最小示例：
    ```python
    from sglang.srt.layers.layer_boundary import append_stages, declare_attn, declare_ffn
    self.attn_boundary, self.ffn_boundary = append_stages(
        (declare_attn(), self.input_layernorm),
        (declare_ffn(), self.post_attention_layernorm),
    )
    ```
    然后跑一个单元测试看看边界是否被正确构建：
    ```bash
    python -m pytest test/registered/unit/layer_boundary/ -v
    ```
  - **预期结果**：测试通过，说明框架能正确识别"这一层的 attn 阶段后面跟着 ffn 阶段"。如果你写错了顺序，`append_stages` 会在构建时抛错。
