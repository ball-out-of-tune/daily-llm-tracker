## 🧪 重要知识点 & 动手实验

### 知识点 1：JIT 预热与 `JitWarmupRegistry`

- **是什么**：vLLM 里很多 kernel（Triton、TileLang、CuTeDSL）是运行时才编译的。第一次调用会触发编译，耗时可能几百毫秒。`JitWarmupRegistry` 就是把这些 kernel 的编译提前到模型加载阶段完成的机制。
- **为什么重要**：生产环境中，用户第一次请求如果卡 500ms 甚至几秒，体验极差。预热能让 P99 延迟稳定。不懂这个，你部署的模型可能"第一个请求特别慢"。
- **动手试试**：

  # 3. 看 registry capture 测试

- **预期结果**：你会看到 `test_registry_capture` 通过，并且理解 `@JitWarmupRegistry.capture` 装饰器如何自动把 `__init__` 里注册的 kernel 收集到 `jit_warmup_registry` 属性上。如果测试失败，说明你的环境缺少 CUDA 或 Triton。

### 知识点 2：KV Cache Offload 与"无前向步骤"的 CPU 存储

- **是什么**：当请求结束时，它的 KV cache 需要从 GPU 搬到 CPU。但如果这个请求是最后一个、之后没有新的 forward 步骤，那么"搬运"这件事就可能永远不被触发——这就是 #56621 修的 bug。
- **为什么重要**：这是典型的"边界条件 bug"。正常流程下，每个 step 都会检查是否有待搬运的数据；但请求结束后的空 step 容易被忽略，导致数据滞留在 GPU 或丢失。
- **动手试试**：
  ```bash
  # 跑今天新增的测试
  pytest tests/v1/simple_kv_offload/test_worker.py::test_no_forward_step_completes_cpu_store -v

  # 用参数化跑 v2 版本
  pytest tests/v1/simple_kv_offload/test_worker.py::test_no_forward_step_completes_cpu_store -v -k "True"
  ```
- **预期结果**：测试会构造一个空的 `SchedulerOutput`，然后断言 CPU store 能在没有 forward 的情况下完成。你会看到 `use_v2=False` 和 `use_v2=True` 都通过，说明新旧两条代码路径都修好了。

### 知识点 3：Per-token-group 量化与"奇数行性能悬崖"

- **是什么**：FP8 量化时，通常按 token 分组计算 scale。当行数（token 数）是奇数时，GPU 的线程块划分会变得不整齐，导致性能骤降——这就是"odd-row performance cliff"。
- **为什么重要**：真实推理中 batch size 经常是奇数（比如 1、7、33），如果没处理这个边界，吞吐量会莫名其妙掉一半。这是量化 kernel 优化的经典坑。
- **动手试试**：
  ```bash
  # 找到相关 kernel 测试
  ls tests/kernels/ | grep -i quant

  # 跑 per-token-group 量化测试（需要 CUDA）
  pytest tests/kernels/test_per_token_group_quant.py -v -k "fp8"
  ```
  如果你想直接看代码，打开 `csrc/libtorch_stable/quantization/w8a8/fp8/per_token_group_quant.cu`，找到 `CHECK_BOUNDS` 模板参数——这就是今天新增的边界检查开关。
- **预期结果**：你会看到 kernel 现在对越界的 group 做了 `valid_group` 判断，避免无效计算。跑测试时，奇数 token 数的 case 应该和偶数一样快。

### 知识点 4：投机解码下的水印（Dual-key Gumbel-max）

- **是什么**：水印是在生成文本里嵌入可检测的统计信号。投机解码会改变采样路径（draft 采样 + 拒绝采样），传统水印算法会失效。#56122 用"双 key Gumbel-max"让水印在投机解码下也能工作。
- **为什么重要**：AI 生成内容追溯是监管刚需。如果水印和加速技术不兼容，企业就得在"快"和"合规"之间二选一。

### 知识点 5：PCP + DCP 在稀疏 MLA 模型上的协同

- **是什么**：PCP（Prefill Context Parallel）和 DCP（Decode Context Parallel）是两种把长上下文切分到多卡上的并行策略。之前它们不能同时用，今天 #56157 让它们在稀疏 MLA（如 GLM-5.2）上能一起工作。
- **为什么重要**：长上下文推理是当前最烧显存的场景。PCP 加速 prefill，DCP 加速 decode，两者结合能同时优化两个阶段——但前提是 attention 的索引逻辑要正确"去交错"。

## 🧪 重要知识点 & 动手实验

### 知识点 1：量化 GEMM 的"形状对齐"陷阱（来自 Commit 1）

- **是什么**：AMD 的 aiter 库有一个高性能 FP8 矩阵乘法内核，但它要求输出维度 N 必须是 64 的倍数，否则会报错。代码里用一个 `use_aiter_bpreshuffle_gemm(output_size)` 函数来决定"要不要走这条快路"。
- **为什么重要**：如果加载权重时做了 shuffle（重排），但推理时走了另一条路径，结果会**静默返回垃圾数据**——不报错，但答案全错。这是量化最可怕的 bug 类型。
- **动手试试**：
  ```python
  # 模拟"形状对齐检查"的逻辑
  def can_use_fast_gemm(n: int, block: int = 64) -> bool:
      return n % block == 0

  for n in [32, 64, 128, 100, 4096]:
      print(f"N={n:5d} -> 走快路: {can_use_fast_gemm(n)}")
  ```
- **预期结果**：你会看到 N=32、100 走慢路，N=64、128、4096 走快路。理解"为什么 32 不是 64 的倍数就要降级"，你就懂了硬件内核对 tile 对齐的硬性要求。

### 知识点 2：CUDA Stream 与内存池的一致性（来自 Commit 10）

- **是什么**：PyTorch 的缓存分配器是"按流"管理的。如果一个内存池在 Stream A 上创建，却在 Stream B 上借用，分配器无法复用预切好的内存段，甚至可能读到未同步的数据。
- **为什么重要**：CUDA Graph 捕获时会预先分配一大块内存，之后推理时"借用"这些空闲段。如果流不一致，轻则性能暴跌，重则数据竞争。
- **动手试试**：
  ```python
  import torch
  if torch.cuda.is_available():
      s1 = torch.cuda.Stream()
      s2 = torch.cuda.Stream()
      with torch.cuda.stream(s1):
          a = torch.randn(1000, 1000, device="cuda")
      with torch.cuda.stream(s2):
          b = torch.randn(1000, 1000, device="cuda")
          # 注意：这里 b 的分配在 s2，但 a 在 s1，跨流使用需要 event 同步
          c = a + b  # 潜在的数据竞争！
      torch.cuda.synchronize()
      print("跨流操作完成，但正确性依赖同步")
  ```
- **预期结果**：代码能跑，但如果你把 `torch.cuda.synchronize()` 去掉，在真实高并发场景下可能读到脏数据。理解"流是内存分配的作用域"是进阶关键。

### 知识点 3：多模态缓存的内存泄漏——视图持有整个 batch（来自 Commit 6）

- **是什么**：PyTorch 的 tensor 切片（view）不复制数据，而是共享底层 storage。如果把一个 batch 的切片存进缓存，整个 batch 的内存都释放不掉。
- **为什么重要**：多模态模型里图像 embedding 很大，一个 batch 可能有几十张图。缓存里存 100 个"切片"，实际可能占了几十 GB。
- **动手试试**：
  ```python
  import torch
  big = torch.randn(1000, 512)          # 一个 batch
  slice1 = big[0:1]                     # 视图，不复制
  slice2 = big[1:2]
  print("视图 storage 大小:", slice1.untyped_storage().nbytes())  # 整个 big 的大小！
  print("视图 numel:", slice1.numel())

  # 正确做法：clone
  slice1_clone = big[0:1].clone()
  print("clone 后 storage 大小:", slice1_clone.untyped_storage().nbytes())
  ```
- **预期结果**：你会看到视图的 storage 大小是 1000×512×4 字节（整个 batch），而 clone 后只有 1×512×4 字节。这就是 Commit 6 用 `tensor.clone()` 修复的泄漏。

### 知识点 4：JSON Schema 中的 union 类型与类型推断（来自 Commit 4）

- **是什么**：工具调用的参数可能是 `string | integer | null`（union 类型）。模型返回 `"42"` 时，你得知道它应该是字符串还是整数。GLM 的 detector 之前会丢类型信息。
- **为什么重要**：如果类型错了，下游 API 调用会失败。比如一个参数应该是整数，你传了字符串，服务端直接 400。
- **动手试试**：
  ```python
  import json

  schema = {
      "type": "object",
      "properties": {
          "count": {"anyOf": [{"type": "integer"}, {"type": "null"}]},
          "name":  {"type": "string"}
      }
  }

  def infer_type(schema_prop):
      if "type" in schema_prop:
          return schema_prop["type"]
      if "anyOf" in schema_prop:
          return [s.get("type") for s in schema_prop["anyOf"]]
      return None

  for k, v in schema["properties"].items():
      print(f"{k}: {infer_type(v)}")
  ```
- **预期结果**：`count` 会输出 `['integer', 'null']`，`name` 输出 `'string'`。理解 union 类型的处理，你就懂了为什么工具调用需要一套"类型系统"。

### 知识点 5：视频编码的 preset 与可复现性（来自 Commit 3）

- **是什么**：ffmpeg 的 libx264 编码器有 preset 参数（ultrafast → veryslow）。不指定时默认是 `medium`，但对扩散模型输出，`fast` 更快且更接近原始帧。
- **为什么重要**：CI 测试需要可复现。如果编码器默认值变了，或者不同机器上默认值不同，测试结果就会飘。显式指定 preset 是工程规范。
- **动手试试**：
  ```bash
  # 如果你有 ffmpeg，生成一个测试视频
  ffmpeg -f lavfi -i testsrc=duration=2:size=320x240:rate=8 -c:v libx264 -preset fast /tmp/test_fast.mp4
  ffmpeg -f lavfi -i testsrc=duration=2:size=320x240:rate=8 -c:v libx264 -preset medium /tmp/test_medium.mp4
  ls -la /tmp/test_*.mp4
  # 查看编码参数
  ffprobe -v quiet -show_streams /tmp/test_fast.mp4 | grep -i preset
  ```
- **预期结果**：`fast` 版本文件更小、编码更快。你会理解"显式指定默认值"为什么是 CI 稳定的关键。
