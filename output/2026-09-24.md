## 🧪 重要知识点 & 动手实验

- **知识点 1：Triton 缓存目录（Triton Cache Dir）**
  - **是什么**：Triton 是写 GPU kernel 的编译器，它编译出来的二进制文件会缓存在一个目录里，下次同样代码就直接复用，不用重新编译。默认 vLLM 会把这个目录塞进自己的大缓存目录，但有时用户想自己指定。
  - **为什么重要**：如果缓存目录被错误地覆盖或混用，会导致"冷启动变慢"或"复用了错误的编译产物导致结果错误"。今天 Commit 1 就是修这个：让用户显式设置的 `TRITON_CACHE_DIR` 优先，同时又不让上一个模型的缓存污染下一个模型。
  - **动手试试**：
    ```bash
    # 先设一个自己的 Triton 缓存目录
    export TRITON_CACHE_DIR=/tmp/my_triton_cache
    mkdir -p $TRITON_CACHE_DIR
    # 跑一个简单的 vLLM 编译流程（需要装好 vllm）
    python -c "
    import os
    print('TRITON_CACHE_DIR =', os.environ.get('TRITON_CACHE_DIR'))
    "
    # 观察第一次编译后目录里会出现 .ptx/.cubin 等文件
    ls -R /tmp/my_triton_cache | head -20
    ```
  - **预期结果**：你会看到 Triton 编译产物出现在你指定的目录里，而不是 vLLM 默认的 `~/.cache/vllm/triton_cache`。这说明你掌握了"缓存隔离"的概念。

- **知识点 2：SSE 保活（Server-Sent Events Keep-Alive）**
  - **是什么**：SSE 是流式响应协议，服务器一点一点把 token 推给客户端。但如果模型在 prefill 阶段卡了 30 秒没吐字，中间的反向代理（Nginx、Cloudflare）可能以为连接死了就掐断。保活就是每隔几秒发一个空注释行"我还在"。
  - **为什么重要**：这是生产环境部署 LLM 服务最常见的坑之一：本地测试好好的，一放到网关后面就断流。Commit 2 给 Rust 前端加了 `--sse-keep-alive-interval` 参数。
  - **动手试试**：
    ```bash
    # 启动一个 vLLM 服务（假设已装好），开启 5 秒保活
    vllm serve Qwen/Qwen2.5-0.5B-Instruct --sse-keep-alive-interval 5 &
    sleep 30
    # 用 curl 观察流式响应，看是否有 ": keep-alive" 注释行
    curl -N http://localhost:8000/v1/chat/completions \
      -H "Content-Type: application/json" \
      -d '{"model":"Qwen/Qwen2.5-0.5B-Instruct","messages":[{"role":"user","content":"写一篇1000字的文章"}],"stream":true}' \
      | head -50
    ```
  - **预期结果**：你会看到流里夹杂着 `: keep-alive` 这样的注释行（SSE 注释以冒号开头，客户端会忽略但连接保持活跃）。这说明你理解了"为什么生产环境需要保活"。

- **知识点 3：MoE 路由权重与 GEMM 的数据类型**
  - **是什么**：MoE（混合专家）模型里，每个 token 要先经过一个"路由器"决定去哪个专家。CPU 上做这个矩阵乘法（GEMM）时，如果权重是 fp32 而输入是 bf16，就可能出现类型不匹配导致的越界写。
  - **为什么重要**：Commit 8 修复了一个"fp32 路由权重导致段错误"的 bug。这是典型的"类型系统在 C++/kernel 层没守住"的问题，新手很容易在混合精度场景踩坑。
  - **动手试试**：
    ```python
    import torch
    # 模拟：权重 fp32，输入 bf16
    layer = torch.nn.Linear(16, 8, bias=False, dtype=torch.float32)
    x = torch.randn(4, 16, dtype=torch.bfloat16)
    try:
        # 直接乘会报错或产生意外结果
        out = x @ layer.weight.T
        print("shape:", out.shape, "dtype:", out.dtype)
    except RuntimeError as e:
        print("报错:", e)
    # 正确做法：显式转换
    out = (x.float() @ layer.weight.T).to(torch.bfloat16)
    print("修正后 dtype:", out.dtype)
    ```
  - **预期结果**：你会看到不转换时 PyTorch 会报 dtype 不匹配的错误（或产生 NaN），转换后正常。这说明你理解了"混合精度下必须显式对齐 dtype"。

- **知识点 4：分块预填充（Chunked Prefill）与确定性（Determinism）**
  - **是什么**：长 prompt 的 prefill 阶段会一次性算很多 token，占用大量显存。分块预填充就是把它切成几块分多次算，降低峰值显存。但切块会改变计算顺序，可能导致浮点结果不一致。
  - **为什么重要**：Commit 15 专门加了测试验证"分块预填充下，batch size 为 1 和为 N 的结果必须逐位一致"。这对需要可复现结果的应用（如评测、RL 训练）至关重要。
  - **动手试试**：
    ```bash
    # 跑 vLLM 的确定性测试（需要 GPU 和装好依赖）
    cd tests/v1/determinism
    pytest -v -s test_batch_invariance.py::test_logprobs_bitwise_batch_invariance_ragged_chunked_prefill
    ```
  - **预期结果**：测试通过说明"无论是否分块、batch 多大，logprobs 逐位一致"。如果失败，说明你的环境里有非确定性算子（比如某些 attention kernel）。这说明你理解了"确定性推理"这个高级话题。

- **知识点 5：稀疏注意力与哨兵值（Sentinel Value）**
  - **是什么**：稀疏注意力只计算一部分 token 之间的注意力，省算力。DeepSelect 是其中一种算法，对无效行会写入一个"哨兵值"（比如一个超大数字）表示"这行不算"。如果后续代码没检查这个哨兵，就会越界访问。
  - **为什么重要**：Commit 16 修复了"哨兵列没有上界检查"导致的内存越界。这是 GPU kernel 编程的经典陷阱：边界检查不做全，就会读到垃圾数据甚至崩溃。
  - **动手试试**：
    ```python
    import torch
    # 模拟：稀疏索引里混入了越界哨兵
    width = 128
    indices = torch.tensor([0, 5, 100, 200, -1], dtype=torch.int32)
    # 错误做法：不检查上界
    try:
        valid = indices >= 0  # 只检查了下界
        print("错误检查结果:", valid.tolist())
    except Exception as e:
        print(e)
    # 正确做法：同时检查上下界
    valid = (indices >= 0) & (indices < width)
    print("正确检查结果:", valid.tolist())
    ```
  - **预期结果**：你会看到只检查下界时 200 被当作合法，正确检查后 200 被标记为非法。这说明你理解了"边界检查必须上下界都做"。

### 10. [Bugfix][KV Offload] Retain offload event metadata through batch translation (#57453)

## 🧪 重要知识点 & 动手实验

- **知识点 1：AMD GPU 上的 wave size 与 kernel 可移植性**
  - **是什么**：AMD GPU 的执行单元叫"wave"，wave64 表示一个 wave 有 64 个线程，wave32 只有 32 个。不同架构（gfx950 vs gfx1250）wave size 不同，写 kernel 时必须适配。
  - **为什么重要**：Commit 3 里，代码把硬编码的 `WARP_SIZE = 64` 改成运行时探测 `torch.cuda.get_device_properties(0).warp_size`，并把 shuffle 偏移量从固定 `(32,16,8,4,2,1)` 改成按 WARP_SIZE 动态生成。如果不懂这个，kernel 在 wave32 硬件上会直接崩溃或结果错误。
  - **动手试试**：
    ```python
    import torch
    if torch.cuda.is_available():
        props = torch.cuda.get_device_properties(0)
        print(f"设备名: {props.name}")
        print(f"warp size: {props.warp_size}")
        print(f"计算单元数: {props.multi_processor_count}")
        # 看看你的设备是 wave32 还是 wave64
        print("wave64" if props.warp_size == 64 else "wave32")
    ```
  - **预期结果**：NVIDIA GPU 会显示 `warp_size: 32`，AMD MI 系列会显示 `warp_size: 64`，新一代 gfx1250 可能显示 32。你会理解为什么同一份 kernel 代码需要运行时探测。

- **知识点 2：FP8 逐张量量化的 amax 归约与 grid barrier**
  - **是什么**：量化需要先找出整个张量的最大绝对值（amax），再算出 scale = amax / 448.0（FP8 最大值）。在大张量上，这需要跨多个 CUDA block 做全局归约。
  - **为什么重要**：Commit 18 里用了一个 Triton kernel 同时完成"全局 amax 归约"和"缩放转换"，中间用 grid-wide barrier 同步。这个技巧在量化推理里非常常见，不懂就只能用两次 kernel launch，性能差一倍。
  - **动手试试**：
    ```python
    import torch
    # 模拟一个逐张量 FP8 量化
    x = torch.randn(1024, 1024, device="cuda", dtype=torch.float32)
    amax = x.abs().max()
    scale = amax / 448.0  # FP8 E4M3 最大值是 448
    x_q = (x / scale).clamp(-448, 448).to(torch.float8_e4m3fn)
    x_deq = x_q.to(torch.float32) * scale
    error = (x - x_deq).abs().mean()
    print(f"amax={amax:.4f}, scale={scale:.6f}")
    print(f"平均量化误差: {error:.6f}")
    print(f"最大误差: {(x - x_deq).abs().max():.6f}")
    ```
  - **预期结果**：你会看到量化误差在 1e-2 量级，理解为什么量化会损失精度，以及 scale 如何控制误差范围。

- **知识点 3：MoE 中的共享专家融合（Shared Expert Fusion）**
  - **是什么**：MoE 模型通常有一个"共享专家"（所有 token 都过）加多个"路由专家"（按 token 选）。融合就是把共享专家的权重塞进路由专家的张量里，当作第 N+1 个专家，减少一次独立的矩阵乘法。
  - **为什么重要**：Commit 12 修复了一个严重 bug——启用融合后共享专家权重被静默丢弃，导致精度崩溃到几乎为零。这种 bug 非常隐蔽，因为模型还能跑，只是结果全错。
  - **动手试试**：
    ```python
    # 概念演示：共享专家融合的权重映射
    num_experts = 8
    # 原始 checkpoint 里的权重名
    ckpt_names = [
        "mlp.experts.0.gate_proj.weight",
        "mlp.experts.7.down_proj.weight",
        "mlp.shared_expert.gate_up_proj.weight",  # 共享专家
        "mlp.shared_expert.down_proj.weight",      # 共享专家
    ]
    # 融合后，共享专家被映射到 index=num_experts 的槽位
    fused_mapping = {
        "mlp.shared_expert.gate_up_proj": f"experts.{num_experts}.gate_up_proj",
        "mlp.shared_expert.down_proj": f"experts.{num_experts}.down_proj",
    }
    for name in ckpt_names:
        for prefix, target in fused_mapping.items():
            if prefix in name:
                print(f"映射: {name} -> {target}")
                break
        else:
            print(f"保持: {name}")
    ```
  - **预期结果**：你会看到共享专家的两个权重被重映射到 `experts.8.*`，理解融合的机制。如果映射写错，权重就丢了，模型精度崩溃。

- **知识点 4：CUDA Graph 与内存管理器的交互（TMS pause/resume）**
  - **是什么**：CUDA Graph 把一串 GPU 操作录制成图，重放时零 CPU 开销。但 RL 训练时需要"暂停"推理引擎来更新权重，暂停时如果 CUDA Graph 的中间张量被释放，恢复后就崩了。
  - **为什么重要**：Commit 16 用 `TorchMemorySaverAdapter` 把 CUDA Graph 相关的张量标记为 `GPU_MEMORY_TYPE_CUDA_GRAPH`，暂停时保留它们。这是 RL + 推理协同的关键工程细节。
  - **动手试试**：
    ```python
    import torch
    # 演示 CUDA Graph 的基本用法
    if torch.cuda.is_available():
        x = torch.randn(8, 8, device="cuda")
        w = torch.randn(8, 8, device="cuda")
        # 预热
        for _ in range(3):
            y = x @ w
        torch.cuda.synchronize()
        # 录制
        g = torch.cuda.CUDAGraph()
        with torch.cuda.graph(g):
            y = x @ w
        # 重放
        x.copy_(torch.randn(8, 8, device="cuda"))
        g.replay()
        torch.cuda.synchronize()
        print(f"重放结果 shape: {y.shape}")
        print("CUDA Graph 录制和重放成功")
    else:
        print("需要 CUDA 设备")
    ```
  - **预期结果**：你会看到 CUDA Graph 成功录制和重放。理解为什么图里的张量在暂停期间不能被释放——因为图里存的是指针。

- **知识点 5：权重热更新的会话机制（Weight Update Session）**
  - **是什么**：RL 训练时，训练进程把新权重发给推理引擎。但量化模型需要"后处理"（如 Marlin repack、MXFP8 shuffle）才能被 kernel 使用。会话机制把多次权重写入攒在一起，最后统一做一次后处理。
  - **为什么重要**：Commit 15 引入了 `begin_weight_update` / `end_weight_update`。如果不理解这个，你可能会在每次 bucket 更新后都调用 `process_weights_after_loading`，性能差几十倍。
  - **动手试试**：
    ```python
    # 模拟权重更新会话的生命周期
    class WeightUpdateSession:
        def __init__(self):
            self.active = False
            self.pending_layers = []
        def begin(self):
            if self.active:
                raise RuntimeError("会话已开启")
            self.active = True
            self.pending_layers = []
            print("会话开启：准备接收权重")
        def update(self, layer_name):
            if not self.active:
                raise RuntimeError("必须在会话内更新")
            self.pending_layers.append(layer_name)
            print(f"  收到权重: {layer_name}")
        def end(self):
            if not self.active:
                raise RuntimeError("没有活跃会话")
            print(f"会话结束：对 {len(self.pending_layers)} 个层做后处理")
            for layer in self.pending_layers:
                print(f"  process_weights_after_loading({layer})")
            self.active = False
    s = WeightUpdateSession()
    s.begin()
    for i in range(3):
        s.update(f"layer_{i}.mlp")
    s.end()
    ```
  - **预期结果**：你会看到 3 个层的权重被攒在一起，最后统一做一次后处理。这就是"会话"的价值——把 O(N) 次后处理变成 O(1) 次。
